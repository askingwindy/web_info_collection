# 采集 Agent 方案描述

> 一句话:输入 URL → Agent 规划操作路径 → 截图采集,目标采集 **20w 条数据轨迹**。现状用 ReAct 每页约 10min,20w 串行需约 3.8 年。本方案通过**模板化复用 + 规划/执行解耦**的"沉淀飞轮",把平均成本压到秒级,一周内可达成 20w,并以"先验证复用率的最小内核"为起点分阶段演进,先证可行再扩规模。

本文为立项/对齐用的方案描述,技术细节(fingerprint、匹配算法、伪代码)见同目录《采集 Agent 系统优化方案.md》。

---

## 一、背景与目标

做一个采集 Agent:

- **输入**:一个站点 URL。
- **动作**:自动规划该站点下各页面的操作路径,沿路径截图采集。
- **产物**:每个页面产出一个"数据轨迹"(操作序列 + 沿途截图 + 结构摘要)。
- **规模目标**:20w 条轨迹。

两类站点代表:
- 内容站(如 wiki 百科):站点下约 100 页,以浏览采集为主。
- 工具站(如后台操作):站点下约 20 个操作页,需规划增删改查等操作(有副作用,需安全层)。

## 二、现状与核心问题

### 2.1 现状
- **生产者**:持续挖掘网站及可操作页,写入 `t1`(站点)/`t2`(页面)两张表,带 `site_type`/`category` 分类,约束**每个分类占比 ≤20%**。
- **消费者**:对库里页面用 **ReAct(设定目标 + tools)** 做采集规划。

### 2.2 两个致命问题 + 一个约束风险

| 问题 | 现象 | 量化后果 |
|------|------|---------|
| ① 规划太慢 | 每页完整规划 ~10min | 20w × 10min ≈ 1388 天 ≈ 3.8 年(串行) |
| ② 新站失败 | ReAct 从 0 探索未知页 → 跑偏/超步 | 失败率偏高,页面卡死、吞吐断流 |
| ③ 配额风险 | naive 持续挖掘 | 撞 ≤20% 顶,20w 类别比例违约 |

**关键判定:单靠加并发不够。** 20 路并发 ReAct 仍需约 70 天。必须把"10min/规划"这个数本身压下来——胜负手不是堆算力,而是让 10min 不再分摊到每个页面。

### 2.3 根因
现状 ReAct 把"规划"和"执行"耦合在一起:**每页都从零在线规划 + 在线执行**,规划成果用完即弃,无沉淀。于是 20w 页 = 20w 次从零规划,瓶颈无解。

## 三、方案核心思路

### 3.1 三个杠杆

| 杠杆 | 作用 | 预期收益 |
|------|------|---------|
| ① **模板化复用** | 同结构页面共享一份规划 | 规划量从 20w 降到 千~万级模板 |
| ② **规划/执行解耦** | 规划产出可回放轨迹 JSON,执行无 LLM、纯并发 | 执行 10min → ~30s/页 |
| ③ **双队列并发** | Planner 队列与 Executor 队列独立扩缩 | 线性加速 |

三个杠杆里,**① 是命门**。它把"每页 10min"压成"每模板 10min,同结构页秒级复用"。

### 3.2 沉淀飞轮(机制本质)

```
新页 P1 ──从 0 规划(10min)──→ 执行成功 ──→ 冻结为模板入库(指纹→轨迹)
                                                      │
同结构页(99 个)──指纹命中──→ 回放(秒级,无 LLM) ◄─────┘
新异页 ──→ 再规划一轮,再沉淀 ──→ 库越来越满
```

- 沉淀门是**执行成功**(不是规划完成),防"毒模板"污染库;
- 入库前 dedup(指纹近邻归并),库按"结构聚类"长而不是按页数长;
- 沉淀是免费的一次 DB 写,不烧 LLM。

**飞轮物理含义:平均每页成本随模板覆盖度单调下降,跨过拐点后趋近秒级。**

### 3.3 模板归属:消费侧,不是站点侧

> 模板正本放**消费者**的 template 库(按 `指纹 + category` 管理);`structure_fingerprint` 由**生产者**预产写入 `t2`;`t1` 带一个 `default_template_id` 指针仅作 warm-start 快路径。

理由:模板按"结构"匹配不按"站点身份"绑定,才能跨站复用(吞吐命门);模板是规划产物只有消费者会生成;模板生命周期与站点存在与否无关。

## 四、系统总览

```
生产者(喂原料) ─────────────────────────┐
 种子→站点发现→分类(≤20%配额)→页面发现      │
 →质量过滤→fingerprint 预计算            │   t1/t2 + 指纹
 └──────────────────────────────────────┤
                                         ▼
消费者(规划+回放)                         │
 ┌─ Matcher(无 LLM 预筛):指纹查模板库      │
 │   命中 → 直接进 Executor(绕开 LLM)      │
 │   灰区 → Planner warm-start(增量)       │
 │   不命中 → Planner(枚举牌/在线 ReAct)    │
 ├─ Planner(持 LLM):产出可回放轨迹 JSON   │
 ├─ Executor(无 LLM):回放 + 截图 + 真机/SafetyHook
 └─ Verifier + Store:校验 + 沉淀 + 反馈飞轮  │
                                         │
                                         ▼
                            产物: 轨迹 + 截图 + 报告
```

两层规划:**站点级发现**(采哪些页)+ **页面级采集**(每页怎么走)。两个方案:**模板复用**(确定路径)与 **ReAct 规划**(新异/动态)。Matcher 路由决定走哪个。

## 五、分阶段实施路线(先证可行再扩)

本方案最大的反过度设计原则:**完整目标架构是终态,不是起点**。先建能验证核心假设的最小内核,数据达标后再扩。

### Phase 0:复用率 PoC(1~3 天,验证命门)
- 现有 ReAct 加一处:成功后输出轨迹 JSON + `INSERT` 进 templates(fp→steps)。
- 新页先查 `similarity(fp) ≥ Ts`,命中→回放,不命中→原 ReAct。
- 跑同站 100 页,只看两个数:
  - 库沉淀出**几个模板**(期望个位数)
  - **复用率命中率**(期望 >80%)
- **这是决定整个方向是否成立的闸门。** 不达标先调 fingerprint 粒度,不铺规模。

### Phase 1:最小消费者内核(1~2 周,打通飞轮)
4 件事,都可同进程函数级实现:
1. Matcher(fingerprint→template 查找)。
2. Planner(现有 ReAct,三模式:增量/枚举族/在线兜底)。
3. Executor(回放轨迹 JSON,无 LLM)。
4. TemplateStore(沉淀 + dedup + 反馈)。
- 验收:模板命中率 ≥80%,复用页平均成本降到秒级。

### Phase 2:生产者配额 + 质量(1 周,解决约束命门)
- 配额主动调度:预占槽 + 反向生产 + 待入库 buffer(≤20% 不违约)。
- 页面质量过滤:拦登录墙/canvas/404,护航下游命中率上限。
- fingerprint 预计算下沉到生产者。

### Phase 3:并发与规模化(仅当 Phase 1 命中率达标后)
- 双队列拆分:Planner M + Executor K 独立扩缩。
- 工具站 SafetyHook(写操作 mock + 黑名单 dry-run + 测试环境)。
- 模板族(多路径页"一操作一模板")。
- 20w 全量压测。

**顺序硬约束:不先验证命中率就上并发 = 更快烧 token 跑废轨迹。**

## 六、关键技术点(详见技术文档)

| 技术点 | 一句话 | 详见 |
|--------|--------|------|
| **structure_fingerprint** | 页面"操作面骨架"压缩签名;只描述结构不描述内容,支撑跨站复用 | §8.1 |
| **模板匹配 4 段流水线** | 站点默认快路径 → 粗分桶 → 精排打分 → 三档阈值裁决 | §8.2 |
| **三档阈值 Tw<Ts** | 高:复用;灰:warm-start 增量;低:从 0 规划 | §8.2 |
| **路由判据** | "可预测性 × 可枚举性",不是"路径多";可枚举→模板族 | §8.3 |
| **模板沉淀** | 执行成功后冻结指纹→轨迹;dedup;冷启动单调增长 | §八 |
| **ReAct 降级为 Planner** | 从"每页在线 Executor"压成"每模板一次 Planner" | §5 |

## 七、预期收益与量化

按平均复用比 1:30 测算(保守,看站点结构同质度可更高):

```
模板数 ≈ 20w / 30 ≈ 6,700 个
需 ReAct 规划 ≈ 6,700 × 10min ≈ 67,000 min
执行:    20w × 30s ≈ 100,000 min
投入 Planner 并发 15 + Executor 并发 40:
  规划 ≈ 75h ≈ 3 天    执行 ≈ 42h ≈ 1.7 天
  重叠流水(规划执行并行)≈ 3-4 天 ✅
```

对比现状 3.8 年 → 目标一周内。**收益放大倍数取决于实际复用率,故 Phase 0 要先测出来。**

## 八、关键指标(决定能否交付)

| 指标 | 决定什么 | 目标 |
|------|---------|------|
| **模板命中率 / 平均复用率** | 能否按期跑完(吞吐命门 1) | ≥80% |
| **分类占比** | 跑完是否合规(约束命门) | 每类 ≤20% |
| **单位轨迹成本**(元/有效轨迹) | 20w 预算 | LLM token + 浏览器实例 |
| **失败页有产物率** | 不丢页、吞吐不断流 | 100%(靠降级兜底) |

## 九、风险与对策

| 风险 | 对策 |
|------|------|
| **复用率不达标(致命)** | Phase 0 先测;低于预期调 fingerprint 粒度或转分层规划 |
| 新站规划失败 | warm-start 同 category 骨架模板 + 降级兜底 |
| 工具站改生产数据 | SafetyHook 写操作 mock + 不可逆操作 dry-run |
| ReAct 跑偏/死循环 | 轨迹栈 + 单页最大步数 + 状态哈希去重 |
| 配额违约 | 预占槽 + 反向生产,接近上限自动止损 |
| 草率规模化烧 token | 严格按 Phase 顺序,命中率不达标不上并发 |

## 十、下一步行动

1. **立即**:启动 Phase 0,跑 100 页同站 PoC,出"模板数 + 复用率"两个数(预计 1~3 天)。
2. **结果分歧**:
   - 复用率 ≥80% → 推进 Phase 1 最小内核。
   - 复用率 50~80% → 调 fingerprint 粒度(多半过细/过粗)后再测。
   - 复用率 <50% → 评估"分层规划"等更重设计。
3. Phase 1 验收后定 Phase 2/3 的并行投入与 20w 时间表。
