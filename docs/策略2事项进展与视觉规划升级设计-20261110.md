# 策略2事项进展与视觉规划升级设计

日期：2026-11-10。状态：用户已认可设计方向；本轮仅新增本文，不修改正在实施的设计、计划或生产代码，不启动测试和采集。

本文在[采集双策略设计](采集双策略设计-20261110.md)和[实施计划](采集双策略实施计划-20261110.md)之上补充策略 2 的升级设计。既有[实施与集成记录](采集双策略实施与集成-20261110.md)保留当时的实现和验收范围，不能仅据其通过结论认定本文新增条款已经覆盖。实现时先核对现有能力，复用已完成部分，只补实际差异。

本轮确认的运行方式为：**首轮根据页面尺寸提供整体图和当前细节；Agent 根据事项进展维护完整路径与当前可执行动作；工程把控件编号绑定到真实元素，逐个执行原子动作并取证，到检查点或发生偏离时再调用 Agent。**

## 1 升级范围与保留约定

保留策略 1，策略 2 仍是独立的 Agent 协议与工程配套。两者继续输出统一策略结果，并使用同一完成回算、首次标注和正式保存链。本次不另建一套消费者、数据库或保存系统。

| 约定 | 本次处理 |
| --- | --- |
| 原目标及完成事项 | 首次接受后冻结，剩余计划不能缩小目标或删除必要事项 |
| 初次完整路径 | 至少 5 个预计必要业务动作，优先 5–8 步，无 8/10 步硬上限；阶段数量不能冒充动作数 |
| 剩余计划 | 允许少于 5 步，只替换尚未执行的部分，不补无用动作 |
| 正式保存 | 原目标完成、实际有效动作至少 5 步、证据可信、无相关未决外部效果 |
| 短流程与异常 | 如实保留 raw、失败、用量及 UNKNOWN，不生成新的正式待审样本 |
| 采集与审核 | 保存最多到 collected_pending_review；独立 AI QC、人工、发布和客户验收分别有证据 |
| 当前执行 | 本文不启动新调用，不重派旧候选，不覆盖原账、原件或正在进行的实现 |

本轮主要深化六点：按尺寸选择截图；图像压缩与分辨率分开；默认使用控件编号操作；一份事项进展记录；完整路径与当前动作段分开；一次模型规划可以驱动多个真实原子动作。

## 2 首轮截图无需预先判断页面类型

工程在模型调用前可以读取当前视口尺寸、页面内容尺寸和滚动范围。它不必先判断页面是方程工具还是百科文章。`scrollHeight` 等浏览器属性能反映包含屏外部分的内容高度。[浏览器尺寸能力](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollHeight)

### 2.1 默认选择规则

| 客观情况 | 首轮给模型的图像 | 用途 |
| --- | --- | --- |
| 当前页面一屏能容纳 | 一张带控件编号的清晰图 | 同时支持整体规划和当前操作 |
| 页面超出当前视口，完整图仍可按有效尺寸输入 | 全页图＋当前视口清晰图 | 全页理解布局，当前图选准控件；范围相同的图不重复发送 |
| 全页图过长，完整细节超出模型有效处理尺寸 | 全页概览＋当前视口清晰图，必要时补指定区域的清晰图 | 概览用于定位区域，清晰图用于阅读与操作 |

选择只依据尺寸、接口接受的图像数量/格式/尺寸和实际验证过的处理能力，不按站点或页面业务硬编码。具体阈值在实现时核对模型接口并验证，不在本文预填未经验证的 GLM 参数，也不引入一个额外模型专门分类页面。

“全页”描述截图范围，“清晰”描述细节保留程度，二者不是互斥选项。浏览器可截图整个可滚动页面，但它只代表本次已经呈现的内容，不能预知提交后才生成的结果，也不保证展开折叠内容、加载未来内容或遍历内层滚动区域。[全页截图能力](https://playwright.dev/python/docs/screenshots)

### 2.2 补图与后续观察

模型认为某区域看不清时，可以请求对应区域的清晰图。已有同次全页原图时，可从该原图提供区域副本，保存它与原图、区域位置和观察身份的关系。补图不是浏览器动作，不计有效步，也不能伪装成真实滚动。

真正操作屏外控件时，工程仍须让目标进入可操作视口，记录实际滚动和执行证据。全页图的位置不能直接作为当前视口的点击坐标。实际滚动、导航或提交之后，使用新观察；旧全页图只能作为注明来源的历史上下文。

后续调用通常发送当前新图、相关进展与必要历史证据，不每轮重发全部图像。布局显著变化或需要重新理解整体时再补概览。全页或裁图中实际提供过的内容可以注明其图像来源，不能声称模型没有看过；未提供给模型的隐藏或屏外 DOM 文本则不能充当已见视觉证据。

### 2.3 压缩与证据保留

| 处理 | 含义 | 本方案要求 |
| --- | --- | --- |
| PNG 等无损编码 | 解码后的像素保持不变 | 原始证据保留；PNG 本身已经压缩，不承诺再次压缩有固定收益 |
| 同分辨率的有损编码 | 降低文件体积，可能损失细节 | 仅用于独立推理副本，在接口支持的格式中验证中文、数字、边框和编号可读性 |
| 缩小分辨率 | 文字和控件在像素空间变小 | 概览可以缩小，关键操作区域保留清晰图，不将巨幅长图强行缩成唯一输入 |

PNG 使用无损压缩，常见 JPEG 编码有损，截图中的文字与锐利边缘更需要保留细节。[图像编码说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types)

原始 PNG 不覆盖。标号、裁图和压缩副本分别保留来源关系；文件体积变小不意味着图像像素减少，也不据此推算模型视觉 token 或成本。工程能测量图片尺寸，不能保证模型一定看清所有文字，因此保留请求补图的能力。

## 3 控件编号连接视觉理解与真实操作

### 3.1 预处理的职责

```text
获取同一次页面观察
→ 提取可操作控件及位置
→ 在截图副本上标号
→ 保存编号到真实控件的绑定
→ 将图像和必要控件信息交给 Agent
```

只给需要操作的输入框、按钮、链接等控件建立操作编号，不要求给所有 DOM 节点编号。阅读正文可以引用图像区域。标号不遮挡关键中文、数字和控件状态；原图保持原样。

工程负责“①对应这个真实输入框”。Agent 看图理解“①旁边写着长度，因此目标是①”。模型返回编号后，工程不再根据中文名称猜一遍控件。编号保证选定对象能对应到执行对象，不保证模型一定理解对中文与空间关系；视觉歧义应通过清晰图或新观察解决。

### 3.2 编号的有效范围

编号随观察绑定，不是整个网站的永久业务身份。同一段稳定表单操作可以复用已确认的绑定；页面滚动、导航或布局变化后核对并按需更新，不能让旧编号静默指向另一控件。浏览器提供的边框通常相对于视口，滚动会改变该位置。[元素位置能力](https://playwright.dev/python/docs/api/class-locator#locator-bounding-box)

未来尚未观察到的页面只写操作意图，不编造未来控件编号。未来步骤进入当前动作段前，Agent 依据新图选择实际编号。已经在全页图中看见的控件，也须在真实操作前确认其当前元素绑定和视口状态。

工程内部继续使用 DOM、可访问性和真实浏览器状态做定位、焦点及值核对。模型默认接收图像和少量操作编号，不接收完整 DOM/HTML。目标不唯一、已失效或与实际状态冲突时暂停该动作并反馈，不选择第一个近似匹配继续执行。

## 4 事项进展由谁维护

### 4.1 工程保存一份记录，判断来源分开

| 内容 | 判断来源 | 方程案例 |
| --- | --- | --- |
| 直接执行事实 | 工程根据真实操作和浏览器状态生成 | a=4、b=7、c=11；求解按钮点击已派发 |
| 业务进展 | Agent 根据图像判断并引用证据 | 已看到解；逐步过程还未看到 |
| 引用与事实一致性 | 工程核对 | 图像是否真实提供过，结果是否对应本次输入和提交 |
| 进展存储 | 工程统一保存 | 保留原事项、当前进展、证据引用和判断来源 |

无需额外建立第二套工程业务判断系统。模型每轮只返回有变化的事项及其证据，无变化的事项不重复填写。工程核对引用后更新同一份记录；引用缺失时保留 Agent 的原判断和具体缺口，不把它直接当成已核验进展，也不抹掉已完成动作。

方程目标始终包含两项必要结果：本次方程的解、本次方程的逐步过程。输入和点击属于支持这些结果的执行事实，不因为输入已完成就把结果事项标完成。

### 4.2 简单状态与证据适用范围

对模型呈现的事项进展可以先保持“待确认／已有证据”两类；缺口用简短说明表达，原始判断和核验过程留在现有事件记录中，不为每一种缺口新增业务状态枚举。

证据必须说明所证明的事项及相关输入、动作、页面和观察。已读正文的历史证据通常可以保留；计算输入变化后，旧输入对应的结果不能继续证明当前输入完成。只撤销实际受到影响的确认，保留原证据，不把所有进展清空重做。

本次点击成功只说明操作已派发，不说明页面接受了输入或已经完成计算。时间晚于提交也不能单独证明结果来自本次提交；仍需对应的输入、页面和结果关联。

## 5 完整路径与当前动作段

### 5.1 先看剩余事项，再修订动作

每次业务检查点按以下顺序判断：对照原目标确认已有证据；找出剩余事项和当前不确定性；保留、删除或替换用于解决这些缺口的动作。

“已执行 6/8 步”只表示路线进度，可能仅完成输入。Agent 应看到“解和过程仍未确认”，再判断下一步需要观察还是修正输入，而不是继续执行列表中剩余的重复求解。

完整路径覆盖从当前状态到原目标完成的自然阶段及预计动作；当前动作段只包含已看明白、已绑定目标、可以立即执行的原子动作。未知页面的参数和控件以后具体化，不要求首屏猜完。首轮至少五个预计必要业务动作仍保留，阶段数或模型单独声明的数字不能替代自然动作规划；当前动作段本身不要求凑满五步。

### 5.2 一次规划可以执行多个真实动作

Agent 一次返回“当前动作段＋执行后的观察检查点”。工程逐项派发、逐项记录前后证据；确定性操作正常时继续，不必每个动作都调用模型。Agent 可指出需要重新判断的位置；工程在目标无法确认、输入异常、意外弹窗或页面变化影响下一步时提前交还判断。

一轮模型调用不等于一个业务动作。一段动作也不是可以跳过中间取证的整体事务。已经执行的部分保留原身份，发生偏离后只处理剩余部分。

### 5.3 原子输入动作与计步

| 当前需要 | 自然动作组合 |
| --- | --- |
| 空框输入 | 点击取得焦点 → 输入 |
| 替换已有内容 | 点击取得焦点 → 全选 → 输入 |
| 显式清空后输入 | 点击取得焦点 → 全选 → 删除 → 输入 |

模型选择当前控件编号，并明确原子动作。全选、删除和输入的目标编号可作为焦点前提，由工程核对，不得删除有意义的目标后作用于任意焦点。默认不把这段声明动作合并成一次 `fill`，也不允许输入动作隐式代做未声明的聚焦、全选或删除。浏览器支持真实文本和按键操作，实施时复用对应原子执行能力。[键盘操作能力](https://playwright.dev/python/docs/input#type-characters)

点击取得焦点只计一次点击，焦点变化是效果；一段文本输入不按字符数增加步数。全选、删除等分别真实执行且有作用时分别记录；空框不增加全选/删除，已聚焦时不重复点击。`wait`、截图、补图、模型调用和完成申请不计有效业务动作。

实际只有一次 `fill` 的历史记录，继续按真实记录解释，不能后加工虚构多步。新动作组合不得为至少五步要求添加无用途操作。

## 6 模型每轮收到和返回的内容

### 6.1 输入

| 信息 | 最小内容 |
| --- | --- |
| 固定任务 | 原目标与原完成事项 |
| 视觉观察 | 当前清晰图、必要全页图/概览/补图，各自注明观察身份及范围 |
| 当前控件 | 图中操作编号及必要类型信息，后台保留真实元素绑定 |
| 真实反馈 | 最新动作尝试、实际输入、派发状态、错误/UNKNOWN；与最后有效动作分开 |
| 事项进展 | 已有证据、原观察引用、待确认事项和具体缺口 |
| 剩余路径 | 尚未执行的意图或动作、本次调用原因及允许决策 |

模型不负责回填 attempt、动作身份、总步数、band 或保存状态。截图中的编号及证据引用是供模型选择的短标识，工程负责补齐内部身份。

### 6.2 输出

模型输出沿用 continue、revise、complete、give_up 四种决策，并按需要携带新增进展及证据、编号控件的原子动作序列和下一观察检查点。无进展变化不重复输出全部事项，continue 不重写完整计划，complete 的逐项答案可以同时构成本轮进展更新，不再要求一份重复声明。

字段名称以下仅作交互示意；实现应复用既有协议字段，只增加必要含义。新旧语义不同处按原版本机制升级，不能让正在执行的旧任务静默改用新解释。prompt、schema、整理、校验和完成回算作为一项改动同步接线。

## 7 方程求解的完整交互示例

为突出执行机制，目标固定为求解 `4x + 7 = 11` 并查看解和过程；初始 `a=3、b=7、c=22`。下面是方案示例，不是新增真实调用结果。

### 7.1 第一轮提供整体和当前表单

工程按页面尺寸发送全页图和当前视口图；两者范围相同则只发一张。在当前表单中，`c1` 为 a 输入框、`c2` 为 b、`c3` 为 c、`c4` 为求解按钮。模型根据图像确认它们的业务含义。

完整路径为“设置指定方程 → 提交 → 查看解和过程”。当前可执行段包含以下七个动作；全选键名按执行器发布的环境定义提供，模型不自行猜平台。

| 顺序 | Agent 返回的操作 | 工程直接核对的事实 |
| --- | --- | --- |
| 1 | 点击 c1 | a 输入框取得焦点 |
| 2 | 在 c1 全选 | 当前选择覆盖原值 |
| 3 | 向 c1 输入 4 | a 显示 4 |
| 4 | 点击 c3 | c 输入框取得焦点 |
| 5 | 在 c3 全选 | 当前选择覆盖原值 |
| 6 | 向 c3 输入 11 | c 显示 11，b 仍为 7 |
| 7 | 点击 c4 | 本次按钮点击真实派发；业务结果尚待观察 |

这七步可以来自一次模型响应，工程仍逐步执行和取证。每步保留基础协议要求的用途及自然语言预期，不要求模型填写 selected/text_selected 等工程枚举。检查点设在提交后；输入不符或下一目标失效时提前停止该段并反馈。

### 7.2 第二轮提交后仍未看到结果

模型收到的关键事实可以表达为：

```json
{
  "goal": "求解4x + 7 = 11，并查看解和逐步过程",
  "current_observation": "o8",
  "screenshots": [{"ref": "o8-viewport", "scope": "viewport"}],
  "latest_attempt": {
    "ref": "a7",
    "action": "click",
    "target_label": "求解",
    "dispatch": "confirmed",
    "inputs": {"a": "4", "b": "7", "c": "11"},
    "business_result": "尚未确认"
  },
  "requirements": [
    {"id": "r1", "description": "本次方程的解", "progress": "待确认"},
    {"id": "r2", "description": "本次方程的逐步过程", "progress": "待确认"}
  ],
  "remaining_route": ["查看本次结果和过程"],
  "reason": "提交后的业务检查点"
}
```

其中 target_label 是历史动作的说明，不是下一次执行用的定位参数。本例当前图未显示结果，且整体布局支持向下查找，模型可返回：

```json
{
  "decision": "revise",
  "reason": "求解按钮已点击，当前尚未看见结果，先查看下方结果区",
  "current_actions": [
    {
      "action": "scroll",
      "direction": "down",
      "purpose": "查看本次方程的结果和过程",
      "expected_result": "下方内容进入当前视口"
    }
  ],
  "checkpoint": "滚动后重新观察"
}
```

两项事项仍待确认，无须重复提交未变化的进展。若原剩余动作本来就是这次滚动，可以返回 continue。若图中显示加载提示或输入错误，Agent 根据实际反馈等待或修正，不硬编码所有提交后都向下滚。

工程执行滚动后生成新的观察 o9。模型不一直看首屏，也不因为当前没看到答案而重复点击求解。提交后的全页图若已提供了清晰结果，则如实记录模型已见范围；额外截图不冒充滚动，也不为了保持初始计划长度继续做冗余操作。

### 7.3 第三轮看见结果并申请完成

o9 的实际图像显示 `x = 1.0000` 以及当前方程的逐步过程。模型引用原图中的两个区域：

```json
{
  "decision": "complete",
  "answers": [
    {
      "requirement_id": "r1",
      "observed_result": "结果显示 x = 1.0000",
      "evidence": [{"observation": "o9", "region": "region_result"}]
    },
    {
      "requirement_id": "r2",
      "observed_result": "过程显示4x + 7 = 11，减去7，再除以4",
      "evidence": [{"observation": "o9", "region": "region_steps"}]
    }
  ]
}
```

工程核对实际来源与本次输入/提交关联，更新两项进展并接受完成。后续动作不再执行。若只是区域引用缺失，要求同帧补引用；若确实没有过程内容，继续处理该事项；都不重新执行已完成输入。

上述三轮是解释流程，不是调用次数配额。保存资格仍由真实有效动作和统一完成凭据决定，不以例子的理论动作数作为产出。

## 8 工程核验保持通用且局部

| 核对内容 | 工程要做的事 | 不扩展成的规则 |
| --- | --- | --- |
| 操作对象 | 编号指向当前真实控件，必要焦点和值一致 | 不按中文近似搜索重猜目标，不强求模型猜内部谓词 |
| 引用存在 | 图像确实提供过，区域可对应原图 | 不因缺少同帧引用就重放业务动作 |
| 来源对应 | 结果与相关页面、本次输入及操作有证据关联 | 不把提交后的任意旧结果或输入标签当答案 |
| 事项覆盖 | 原目标中的解和过程均有实际说明与证据 | 不用游标走完或单个关键词命中代替完成 |
| 已知矛盾 | 输入错误、操作失败或相关 UNKNOWN 如实反馈 | 不把所有工程异常交给模型重写计划 |

业务语义由 Agent 判断，工程核对直接事实和来源，独立 QC 检查语义充分性。工程不能靠几条通用规则证明所有页面语义正确，也不为每类网站另写一套复杂的完成规则。既有完成凭据、统一资格和保存接口继续复用。

## 9 增量实施与验收计划

### 9.1 接线顺序

| 顺序 | 工作 | 复用与边界 |
| --- | --- | --- |
| U1 观察输入 | 按尺寸选择全页/视口/区域图，保留推理副本来源和当前控件编号 | 复用原截图、DOM及证据模块，不增加业务页面分类模型 |
| U2 协议与进展 | 明确完整路径、当前动作段、检查点、事项增量及证据引用 | 复用策略2 prompt/schema/normalizer；先核对现有覆盖，字段与版本同步 |
| U3 执行循环 | 编号绑定，逐原子动作派发取证，确定性步骤连续执行，偏离提前反馈 | 复用现有会话、动作身份、latest_attempt和原账，不复制浏览器执行器 |
| U4 完成接入 | 一份进展记录、来源与已知矛盾核对、同帧局部补证 | 复用已实现的完成凭据、封存回算、annotation和统一保存 |

可按既有执行记录定位 `screenshot_plan.py`、`screenshot_session.py`、`collection_strategy.py` 及其复用的观察/执行/保存模块；具体差异以实施时源码为准。不得把本文新增含义直接塞入已经冻结的旧协议而不保留版本解释。

### 9.2 只补受影响的集成覆盖

集中完成实际增量后，运行一次相关集成，使用新隔离目录。既有通过且未受影响的检查不重跑。以下是新增或需核对已有覆盖的具体场景，不代表本轮已执行：

| 场景 | 期望结果 |
| --- | --- |
| 未经模型判断的一屏/多屏/超长页面 | 只依据尺寸和接口配置选图；同范围不重复发送，补图保留原来源 |
| 图像压缩、标号和裁图 | 原 PNG 不变，副本可追溯；模型使用的编号和文字保持可读，几何映射正确 |
| 中文标签未通过 DOM label 正确关联 | 模型选择图中编号后定位到对应元素，不重新按中文猜测 |
| 编号随页面变化失效 | 不操作旧编号指向的其他元素，返回当前观察并重新确认 |
| 一次规划包含七个表单动作 | 各步真实派发与取证，正常步骤不逐步调用模型，不合并为一次 fill |
| 聚焦、全选、删除和输入 | 焦点不重复计步，未发生的动作不补写，空框不添加无用清空操作 |
| 当前动作段中出现输入异常或意外弹窗 | 停止受影响的剩余段，历史动作保留，反馈最新尝试 |
| 点击已派发但结果不在当前视口 | 先观察/滚动，Agent 收到新图，不能因未见答案重复提交 |
| 输入变化后旧结果仍显示 | 旧结果不能证明当前输入完成，受影响事项恢复待确认，原证据保留 |
| 新进展只有来源缺口 | 同帧补证，不重放输入或提交；无变化的事项不要求模型重复填写 |
| 完成证据成立但剩余列表未走完 | 停止冗余动作，按同一完成凭据判断保存，不能机械落 no_path |

真实 GLM 可读性、控件选择和规划效果不能由夹具 PASS 替代。图像尺寸、压缩和多图效果在后续明确授权的固定真实基线中核对；本次不确定新候选、并发或采集数量，不沿用已结束批次的授权。

### 9.3 验收报告的区分

报告工程输入兼容、动作执行、事项完成和正式保存各自结果。重点观察控件选错与绑定出错的区别、重复提交、每次调用后的真实有效动作、同帧补证是否避免重做、完成后保存是否一致。

截图生成和补图不算业务动作；本地任务生成不算模型规划响应；采集级完成与待审保存不算独立 QC 或客户验收。历史失败、费用及 UNKNOWN 不因升级重置。
