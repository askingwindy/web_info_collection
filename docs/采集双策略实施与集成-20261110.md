## 4 修复的实际断点（实施中发现并修复）

1. 策略2 step schema 最初把 scroll/hotkey 的可选 target 写成必填（w01 scroll 整理后仍被 oneOf 拒绝）→ 拆分 required/optional。
2. 整理器先删 `expected` 再取值导致 `expected.value` 丢失 → 先拆值/标签再清理非协议字段，并汇总每步缺必填字段路径。
3. hotkey 原生变体要求显式可空 `control_id` → `_react_step` 补 None/绑定值（与策略1控制器一致），keys 经 `execution_keys` 平台映射。
4. 首帧控件探针缺失时策略1控制器自行定向观察，策略2循环最初直接失败 → 工程补一次 `observe(cid)` 再派发（不把可确定资格问题推给模型）。
5. 提交后结果延迟可见：原 ReactSession 硬性 NO_EFFECTIVE_ACTION 会终止会话 → 策略2与计划任务同样按零效果记账并进入检查点（观察/滚动），完成因果用"提交后同文档首现"确定性核验，尾部核算接受效果已被后续同文档观察覆盖的派发（在线 `_range_close` 与离线 `validate_record` 同规则）。
6. `continue` 语义最初不越过已派发步导致重复提交/无进展 → 已派发检查点的 continue 推进游标，重试必须 revise+new_basis。
7. **（2026-11-11 收口补记）CLI 策略参数挂死全部真实 worker**：`--collection-strategy`（缺省 `banded-react` 同样触发）把 `collection_strategy` 传入 `candidate_consumer.run()`，落入 `**kwargs` 后在 `startup_check(**kwargs)` 处 TypeError，worker 每轮记 `consumer_error` 后无限轮询——`test_unified_entry_contract_20261110` 因此无限挂起（上一会话遗留的后台回归进程即卡死于此）。修复：`run()` 增加 `collection_strategy` 显式参数并显式传给 `consume`；修复后该用例 8.00s 通过（修复前三次复现挂死）。详见 `verify_results/dual-strategy-20261110-r01/regression-batch-20261111.json`。
