## 0. 执行摘要

本轮目标不是“多保存文件”，而是提高**客户可用样本**的单位时间产出。优先级如下：

1. **先修会造成登记丢失和错误短样本的工程断点**：visit UNKNOWN 与迟到 failed 的竞态、事件循环被同步重段阻塞、泛化 `finish_when` 导致剩余计划未走就收尾、反馈收据重名。
2. **再修规划语义**：首帧已经成立的弱终点不能驱动无意义动作；动作后只有当前目标证据完整才允许正常收尾。自然 1–4 步仍如实标短，不凑到 5 步。
3. **性能主攻本地段，而非只调 reasoning effort**：给取证、前缀投影、派生、审计、去重、提交分别计时；把可安全离线的重计算移出事件循环。正确性基线先并发 2，再独立比较并发 2/4。
4. **截图优化不删原始证据**：当前 V10 已把默认模型图派生为 960×540 JPEG，原清晰 PNG 和 ROI 按需追加。本轮只减少重复发送、无效重复取证和不必要的模型上下文；原 PNG、前后帧、DOM、动作和 SHA256 绑定完整保留。
5. **effort 不作预设胜者**：昨晚 A/B 的候选不同，只能作为探索信号。修复后使用同候选、同版本、同显式目标的 high/high 与 high/low 配对实验，再决定默认档位。
6. **不把待审当合格**：本批 86 条 committed 的客户包格式检查通过，但累计机械门禁为 `MECHANICALLY_BLOCKED`，真实 AI QC 调用为 0。真实 Agent 基线通过后，后续才复用现有 QC 链；本轮不借优化之名预填 AI、人工或发布结论。

## 1. 事实基线与旧结论纠偏

### 1.1 证据来源

- [AB100 初步报告](../verify_results/consumer-effort-ab100-20261107-r01/report.md)：保留原始运行、请求和失败事实；其中磁盘收据分组数、每应用第二候选、心跳和浅目标归因需要按下列复核修正。
- [独立 QC 报告](../verify_results/consumer-effort-ab100-20261107-qc-r01/final-report.md)：86 条 committed 的本批格式 PASS、累计机械 FAIL、AI NOT_RUN。
- 当前源码：`candidate_consumer.py`、`collect_runtime.py`、`batch_core.py`、`site_failure_stop.py`、`banded_plan.py`、`browser.py`、`inference_image.py`、`react_session.py`、`model_gateway.py`、`agent_feedback.py` 和 `snapshot.js`。
- 原样本：GPA `S000064_sample_000024` 的计划、观察和 `0047-host-plan-finish.json`。

### 1.2 保存和步数的统一口径

按磁盘 `saved_sample.json` 定位，再读取同一样本 `derived.json` 的 `effective_steps` 重算，不能直接使用旧报告分组数，也不能以 `len(annotation.steps)` 代替有效业务动作数：

| 口径 | A（high/high） | B（high/low） | 合计 |
| --- | ---: | ---: | ---: |
| 磁盘保存收据 | 78 | 71 | 149 |
| 1–4 步 | 66 | 58 | 124（83.2%） |
| ≥5 步 | 12 | 13 | 25 |
| 可信前缀 | 47 | 41 | 88 |
| Runtime `collected_pending_review` | 44 | 42 | 86 |
| 已保存但登记为 `interrupted / lease_expired` 等未 committed | 34 | 29 | 63 |

149 张收据的步数直方图为：1 步 58、2 步 34、3 步 9、4 步 23、5 步 8、6 步 5、7 步 10、8 步 2。

在 25 条 ≥5 步中，只有 7 条属于正常宿主收尾，18 条是可信前缀；不能把全部长轨迹称为原目标完整完成。86 条 committed 中 83 条短流程、3 条 ≥5 步；63 条未 committed 中 22 条 ≥5 步，说明租约/收尾断点确实选择性损失长轨迹，但磁盘收据不能因此直接抵扣生产或质量缺额。

### 1.3 一步样本不是同一类问题

58 条一步样本的复核分类：

| 类型 | 数量 | 处理方向 |
| --- | ---: | --- |
| 明确 `short / 1` 的自然浅目标 | 4 | 如实 short；不靠凑步改变事实 |
| 首帧已满足泛化终点，仍有剩余计划 | 23 | 首帧弱终点校验与目标语义修复 |
| 第一动作后满足泛化终点，仍有剩余计划 | 7 | 动作后收尾门禁修复 |
| 可信前缀 | 24 | 与原目标完成分开，不伪装正常收尾 |

34 条正常宿主收尾的一步样本中，30 条存在未执行剩余计划。由此可见，主要问题不是“所有页面天然只需一步”，而是弱终点和宿主自动提前收尾。

GPA 原样本给出了直接反例：计划为 five 档，`finish_when={"kind":"visible_text","text":"4.0"}`；页面说明文字本来就有“支援 4.0 与百分制”，宿主在两个有效动作后以“已证实计划可见终点；自然提前完成不凑步”结束，剩余计算计划未执行。文字条件成立不等于计算结果已经产生。

### 1.4 UNKNOWN 竞态，不是“每应用第二候选非法”

旧报告把 267 次身份守卫归结为“每应用只有第一个候选可用”，这个结论不成立。

已定位的真实冲突链是：visit `f78ef28581964de2a9f335d0894c514c` 先经恢复/同步路径以 `unknown / Unresolved visit dispatch` 写入站点执行账，原 worker 随后用同一 visit 结算 `failed / Error`；`SiteFailureStore.record` 对同一 execution id 的不同状态触发不可变守卫，后续候选在派发前同步该事实时快失败。

正确修复是保留 UNKNOWN 的保守语义和 execution identity 不可变性，同时让同一原始 visit 的迟到结算成为可重放、不冲突的事实。不能采用“队列每应用只放一条”掩盖 bug，也不能放开身份守卫或给每候选换身份绕过原账。

### 1.5 不是“没有心跳”

当前已有两层续租：

- `candidate_consumer.consume` 的 `renew()` 每 2 秒执行 `pool.heartbeat(claim)`。
- `collect_runtime._with_lease` 的 `heartbeat_lease()` 每 `lease_seconds / 3` 续租 attempt。

63 条已保存未 committed 的关键问题是：`candidate_end`、`session_record`、`project_prefix`、`postprocess.process`、其内部 capture audit / dedup、哈希和收尾等同步重段占用同一事件循环，续租任务无法运行。只把 300 秒调大或再添加一个心跳任务，不能消除根因。

当前非 React 分支已有部分 `asyncio.to_thread`，但 React 的 `_react_collection` 仍在事件循环内执行前缀投影和完整派生；应修实际断点，不重复宣称“全面没有离线化”。

### 1.6 本地段和模型段分开优化

保存会话补充分项复核的 p50：本地残余耗时 A 182.1 秒、B 170.0 秒；模型累计耗时 A 77.1 秒、B 67.2 秒。各分位数分别计算，不能把它们机械相加去替代整体会话 p50。

这组数据与旧报告的“8 路本地饱和”共同说明：降低本地阻塞和无效取证优先于单纯降 effort。并发收益必须看 committed/小时和异常率，不能只看单会话是否更快。

### 1.7 invalid 和 effort 只作配对实验输入

按补充复核的共同后续分支口径（各 562 次）：A high invalid 44（7.8%），B low invalid 82（14.6%）。B 的 82 条中 65 条是 JSON 语法错误，主要为 `Extra data`，即返回多个结构化对象；另有 65 条首轮“无 tool call 但正文符合 plan schema”的响应，当前 `strict-plan-content-1` 已有接收路径，应先做原件离线回放再真实验证。

不能为降低 invalid 而从拼接 JSON 中静默挑一个对象执行；也不能对 UNKNOWN 做格式纠正。昨晚两组候选不同，因此不能直接推广为全局 low/low 或 high/high。

### 1.8 其他已确认事实

- `planning-feedback-{outcome}.json` 固定文件名导致 14 次二次收尾 `FileExistsError`，原件未被覆盖。
- `EvidenceStale` 68 次、旋转几何 `UNSUPPORTED_GEOMETRY` 34 次需要按原件分类。当前 `snapshot.js` 已存在 `webcollect-unrelated-transform-2`，所以先回放当前代码，不能把旧失败数直接当成当前仍未修的 bug 数。
- token 的 cached input 是 input 子集，reasoning 是 output 子集；计算总量或费用时不得再次叠加。
- 独立 QC 的累计有效集为 122 条，短流程 108/122＝88.52%，超过 2% 合同上限；另有两对重复、`application capacity: 'S000077'` 和历史包 325 条错误。86 条本批格式 PASS 不等于累计机械 PASS，更不等于客户可用。

## 2. 目标、非目标和计量合同

### 2.1 本轮目标

1. 同一原始执行不再因 UNKNOWN 竞态或事件循环阻塞出现“磁盘有收据、Runtime 未 committed”的新增案例。
2. 正常收尾不再由弱 `finish_when` 绕过未执行剩余计划或显式目标 checks。
3. 在不删证据、不凑步、不放宽身份/UNKNOWN/质量门禁的前提下，提高 committed/小时和后续客户可用样本/小时。
4. 让 Agent 输出协议、goal/prompt/tools、gateway 解析、宿主校验、引用回算和保存保持同一语义。
5. 用固定同候选真实 GLM 配对基线判断 effort、图像和工程优化的实际效果。

### 2.2 非目标

- 不恢复昨晚 63 条旧收据、不回收 claim/attempt、不重发 5 条 UNKNOWN。
- 不修改历史证据、旧 PASS、质量阈值或累计 QC 结果。
- 不启动批量生产、生产者扩量、独立 AI QC、人工审核、发布、客户验收或定时任务。
- 不把动作上限提高到 12–15；当前 8 步上限保留。
- 不新增多机 SQLite、通用浏览器平台或通用任务恢复框架。
- 不强制每条样本满 5 步，不以“自然完成”为由把短流程改标普通流程。

### 2.3 状态和产量必须分别报告

| 字段 | 权威来源 | 含义 |
| --- | --- | --- |
| `disk_saved_receipt` | `saved_sample.json` | 本机已有保存收据，未必登记成功 |
| `committed` | Runtime attempt + 保存收据 + 样本字节 | `collected_pending_review`，可进入 QC 人口 |
| `normal_completion` | 原始终止证据 | 正常宿主收尾；可信前缀另列 |
| `trusted_prefix` | 前缀投影和绑定 | 仅连续可信区间，原目标未完成另标 |
| `short_flow` | 最终有效业务动作数 | 1–4 步；≥5 普通；0 不成样本 |
| `goal_completion` | 目标/checks 的实际证据 | 不能由计划长度、Agent 自述或保存状态替代 |
| `mechanical_pass` | 正式机械报告 | 本批与累计分别报告 |
| `ai_pass / human_pass / published` | 各自审核/发布收据 | 未执行就是 NOT_RUN/0，不预填 |

主要效率指标为 committed/墙钟小时；最终业务指标为机械及语义合格/墙钟小时。研发 replay `production_counted=false`，不能计入正式生产量。

token 报告同时列 `input_tokens`、`cached_input_tokens`、`output_tokens`、`reasoning_tokens_known` 和 usage 未知数。非缓存输入为 `input - cached`；不另造“input + cached”总量。

## 3. 工程 bugfix

### BF1 / P0：修复 visit UNKNOWN 与迟到 failed 的投影竞态

**涉及**：`batch_core.py` 的 `recover`、`finish_visit`、`sync_visit_failures`，`site_failure_stop.py` 的 `record`，以及调用它们的 candidate/probe 路径。

**实施要求**：

1. 原 visit 一旦因租约恢复封存为 UNKNOWN，原 worker 的迟到 definite failure 不得改写该 visit 或站点执行身份。
2. 在 BatchLedger 原事务中保留迟到结算事件和错误证据；`finish_visit` 对这种已证明的同 visit 迟到结果返回明确 `late_outcome_recorded`，而不是抛出会触发全局同步冲突的异常。
3. `sync_visit_failures` 读取同一 execution id 的已封存事实时，只对“原 UNKNOWN 已封存、当前是其后到结算”的精确情形幂等跳过；应用、阶段、原始 evidence/usage 不一致仍必须拒绝。
4. UNKNOWN 的隔离、费用和不可重发规则不变；不能把 UNKNOWN 改判 failed 来减少 hold，也不能新增 execution id。
5. 普通新 failure 仍按原站点账规则记录；本修复不构成整站停派或每应用单候选策略。

**验收**：确定性重放“recover 先 UNKNOWN、finish_visit 后 failed”至少两轮；站点账只有原 execution id 和原 UNKNOWN，迟到错误有独立事件，后续同应用候选不因该投影冲突快失败。反向顺序、不同 visit、不同应用和真正身份改判仍拒绝。

### BF2 / P0：移除事件循环中的重同步段，保持租约与提交边界

**涉及**：`collect_runtime._react_collection`、`candidate_consumer.consume`、必要的 `postprocess/trusted_prefix` 纯函数调用点。

**实施要求**：

1. 将前缀识别/投影、raw record 构建、文件哈希、图像/文本派生等 CPU/文件重段放入有界 `asyncio.to_thread`；React 的完整 postprocess 可离线化，但其中 Runtime 提交和需要序列化的索引/账本操作保持原事务边界。
2. capture audit、dedup 若随 postprocess 离线执行，先验证其连接和索引快照的线程边界；不能共享一个非线程安全 SQLite connection，也不能把 `store.finish_attempt` 或 `index.add_sample` 随意移到 worker 线程。
3. 保留现有 candidate/attempt 心跳，不新增重复心跳层，不先调大 300 秒。只有重段移出后仍有独立证据时才另议租约配置。
4. 离线函数只写本 attempt 的新文件；原 raw 不覆盖，派生仍 create-or-identical，最终只有一次 `finish_attempt`。
5. 离线化失败按原错误分类保存，不将异常吞成成功；取消时仍遵守 lease fencing。

**验收**：在前缀投影和派生各注入超过一个心跳周期的可控阻塞，candidate 与 attempt 的续租时间仍持续推进；最终 committed 一次、保存收据与样本哈希一致、候选投影回读一致，无重复编号和重复图片声明。

### BF3 / P0：修复弱终点与剩余计划未执行的提前收尾

**涉及**：`banded_plan.py` 的计划接受、`round`、`step` 末尾，`goal_evidence.py` / `session_objective.py` 的既有进度证据，以及对应 prompt/schema。

**首帧接受**：

1. 在首次业务派发前检查 `finish_when` 是否已在初始观察成立。
2. 若计划仍包含业务动作而终点仅是首帧已有静态说明、导航、标签或参数文字，走现有首次计划反馈，要求改成由目标动作产生的结果证据；零业务派发。
3. 若原目标本身就是纯观察且首帧已完整回答，则如实零动作结束且“不成样本”，不能为产生样本插入动作。
4. 不能一律禁用 `visible_text`；正文阅读、列表出现等合理条件仍允许。判断依据是目标语义和动作前后证据，不是字符串长度或是否含数字。

**动作后收尾**：

1. 保留当前步骤预期成立后的零模型收尾能力，但把 `position += 1` 后的自动完成拆成明确条件。
2. 有显式 contract/session_objective 时，必须同时满足目标进度/checks 和 `finish_when`；缺项不能正常完成。
3. 无显式 contract 且仍有未执行步骤时，宿主不得只因泛化 `finish_when` 成立就自动完成。允许继续原计划、重规划剩余路线，或由 Agent 在新协议分支中明确申请提前完成并给出当前可见证据；宿主仍需核对同步末帧、无 pending effect、无未决动作和未削减显式目标。
4. 无显式 contract 的普通目标不能伪标为工程 `VERIFIED`；分别记录宿主正常收尾、模型可见终点声明和后续独立 QC。
5. 真正自然 1–4 步仍按事实 short；不得新增“少于 5 步拒绝保存”或“必须继续到 5 步”的硬门禁。

**GPA 验收**：原首帧 `4.0` 计划在任何输入/计算前不得被接受为计算终点；若只进入页面并聚焦输入框，不能因说明文字再次命中而正常完成。输入参数并实际计算后，结果区域的新证据才可完成。自然静态阅读反例仍允许合理结束。

### BF4 / P0：反馈收据追加且可重放

**涉及**：`agent_feedback.save_attempt_feedback`、`collect_runtime` 的引用、`collect_runtime.verify_committed_samples` 与 `postprocess` 的冻结哈希排除列表。

**实施要求**：

1. 同一 attempt/outcome 首次仍使用原规范名；完全相同内容重复调用可返回原引用。
2. 内容不同的第二次收尾使用带 attempt 和内容摘要的独占文件名，并记录前一份引用；不得覆盖第一份，也不得简单吞掉 `FileExistsError`。
3. 所有版本化 feedback 文件都纳入“封存后追加收据”的哈希排除规则，Runtime 证据显式绑定本次引用；旧规范名读取保持兼容。
4. 同一 rejected 原因此重放返回同一引用；不同错误形成不同收据，原收据字节不变。

**验收**：连续构造两次 rejected 和一次 collected 收尾无 `FileExistsError`，三份内容/引用可追踪；committed 样本复核不被合法的封存后追加收据误判为原始证据改变。

### BF5 / P1：invalid 原件回放与协议收敛

**涉及**：`model_gateway.py`、`react_session.py`、`banded_plan.py` 的模型可见 schema 与解析。

1. 对 65 条首轮 content-plan 原件离线调用当前 `strict_plan_content` + `validate_plan` 路径，记录可接受、业务校验拒绝、JSON/schema 拒绝，不发模型、不打开浏览器。
2. 对 low 的 `Extra data` 保留原错误；多个对象、计划加第二计划、计划加结构化解释均不猜测执行。提示词继续强调“只一个 JSON 对象”，不重复塞多份 schema。
3. 已结算的确定格式错误沿用现有最多一次纠正；UNKNOWN、reserved、传输未决不进入格式纠正。
4. 原件回放只证明解析分支，Agent 修改后的最终验收仍必须来自固定真实 GLM 基线。
5. 本轮不预设修改全局 effort；真实派发记录必须保留首轮/分支实际档位。

### BF6 / P1：旋转几何与 EvidenceStale 先分类，定向补缺

**涉及**：`snapshot.js`、`browser.py`、`dynamic_regions.py`、`capture_geometry.py`。

1. 用旧失败诊断中的元素类型、保护区域、mismatch fields 和重试次数分类；在当前代码离线回放/最小页面复现 34 个旋转问题。
2. 当前 `webcollect-unrelated-transform-2` 只对无文字、无交互、无目标/断言成员且不重叠保护内容的子树降级；目标、正文、控件、图片、遮挡和必要内容继续严格拒绝。
3. 若当前规则已覆盖旧失败，只保留回归证据，不再新增一套 transform 规则；若仍失败，补实际未覆盖的等价几何证明。
4. EvidenceStale 不通过全局延长时间、关闭 loading/像素检查或接受陈旧帧来“修复”。只针对已证明无关的动态区域复用现有投影；无法证明时保留失败和可信前缀资格判断。

## 4. 性能、并发和报表优化

### PERF1：补齐实际阶段计时

复用 `telemetry.phase` 和现有 `metering/phases.jsonl`，不新建监控平台。至少增加：

- React `session.run`：首观察、动作后观察、模型等待、动作编译/派发、效果验证。
- `_capture`：before DOM、PNG 1、after DOM、PNG 2、final DOM、retry/backoff、每次失败原因。
- 收尾：prefix candidate、prefix projection、postprocess、capture audit、dedup、feedback、sample/capture hashes、Runtime commit、candidate projection。
- 模型图像：原始/派生 SHA、尺寸、字节数、crop、是否原图/ROI、每请求实际图片数。

日志不复制 base64 或完整 DOM。模型耗时从原请求账计算，本地残余按同一 session 的时间轴定义；报告写清 p50/p90 的分母，不把不同分位的分项强行相加。

### PERF2：只在证据成立时减少重复工作

1. 先依据阶段计时定位 DOM/PNG/派生热点，再改实际最高耗时段。
2. 动作后的 before/after/final 新鲜证据不能互相替代；同 operation 的复用必须同时证明同页面状态、同坐标系、同哈希和同步新鲜度。
3. 不机械把两次 PNG 改成一次，也不减少客户交付逐动作图片。对纯重复观察、无动作重入和相同派生资源可做缓存，但缓存键必须包含原 observation/hash 和协议版本。
4. 并发 2 是修复后的正确性基线。稳定后在同一代码、同层候选和相同预算下独立比较并发 2/4，记录 CPU、Chromium 数、committed/小时、lease/UNKNOWN/invalid、本地与模型 p50/p90；不恢复 8 路。

### COUNT：报告和停止条件使用权威状态

1. 报表同时给 disk receipt、committed、正常完成、可信前缀、short、mechanical/AI/人工/发布，不把任何一个字段冒充另一个。
2. 发现“磁盘有收据但未 committed”时列出原 attempt、lease、保存收据和候选投影；新轮出现此类差异应停止扩量并对账，不能继续用收据数触发目标完成。
3. 生产目标只以 committed 进入 QC；研发 replay 单独计数。最终客户可用仍以正式机械/语义及后续验收为准。
4. 步数取 `derived.effective_steps` 或同一 `effective_trajectory` 规则；不能以包含非业务末项的交付数组长度替代。

## 5. 规划采集 Agent 设计优化

### 5.1 goal：明确目标，不制造伪用户目标

1. 配对实验两臂使用完全相同的显式 `session_objective`：candidate id、version、entry URL、requested goal、目标描述、参数、checks、preferred band 和 minimum effective steps 全部冻结。
2. 目标应描述自然必要的业务结果，例如“进入工具、输入指定参数、触发计算、读取新结果”，而不是“执行五步”。
3. 生产候选没有显式目标时仍可由 Agent 提出 working goal，但必须标为 model-proposed，不得伪称用户目标或事后把模型提案回写成生产者原目标。
4. `minimum_effective_steps` 是规划提示，不是成功充分条件或保存硬门禁。short ≤2% 是集合交付门禁，不能用无关动作解决。

### 5.2 prompt：首轮和后续使用同一目标语义

首轮补充并落实：

```text
终点必须证明 requested_goal/session_objective 所要求的结果，而不是页面任意位置已有关键词。
若终点在首帧已经成立，检查它是否只是说明、导航、标签、默认参数或示例；需要动作产生的结果必须绑定动作后的新证据。
计划长度是路线估计，不是完成依据；不得为达到档位添加无关动作，也不得删去原目标必要步骤。
```

后续补充并落实：

```text
先核对原目标/checks、已执行动作的真实效果和剩余计划。
finish_when 命中只说明该条件可见；剩余计划未走时，确认它确属冗余才能申请提前完成。
聚焦不是输入，输入不是计算，计算说明/示例不是本次计算结果；列表标题不是已读正文。
自然完成可少于五步并如实标短；无法证明完成时继续有据路线或停止，片段保存由宿主另行判断。
```

若新增 `finish_early` 分支，必须同步修改 choice schema、模型可见 options、gateway normalize/validate、宿主执行、finish basis、postprocess 和测试；不能只加 prompt 让模型输出一个旧校验不认识的 choice。

### 5.3 tools：保持原子动作和有界决策

- click/type/select/scroll/hotkey/open_url/back 继续一计划步一原子动作。
- `request_original_image` 只补图证，不执行动作、不推进计划；同 observation＋branch context 仍只提供一次。
- replan 只替换未执行步骤，保留原 goal/checks、已执行证据、总额度和 25 次 GLM 上限。
- 工程生成 effective_steps、short_flow、实际 effort、图像哈希和保存状态；Agent 不申报这些值作为事实来源。

## 6. 有效步数与完成状态设计

### 6.1 不变规则

- 0 个有效业务动作：不成样本。
- 1–4 个：`short_flow=true`，原因由工程生成。
- ≥5 个：普通流程，但不自动代表目标完成或质量合格。
- 8 步动作上限、25 次真实 GLM/会话上限不变。
- observe/inspect/wait/finish/request_original_image、未派发提案、已知零效果不计有效步。

### 6.2 新增区分，而非新增长度门槛

正常收尾收据至少能区分：

| 维度 | 必须记录 |
| --- | --- |
| 路线 | 原计划总步数、已执行有效步数、未执行剩余步数 |
| 终点 | `finish_when` 证据、是否首帧已成立、是否动作后新产生 |
| 目标 | 显式 checks 进度；无契约时为 UNCONFIGURED/待独立 QC，不伪造 VERIFIED |
| 收尾 | 正常完成、Agent 申请提前完成、可信前缀、预算/阻断/UNKNOWN |
| 长度 | 由最终有效动作生成的 short/normal |

实验可以报告 ≥5 占比用于诊断路线是否过浅，但不设置“≥5 占比 50% 即通过”的验收。与最终 short ≤2% 一致的方向是：生产目标尽量本身需要 ≥5 个自然必要动作，同时允许极少数有具体原因的自然短流程。

## 7. 截图采集与模型图像输入优化

### 7.1 当前真实链路

1. 浏览器固定 1280×720、`device_scale_factor=1`，`full_page=False`，坐标系为 `screenshot_css_pixels`。
2. `_capture` 在 V2 每次尝试中读取 before DOM、PNG、after DOM、比较 PNG、final DOM，最多 8 次，以证明截图和界面树同步。
3. `ReactSession._accept` 独占保存原始 PNG/HTML/state/capture，并绑定 SHA256。
4. V10 `banded_plan.prompt` 已通过 `inference_image.derive` 生成默认 960×540、quality 85 的 JPEG；`request_original_image` 使用原清晰图，区域条件可追加 ROI PNG。
5. V10 当前请求通常是一张派生当前图，必要时为当前图＋ROI；不是固定的“当前图＋4 张历史图”。最多 4 张 `site_context` 历史图属于 `FragmentController/model_chooser` 路径。
6. `model_gateway` 对收到的文件直接读取字节并 base64，不再二次缩放。派生图有 `source_sha256`、crop 和像素映射，原图始终是客户/QC 证据。

### 7.2 本轮优化原则

1. **原始证据不少**：保留原视口 PNG、逐动作 before/after、DOM、capture receipt 和哈希；ROI/JPEG 只供模型推理，不能替换客户/QC 原图。
2. **默认模型输入保持小图**：沿用 960×540 JPEG，不再加一层重复压缩；需要小字、遮挡或局部值时按需原图/ROI。
3. **相同图片不重复传**：以图像 SHA 和 observation 为键，在同一请求 history 中把重复图片替换成文本引用；不同 hash 的历史图保留。V10 不盲目新增历史图。
4. **ROI 只作补充**：必须引用原图 SHA、crop 和 source/output 映射；不能裁剪掉目标周边必要上下文，不能改写原始 PNG。
5. **新鲜帧优先于缓存**：模型图 hash 复用不等于浏览器取证复用。凡动作后、文档变化、值变化或同步状态未知，必须重新取证。
6. **计量实际收益**：记录每请求图片数、原始/派生字节和原图/ROI 触发原因，比较无效响应、目标结果和 committed，而不是只报告图片变小。

### 7.3 验收

- 同一 V10 观察普通分支不重复附同一 hash；需要 ROI 时绑定正确，原图请求同情境第二次仍被拒绝。
- 非 V10 history 超限仍按 max_images 截断 oldest，重复 hash 不占多个图片名额；文本中保留对应 observation 引用。
- 所有保存样本的原始 PNG 哈希与 capture、step image 一致；QC 仍读原 PNG，不读 JPEG/ROI 替代图。
- 动作后不复用旧帧；不同页面状态即使尺寸相同也不能因路径相同去重。

## 9. 固定真实 GLM 配对基线

- 每会话最多 25 次真实 GLM；并发 2。配对顺序用冻结 seed 随机化并记录，失败不补位。
