# WebCollect 工程说明

## 本机有界批次启动

[启动脚本](../projects/code/scripts/start_candidates.py)每次启动一个前台角色。生产者和消费者通过同一个本地候选池交换数据。监视器只读原账，分别记录生产者调用、消费者调用、访问与错误。当前生产状态为 `STOPPED_BY_USER`，可用 `--dry-run` 核对命令。下列实跑命令供后续明确恢复的批次使用。

### 准备本轮范围

1. 将[范围模板](../projects/code/config/candidate-scope.example.json)复制为新试跑目录的 `scope.json`。填写同一台机器上的绝对路径，将 `started_at` 替换为开跑前 `date +%s` 的数值。示例里的 0 和文件路径均为占位。运行范围只保存路径、批次和 worker 身份。
2. `pool` 是两个角色共享的 V2 候选池。`history_set` 指向现有当前链 manifest。`registry` 和 `policy` 分别指向该链绑定的生产专库和已登记的活动策略。`output` 是链内的消费者结果目录。生产者默认由 manifest 派生证据目录，实际路径见生产报告的 `evidence_output`。首次安装候选池的命令见[原生入口](#候选-v2-的两个-python-入口)。
3. `producer_config` / `producer_db`、`consumer_config` / `consumer_db` 分别绑定各角色的配置和作业账。消费者启动前需要已初始化的作业账。首次准备**新作业**可用 `python -m webcollect.batch init --config <消费者配置> --ledger <新消费者作业账>`，已有作业沿用原配置和原账。模型配置沿用本轮的 GLM、预算、运行时限和整站止损。需要交接 QC 的批次在 `qc_policy` 指定抽检策略文件。
4. `batch` 填写 `<生产者配置的 run_id>/entry-batch/<本批键>`。脚本从它取出生产者的 `--batch-key`，并将完整值作为消费者的 `--producer-batch`。各消费者的 `consumer_worker` 和 `request_prefix` 必须独立。单机增加消费者时，为每个 worker 准备各自的范围文件，沿用同一批、池、专库和适用的原账。

### 启动与结束

在仓库根目录操作。每个终端先设置同一个试跑目录和命令，可在项目虚拟环境中直接运行，无需 AI 客户端。

```sh
TRIAL=/absolute/trial
SCOPE="$TRIAL/scope.json"
mkdir -p "$TRIAL/logs"
wc_run() { projects/code/.venv/bin/python projects/code/scripts/start_candidates.py --scope "$SCOPE" "$@"; }
```

分别在三个终端运行。预览时给 `wc_run` 加 `--dry-run`，只打印参数，只需 scope 文件。生产者的 `--query` 可替换为 `--directions "$TRIAL/directions.json"`。

```sh
# 终端 1，先让该消费者在原账时间窗口内轮询本批候选
wc_run consumer --limit 20 --poll-seconds 3 >>"$TRIAL/logs/consumer.log" 2>&1

# 终端 2，发现约 20 条新候选，逐条发布
wc_run producer --query '中文在线计算工具' --target 20 --batch-size 8 --max-batches 8 --max-searches 8 >>"$TRIAL/logs/producer.log" 2>&1

# 终端 3，独立读取本批过程和调用记录
wc_run monitor --log-dir "$TRIAL/logs" >>"$TRIAL/logs/monitor.log" 2>&1
```

生产者也可以先启动。完成后，已入池的候选可由稍后启动的消费者领取。返回 403、404 的入口在生产侧逐条留存拒绝收据。生产者报告的 `NEW` 是实际新增数，目标 20 允许有缺额。消费者的 `--limit 20` 是该进程的处理上限。在轮询模式下，本批完成且已无可领取候选时会提前退出，原账运行时间和预算继续生效。

生产者和消费者结束后，可单独停止持续监视，再运行 `wc_run monitor --log-dir "$TRIAL/logs" --once` 从原 SQL 补导最后一轮。调用记录见 `producer-calls.jsonl`、`consumer-calls.jsonl`，页面访问见 `consumer-visits.jsonl`，领取与正式尝试见 `pipeline.jsonl`，异常见 `issues.jsonl` 及各进程自己的标准错误日志。监视器写入失败时，只处理其日志目录并重跑监视器，消费者继续按原账运行。

多个消费者共用一个作业账时，`consumer-calls.jsonl` 包含这份账从 `started_at` 起的调用。按 `formal_attempt` 与 `pipeline.jsonl` 中的 attempt 和 claim 对照，可以定位到具体消费者。每个同时运行的监视器使用独立日志目录。

## 候选 V2 的两个 Python 入口

- 首次准备本地候选池使用 `python -m site_planner.candidate_discovery install --pool <本地数据库> --create-pool`。已有池只需按需运行 `install --pool <本地数据库>` 安装候选扩展。各进程在同一台机器上使用同一个池，并能读取池所引用的来源证据。消费者使用当前链的策略和账本。
- 生产者使用 `python -m site_planner.candidate_discovery produce-entries --help` 查看来源、方向、目标、批次和预算参数。全新的 GLM-5.3-Flash 作业默认走 `entry-tools-1`。宿主冻结检索来源，模型提交索引；发布回执逐行记录新增、重复或拒绝。生产者可以在写库后退出。
- 消费者使用 `python -m webcollect.candidate_consumer --pool <本地数据库> run --protocol entry --help`。每个并发进程使用独立的 `--worker-id` 和 `--request-prefix`，共享池及适用的原账。启动检查先于领取。有界 `--limit` 表示本次最多处理的候选数；默认空池返回 `EMPTY`。消费者先启动时，可加 `--poll-seconds 5` 在原作业的运行时间内等候新候选，每次空轮询使用新的请求 ID。已入库的候选在生产者退出后仍可消费。 有界联调可给消费者增加 `--producer-batch <生产者run_id>/entry-batch/<batch-key>`。它只领取该批实际新增的候选，按原账记录逐个访问失败；生产者在 SQLite 标记本次结束后，消费者会在队列耗尽时退出。
- 消费者自行取得首张同步图树、解析页面身份，再登记正式 attempt。ReAct 复用该页面并保留原始日志，整条加工通过后写入 `collected_pending_review`。运行只需要 Python、项目依赖、浏览器和已配置的 GLM 服务。

**生产者证据目录。** 新建真实候选批次需要原整站止损配置。`produce-entries` 与消费者共用 `--history-set <当前链 manifest>`。省略 `--output` 时，生产者将搜索原件、模型响应、工具收据和报告写入 `<manifest 所在目录的父目录>/producer-evidence/<批次身份摘要>/`，报告的 `evidence_output` 给出绝对路径。也可以显式指定当前链的验证证据根或结果根下的批次目录。显式来源和调用方目标文件中的证据引用遵守同一范围。

**生产者入口检查。** 搜索或显式来源经模型选中，以及调用方通过 `--goals` 提供目标时，程序在候选发布前对实际 URL 执行 GET。它遵循公开地址、应用归属、访问预算与整站止损规则，读取最终响应头后关闭连接。最终 2xx 才可入待消费池。403、404 等非成功 HTTP 响应记录为 `REJECTED`，超时或没有确定状态记录为 `HELD`。V2 两种来源逐条写入批次结论，好入口可以继续入池。同一批次对同一请求 URL 复用原检查收据，续跑和多目标不会重复访问。原始状态码、落地 URL、跳转记录和访问账 ID 写入批次证据目录的 `entry-http-*.json`，独立监视器将入口拒绝写入 `issues.jsonl`。页面返回 200 但显示验证码、登录墙或页面异常时，仍由消费者在实际浏览器会话记录。

**独立监视。** 生产者、消费者按各自入口运行。另开一个进程执行下列命令读取本轮账本。运行范围 JSON 包含 `pool`、`producer_db`、`consumer_db`、`registry` 的绝对路径，以及 `batch`、`consumer_worker` 和开始时的 Unix 秒数 `started_at`。为本轮选择单独的日志目录，按角色使用各自的作业账。监视器将搜索记录的 `kind` 与日志事件名分别保存。写盘失败会报告到该进程的 stderr，消费者按原账继续运行。

```bash
python -m webcollect.candidate_monitor --scope ./trial-scope.json --log-dir ./trial-monitor-logs --once
```

`--once` 用于一次核账，省略后按秒持续观察。修复日志目录后可从原 SQL 记录重新导出；已完整写入的同一事件按 ID 去重。

## 3. 当前主调用链

普通新任务的高层入口是 `python -m webcollect.task_generation`。`generate` 从真实能力目录和显式当前链生成 M4 计划；`execute` 使用同一实际计划运行采集。生产前必须已有授权 campaign 与原专库，该 wrapper 不自动新建生产 campaign。

```text
site_planner discover → probe → 实际能力复核
  → task_generation.generate
  → task_generation.execute
      ├── 核验来源、当前链、业务/页面身份、原campaign与预算
      ├── preflight_plan（只读）→ publish_plan
      ├── collect_m4 → collect_one → browser.capture / execute
      ├── 结构检查 / 采集证据审计 / 精确图像冲突检查
      └── derive facts → build_client_package → prepare_qc_inputs
  → quality_inspector check-set（对冻结有效集合生成跨包报告）
  → quality_inspector.delivery_pipeline
      prepare → run → status / import-human → finalize
```

`execute --qc-policy` 接收恰含 `ai_percent`、`human_percent`、`seed` 的 JSON。比例均为 0–100，seed 为非空字符串；这里不指定生产默认值。无策略时可保存候选，但返回 `qc_configuration_required`，不会自动选比例或开始审核。有策略时只冻结 `sampling-plan.json`、`effective-set.json`、收据及可选 `collection-checks.json`，返回 `QC_NOT_RUN`。

上述为现有接口行为；后续默认10%及扩检的完整语义以[新策略](QC抽检与批次合格计数方案-20261030.md)为准，尚未落实为本接口的运行默认值。实际审核与批次接纳分别回写，未抽中但有效接纳的数据不应继续占用待审库存，也不能冒充逐条AI审核通过。

采集不要求事先完整执行一遍任务。兼容任务若已有 `task_admission` / `workflow_admission`，仍核验其绑定。`observed_workflow` 是独立兼容路线，不代表所有任务都走这里。底层 `python -m webcollect collect` 仍支持旧计划及严格 M4；不能把旧入口当作当前链范围与预算的替代。

## 4. 命令与副作用

使用 `projects/code/.venv/bin/python -m <模块> <子命令> --help` 查看精确参数。以下是定位表，不是自动执行清单。

| 模块 / 命令 | 输入与输出 | 主要副作用 |
| --- | --- | --- |
| `webcollect.batch validate-config` | 配置检查 | 不派发模型；不证明模型可用 |
| `webcollect.batch init / recover / model-smoke` | 作业账、恢复或模型协议 | 写账；`model-smoke` 可能真实调用模型 |
| `site_planner discover / probe` | sources/candidates → candidates/catalog | 真实模式可访问网络；probe 可调用已配置模型 |
| `webcollect.task_generation generate` | config/ledger/catalog/history → plan | 写作业账与冻结产物；model 生成器可调用模型 |
| `webcollect.task_generation execute` | plan/catalog/registry/policy → capture/candidate/QC inputs | 真实浏览器操作、编号和账本写入 |
| `webcollect runtime-status` | 原 registry/output | 只读查看现有 scope，不初始化账本 |
| `webcollect runtime-policy / runtime-resume / runtime-close-replan` | 原 scope 和原因 | 修改持久预算/运行状态；并非只读命令 |
| `webcollect.qc_handoff` | 当前候选/history-set/显式抽检参数 → QC inputs | 冻结文件；不调用模型、不写生产 registry |
| `quality_inspector check / check-set` | 实际包或有效集合 → 包外报告 | 确定性重验及读取实际审核；不派发模型 |
| `quality_inspector.delivery_pipeline prepare` | config/ledger/input/plan/effective-set/cross-package-report/profile | 冻结并排队审核；资料模式须显式 `ai` 或 `human` |
| 同模块 `run` | receipt → 审核输出 | 可能发送真实模型请求 |
| 同模块 `status / import-human` | receipt、实际审核记录 → 状态报告 | 不发模型，但可发行状态记录、导入人工结果及同步进度，并非文件系统只读 |
| 同模块 `finalize` | receipt/status → 新完整包，可选 archive | 核验门禁、final 重验、封包；不新发 AI 请求 |

当前 `delivery_pipeline` 的 real 模式接受原智谱 GLM `glm-5.3-flash`，以及 Ark 的 `glm-5-3-flash-260828`、`deepseek-v4-1-flash-economy-261017`；Ark标准版 `deepseek-v4-1-flash-261017` 继续兼容既有冻结账本。上述模型均须显式支持视觉；`ModelGateway` 支持的 provider 范围更广，不代表 pipeline 任意接受它们。controlled 模式需要 synthetic 账，不能生成真实审核结论。配置和参数限制以入口实现为准。

| 生产 policy | `runtime.validate_policy()` | campaign 总尝试/待审/并发/重试/分布/资源限制；当前站点止损账显式绑定 |
| 交付 profile | QC 内 `delivery.json` 或 `projects/quality-inspector/config/` | 历史/试点 profile 不等于正式总体已满足；必须随报告绑定 |
| M4 计划与发布 | `webcollect-plan-m4-1`、`planning.publish_plan()` | task ID/version、能力、源实现、预检与内容摘要绑定 |
| Schema | `projects/code/webcollect/schemas/` | 标注、界面树、manifest、metadata；QC 有独立解析实现，不能只跑生产端 validate |

火山方舟使用独立 `provider=ark` 和北京数据面 `https://ark.cn-beijing.volces.com/api/v3/chat/completions`。首选配置为 `projects/code/config/batch-ark-glm.example.json`，备选为 `batch-ark-deepseek.example.json`；两者是同一 Ark 平台的不同模型，均不走智谱/DeepSeek 官方端点。`model_credentials.py` 在运行时依次使用 `ARK_API_KEY`、显式 `api_key_file`、项目忽略的 `request/token` 中唯一的 `ark1` 标签；若该位置是目录则读其 `ark1` 文件。密钥不写配置和账本，缺失或歧义在预留前停止。

本机文件现已改名为 `request/token.yaml`；复验配置通过绝对路径 `model.api_key_file` 显式绑定该文件。YAML按厂商选账户：Ark只读取 `ark1`，智谱只读取 `glm1`，缺失或歧义不跨账户回退。若全文件不能按严格YAML解析，Ark可读取唯一显式顶层 `ark1` 旧标签，不从其他账户猜测。Ark GLM已通过原图/JSON/usage诊断，见[开通后复验报告](../verify_results/ark-integration-20261029-live-r03/复验报告.md)；经济版也已通过，见[经济版与凭据格式复验](../verify_results/ark-integration-20261029-live-r06-economy-format/复验报告.md)。旧UNKNOWN原账保持不变。

Ark 请求将完整 Schema 放入系统指令，本地严格校验 JSON；GLM 不发送结构化输出参数，DeepSeek 使用 `json_object`。原图使用 PNG data URL，`max_completion_tokens` 同时限制思考与回答，响应必须返回所选模型版本和完整用量。每份示例限制1次请求、0.10元预留、零页面访问；扩大预算或进入实际发现/QC须使用对应授权范围的冻结配置。新通道不修改旧账模型，不自动跨通道重发 UNKNOWN。可运行方式见[模型接口](../projects/code/README.md#火山方舟-ark-双链路2026-10-29)。

自主发现的 `web_search` 是独立的智谱搜索服务。选择Ark推理时，搜索仍单独读取 `GLM_API_KEY` 或项目GLM凭据，不向智谱发送Ark key；搜索费用及其UNKNOWN状态继续单列。Ark推理接通不证明智谱搜索服务可用。

典型高层 `execute` 输出如下；不同入口可能省略外围目录，以其收据为准：

```text
<execute-output>/
├── preflight/                    # 诊断截图、报告、scheduled-plan

│   ├── bootstrap.json           # 恢复时核对原计划/源码/输出/账本
```

## 7. 常见阻塞的排查顺序

| 现象 | 优先核对 |
| --- | --- |
| `ModuleNotFoundError` | 同一 Python 虚拟环境、三个 editable 包或 `PYTHONPATH`；AI支路需要采集包 |
| 源码/能力/预检不匹配 | 输入收据原 SHA、能力有效期、generation/source identity；保留原版本，重新生成适用后继，勿改摘要蒙混 |
| 已有输出或收据拒绝覆盖 | 是否应复用原请求或生成新版本目录；不要删除失败目录重跑 |
| pending 或 `REVIEW_REQUIRED` | 逐项区分机械失败、语义缺失、AI_REQUIRED、HUMAN_REQUIRED、替换缺额和分布门禁 |
| resume 拒绝 | 原 registry、bootstrap、计划、已提交样本/raw 字节、租约和 scope 状态；禁止拼接中断轨迹 |
| 站点无法派发 | 原整站失败账、UNKNOWN hold、域限速、campaign attempt/pending/resource 额度 |
| 模型超时或 usage 不完整 | 原请求行与预留、provider 响应及 request ID；UNKNOWN 不记零、不另起账重发 |
| Ark `404 ModelNotOpen` | 当前账号未开通对应模型服务；先核对控制台开通状态，保留原请求和费用UNKNOWN，不自动换模型或重试 |
| 单条 PASS 但不能发布 | payload/final 阶段、完整包资料、总体分布、有效集合、跨包版本与最终报告绑定 |

当前工程尚未证明通用网站的自动任务容量、真实大规模吞吐、跨机器运行或客户实际验收。静态分片接口见[协议说明](../projects/code/docs/static-batch-protocol.md)；它是离线协议能力，不是已经运行的集群。
