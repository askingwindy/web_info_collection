# WebCollect 工程说明

共享池状态闭环由 `webcollect/site_pool_sync.py` 承接：来源资格目录的 `site-pool-binding.json` 绑定原池及能力目录摘要，`task_generation.execute` 自动消费（也可显式 `--site-pool`）；采集bootstrap和原生产scope持久保存池路径，后续不能替换。`RuntimeStore` 每次事务提交后同步任务/尝试，写入失败仅留下 `m4_site_pool.pending`，下一次claim/start前强制补写成功。只补写不重新执行浏览器或模型。`delivery_pipeline.prepare --production-handoff` 绑定原QC交接；run/status产生报告后核验原始保存证据、报告与样本集合，登记待审/通过/失败并同步池。`single_record.qc` 自动传递交接，包括已保存结果恢复。

同站双功能最小支路见[执行说明](同站双功能与20站最小执行-20261029.md)。`single_record.identity`可读取原registry中的应用名称，多个功能页复用原应用映射。原作业账有未核实HTTP401/403时，`reserve_request`拒绝其他新请求，已有成功缓存可读；source入口在浏览器取证前返回`PROVIDER_AUTHORIZATION_HOLD`。不通过新账或换功能重发UNKNOWN。

单条运行入口 `webcollect.single_record` 复用共享池精确候选导出、probe/qualification、`generate(max_tasks=1)`、原单次execute与独立delivery_pipeline；阶段可单独核查，既有链和编号账不由入口重建。QC自动提供原始manifest/runtime/facts和冻结抽检计划；`--sample-reviews`接已有实际样本审核，资料任务先由独立engine校验原件和策略，再检查覆盖声明。`--supporting-file`只补来源事实，不能代替审核。设计和本轮证据位置见[今日单条真实闭环计划](今日单条真实闭环计划-20261029.md)。

共享站点池新入口：`site_pool.py` 维护分层发现与工具账，`discovery_agent.py` 驱动类目搜索和只读观察，`discovery_tools.py` 执行独立搜索/隔离浏览器，程序2 `site_pool_reader.py` 提供只读候选及既有能力校验。命令、配置、恢复和验证见[共享站点池与自主发现](共享站点池与自主发现.md)。

本文用于从代码进入工程，配合[设计说明](设计说明.md)理解行为。阅读基线：2026-10-28，`34afaaa`。这是实现说明；实际运行范围见[当前入口](../projects/prd/三程序计划执行入口.md)，本机进度与账本不由本文代替。

2026-10-29一致性修复接续见[有限修复计划](需求一致性修复计划-20261028.md)。新增 `workflow_proposal.py` 接受 `generate --workflow-specs` 显式提案：`webcollect-workflow-proposals-1` 的 tasks 绑定能力ID/版本、任务族、操作/子目标/断言及原始 anchors；控制步骤的 `evidence.anchor_index/anchor_element_id/target_label` 必须对应原PNG的可见树，实际选择器、动作和终态仍在单次采集中复验。它不自动产生任意网站的任务，也不为未知能力编造完成判据。

来源探测在同次只读访问中保存 `page-anchor.png/state.json/capture.json` 同步锚点到库存的 `page_anchor`。`generate --page-identities` 消费 `webcollect-page-identities-1` 的pages映射（精确初始URI→既有pilot_identity对象），在生成和登记任务前冻结整体应用名称、目标/共享页面角色及原始锚点；无需手改生成计划或追加完整演练。任务mode与来源mode一致，真实execute拒绝synthetic任务。

派发前相关状态或像素复核失败时，`capture_failure.json` 同时保留当次原帧、比较帧、live/final树和可重算的拒绝证明；不得只依赖较晚的 `failure_after.png` 推断原因。该记录标明动作未执行、不能作为正式帧，判定标准保持不变。

GLM运行凭据由 `model_credentials.py` 消费：环境变量优先，随后显式绝对路径 `model.api_key_file`，否则使用用户已授权的项目 `request/token`。仅运行时读取，拒绝内容和文件文本不回显；旧冻结配置无需写入token或原地修改，`model:null`不读取此文件。

`BatchLedger` 可绑定原 `site_failure_guard`，每次来源/探测/预检派发前核对整站账；导航失败及导航成功后的预检失败分别用原执行ID幂等入账。正式采集导航由生产尝试账负责，避免双算。应用跨host仅使用 `application_identity.py` 的显式证据别名；无归属证据时不猜测，已有账本绑定不得替换。

单次执行的 `completion_view={schema_version: webcollect-live-completion-view-1, distance: 1..480}` 不要求旧准入。只支持同一最终结果容器的文字/数值断言，并在原始动作前截图核实结果存在、符合断言、部分超出视口且一次有界滚动足够完整展示。旧 `webcollect-bound-completion-view-1` 继续核验其完整原收据。

## 3. 当前主调用链

普通新任务的高层入口是 `python -m webcollect.task_generation`。`generate` 从真实能力目录和显式当前链生成 M4 计划；`execute` 使用同一实际计划运行采集。生产前必须已有授权 campaign 与原专库，该 wrapper 不自动新建生产 campaign。

```text
site_planner discover → probe → 实际能力复核
  → task_generation.generate
  → task_generation.execute
      ├── 核验来源、当前链、业务/页面身份、原campaign与预算
      ├── preflight_plan（只读）→ publish_plan
      ├── collect_m4 → collect_one → browser.capture / execute
      ├── 结构检查 / 采集证据审计 / 精确图像冲突检查
      └── derive facts → build_client_package → prepare_qc_inputs
  → quality_inspector check-set（对冻结有效集合生成跨包报告）
  → quality_inspector.delivery_pipeline
      prepare → run → status / import-human → finalize
```

`execute --qc-policy` 接收恰含 `ai_percent`、`human_percent`、`seed` 的 JSON。比例均为 0–100，seed 为非空字符串；这里不指定生产默认值。无策略时可保存候选，但返回 `qc_configuration_required`，不会自动选比例或开始审核。有策略时只冻结 `sampling-plan.json`、`effective-set.json`、收据及可选 `collection-checks.json`，返回 `QC_NOT_RUN`。

采集不要求事先完整执行一遍任务。兼容任务若已有 `task_admission` / `workflow_admission`，仍核验其绑定。`observed_workflow` 是独立兼容路线，不代表所有任务都走这里。底层 `python -m webcollect collect` 仍支持旧计划及严格 M4；不能把旧入口当作当前链范围与预算的替代。

## 4. 命令与副作用

使用 `projects/code/.venv/bin/python -m <模块> <子命令> --help` 查看精确参数。以下是定位表，不是自动执行清单。

| 模块 / 命令 | 输入与输出 | 主要副作用 |
| --- | --- | --- |
| `webcollect.batch validate-config` | 配置检查 | 不派发模型；不证明模型可用 |
| `webcollect.batch init / recover / model-smoke` | 作业账、恢复或模型协议 | 写账；`model-smoke` 可能真实调用模型 |
| `site_planner discover / probe` | sources/candidates → candidates/catalog | 真实模式可访问网络；probe 可调用已配置模型 |
| `webcollect.task_generation generate` | config/ledger/catalog/history → plan | 写作业账与冻结产物；model 生成器可调用模型 |
| `webcollect.task_generation execute` | plan/catalog/registry/policy → capture/candidate/QC inputs | 真实浏览器操作、编号和账本写入 |
| `webcollect runtime-status` | 原 registry/output | 只读查看现有 scope，不初始化账本 |
| `webcollect runtime-policy / runtime-resume / runtime-close-replan` | 原 scope 和原因 | 修改持久预算/运行状态；并非只读命令 |
| `webcollect.qc_handoff` | 当前候选/history-set/显式抽检参数 → QC inputs | 冻结文件；不调用模型、不写生产 registry |
| `quality_inspector check / check-set` | 实际包或有效集合 → 包外报告 | 确定性重验及读取实际审核；不派发模型 |
| `quality_inspector.delivery_pipeline prepare` | config/ledger/input/plan/effective-set/cross-package-report/profile | 冻结并排队审核；资料模式须显式 `ai` 或 `human` |
| 同模块 `run` | receipt → 审核输出 | 可能发送真实模型请求 |
| 同模块 `status / import-human` | receipt、实际审核记录 → 状态报告 | 不发模型，但可发行状态记录、导入人工结果及同步进度，并非文件系统只读 |
| 同模块 `finalize` | receipt/status → 新完整包，可选 archive | 核验门禁、final 重验、封包；不新发 AI 请求 |

当前 `delivery_pipeline` 的 real 模式接受原智谱 GLM `glm-5.3-flash`，以及 Ark 的 `glm-5-3-flash-260828`、`deepseek-v4-1-flash-economy-261017`；Ark标准版 `deepseek-v4-1-flash-261017` 继续兼容既有冻结账本。上述模型均须显式支持视觉；`ModelGateway` 支持的 provider 范围更广，不代表 pipeline 任意接受它们。controlled 模式需要 synthetic 账，不能生成真实审核结论。配置和参数限制以入口实现为准。

本机文件现已改名为 `request/token.yaml`；复验配置通过绝对路径 `model.api_key_file` 显式绑定该文件。YAML按厂商选账户：Ark只读取 `ark1`，智谱只读取 `glm1`，缺失或歧义不跨账户回退。若全文件不能按严格YAML解析，Ark可读取唯一显式顶层 `ark1` 旧标签，不从其他账户猜测。Ark GLM已通过原图/JSON/usage诊断，见[开通后复验报告](../verify_results/ark-integration-20261029-live-r03/复验报告.md)；经济版也已通过，见[经济版与凭据格式复验](../verify_results/ark-integration-20261029-live-r06-economy-format/复验报告.md)。旧UNKNOWN原账保持不变。

Ark 请求将完整 Schema 放入系统指令，本地严格校验 JSON；GLM 不发送结构化输出参数，DeepSeek 使用 `json_object`。原图使用 PNG data URL，`max_completion_tokens` 同时限制思考与回答，响应必须返回所选模型版本和完整用量。每份示例限制1次请求、0.10元预留、零页面访问；扩大预算或进入实际发现/QC须使用对应授权范围的冻结配置。新通道不修改旧账模型，不自动跨通道重发 UNKNOWN。可运行方式见[模型接口](../projects/code/README.md#火山方舟-ark-双链路2026-10-29)。

自主发现的 `web_search` 是独立的智谱搜索服务。选择Ark推理时，搜索仍单独读取 `GLM_API_KEY` 或项目GLM凭据，不向智谱发送Ark key；搜索费用及其UNKNOWN状态继续单列。Ark推理接通不证明智谱搜索服务可用。

典型高层 `execute` 输出如下；不同入口可能省略外围目录，以其收据为准：

```text
<execute-output>/
├── preflight/                    # 诊断截图、报告、scheduled-plan
├── publication.json             # 冻结发布收据
├── pending-quality-checks.json  # 待独立QC核实的采集侧线索
├── capture/
│   ├── bootstrap.json           # 恢复时核对原计划/源码/输出/账本
│   ├── manifest.json
│   ├── runtime-snapshot.json
│   ├── samples/<sample_id>/     # annotation.json + images/ + ui_tree/
│   ├── evidence/<sample_id>/    # raw、capture_audit、saved_sample/失败收据
│   ├── rejected/               # 保留未成功轨迹
│   └── metering/               # 网络和阶段计量
├── facts.json
├── candidate/                  # 实际客户候选布局，不代表发布
├── candidate-receipt.json      # 候选全部字节的绑定
└── qc-inputs/                  # 显式配置后生成冻结的QC输入
```

客户包核心为 `samples/<sample_id>/{annotation.json,images/,ui_tree/}`，以及 `metadata.csv`、`site-list.json`、`ground_truth/`、说明资料和校验清单；最终阶段增加已绑定 QC 摘要。精确文件名与角色由 `client_package.py`、QC `profiles.py` / `engine.py` 核对，不宜由 agent 手工拼包。

`results/`、`verify_results/`、真实投影 fixtures、SQLite、原始模型请求、ZIP 和凭据均不入 Git。新克隆可能缺少旧 README 链接指向的运行文件；这表示缺本地证据，不能重建空账冒充原运行。旧工具的 `temporary` 或 `build` 名称也不是删除依据。

## 6. 验证与开发路径

默认使用根 README 的 `verify_current_offline.py` 命令，按改动挑选模块。验证器将三个包和两个 tests 目录加入 import path；某些测试名在两个目录重复时应先确认解析到哪一份。需要测试 QC 目录特有用例时可在该目录直接运行其 unittest，并保持包路径明确。

| 改动领域 | 现有相关测试，主要位于 `projects/code/tests/` |
| --- | --- |
| 单次执行与完整保存 | `test_single_execution_path`、`test_collect_runtime`、`test_unknown_collection_outcomes` |
| 当前链与交接 | `test_current_chain`、`test_current_chain_cohort`、`test_qc_handoff` |
| 页面身份与来源 | `test_production_identity`、`test_site_source_provenance` |
| 模型协议与凭据 | `test_ark_provider`、`test_model_provider_protocols`、`test_model_credentials`、`test_site_qualification_provenance` |
| 图树稳态、资源与终态 | `test_related_capture_stability`、`test_preflight_related_images`、`test_complete_refresh`、`test_completion_evidence` |
| 抽检、审核复用与转人工 | `test_three_layer_sampling_policy`、`test_semantic_reuse`、`test_delivery_sampling`、`test_delivery_pipeline` |
| 止损、并发与分片 | `test_site_failure_stop`、`test_site_failure_portability`、`test_site_concurrency`、`test_batch_protocol` |

新增策略时同时检查生成器注册、业务身份验证、task contract、实际执行和独立终态验证，不能仅增加一个 `*_strategy.py`。改变合同文档时同步核对 QC 随包 authority 及摘要；改变检查含义时更新对应规则版本。运行检查的实际结束状态、skip、失败及覆盖范围均应记录；不把旧提交消息中的测试数当作本次测试结果。

## 7. 常见阻塞的排查顺序

| 现象 | 优先核对 |
| --- | --- |
| `ModuleNotFoundError` | 同一 Python 虚拟环境、三个 editable 包或 `PYTHONPATH`；AI支路需要采集包 |
| 源码/能力/预检不匹配 | 输入收据原 SHA、能力有效期、generation/source identity；保留原版本，重新生成适用后继，勿改摘要蒙混 |
| 已有输出或收据拒绝覆盖 | 是否应复用原请求或生成新版本目录；不要删除失败目录重跑 |
| pending 或 `REVIEW_REQUIRED` | 逐项区分机械失败、语义缺失、AI_REQUIRED、HUMAN_REQUIRED、替换缺额和分布门禁 |
| resume 拒绝 | 原 registry、bootstrap、计划、已提交样本/raw 字节、租约和 scope 状态；禁止拼接中断轨迹 |
| 站点无法派发 | 原整站失败账、UNKNOWN hold、域限速、campaign attempt/pending/resource 额度 |
| 模型超时或 usage 不完整 | 原请求行与预留、provider 响应及 request ID；UNKNOWN 不记零、不另起账重发 |
| Ark `404 ModelNotOpen` | 当前账号未开通对应模型服务；先核对控制台开通状态，保留原请求和费用UNKNOWN，不自动换模型或重试 |
| 单条 PASS 但不能发布 | payload/final 阶段、完整包资料、总体分布、有效集合、跨包版本与最终报告绑定 |

当前工程尚未证明通用网站的自动任务容量、真实大规模吞吐、跨机器运行或客户实际验收。静态分片接口见[协议说明](../projects/code/docs/static-batch-protocol.md)；它是离线协议能力，不是已经运行的集群。
