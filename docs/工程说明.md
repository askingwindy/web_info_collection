消费者单条实测和旧活动的原账核对见[运行时恢复与古文岛基准方案](消费者运行时恢复与单站实测计划-20261101.md)。

[启动脚本](../projects/code/scripts/start_candidates.py)每次启动一个前台角色。生产者和消费者通过同一个本地候选池交换数据。监视器只读原账，分别记录生产者调用、消费者调用、访问与错误。批量生产状态为 `STOPPED_BY_USER`，可用 `--dry-run` 核对命令。本轮已授权的单条验收按上方实施方案限定输入；下列批量命令仍供后续明确恢复的批次使用。

### 新候选工程

本机已准备好 [candidate-project-20261101-r01 的 scope](../results/candidate-project-20261101-r01/scope.json)。下方各角色使用同一份 scope。工程初始化仅执行一次。重启沿用原文件，新批次只换批次键和该批的请求前缀。生产者、消费者分别在首次实际启动时创建自己的作业账并记录起始时间。只有显式恢复时才执行实跑命令。

在新机器或新的工程代际上，使用下列入口。参数指向经过核对的角色配置和运行策略模板。既有编号用 `--numbering-from` 接续，有多个前代编号库可重复传入。输出目录必须尚未存在。命令只准备本地文件和 SQLite，无需站点或模型连接。

```sh
PYTHONPATH=projects/code:projects/site-planner:projects/quality-inspector \
  projects/code/.venv/bin/python -B -m webcollect.candidate_project init \
  --root "$PROJECT_ROOT" --project-id "$PROJECT_ID" --policy-template "$POLICY" \
  --producer-config "$PRODUCER_CONFIG" --consumer-config "$CONSUMER_CONFIG" \
  --numbering-from "$PRIOR_REGISTRY" --qc-policy "$QC_POLICY"
```

初始化生成 `scope.json`、`chain/manifest.json`、`state/` 和 `collections/`。已知站点的其他入口可用生产者 `--discovery-mode expand`。同一入口的不同明确目标用 `target` 候选表达，`entry` 类型仍对同一入口去重。当前项目内的首访来源、证据、实际分类和采集结果均沿本项目登记。反馈只读取本工程范围。[派发及去重口径](历史门禁审查与新工程切换-20261101.md)

### 准备本轮范围

1. 新工程使用上一步生成的范围。创建另一批运行范围时复制该工程的 scope，沿用库与 manifest。将 `started_at` 设为本批监视起点。`batch` 和各 worker 的 `request_prefix` 使用本批身份。[字段模板](../projects/code/config/candidate-scope.example.json)
2. `pool` 是两个角色共享的 V2 候选池。`history_set` 指向现有当前链 manifest。`registry` 和 `policy` 分别指向该链绑定的生产专库和已登记的活动策略。`output` 是链内的消费者结果目录。生产者默认由 manifest 派生证据目录，实际路径见生产报告的 `evidence_output`。首次安装候选池的命令见[原生入口](#候选-v2-的两个-python-入口)。
3. `producer_config` / `producer_db`、`consumer_config` / `consumer_db` 分别绑定各角色的配置和作业账。新工程角色首次启动时自行初始化，以后沿用账内原始时间、用量和请求状态。旧版消费者复盘仍需要原作业账。需要交接 QC 的批次在 `qc_policy` 指定抽检策略文件。
4. `batch` 填写 `<生产者配置的 run_id>/entry-batch/<本批键>`。脚本从它取出生产者的 `--batch-key`，并将完整值作为消费者的 `--producer-batch`。各消费者的 `consumer_worker` 和 `request_prefix` 必须独立。单机增加消费者时，为每个 worker 准备各自的范围文件，沿用同一批、池、专库和适用的原账。

### 启动与结束

在仓库根目录操作。每个终端先设置同一个试跑目录和命令，可在项目虚拟环境中直接运行，无需 AI 客户端。

```sh
TRIAL=/absolute/trial
SCOPE="$TRIAL/scope.json"
mkdir -p "$TRIAL/logs"
wc_run() { projects/code/.venv/bin/python projects/code/scripts/start_candidates.py --scope "$SCOPE" "$@"; }
```

分别在三个终端运行。预览时给 `wc_run` 加 `--dry-run`，只打印参数，只需 scope 文件。生产者的 `--query` 可替换为 `--directions "$TRIAL/directions.json"`。

```sh
# 终端 1，先让该消费者轮询本批候选
wc_run consumer --limit 20 --poll-seconds 3 >>"$TRIAL/logs/consumer.log" 2>&1

# 终端 2，发现约 20 条新候选，逐条发布
wc_run producer --query '中文在线计算工具' --target 20 --batch-size 8 --max-batches 8 --max-searches 8 >>"$TRIAL/logs/producer.log" 2>&1

# 终端 3，独立读取本批过程和调用记录
wc_run monitor --log-dir "$TRIAL/logs" >>"$TRIAL/logs/monitor.log" 2>&1
```

生产者也可以先启动。完成后，已入池的候选可由稍后启动的消费者领取。返回 403、404 的入口在生产侧逐条留存拒绝收据。生产者报告的 `NEW` 是实际新增数，目标 20 允许有缺额。消费者的 `--limit 20` 是该进程的处理上限。在轮询模式下，本批完成且已无可领取候选时会提前退出，实际用量继续写入原账。

生产者和消费者结束后，可单独停止持续监视，再运行 `wc_run monitor --log-dir "$TRIAL/logs" --once` 从原 SQL 补导最后一轮。调用记录见 `producer-calls.jsonl`、`consumer-calls.jsonl`，页面访问见 `consumer-visits.jsonl`，领取与正式尝试见 `pipeline.jsonl`，异常见 `issues.jsonl` 及各进程自己的标准错误日志。监视器写入失败时，只处理其日志目录并重跑监视器，消费者继续按原账运行。

多个消费者共用一个作业账时，`consumer-calls.jsonl` 包含这份账从 `started_at` 起的调用。按 `formal_attempt` 与 `pipeline.jsonl` 中的 attempt 和 claim 对照，可以定位到具体消费者。每个同时运行的监视器使用独立日志目录。

## 未决请求与候选派发

对当前工程的 Table2 候选，选样程序可调用 `candidate_consumer.guard_candidate_dispatch(ledger, entry_url, candidate_id=candidate_id)`。消费者在同一工程原账上复用该检查，领取之后、打开网页之前再核一次。它只读模型和站点两处派发条件。候选版本、独占领取、资源余量由各自的正式入口核对。

页面 GET 或访问预约有可信原访问记录时，只保护对应 HTTP 地址。模型请求和中断的浏览器操作可以定位到原 attempt 与候选时，只保护该候选。规划和正式执行会再次按候选核对。当前工程的 worker 遇到局部未决时记录该条，在处理上限内继续领取，账号级未决在下次领取前检查。实际请求身份、用量或浏览器效果仍未决时，保留原编号和收据。已提前转为 `reconcile` 的旧候选保留原处置，需要继续时按原候选 ID 区分派发前拦截与已派发的任务。具体匹配见[设计口径](设计说明.md#未决范围)。

## 候选 V2 的两个 Python 入口

### 后台生产和逐候选用量

旧的显式入口 GET 隔离决定由 `python -m site_planner.producer_authority --scope <工程范围> --closed-entry-get-uri-scope --reason <原指令>` 记入工程站点账。当前工程直接按[请求和任务归属](#未决请求与候选派发)检查。对已关闭的生产者入口检查仍核对原作业已完成、访问有结束时间、无 HTTP 状态码、该作业无模型请求以及原 GET 收据。原 URI 和指向它的入口重定向继续受阻，其他独立 URI 可照常验证。

混合生产可给新批次指定 `--discovery-mode mixed`。新应用先选一个有来源的入口；已知应用只有在来源中有可引用的独立功能名和操作、页面角色是功能页或检索页时，才会再对新入口执行 GET。同路径的语言版、参数和分页变体以及已收录的同名功能会被过滤。已有官网目录和明确工具链接也可以用 `expand` 独立成批，与新站批共用工程候选池和净新增总目标。

本机长批可为 `start_candidates.py --scope <本批范围>` 增加 `--background-dir <全新目录>` 后运行 producer。启动器向当前 macOS 用户的 launchd 登记一个单次作业，返回 service 名称。标准输出、标准错误和实际参数保存在该目录。用 `launchctl print <service>` 查看 PID、状态与退出码。确认本批报告后用 `launchctl bootout <service>` 移除这次登记。方向文件可写成数组或含 `directions` 数组的对象。`--search-count` 允许新查询请求 1 至 50 个搜索结果，已执行的查询复用原件。

旧生产者的显式隔离决定由专用入口登记，在配置的 Python 环境运行 `python -m site_planner.producer_authority --scope <工程范围> --reason <原指令>`。若要继续其他来源，使用 `--defer-request <原请求ID>` 显式指明已因租约过期进入 UNKNOWN 的选源调用。决定追加到同一工程的生产者原账，停止条件仍有净新增目标及本次给定的来源。速率、并发、单次请求参数、原请求幂等及账户授权检查继续生效。

当智谱明确以 HTTP 400、业务码 1301 拒绝一组输入，并且原选源作业已结束但未返回用量时，具名隔离也支持这类内容拒绝。整组来源主机进入排除范围，原请求及预留保持未结算，后继批次只能处理其他来源。搜索 429 使用提供方退避时间及连续限流退避，保留原查询与未知费用。

运行 `python -m webcollect.candidate_accounting --scope <工程范围> --since <本轮起始Unix秒> --batch <原批次全名> --output <新JSON文件>` 可读出工程与本轮的两份角色用量和逐候选详情。`--batch` 可重复，筛选详情；用量窗口由起止时间决定。入口候选的正常 `candidate_consumer list --protocol entry` 同样返回 `discovery_tokens` 与 `consumer_result`。新来源记录的 `discovery_request_tokens` 是该次共享请求的实测值。逐候选份额可相加，详情包含对应的 claim、attempt、样本、当前 QC 状态和可归属的消费者请求。尚未领取显示 `unclaimed`。

新批次的去重位置、GET 复用、消费原账回算和离线用例见[生产者与站点发现 Agent 优化方案](生产者与站点发现Agent优化方案-20261101.md)。

- 首次准备本地候选池使用 `python -m site_planner.candidate_discovery install --pool <本地数据库> --create-pool`。已有池只需按需运行 `install --pool <本地数据库>` 安装候选扩展。各进程在同一台机器上使用同一个池，并能读取池所引用的来源证据。消费者使用当前链的策略和账本。

- 消费者使用 `python -m webcollect.candidate_consumer --pool <本地数据库> run --protocol entry --help`。每个并发进程使用独立的 `--worker-id` 和 `--request-prefix`，共享池及适用的原账。启动检查先于领取。有界 `--limit` 表示本次最多处理的候选数；默认空池返回 `EMPTY`。消费者先启动时，可加 `--poll-seconds 5` 等候新候选直至本批排空或显式取消，每次空轮询使用新的请求 ID。已入库的候选在生产者退出后仍可消费。 有界联调可给消费者增加 `--producer-batch <生产者run_id>/entry-batch/<batch-key>`。它只领取该批实际新增的候选，按原账记录逐个访问失败；生产者在 SQLite 标记本次结束后，消费者会在队列耗尽时退出。
- 消费者自行取得首张同步图树、解析页面身份，再登记正式 attempt。ReAct 复用该页面并保留原始日志，整条加工通过后写入 `collected_pending_review`。运行只需要 Python、项目依赖、浏览器和已配置的 GLM 服务。

**生产者证据目录。** 新建真实候选批次需要原整站止损配置。`produce-entries` 与消费者共用 `--history-set <当前链 manifest>`。省略 `--output` 时，生产者将搜索原件、模型响应、工具收据和报告写入 `<manifest 所在目录的父目录>/producer-evidence/<批次身份摘要>/`，报告的 `evidence_output` 给出绝对路径。也可以显式指定当前链的验证证据根或结果根下的批次目录。显式来源和调用方目标文件中的证据引用遵守同一范围。

**生产者入口检查。** 搜索或显式来源经模型选中，以及调用方通过 `--goals` 提供目标时，程序在候选发布前对实际 URL 执行 GET。它遵循公开地址、应用归属、访问间隔与整站止损规则，读取最终响应头后关闭连接。最终 2xx 才可入待消费池。403、404 等非成功 HTTP 响应记录为 `REJECTED`，超时或没有确定状态记录为 `HELD`。V2 两种来源逐条写入批次结论，好入口可以继续入池。同一批次对同一请求 URL 复用原检查收据，续跑和多目标不会重复访问。原始状态码、落地 URL、跳转记录和访问账 ID 写入批次证据目录的 `entry-http-*.json`，独立监视器将入口拒绝写入 `issues.jsonl`。页面返回 200 但显示验证码、登录墙或页面异常时，仍由消费者在实际浏览器会话记录。

**独立监视。** 生产者、消费者按各自入口运行。另开一个进程执行下列命令读取本轮账本。运行范围 JSON 包含 `pool`、`producer_db`、`consumer_db`、`registry` 的绝对路径，以及 `batch`、`consumer_worker` 和开始时的 Unix 秒数 `started_at`。为本轮选择单独的日志目录，按角色使用各自的作业账。监视器将搜索记录的 `kind` 与日志事件名分别保存。写盘失败会报告到该进程的 stderr，消费者按原账继续运行。

python -m webcollect.candidate_monitor --scope ./trial-scope.json --log-dir ./trial-monitor-logs --once

`--once` 用于一次核账，省略后按秒持续观察。修复日志目录后可从原 SQL 记录重新导出；已完整写入的同一事件按 ID 去重。

`BatchLedger` 可绑定原 `site_failure_guard`，每次来源/探测/预检派发前核对整站账；导航失败及导航成功后的预检失败分别用原执行ID幂等入账。正式采集导航由生产尝试账负责，避免双算。应用跨host仅使用 `application_identity.py` 的显式证据别名；无归属证据时不猜测，已有账本绑定不得替换。

单次执行的 `completion_view={schema_version: webcollect-live-completion-view-1, distance: 1..480}` 不要求旧准入。只支持同一最终结果容器的文字/数值断言，并在原始动作前截图核实结果存在、符合断言、部分超出视口且一次有界滚动足够完整展示。旧 `webcollect-bound-completion-view-1` 继续核验其完整原收据。

## 3. 当前主调用链

普通新任务的高层入口是 `python -m webcollect.task_generation`。`generate` 从真实能力目录和显式当前链生成 M4 计划；`execute` 使用同一实际计划运行采集。生产前必须已有授权 campaign 与原专库，该 wrapper 不自动新建生产 campaign。

```text
site_planner discover → probe → 实际能力复核
  → task_generation.generate
  → task_generation.execute
      ├── 核验来源、当前链、业务/页面身份、原campaign与预算
      ├── preflight_plan（只读）→ publish_plan
      ├── collect_m4 → collect_one → browser.capture / execute
      ├── 结构检查 / 采集证据审计 / 精确图像冲突检查
      └── derive facts → build_client_package → prepare_qc_inputs
  → quality_inspector check-set（对冻结有效集合生成跨包报告）
  → quality_inspector.delivery_pipeline
      prepare → run → status / import-human → finalize
```

`execute --qc-policy` 接收恰含 `ai_percent`、`human_percent`、`seed` 的 JSON。比例均为 0–100，seed 为非空字符串；这里不指定生产默认值。无策略时可保存候选，但返回 `qc_configuration_required`，不会自动选比例或开始审核。有策略时只冻结 `sampling-plan.json`、`effective-set.json`、收据及可选 `collection-checks.json`，返回 `QC_NOT_RUN`。

上述为现有接口行为；后续默认10%及扩检的完整语义以[新策略](QC抽检与批次合格计数方案-20261030.md)为准，尚未落实为本接口的运行默认值。实际审核与批次接纳分别回写，未抽中但有效接纳的数据不应继续占用待审库存，也不能冒充逐条AI审核通过。

采集不要求事先完整执行一遍任务。兼容任务若已有 `task_admission` / `workflow_admission`，仍核验其绑定。`observed_workflow` 是独立兼容路线，不代表所有任务都走这里。底层 `python -m webcollect collect` 仍支持旧计划及严格 M4；不能把旧入口当作当前链范围与预算的替代。

## 4. 命令与副作用

使用 `projects/code/.venv/bin/python -m <模块> <子命令> --help` 查看精确参数。以下是定位表，不是自动执行清单。

| 模块 / 命令 | 输入与输出 | 主要副作用 |
| --- | --- | --- |
| `webcollect.batch validate-config` | 配置检查 | 不派发模型；不证明模型可用 |
| `webcollect.batch init / recover / model-smoke` | 作业账、恢复或模型协议 | 写账；`model-smoke` 可能真实调用模型 |
| `site_planner discover / probe` | sources/candidates → candidates/catalog | 真实模式可访问网络；probe 可调用已配置模型 |
| `webcollect.task_generation generate` | config/ledger/catalog/history → plan | 写作业账与冻结产物；model 生成器可调用模型 |
| `webcollect.task_generation execute` | plan/catalog/registry/policy → capture/candidate/QC inputs | 真实浏览器操作、编号和账本写入 |
| `webcollect runtime-status` | 原 registry/output | 只读查看现有 scope，不初始化账本 |
| `webcollect runtime-policy / runtime-resume / runtime-close-replan` | 原 scope 和原因 | 修改持久预算/运行状态；并非只读命令 |
| `webcollect.qc_handoff` | 当前候选/history-set/显式抽检参数 → QC inputs | 冻结文件；不调用模型、不写生产 registry |
| `quality_inspector check / check-set` | 实际包或有效集合 → 包外报告 | 确定性重验及读取实际审核；不派发模型 |
| `quality_inspector.delivery_pipeline prepare` | config/ledger/input/plan/effective-set/cross-package-report/profile | 冻结并排队审核；资料模式须显式 `ai` 或 `human` |
| 同模块 `run` | receipt → 审核输出 | 可能发送真实模型请求 |
| 同模块 `status / import-human` | receipt、实际审核记录 → 状态报告 | 不发模型，但可发行状态记录、导入人工结果及同步进度，并非文件系统只读 |
| 同模块 `finalize` | receipt/status → 新完整包，可选 archive | 核验门禁、final 重验、封包；不新发 AI 请求 |

当前 `delivery_pipeline` 的 real 模式接受原智谱 GLM `glm-5.3-flash`，以及 Ark 的 `glm-5-3-flash-260828`、`deepseek-v4-1-flash-economy-261017`；Ark标准版 `deepseek-v4-1-flash-261017` 继续兼容既有冻结账本。上述模型均须显式支持视觉；`ModelGateway` 支持的 provider 范围更广，不代表 pipeline 任意接受它们。controlled 模式需要 synthetic 账，不能生成真实审核结论。配置和参数限制以入口实现为准。

本机文件现已改名为 `request/token.yaml`；复验配置通过绝对路径 `model.api_key_file` 显式绑定该文件。YAML按厂商选账户：Ark只读取 `ark1`，智谱只读取 `glm1`，缺失或歧义不跨账户回退。若全文件不能按严格YAML解析，Ark可读取唯一显式顶层 `ark1` 旧标签，不从其他账户猜测。Ark GLM已通过原图/JSON/usage诊断，见[开通后复验报告](../verify_results/ark-integration-20261029-live-r03/复验报告.md)；经济版也已通过，见[经济版与凭据格式复验](../verify_results/ark-integration-20261029-live-r06-economy-format/复验报告.md)。旧UNKNOWN原账保持不变。

Ark 请求将完整 Schema 放入系统指令，本地严格校验 JSON；GLM 不发送结构化输出参数，DeepSeek 使用 `json_object`。原图使用 PNG data URL，`max_completion_tokens` 同时限制思考与回答，响应必须返回所选模型版本和完整用量。模型冒烟显式执行一次调用，示例保留单次费用预留；扩大预算或进入实际发现/QC须使用对应授权范围的冻结配置。新通道不修改旧账模型，不自动跨通道重发 UNKNOWN。可运行方式见[模型接口](../projects/code/README.md#火山方舟-ark-双链路2026-10-29)。

## 6. 验证与开发路径

后续按一次功能交付组织工作：先在现有工程文件中写清目标、涉及模块、输入输出及稳定基线，再集中完成所有代码更新，随后通过现有正常入口进行一次集成测试。集成通过后直接试跑固定基线；Agent 的 goal、prompt、tool 或宿主接入有变化时，使用真实 GLM 调用，以同一基线目标的实际结果与正式保存收据验收，相关 QC 按任务范围执行。不要在实现过程中反复单测或用模拟响应代替真实 Agent 验收。基线失败时定位实际断点，修复后仅复验相关链路。

Agent 协议/实际输出与工程文件不一致时，优先修复工程解析、工具宿主及文档以接住 Agent 输出，用真实结果检查修复效果；不要默认再加拒绝层、兼容框架或更多前置检查。实现服务于快速完成当前功能和上线，只处理实际需求与已出现的问题。完整约定见 [AGENTS.md](../AGENTS.md#修改与验证)。

取证报错标记 `comparison_scope=single_frame` 时，检查该帧重试记录中的 `mismatch_fields`、加载状态和像素差异。动作前后发生的合法变化在轨迹的 `effect_evidence` 中核对。媒体预检的 `bounded_irrelevant_image_change` 表示同步证据已将变化限定在无关装饰图内。预检可读取采集器支持的各版稳态证明，遇到混合版本或同时用了边框、重绘豁免时保留各自的差异来源。[图书馆实例与离线验收](Agent优化与39条问题统一实施计划-20261101.md#操作引起的合法变化)

## 7. 常见阻塞的排查顺序

| 现象 | 优先核对 |
| --- | --- |
| `ModuleNotFoundError` | 同一 Python 虚拟环境、三个 editable 包或 `PYTHONPATH`；AI支路需要采集包 |
| 源码/能力/预检不匹配 | 输入收据原 SHA、能力有效期、generation/source identity；保留原版本，重新生成适用后继，勿改摘要蒙混 |
| 已有输出或收据拒绝覆盖 | 是否应复用原请求或生成新版本目录；不要删除失败目录重跑 |
| pending 或 `REVIEW_REQUIRED` | 逐项区分机械失败、语义缺失、AI_REQUIRED、HUMAN_REQUIRED、替换缺额和分布门禁 |
| resume 拒绝 | 原 registry、bootstrap、计划、已提交样本/raw 字节、租约和 scope 状态；禁止拼接中断轨迹 |
| 站点无法派发 | 原整站失败账、UNKNOWN hold、域限速、campaign attempt/pending/resource 额度 |
| 模型超时或 usage 不完整 | 原请求行与预留、provider 响应及 request ID；UNKNOWN 不记零、不另起账重发 |
| Ark `404 ModelNotOpen` | 当前账号未开通对应模型服务；先核对控制台开通状态，保留原请求和费用UNKNOWN，不自动换模型或重试 |
| 单条 PASS 但不能发布 | payload/final 阶段、完整包资料、总体分布、有效集合、跨包版本与最终报告绑定 |

当前工程尚未证明通用网站的自动任务容量、真实大规模吞吐、跨机器运行或客户实际验收。静态分片接口见[协议说明](../projects/code/docs/static-batch-protocol.md)；它是离线协议能力，不是已经运行的集群。

## 批量消费者目标、处置与修复轮

实现入口是 `webcollect.candidate_consumer.run`、`webcollect.candidate_batch`、`CandidatePool.record_disposition/claim_next`。`--limit` 限制本次处理候选数；`--target N --target-basis saved|qualified` 表示指定生产者批次的累计收据目标。恢复仍使用原 scope、模型账和 RuntimeStore。目标模式返回 `processed`、`stop_reason`、`stop_details`、逐候选 `results` 和只读 `summary`；无目标的旧入口仍返回列表。scope 可选择冻结 `consumer_target`、`consumer_target_basis`，否则从消费者 CLI 传入。

下面只预览命令，不启动消费者：

```sh
projects/code/.venv/bin/python projects/code/scripts/start_candidates.py --scope projects/code/config/candidate-scope.example.json --dry-run consumer --limit 5 --target 3 --target-basis saved
```

`webcollect.candidate_batch --pool <原候选池> report --producer-batch <完整批次名> --target 3 --target-basis saved` 是只读报告。增加 `--usage-scope <原scope.json>` 会复用 `candidate_accounting`，显示原生产者账、正式消费、显式诊断和未归属请求；用量、费用未知时保留 null。处置组按原因/策略版本关联候选、请求与费用。报告不会启动或补做审核。

`disposition` 需要原 `--claim-id`、`--kind`、`--reason`、`--stage`、`--evidence`（原 path/sha256 引用数组文件）及 `--policy-version`。`optimize` 为待优化，`reprocess` 为只需重加工，`abandon` 为候选与目标级放弃，`reconcile` 和 `paused` 分别保留原账未决与资源暂停。普通 worker 跳过处置项目；同站其他候选仍可处理。

`recover` 必须给 `--producer-batch`、一个或多个 `--reason`、明确的 `--candidate-id` 集合与 `--fix-version`。只对原因匹配且通过原 `retry` 请求、访问、RuntimeStore、保存和 QC 校验的项目准备下一轮。未决/暂停项只有在原账已明确且原处置允许时才能准备；`UNKNOWN` 本身不是可重试结论。随后 `run --recovery-version <相同版本>` 仅领取该组。版本与原候选集合绑定，相同版本重复准备不增加 attempt，不回收旧编号，不拼接轨迹。

`reprocess --candidate-id <原候选> --output <数据集外全新目录> --reason <原因> --fix-version <修订版本>` 仅读取原封存 raw、动作和同步图树，派生 `revision_pending_review` 修订件。原保存收据、原有效结果和审核仍保留；修订件不能自动计为新采集或独立合格。重复同版本和修订收据写出后的投影恢复均无浏览器/模型调用。已有审核不会转移给修改后的字节。未封存且加工失败的原入口仍使用 `postprocess.process`；封存后使用 `postprocess.revise`。

停止原因包括 `target_reached`、`processing_limit`、`candidates_exhausted`、`inventory_empty_producer_open`、`awaiting_review`、`account_reconciliation`、`resource_pause`。生产者仍开放时沿用显式轮询和原时间窗；并发在途任务可能使结果超过目标，样本仍按独占领取、原配额和唯一有效结果计一次。

`produce-entries --category <类目> --discovery-mode new-sites` 接受仅含类目的新批。用 `--max-searches` 限定独立检索轮数，默认最多四轮。每轮先冻结模型生成的中文词和实际查询引擎，再向宿主搜索工具派发。新的类目找站批次默认查询公开索引，支持 360 自然结果、DuckDuckGo HTML 与 Bing RSS，保留响应原件和解析记录。遇到访问验证或不可用响应时，暂停该公开索引 30 分钟。普通 GLM 对话继续承担拟词、核类与选页。显式选择 `--search-engine search_std` 或 `search_pro` 才使用智谱按次计费的搜索。用新业务查询复核智谱搜索时再增加 `--probe-search-hold <当前1113请求ID>`。同一原错误只预约一次，新的明确 1113 成为当前待核记录。成功复核追加服务可用回执。程序按原查询身份和原账阻止未决请求重发。

### 首轮 GLM 超时诊断

当前 V7 的 GLM 在第一次看到页面时提交整段计划。首轮传输的套接字等待上限为 600 秒，宿主在原子作业的原所有权下为本次请求预留至少 630 秒有效租期。父采集作业独立续租。后续选项判断使用账本中的模型超时。首轮遇到传输未决时保留请求 ID、用量状态与原账，只能按原请求对账。

普通 V7 的首轮读取账本的 `model.reasoning_effort`，缺省为 `max`，分支沿用 `max`。带显式 `evidence_contract` 的计算、阅读目标首轮和分支使用 `low`。已结算且有有效用量的格式错误最多纠正一次，计入同一次采集的 25 次 GLM 上限。实际档位与等待值写入请求收据。客户截图和独立审核使用原图。

`webcollect-goal-evidence-2` 在候选绑定的 `session_objective.objective` 中描述所求量和单位，或阅读主题及要核对的关系。宿主从对齐的前后图树验证每项输入、最后一次修改后的具名数值，或来自实际搜索结果的新文档与滚动后可见的引文。阅读 Agent 只能选择当前帧提供的段落引用；目标和计划终点有据时即可收尾。原始回包、宿主补全的本请求 ID、动作、引用和独立质检分别落账。

使用 `strict-plan-content-1` 的新 GLM 首轮请求将原账的每次 HTTP ID 同时传入请求体的 `request_id`，可用该 ID 向服务端核对。该字段与响应中的服务端 ID 分开记录。[智谱对话补全 API](https://docs.bigmodel.cn/api-reference/模型-api/对话补全)

`model_requests.response.http_timing` 记录请求体字节数、套接字超时秒数、收到响应头的毫秒数 `headers_ms`、传输耗时 `elapsed_ms`，以及正文读取是否返回 `body_read_returned`。两项毫秒数均从发起 HTTP 计时。`headers_ms=null` 表示本地未观察到响应头，可能涉及建连、发送或服务端等待。已有响应头但正文读取中断时，保留状态与 HTTP ID 对账。正文有效性另经 JSON、协议和用量核验。非流式请求无法从这些时间推算首个推理 token 的时刻。旧收据可能没有该字段。
