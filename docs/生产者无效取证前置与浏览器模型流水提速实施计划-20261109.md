## 1. 本轮结论与目标

本轮只解决生产者吞吐，不改变消费者、QC 或 Table2 接线协议。

采用两个最小改动：

1. **站点余量前置**：已知某应用达到 `application_pending_cap` 时，不再对该站后续页面执行浏览器读取和用途模型判断；只剩少量余量时，按余量有界准备本批。
2. **单批预取流水**：模型判断第 N 批时，浏览器预取第 N+1 批；模型仍逐批串行，候选仍按原 chunk 顺序发布。

新增显式运行模式 `producer_pipeline=overlap-1`。未显式指定时继续按原串行方式运行，旧批次、旧 checkpoint 和旧收据的解释不变。

目标是用同一固定输入比较：

- 实际 NEW/小时与整批墙钟时间；
- 浏览器、模型和预取等待时间；
- 已知到上限站点在浏览器/模型前被跳过的数量；
- 发布后 `OVER_LIMIT`、重复、invalid、UNKNOWN 和账本一致性。

不预设提速百分比，不把离线夹具的加速折算成真实产量。

## 4. 运行模式与兼容边界

### 4.1 显式模式

为生产者增加可选配置/CLI 参数：

```text
producer_pipeline = serial | overlap-1
```

要求：

- 缺省为 `serial`，现有命令不改变行为。
- `overlap-1` 只在显式新批次启用。
- 将模式冻结进该 run 的配置和最终报告；同一 run 恢复时不得切换模式。
- 旧 run 没有该字段时按 `serial` 解释。
- 模式只改变调度，不改变业务模型输入，因此继续使用同一 `entry-tools-13 / producer-business-value-2` 和原业务缓存语义。
- 不为了本轮新增 `entry-tools-14`，避免把工程流水与后续 Agent 协议修复混为一谈。

### 4.2 Table2 与消费者零改动

新流水最终仍通过原 `_publish_entry()` 和原候选校验发布：

```json
{
  "schema_version": "webcollect-data-candidate-2",
  "candidate_kind": "entry 或 target",
  "entry_url": "原入口 URL",
  "requested_goal": "entry 为 null；target 保留调用方目标"
}
```

保留最终发布时的应用上限检查，因为预检查不能替代发布事务，也不能排除其他进程造成的并发竞争。

## 5. 站点余量前置设计

### 5.1 复用原上限口径

在 `candidate_discovery.py` 增加小的只读辅助函数，复用 `_application_pending_cap()` 的配置来源：

```text
application_pending_remaining(pool, batch, application_id)
= max(0, application_pending_cap - 当前 pending 数)
```

不要复制另一份上限配置或另建配额表。

### 5.2 调度前检查

在 `grounded_entries.py` 每次准备浏览器预取前：

1. 读取该应用当前剩余量。
2. 减去本次已经预取、尚未完成发布的同应用链接数，得到本轮可调度数。
3. 为 0 时跳过该站后续链接，不调用 `screen()` 和 `classify()`。
4. 小于拟处理链接数时，只准备有界数量；当前批发布结束后重新读取数据库余量，再继续调度。
5. 预取中的数量只是本进程调度状态，不写正式配额账，不把潜在 NEW 记为产量。

允许保守地少预取，不允许明知已经超过上限仍继续读取。被拒绝或 NOT_SELECTED 的页面不形成 NEW，下一轮根据真实数据库余量重新补充调度。

### 5.3 跳过记录

预检查跳过页面没有经过模型选页，不能伪造与该模型响应绑定的 `candidate_batch_rows/OVER_LIMIT`。

应新增宿主流水记录，至少包含：

- run、unit、chunk_key；
- application_id；
- 当时 pending、cap、remaining 和预取占用；
- 跳过链接数及原因 `APP_PENDING_CAP_PREFLIGHT`；
- 时间戳和 pipeline 版本。

原发布后 `OVER_LIMIT` 仍用于处理最终竞争或绑定变化，旧 96 条记录保持原义。

## 6. 单批预取流水设计

### 6.1 最小流水范围

先只在**同一个 prepared unit 内**做一批前瞻：

```text
先读取 chunk 0
for 当前 chunk N：
    后台开始 screen(chunk N+1)
    主线程 classify(chunk N)
    主线程按原顺序 publish(chunk N)
    取得 chunk N+1 的 screen 结果
```

unit 之间先等待已有预取结束，不跨 unit 预取搜索、扩页或新站点。首版不增加浏览器并发页数，也不并行调用多个用途模型。

### 6.2 代码组织

在 `grounded_entries.py` 抽出现有 chunk 处理中的最小阶段函数，供 serial 与 overlap-1 共用：

- 观察准备：现有 `screen()`；
- 业务判断：现有 `classify()`；
- 来源绑定与发布：现有 `isolate_decisions()`、items 构造和 `publish_items()`。

避免复制两套业务逻辑。默认 serial 的调用顺序必须保持“观察→判断→发布→下一批”。

`producer_observation.screen()` 和 `page_consumption.screen()` 首版尽量不改。预取线程内部仍调用现有同步函数，由其创建自己的 event loop 和浏览器；主线程不同时使用该浏览器。

### 6.3 线程与账本边界

- 只使用一个有界预取 worker，例如单线程 executor；不得无界创建线程。
- 主线程只执行当前批模型判断和发布，预取 worker 只执行下一批观察准备。
- 不共享 SQLite connection/事务；沿用 `pool`、`ledger` 各自按操作创建短事务的现有方式。
- 每个浏览器读仍使用原 URI、job、visit、tool request 和证据引用身份。
- 模型仍按原 chunk 逐次调用，发布仍按原 chunk 顺序执行，避免编号和报告顺序变化。
- 预取线程不得直接发布候选、推进全局 NEW 计数或生成消费者任务。

### 6.4 异常与恢复

必须保持以下顺序：

1. 当前批模型判断和可发布结果先按原流程落账。
2. 再处理下一批预取的未预期异常并停止诊断。

页面级已结算 failed/unknown 继续由原 `screen()` 隔离；不得把整批异常改写成单页失败。

恢复要求：

- 已保存的 selection checkpoint 继续原样复读，不因流水模式重发模型。
- 已保存的观察请求按原 tool request/job/visit 对账；UNKNOWN 不换作业、不换 URI、不重新派发。
- 当前批发布成功、下一批预取未决时，恢复只能核对下一批原请求，不能重复当前批发布。
- 同一 run 不得从 overlap-1 改成 serial 后继续并拼接新解释；如需对照，使用独立 run。
- 进程退出时等待并关闭 executor、浏览器和 event loop，不留后台任务。

## 7. 轻量度量

为新流水增加追加式 checkpoint/收据，建议版本 `webcollect-producer-pipeline-metrics-1`。每 chunk 至少记录：

- unit、chunk_key、输入链接数、预检查跳过数；
- screen 开始/结束与耗时；
- classify 开始/结束与耗时；
- publish 结束时间；
- 主线程等待预取的耗时；
- selected、NEW、DUPLICATE、REJECTED、OVER_LIMIT、HELD；
- invalid_response、unknown、failed；
- 当前 pending/cap 快照和异常类型。

最终报告分别给出：

- 实际总墙钟时间；
- `sum(screen) + sum(classify)` 的串行工作量参考；
- 实际流水等待和整批耗时；
- 实际 NEW/小时；
- 预检查跳过数与发布后 OVER_LIMIT 数。

“串行工作量参考”不是实测串行墙钟，不能写成节省时间的直接证据；真实对照来自独立 serial/overlap 两轮。

### 8.2 流水正确性

1. 用受控事件证明：下一批 screen 尚未完成时，当前批 classify 已开始；默认 serial 不出现该重叠。
2. 模型调用次数、输入 payload、tool schema 与串行相同。
3. 发布顺序、Table2 四字段、candidate ID/去重键和来源引用与串行契约一致。
4. 下一批预取发生页面级 failed/unknown，当前批仍能完成原发布；原未决记录保留。
5. 下一批发生未预期宿主异常时，不丢当前批已选结果，不重复发布。
6. 每个阶段完成后重入，model/GET/search 新派发均为 0；UNKNOWN 不重发。
7. 预取线程退出后无存活浏览器、线程或未写回事务。
8. metrics 的阶段计数与原 model_requests、top_level_visits、candidate_batch_rows 可对账。

- 原 V13 业务证据测试保持原结果，尤其是无主区证据零模型、引文绑定、UNKNOWN 和缓存。
- 原 grounded producer CLI 在未传 pipeline 参数时保持 serial 和重启零新增 I/O。
- Table2 候选继续通过四字段校验；消费者 claim 快照、首帧和 ReAct 输入路径不变。
