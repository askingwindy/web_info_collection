## 1. 结论需要收紧

**真实保存和导出链确已走通，但“5 条保存并导出”不能写成“5 条内容均符合客户要求”。** 三条 Muxtly 主链得到图像支持；印花税样本有原目标覆盖不足；Wiki 样本有明确内容缺陷，不能按内容合格交付。五条还有共同末步字段缺口。

## 3. Wiki 低保存率：不是一个原因

十条终态分布为：2 条全事项核验但实际短流程，3 条协议/字段修复终止，4 条 NO_PROGRESS_END，1 条保存。另从实际动作看，6/10 只有 1–2 步，其中只有前述两条全事项核验。不能把全部失败统称为“目标已经完成但步数不够”。

### 3.1 首轮的五步只是形式成立

历法列表、世界、世界遗产、行政区统计等目标，在一个锚点点击或一两次移动后就可能同屏可读。首轮用“点章节后再滚动”“每段各滚一次”补足五步，但这些是假设，不是必要动作证据。冻结后完成即停、短流程不交付是正确的；问题应在冻结前的目标选择解决，不能在完成后补动作。

年号样本又暴露相反方向：goal 要比较列表导语/汉朝表及六字例子，requirements 却额外冻结了“年号条目定义”义务。辅助路线被升级成必须完成的独立目标，促使额外导航。应同时检查 goal→requirements 的无遗漏和无额外义务。

### 3.2 零派发也推进游标，是确证的实现缺陷

`screenshot_session.py:688` 把 `new_attempt and not advanced` 传为 executed；`:1329–1332` 在 continue 后推进 position。新增 attempt 包含 `NOT_DISPATCHED`，因此动作未派发也会被跳过。

zh-04 原件 `0026-business-attempt.json` 为零派发，第 `0032` 个决策 continue 后，下一次有效动作的 `0046` 决策已经 position=3；`0080→0086→0090` 又把零派发步骤越过并到达 plan_exhausted。zh-01/05 也有同类事实。应依据实际派发增量区分未派发/已派发未证效/已核验，不能靠“发生过 attempt”推进路线。

### 3.3 眼睛看到的正文、表格和图，宿主不能一致接收

- zh-07：原图清楚有“意大利 (62)”柱形图标签，DOM 没有该图内文字；模型读对也无法通过纯 DOM 验真。
- zh-09：完整统计表在一屏，模型给整行“全国 34 4 23 5 2”，验真却只匹配单个 td，连续 complete 失败；继续滚动不能修复结构不匹配。
- zh-06：短山名是链接，region 排除 a；无 region 的引用又必须至少8字；完整列表被拆成短链接与标点，两个限制合起来使合法内容难以引用。
- 另一面也过宽：引用一个真实短片段就可把“读取清单”“核对使用者”等较大事项记为 VERIFIED，导致遗漏仍被接受。引用真实与语义覆盖完整不是同一个检查。

相关位置：`snapshot.js:604–614` 的直接文本、`:1173` 仅为 p 补全内联文本块；`screenshot_observation.py:192–230` 的 region；`screenshot_plan.py:1096–1112` 的长度及单节点匹配、`:1148–1152` 的证明接受。应复用可见文本块，补 li/tr、表头/单元格绑定与短链接的准确区域；保留原字符、bbox、来源，不能任意拼接全页文字。图内文本要么有真正与 PNG 绑定的视觉证据接口，要么在自主目标冻结前明确当前能力不支持，不能反复要求模型重新滚动。

### 3.4 历史补图被实际配置关闭

195 个实际 HTTP 请求全部 `image_count=1`、`history=[]`，推理强度均 high。Wiki 的82个应用层 intent 中，45次历史补图均 IMAGE_LIMIT 丢弃。当前 `consumer-config.json` 的 max_images=1 与实际请求一致；`screenshot_session.py:236–245` 因少于2图而丢弃历史帧。

`screenshot_chooser` 每次发送重建的 facts，不发送完整对话历史。所谓历史证据是文本索引，不是模型仍能看到过去的图。代码一边提供历史候选和观察ID，一边提示“历史图未提供，可导航重显”，使引用错误转成重复操作。应接通已有“当前图+必要历史图”的按需能力，或明确一致的单图合同；不能把“这次没带图”与“本会话从未提供过”混为一谈。内部补图不会改变客户每步一张原PNG的格式。

### 3.5 阅读进展比“完整事项已核验”更细

zh-04 持续首次读到新的区域组织章节，但 `_progress_marker` 只计输入和 VERIFIED 证据，未抵达金融章节前已消耗8个停滞检查点。零派发拒绝和每次滚动检查点进一步放大问题。应把与缺项绑定、首次覆盖的新正文范围纳入进展，并稳定去重；不能将任意新文字、公告、截图ID或滚动次数都视为进展，也不宜直接增大停滞上限。

## 4. Prompt 是否过长

**总请求明显有冗余；本轮证据不足以单独证明“长度导致注意力偏移”。** 可以证明的是：重复字段、条件复杂的工具协议、无法兑现的历史图能力和互相冲突的反馈共同增加了返工。仅删系统提示不能解决上述确定问题。

实际请求结构：

- 系统提示每次 3,942 个字符；首轮仍含大量分支、验算、完成与历史图规则，纯阅读也携带算术细则。
- 正常工具 schema 序列化约 1.4 万字符，多个动作变体反复描述共同字段。少数字段修复请求会换成较小 repair 工具。
- 全部调用的输入 token 中位数 28,015，范围 9,716–54,047。Wiki 后续请求的中位数33,949，Muxtly后续22,985。
- 最大请求来自 zh-08：用户事实 JSON 为105,245字符，工具schema14,601字符，系统3,942字符；含200个 page_directory 地址但仅2页实际访问，60个控件。
- 该最大请求仅 page_directory 就有26,928字符；historical_evidence17,855，controls19,107，action_facts11,454，visual_evidence6,683。这些都有直接精简空间。

按195次请求用户JSON字段值的累计字符量统计（不是精确token归因）：controls25.0%、historical_evidence15.6%、page_directory13.8%、action_facts11.3%、visual_evidence9.3%；五项合计75.0%。系统提示不是最大的可压缩部分。

`page_directory` 将未访问的发现链接全部重复传入，而 open_url 只允许本会话已观察页面。保留宿主完整目录，模型侧只给允许执行/当前目标相关条目即可。controls 与 visual_evidence.control_mapping 重复；历史 regions、最后8动作、last_effective_action、known_business_state 也重复承载事实。模型可见视图可压缩为“目标/缺项、当前可动作控件、必要证据片段、上次动作效果、当前反馈”；账本和原证据照常完整保留。

47次invalid中31次都是 **continue同时重写了非空remaining_plan**，不是空数组噪声。这31次本身消耗869,260输入token、36,335输出token、821.7模型秒。不能无条件丢弃这些尾部来消错：只有与当前尾部确证等价时才可正规化；含真实改动必须 revise。更小的 continue/complete 回包、与 revise 分离的字段展示和示例，比再加一段长警告更直接。

不建议在本轮证据下首先换模型、降低 high 推理或硬砍步数；先解决合同矛盾和重复上下文，再评估这些变量，才能判断收益来源。

## 7. 整体设计判断和优化顺序

当前“首轮完整计划+真实偏差时修尾部+宿主执行/验真+独立保存链”的单Agent框架可以继续使用，无需重建多Agent编排。原始证据、UNKNOWN、输入因果、保存收据、候选回写的严格边界值得保留。问题是模型可选目标、模型可见信息、宿主可验事实和客户可读标注没有保持同一语义。

建议按以下顺序集中处理，而不是继续逐个失败追加prompt规则：

1. **正确性先收口。** 修零派发跳游标；修同文档输入身份与导航叙述优先级；修完整正文内联文本、列表/表格证据和必要事实覆盖；明确单场景与历史多场景的支持边界。客户包中的错误不能靠哈希门禁解决。
2. **把观察和反馈接通。** 使实际max_images与补图能力一致，模型能看到必要历史图；已提供但未绑定、区域错误、短文本、图内文字不支持、真正没看到，要给不同反馈。先修证据引用，只有页面内容确实未出现才执行定位动作。阅读探索进展与重复回访分别计量。
3. **同步精简prompt/tool/schema/宿主。** 首轮只下发目标选择与完整路线规则，分支只下发本决策适用规则；计算推导义务按需出现。控制目录、历史索引、控件与图像映射重复。continue/complete采用小回包，revise才附尾部；确定等价格式正规化，歧义不猜。保持原证据不裁剪，只裁模型视图。
4. **改善目标与路线。** 选自然需要独立取证/比较的具体问题，冻结前验证当前能力和显见操作前置条件；不以预计滚动数量证明五步，不额外冻结定义/验算等非目标义务。首轮考虑结果回呈，未来控件以条件路线描述，不假装已经看见。

更简单的替代方案是先在已有框架修上述合同与上下文，不新增独立规划模型、二次强制AI核验调用、长期记忆框架或新协议代际。只用更强模型/提高重试额度可能提高部分格式遵从，但不能让互斥输入同时成立，也不能使DOM突然包含图内文字。

若后续实施，应用本轮封存证据覆盖受影响的少量核心场景：零派发游标、内联/列表/表格完整引文、图内证据能力反馈、双场景拒绝或绑定、导航叙述、末步字段；保持全工程≤50条核心用例，只跑受影响项，再核对正常派生/保存链。当前仅提出验证判据，没有运行这些测试，没有自动安排真实验证。不能用本轮读证据推算修复后的合格率或节省比例。
