# QC抽检与批次合格计数方案

2026-10-30，策略版本 `qc-sampling-v1-20261030`。用户已明确将后续方案调整为“全量程序检查＋AI抽检”，同时用于今日新增1000条和最终20万条。本策略取代后续新批次“每条必须完成AI终审才能计合格”的规划口径；历史任务、原审核及失败不改签。当前仅更新文档，尚未改代码、配置、冻结策略或生产账，不启动采集、模型审核或人工服务。

轨迹仍按[最新片段口径](../request/轨迹采集口径补充-20261030.md)执行：动作合法、满足5步要求、重复度达标；不要求完整业务结束。同页多条、多轮操作、参数变化可以入候选，连续切段的已证明共享边界单列。

## 1. 默认比例和职责

| 检查层 | 默认范围 | 通过依据 |
| --- | --- | --- |
| 程序检查 | 100%候选片段 | 字段/文件、原图与同步树、动作空间/步数/坐标、执行身份/来源、可计算异常、全局累计判重等实际报告 |
| 稳定组AI随机抽检 | 每个质量单元10%，向上取整，非空单元至少1条 | 冻结总体和随机顺序，独立审查选中轨迹的全部原图及动作序列 |
| 新策略启动首批 | 本策略启用后本campaign最先保存的10条全审 | 与随机样本取并集；不足10条时审已有全部，不等凑满才交接 |
| 新站点或新操作模板 | 每个新风险组累计前5条全审 | 相关采集/QC语义版本变化的组同样执行；不足5条时审已有全部，后续补足前5条覆盖 |
| 风险必审 | 风险清单中100% | 包括未能自动裁决的重复候选、可疑空白/遮挡/画面与动作不一致、异常状态或计划修订后仍有风险的样本 |
| 已发现问题 | 按第4节扩至30%或100% | 原样本与分母保留，新增审核覆盖原冻结总体 |
| 内部固定真人抽检 | 不新增固定比例 | 必要复核记录实际审核者；AI不确定不能自动记通过 |
| 客户验收 | 保留原需求每个交付批次随机2%人工抽检等条款 | 独立于本内部AI抽检，不用AI记录代替真人记录 |

工程负责100%程序检查、分组、抽样、扩检与计数；默认GLM执行独立AI审核。桌面Codex处理难例和共性问题，实际看图只能记为AI复核。规划者的自评不作为QC结论。

10%是本版为减少模型开销选择的内部运行比例，不是“其余90%已逐条看图”的证明，也不能推导视觉错误率或近重复率必然小于某个数。客户质量标准、近重复上限0.1%和总体类目上限20%不因此放宽。

## 2. 批次与风险组

采集后异步交QC：启动首批最多10条，之后通常每50条冻结一批；队列结束、停机或日结时，已有不足50条也正常交接。其他批次继续采，不等某站全部完成。

风险组由“整体应用ID＋可复用操作能力模板＋相关采集/QC语义版本”确定。模板描述导航/点击滚动、表单输入选择等执行能力，不能为每个URL、参数、货币对或5步组合新建模板。工程登记分组依据，GLM不能通过重命名模板规避风险或重置失败。

一个“QC批次×风险组”是一个质量单元，随机抽检和局部接纳在此执行。不同组分开判定；一组待审不阻塞无关联组。跨组重复或同版本共性缺陷涉及的组须一起处理。

新组尚未覆盖的累计前5条始终必审，不因跨批次或换ZIP重新计数。其余数据可并行采集，但该组待判期间不提前批次接纳。不足5条且已有样本全部通过时，可接纳已有范围；后续前5条仍必审，发现相关问题仍可撤回先前接纳。

程序检查失败直接保留原因并排除，不靠AI投票覆盖。程序检查通过不等于视觉语义已逐条通过；可计算异常与风险线索送必审清单。

## 3. 冻结与抽样

每个质量单元冻结原始候选ID集合、数量N、原件摘要、分组/规则版本、随机种子及风险原因。N是该单元程序检查通过后、AI判定前的候选数；机械失败另保留在总尝试/保存分母中。

对N个候选生成可复现随机顺序：

- 基础随机集合R10取前 `ceil(0.10×N)` 个。
- 首批、新组、风险必审集合记为M；实际初选集合为 `R10 ∪ M`。
- 扩检随机集合R30取同一顺序的前 `ceil(0.30×N)` 个，包含R10；100%阶段覆盖全部N个。
- 同一样本被多条规则命中只审一次，记录全部选中原因。已有原件与规则绑定仍有效的实际审核可复用。

不能先挑容易样本再称随机抽检，也不能通过更换seed、删除失败、拆小总体或新建作业账换一批样本。抽样总体、名单和阶段结果追加留存；扩检生成引用原总体和原种子的后继计划，不覆盖旧计划。QC产物写在被检查数据包外，采集不修改已经冻结的原件视图。

AI抽检的单位是完整轨迹片段：选中一条，就覆盖其全部原图及动作序列；不是每条只看一帧，也不是所有轨迹各看10%的帧。图像分组请求应保留相邻动作覆盖与整段结论。

## 4. 发现问题后的扩检

| 发现情况 | 扩检与接纳规则 | 范围 |
| --- | --- | --- |
| 基础随机和必审全部PASS，无其他未决 | 该单元可按第5节接纳 | 当前质量单元 |
| 稳定组发现1个普通质量FAIL | 暂停该单元接纳；随机覆盖由10%扩至累计30%，必审集合仍全部覆盖 | 原冻结N个候选，不以剔除坏样本后的较小分母重算 |
| 30%扩检无新增FAIL，唯一问题有证据定位为局部异常 | 剔除已失败样本；全部要求的审核完成且无未决后，其余可以按批次接纳 | 失败原件、原分母及淘汰原因保留 |
| 累计出现第2个普通FAIL，或问题重复/有共同原因/原因范围无法定位 | 升为100%审核；同组后续数据保持100%，修复后重新执行前5条全审 | 当前单元及同应用/模板/受影响版本的关联范围 |
| 启动/新组必审发现FAIL，或发现严重问题 | 直接100%审核相关范围，不等待30%阶段 | 严重问题包括真实隐私泄露、原件/来源错配、轨迹拼接、实际动作不符合记录或有效步数虚计等 |
| AI返回REVIEW_REQUIRED或审核请求失败/UNKNOWN | 所需审核保持待审；不能当作PASS或靠重抽跳过 | 阻塞依赖该结论的单元，无关联组可继续；UNKNOWN先核原账 |

普通问题指尚无共性证据的局部标注、局部画面可读性或动作说明问题；不包含严重问题。有效审核返回FAIL即进入上述流程，不以再问同一模型一次来覆盖失败。争议可通过有原件依据的独立复核澄清，旧结论和修订原因保留；没有结论时仍待审。

扩检中任一样本的未决、已知程序失败或未解决重复关系，都不能随批次混入合格集合。已失败样本可据真实新执行补采，但不能覆盖原件、复用原ID或清除扩检要求；补采新版本进入新QC范围并必审。无需为所有失败强制新增真人服务门禁，必须保留实际解决依据。

共性缺陷跨批次时，从该风险组最近有效检查点至修复生效的相关范围追溯；涉及更早版本则按证据扩大。范围未明时保守冻结相关应用/模板/版本，不能只重审眼前一批即放行。对已接纳样本追加撤回/失效记录并从当前有效计数扣除，不修改旧报告或重做无关站点。

按“随机样本问题数/实际随机审核数”和“必审问题数/实际必审数”分别报告，并报告两者并集。10%→30%→100%是内部问题处置规则，不套用客户2%人工抽检的退批阈值作为内部放行理由。

## 5. 合格计数与状态

每个片段区分四件事：程序检查结果、实际AI审核结果、所属质量单元接纳结果、发布/客户验收结果。以下为待实现的概念字段，不是现有CLI或数据库字段承诺：

| 维度 | 含义 |
| --- | --- |
| `program_check` | PASS / FAIL / PENDING |
| `ai_review` | PASS / FAIL / REVIEW_REQUIRED / NOT_SELECTED；只记录实际审核事实 |
| `quality_admission` | PENDING / ACCEPTED_BY_BATCH_POLICY / REJECTED / REVOKED，并引用质量单元收据与策略版本 |
| 发布与客户验收 | 独立记录，不能由内部批次接纳自动生成 |

一个片段可计入内部合格集合，当且仅当：

1. 来自本链真实采集，有唯一片段ID、原执行/来源和真实原件，符合最新片段口径。
2. 全量程序检查通过，当前累计重复与范围内分布等适用指标通过；相关重复候选已裁决，切段共享边界有来源证明。
3. 所属质量单元完成本策略要求的随机、必审及扩检，全部应完成事项有实际结果，无未决，已产生有效的批次接纳收据。
4. 本片段未FAIL、未被撤回；选中或实际复核过的片段有有效PASS，未选中的保持NOT_SELECTED。

因此，内部合格数 = “实际AI复核通过且所在单元已接纳”数 ＋ “未抽中AI、但所在单元已接纳”数，两项互斥。仅有AI PASS但单元仍在扩检，也不能提前计合格；NOT_SELECTED本身同样不自动合格。

未抽中且已按批次接纳的数据不再属于待审，但不能写成逐条AI终审、真人审核或伪造`reviewed_pass`收据。后续需用批次接纳维度驱动生产回写、待审库存和目标计数；旧字段若专指逐条终审，保留旧含义，不能强行塞入新计数。

今日新增数取“当前有效合格ID集合减启动时已有效ID集合”的唯一ID数量，目标为1000；旧历史不补今日数量。撤回涉及本日新增样本时立即扣减，少于1000就恢复为未达标。一次原执行切2段且各自合格可计2片段，但原执行尝试仍只计1。

每次报告列出：原执行尝试、保存片段、程序淘汰、AI随机选中/必审/扩检并集、实际AI已审及PASS/FAIL/未决、未抽中但按批次接纳、批次合格总数、待审/撤回、普通重复/边界共享、发布/客户验收、距目标缺额。费用按实际作业/调用/usage记录，不用“审了10%”推定固定节省90%。

## 6. 计数算例

以下均是假设全局检查已通过的规则算例，不是实际生产结果。

| 情形 | 实际处理 | 可计合格 |
| --- | --- | ---: |
| 稳定组50条，无额外必审，基础抽5条全PASS | 单元接纳；AI PASS 5，NOT_SELECTED但批次接纳45 | 50 |
| 稳定组50条，首5条随机中1条普通FAIL | 扩至累计15条随机审核；新增10条无问题，唯一问题局部化，其余要求完成 | 49：AI PASS 14＋未抽中35；失败1不计 |
| 上例扩检再发现1条FAIL | 升100%；假设最终只发现这2条失败，其余48条实际通过 | 48 |
| 一个批次含A组40条、B组10条，A完成接纳、B必审未完成 | 只接纳无关联的A，批次报告保留部分完成 | 40 |
| 今日1000条均完成程序与批次接纳，实际AI审120条均PASS | 报告AI PASS 120、未抽中但按批次接纳880 | 1000，不声称AI审了1000条 |
| 保存1000条，其中40条所在单元仍待审 | 最多计其余已接纳960；还缺40 | 最多960 |

30%扩检通过不证明其余轨迹逐条视觉合格；其接纳依据是本版批次质量政策。抽检发现共性问题后，仍按第4节追溯和扣减。

## 7. 适用于最终20万条

最终合格集合使用同一策略、逐条程序检查、批次接纳及全局增量重复索引，累计为20万条，按1万条组织20个ZIP。采集/QC小批保持约50条，不等1万条凑齐才发现质量问题。类目总体20%和近重复0.1%等约定按最终显式集合核算，不能用抽检率代替全局指标。

稳定数据的基础随机审核量约为候选量的10%：1000条约100条、20万条约2万条；各单元向上取整、首批、新组、风险和扩检会增加实际覆盖。实际AI选择数取所有规则并集，不把约2万条当作费用或调用次数上限。

每包及最终总集合核对基础随机覆盖、必审和扩检是否仍有效；不能拼包时专挑未抽中数据、排除已审样本来降低覆盖。最终有效集合内各稳定组的基础随机实际覆盖不足10%时，按冻结顺序补抽并完成接纳；失败记录和原分母继续报告，不能删失败后重新声明随机。

封包重新做全量程序检查、累计/跨包判重和有效集合校验，原件与规则绑定未变的真实审核可复用，不因重新打ZIP额外重审全部图片。最终发布、客户2%人工抽检和重跑验收独立记录；内部20万合格不等同客户已经验收。

## 8. 实施差距与边界

现有`delivery_sampling`已有显式比例、向上取整、batch/site分层、风险清单和NOT_SELECTED事实记录；这不能证明本策略的模板/版本分组、自动扩检、跨批次撤回和新计数已实现。当前`qc_handoff`的简单比例参数也不足以表达整套策略。

后续需同步`delivery_sampling`、`delivery_pipeline`、`semantic/engine`，生产侧`qc_handoff/batch_qc/site_pool_sync/runtime/site_progress`及交付报告/累计索引：接通策略版本、批次收据、扩检父子关系、NOT_SELECTED的批次接纳与撤回。不靠仅把`ai_percent`改成10，或手写新PASS完成切换。P0顺序与验收见[P0第12节](P0快速闭环实施计划-20261030.md#12-qc抽检与批次计数改造待实施)。

本次只更新策略文档及关联规划。原campaign、manifest、冻结计划、UNKNOWN、三次失败停站、编号、原件与费用账保持原样；未恢复采集、真实模型请求、审核或发布。
