## 本轮固定范围

- 所有实现、集成和验证子会话使用 `gpt-6.1-sol / low`；真实采集 GLM 保持冻结配置的 high/high。
- 普通首次完整成功路径至少 5 步、当前最多 10 步；剩余重规划可以不足 5 步。任务天然提前完成仍停止，不为长度补动作。

## 这轮实际解决和暴露的边界

实现已加入 V12 首轮字段绑定与 5–10 步准入、Wiki2 稳定正文编号与跨页来源、明确原目标完成的交付筛选、内部片段出队及取消结账，并将新策略接到导出和包外 QC 交接。旧策略和收据保持历史解释。上述部分得到离线接口证据，**本轮未取得任何完整真实目标成功轨迹**，不能宣称长阅读规划、完整目标完成率或客户可用产出已改善。

真实失败集中在工具协议边界：原 `submit_plan` schema 根为 `type=object + oneOf`，多数回包 `arguments={}`；另有回包将 `steps/checks` 等嵌套结构编码成字符串，当前校验拒绝。原错误和 schema 分别见[格式回包分析](../verify_results/consumer-completion-policy-20261110-r01/validation-r01/format-response-analysis.json)、[首轮工具 schema](../verify_results/consumer-completion-policy-20261110-r01/validation-r01/first-request-tools.json)。这证明实际接入没有跑通；`oneOf` 与异常回包并存尚不足以确定唯一供应商原因。target 的依赖实际为 observation_id→node，并非有 node 必须复制 observation_id，这轮没有到达目标身份冲突层。

另一个已确认的工程缺口是 [ModelGateway](../projects/code/webcollect/model_gateway.py) 消费者协议错误仍走无限 `count()` 纠错循环，没有接入 Controller 的同状态无进展收口；于是十个首次请求后又发出 37 次自动纠错。先前“沿用无进展处理”的方案没有在这层完整落实。本轮停止后不再修改它，保留为未解决事项。

若后续继续，最小修复方向应先集中于：让模型看到扁平、明确的原生工具字段；对可以确定等价的 JSON 字符串对象/数组只做解析并保留原回包，缺失业务内容仍拒绝；将重复同一协议错误纳入原会话无进展判断；补好离线账户和 QC wrapper 夹具后验证真实全链。以上是根据本轮结果提出的下一步，不是本轮已做的修复或新的执行授权，也不建议先放宽 5 步、重改目标或扩大并发。
