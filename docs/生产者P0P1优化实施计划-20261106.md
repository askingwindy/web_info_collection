# 生产者 P0–P1 优化实施计划（2026-11-06）

背景：思考强度实验（`verify_results/thinking-effort-abcd-20261106-r01/`）对 7,645 条 pending 库存的实测——
100% 无 requested_goal、库龄中位 3.7 天零复验、~35% 入口腐烂、81 主机上 top5 应用占 50%（chnmuseum 单站 17.7%）。
本轮完成 P0-1、P0-3、P1-4、P1-5、P1-6；**P0-2（目标供给）因需改消费者供给协议（target 候选、goal 契约、
task_key 语义联动）暂缓**，仅在文末列出方向，不实施。

## P0-1 库存复验（inventory_recheck）

- 新增 `site_planner/inventory_recheck.py`，CLI 维护作业，不进生产链热路径。
- 复验对象：`state='pending'` 且无任何 claim 的候选；默认先复验从未验证或验证超过 72 小时的。
- 手段：轻量 GET（无浏览器无模型，普通浏览器 UA，15 秒超时，同主机间隔 ≥2 秒）。
- 判定与剔除（记入新表 `inventory_rechecks`，追加式）：
  - 2xx/3xx → `ok`，只记录；
  - 404/410/DNS/SSL 错误 → `dead_hard`，**立即**将候选置 `failed`（事件 `recheck_failed`，生产者自有库存状态，无消费者耦合）；
  - 403/429/5xx/超时 → `strike`，连续两次 strike 剔除；恢复 ok 清零。
- `--dry-run` 只记录不动状态。剔除只发生在生产者池内，历史 claim/事件不触碰。

## P0-3 应用在库上限

- `_publish_entry` 发布前检查：该 `application_id` 的 pending 在库数 ≥ 上限（batch config `application_pending_cap`，默认 100）→
  行级 `OVER_LIMIT (APP_PENDING_CAP)`，不发布。
- 存量超限（如 chnmuseum 1,351 页）不强制降级：由复验自然清死库存 + 消费轮转消化；不改 claim 排序（避免过度设计）。

## P1-4 语义精度/覆盖自动初核

- 复验作业的 `--audit N` 模式：抽样 N 条 pending，GET 正文 `<title>`/`<h1>`/meta 与来源 `category_hint`
  做关键词一致性初核（启发式关键词表，按 8 个规范分类），输出抽样精度/覆盖报告。
- 定位为**自动化初核**：给"语义精度/覆盖验收"提供第一个可复算口径；人工终审与 GLM 用途标注复核不在本轮。

## P1-5 structured_output:'json_object' —— 核实为不适用，不实施

- 依据：生产者现行请求全部为原生工具调用（producer 账本最近请求 `native-tool-1`、tools=True）；
  `response_format: json_object` 只作用于文本模式输出，对工具调用路径无效。开启只会扰动冻结配置，无收益。

## P1-6 浏览器级冒烟抽样

- 复验作业 `--smoke N`：对 GET 通过的候选抽样 N 个，用无头浏览器开页取一帧（复用 `webcollect.browser` 观察栈，
  0 模型调用）：导航失败/`ERR_BLOCKED_BY_CLIENT` → `browser_dead` 立即剔除（实验证明此类页面重试必然同样失败）；
  正常渲染 → `browser_ok`。
- 不在发布热路径上做冒烟（保持发布吞吐）；冒烟只作为库存维护的抽样手段。

## 验收

1. 离线集成：临时池夹具验证应用上限拒绝、strike 两次剔除、dead_hard 即剔、dry-run 不动状态。
2. 有界真实试跑（`verify_results/producer-p0p1-20261106-r01/`）：真实池 dry-run 切片（跨应用 ~100 条）→
   小样本真实剔除运行（~100 条，含 smoke 5、audit 100）；产出验证前后库存差、剔除原因分布、审计报告。
3. 全程 0 模型调用；发布链改动（P0-3）不改变现有发布行为，除非超限。

## P0-2 暂缓项（仅记录方向，不实施）

target 类候选供给（带 requested_goal）、消费端 goal 契约与 task_key 语义联动、用途真实性从分类 hint 层
推进到目标层——需生产者与消费者协议同轮设计，待用户单独授权。

## 实施结果（2026-11-06 当日完成）

- 代码：`site_planner/inventory_recheck.py`（P0-1 复验/N-strike 剔除 + P1-6 冒烟 + P1-4 审计）；
  `candidate_discovery._publish_entry` 应用在库上限（P0-3，OVER_LIMIT/APP_PENDING_CAP，默认 100，
  batch config `application_pending_cap` 可调）；P1-5 核实不适用未实施（生产者请求全为原生工具调用）。
- 离线集成：`tests/test_inventory_recheck.py` 4/4（剔除/连击/dry-run 零副作用/上限）；生产者发现链
  `test_application_discovery` 22/22 与 HEAD 持平。
- 有界真实试跑（`verify_results/producer-p0p1-20261106-r01/`，300 条切片，0 模型调用）：
  最老两批各 150 条 GET 可达率 98%（294 ok / 5 strike / 1 dead_hard），真实剔除 1 条
  （chnmuseum 展览页 DNS 失效，事件 `recheck_failed` 留痕）；冒烟 12/12 浏览器正常；
  审计 77 条全有分类 hint，关键词初核一致率 76%（自动初核口径，人工终审另计）。
- 观察：GET 级腐烂率远低于实验入口失败率——实验的 ~35% 入口失败主要发生在浏览器级
  （BLOCKED_BY_CLIENT 等），GET 复验挡不住该层，冒烟抽样是该层唯一生产者侧手段。
