# 生产者与站点发现 Agent 优化方案

2026-11-01，设计基线为 `5fc123f`。目标是在积累 20 万条有效轨迹的过程中，把发现预算用在新站和有依据的新入口上。生产者的两个主指标是净新增候选数和这些候选的浏览器首帧成功率。实现及本轮验收使用本机代码、临时库和已有收据。真实增益留待另行恢复后的可比批次观测。

## 一、现状和对照批次

- `produce-entries` 已冻结搜索来源，按索引接收模型建议，逐行发布。SQLite 有候选唯一键、来源和行收据。新批遇到旧入口时，模型判断和 GET 可能先于候选去重。V2 还复用会读取全部应用、别名的 `freeze_run`，而 V2 的两处调用均未消费其返回的库存清单。旧发现流程有调用方确实依赖这份基线。[生产者](../projects/site-planner/site_planner/candidate_discovery.py) · [站点池](../projects/site-planner/site_planner/site_pool.py) · [候选键](../projects/site-planner/site_planner/candidate_pool.py)
- GET 已只放行最终 2xx。消费者用本次浏览器导航、同步 PNG、界面树与取证元数据完成首次观察。现有 15 个父类及版本可复用，但 V2 消费者会把来源里第一个合法的 `category_hint` 当作已确认类目。[入口 GET](../projects/site-planner/site_planner/entry_access.py) · [首次观察与取类目](../projects/code/webcollect/candidate_consumer.py) · [父类枚举](../projects/site-planner/site_planner/qualification.py)
- R03 净新增 20，生产者 GET 200 共 20，浏览器 HTTP 200 共 18，有完整可信首帧 16，首帧成功率 80%，可判定覆盖 20/20。其余为 2 个浏览器 521、2 个图树不同步。15 个全局工时暂停和 1 个规划阶段类目未知都发生在成功首帧之后。正式尝试和保存均为 0。20 个候选的来源均无可用页面类型。下面的历史回算应从原账得出这些数。[运行记录](../verify_results/producer-consumer-live-20261101-r03/运行记录.md) · [逐候选记录](../verify_results/producer-consumer-live-20261101-r03/accounting/candidate-outcomes.jsonl)

## 二、工程设计

| 环节 | 新发现批次的行为 |
| --- | --- |
| 新站发现 | 默认以整体应用为单位探新。收到显式来源或搜索命中后，先核对来源、原 hold 和排除范围，再按本批主机点查应用、经过证据确认的别名及合并关系。跳过已知应用，同批同一新应用优先保留最有功能证据的入口。记录跳过的来源索引和原因。全部命中旧站时，本批后续模型调用和入口 GET 都为零。 |
| 已知站扩展 | 显式选择扩展模式时，允许有新来源证据的不同功能入口。入口沿用 `application_id + entry_identity(URL)`，去跟踪参数、保留业务查询和路由 fragment。调用方通过 `--goals` 给出的目标始终按现有“应用＋规范化明确目标”处理，同 URL 的不同明确目标可以并存。相同键在 GET 前跳过。分类或建议文字不参与身份计算。 |
| 续跑与并发 | 同一已结算批次恢复后返回原累计数，并单列本次新增派发数。部分完成从原输入、响应、GET 收据和行检查点接续。查询本批键走索引，避免复制全池清单或把历史候选送入模型。相关别名和合并仍核验证据。原短事务与唯一约束处理发布竞争，两个写入方竞争同一键最多产生一条 `NEW`。 |
| 轻量 GET | 只对仍可能新增的入口使用现有公开 GET，核验最终归属、状态码与原访问账。最终 2xx 可进入发布。403、404、521 等明确失败本次逐条拒绝，超时或派发结果未决按原账挂起。同批同请求 URL 复用收据。真实浏览器后来收到 521 时，保留生产端原先的 200。 |
| 原件与兼容 | 在新会话或新协议中冻结发现模式、工具及枚举版本、来源排序和反馈依据。新逻辑同时经过正常 CLI 和本机启动脚本。V1、旧工具版本、已冻结批次、claim 快照及原 UNKNOWN 按原绑定恢复。优先复用原表和证据，确需扩展 SQLite 时使用项目已有的显式安装机制。 |

预筛必须覆盖模型输入之前以及调用方目标进入 GET 之前。区分“搜索后跳过”“原模型返回的行结论”和“最终新写入的候选”；跳过项可溯源，只有实际首次写入的候选进入本批 `NEW`。同一批恢复重放时使用当时冻结的输入和顺序，期间新增库存由写入时唯一键处理。

## 三、站点发现 Agent

**站点类别。** 发现 Agent 对整体应用的主营功能给出一个版本化父类，复用 `CANONICAL_CATEGORIES`。新批在现有一次候选选择调用中提交来源索引、站点父类建议、页面类型和主营功能引文。宿主从已核验的来源 URL 提取主机名，校验主营引文的来源、同应用归属和原件摘要。搜索方向、单个页面用途、模型自报置信度都不能独自确认父类。多个来源指向同一应用时复用已有判定。缺证据记 `UNKNOWN`，证据冲突保留各个判断、原件和待核实状态。分类绑定到应用和证据版本，候选 body 继续使用原契约。

**页面类型。** 首版区分功能页、检索或列表、内容详情、第三方介绍或下载、未知。记录的是输入 URL 指向的页面角色。例如政务大厅的办事检索页归入站点父类“政务与公共服务查询”、页面类型“检索或列表”。找计算工具时优先直接功能页；以阅读为目标时，报道可作为其发布站的内容入口。工具只接受宿主提供的来源索引。业务目标仍由调用方或消费者既有协议决定。

**分工与配比。** 正常生产路径是轻量 `produce-entries`。借用现有发现 Agent 关于“当前应用、第三方介绍、证据不足”的判断规则，在已经预算的调用中完成选源和归类。规划采集 Agent 从原来就要取的首帧返回落地身份、公开页面证据或反证。首次观察出现软 404、登录墙或验证码时，分别登记取证情况和页面可用性。发现侧可用已存在的证据追加分类版本，修订不得覆盖冻结任务。新协议的消费者按有证据的应用父类使用配额，缺证或冲突单列。

按去重后的整体应用数统计各父类和未知数，每个应用只计一次。搜索方向已指定目标配比时优先补缺，只有类目列表时优先应用较少的可用方向，同分沿用既有顺序。对抽到的应用逐一对照证据核验归类。另按有效样本检查每 5,000 条和跨批累计的单一站点类目均 ≤20%。站点分布与交付样本分布分别显示。[现有发现判断](../projects/site-planner/site_planner/discovery_agent.py) · [正式比例口径](../request/需求澄清记录.md)

## 四、用消费结果调整下一批发现

1. 从显式批次范围读取池中的 `NEW` 候选，通过 `candidate_id → claim_id → candidate-observation job → visit / 首帧收据` 关联消费作业账，必要时关联生产专库的资源事件。可跨同机 worker、同一范围的多个已绑定原账去重折叠。一个候选只按首次真实首访计一次，重复运行报表不增加样本。未领取、未派发、未决和证据缺失分别报告。
2. 主机取请求入口的实际 hostname，保留子域差别和落地主机。页面类型取入池时冻结的类别，旧记录缺证据归入未知，以便失败页也进入相应分母。按“主机 × 页面类型”输出成功数、可判定数、失败原因、可归因失败数及原证据引用。已保存的首帧要验证同一观察作业的 PNG、状态及取证摘要。HTTP 200 或 claim 的终态均不足以代替首帧。
3. `campaign_worker_time_limit` 单独计数。首访前暂停属于未评估，成功取帧后暂停同时保留首帧成功和工时事件。截图与界面树不同步计首帧失败，另列取证原因。采集器异常、工时、类目未知、未决请求均不提供站点降权依据。没有确定首帧结论的组报告分母为零，比例为未评估。
4. 同组合最近连续两个不同候选出现可归因的首访失败时，下一发现批次将该组合排在正常组合之后。成功首帧中断连续失败。样本不足的组合保持中性。已有整站三次真实失败的 stop/hold 先执行。R03 的两个 521 各在一个子域，两者不能拼成一个组合。选择已有类型的来源时直接应用排序；对新线索，将该主机各类型的反馈随本次选源输入提供给 Agent，未知类型单列。有替代来源时，正常入口优先。保留排序原因和相关候选 ID。
5. 反馈使用当前链显式范围的只读结果，供下一批通过本机 scope 或原生入口读取。冻结使用的反馈摘要、范围和版本，重启沿用原决策。有现成的报表/池接口优先复用。反馈写在新报告或有源证据的本地派生记录，R03 原账和任务状态均只读。[现有监视器](../projects/code/webcollect/candidate_monitor.py) · [原整站止损](../projects/code/webcollect/site_failure_stop.py)

## 五、实施顺序与验收

先接通预筛、重启和 GET 计数，再接通分类与新版本工具输入输出，最后从消费原账产生反馈并接回真实选源入口。每一段都需从对应的 CLI 或其正常调用链验证。实现者可根据代码选择最小表结构和字段名。

| 验收 | 判定方法 |
| --- | --- |
| A. 重启与规模 | 原完成批次重启，新增检索、模型、GET 和候选均为 0，原批累计不变。新批输入全为旧站时模型/GET 均为 0，混合输入只处理新站。扩展模式下同站新功能页、新明确目标可进入，追踪参数重复被跳过。用含 20 万条合成历史键的临时 SQLite 或等效的查询计划与触达计数，证明本批热路径按索引点查，启动不复制全池。 |
| B. GET 与恢复 | 覆盖 2xx、403、404、521、超时、整站 hold，以及生产者 200 后消费者 521。核对逐条收据、实际派发数、失败后其他好行可继续、原 UNKNOWN 不重发。模拟行间中断、冻结批次复读和竞争写入。 |
| C. Agent 与类目 | 验证正常入口发出的工具契约，混合有证据、仅有 hint、缺证、同应用冲突、第三方介绍、同站不同页面类型的返回。断言父类、归属、可复核证据、未知数，以及独立应用占比与样本占比。涉及新旧协议时分别从新作业和旧冻结作业测试。 |
| D. 反馈改变实际选择 | 临时库覆盖有效首帧、软错误页、521、图树不同步、工时暂停前后、重复 claim/报表及缺证。断言“两个不同候选同组连续失败”实际改变下一批在有替代来源时的优先顺序。单次失败、不同主机/类型、全局工时和未决不能触发降权。旧冻结输入可重放。 |
| E. 历史对账与主指标 | 在新目录分别给出离线夹具验证及 R03 的只读回算。净新增取本批不同 `NEW candidate_id`。成功率为可信首帧数 / 首访可判定候选数，另报可判定数 / 净新增数。R03 应复算为 20、16/20、20/20、首帧后工时暂停 15，并列出 2 个 521、2 个同步失败、1 个首帧后类目未知、0 正式尝试与保存。 |

按 [README 的离线验证入口](../README.md#离线验证) 选受影响模块，使用尚不存在的 `verify_results/` 子目录。优先从 `test_producer_tools`、`test_candidate_inventory`、`test_candidate_entry_engineering` 和 `test_pipeline_offline_e2e` 中按改动选取，再覆盖新增的反馈与归类回归。R03 用独立只读入口回算，不把历史文件带进合成测试。交付实际命令、源码摘要、逐项结果、失败原因和报告路径，并执行 `git diff --check`。

当前生产状态为 `STOPPED_BY_USER`。本轮可验收工程行为和历史统计口径。真实增益需后续另行授权，在可比的方向、预算和首访覆盖率下同时比较净新增候选数与首帧成功率。R03 的 20 条和 80% 用作小批对照。采集、独立 QC、发布及客户验收各自沿用原证据。
