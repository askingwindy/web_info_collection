# 历史门禁审查与新工程切换

2026-11-01 用户确认，本代停用“一页一次”和“整站累计三次失败停止”，包括本代自己产生的记录。同一候选仍只有一个有效领取者，同一任务仍只有一个有效结果。单机生产者和多个消费者继续使用 Python 与本地 SQLite。

## R03 为什么换批次仍被阻断

R03 新建了角色作业账和批次，仍指向旧活动的共享候选池、生产注册库、站点止损账和资源预算。20 条均被消费者领取，其中 15 条已经规划入队，旧活动的累计工时在编号前耗尽，消费者 GLM 派发为 0。其余 5 条分别是浏览器 521、图树不稳及类目未知。旧工时暂停被候选池记为失败，和实际站点失败混在了一起。整站停派及页面占用是历史基准站另有的限制。[R03 原账](../verify_results/producer-consumer-live-20261101-r03/运行记录.md) · [基准站审计](../verify_results/consumer-plan-baseline-20261101-r01/核对依据.json)

使用 [candidate-project-20261101-r01 的 scope](../results/candidate-project-20261101-r01/scope.json)。初始化只从前代读取站点和逐日批次的编号高水位，四份前代编号库的站点高水位为 34。新工程的页面、领取、任务、样本、截图索引、失败及工时起始均为空。Muxtly 的一元二次方程计算器在 R03 登记给 `S000003_sample_000001`，共享池还有 3 个阻挡同页的排队任务。新工程该页没有旧占用，站点允许派发。前后核对了 11 份旧账和绑定文件的 SHA-256，一致。三个角色均只做了命令预览。[切换收据](../verify_results/candidate-project-cutover-20261101-r01/cutover.json) · [同一计算器的双库对照](../verify_results/candidate-project-cutover-20261101-r01/benchmark.json)

首次建工程使用 `webcollect.candidate_project init`。日常启动、重启和后续批次沿用这个工程，同批多消费者分别提供自己的 worker 身份和请求前缀。历史成功站点可作为基准，实测时重新取入口来源、分类、GET 和浏览器首帧。R03 的 15 条旧任务单独复盘。[启动说明](工程说明.md#新候选工程) · [消费者实测基准](消费者运行时恢复与单站实测计划-20261101.md)

## 验证口径

- 用临时库给同站记三次失败，然后让同页两个不同目标分别入库、独占领取、正式编号和启动新的 ReAct 会话。每个目标完成五轮受控工具调用。第一个样本保存并生成 `QC_NOT_RUN` 交接收据，第二个因相同截图停在保存前。指定双目标用例使用兼容的 `entry-tools-1` 入口。
- 另一个用例从新工程的默认 `entry-tools-2` 发现入口出发，验证生产者 `low`、消费者 `max` 的原生工具调用，再检查同一次尝试的保存和 QC 交接。独立用例覆盖可重入的原领取、双进程竞争、未决请求、资源暂停和旧规则。[原生入口用例](../projects/code/tests/test_pipeline_offline_e2e.py) · [新旧规则用例](../projects/code/tests/test_candidate_project.py)
- 当前类目证明仍属于本代的输入要求。`entry-tools-2` 的调用方显式目标如果只有 `category_hint`，该提示本身不能证明类目。历史基准实测可以走具有当次可核验分类来源的发现入口。
- 本轮 112 项门禁回归与 33 项生产消费链路用例全部通过，两组验证前后源码摘要一致。用例使用本地临时数据库和受控页面、模型传输。真实基准站的本次可达性、真实 GLM 首调、轨迹质量及独立审核结果，需要后续单站实测。[门禁回归](../verify_results/candidate-project-cutover-20261101-r02-gates/summary.json) · [端到端回归](../verify_results/candidate-project-cutover-20261101-r02-chain/summary.json)
