## 1. 冻结 SQLite 交接协议

- 在原 `site_pool` SQLite 中显式新增生产者输出协议 `candidate-producer-3` 和库存协议 `webcollect-data-candidate-2`。前者是生成批次版本，后者是候选 body 版本，现有行的 `version` 仍是该候选的内容版本。现有 `webcollect-data-candidate-1`、`produce --strict`、冻结 run/config 和旧 claim 按原语义读取、校验和恢复。新入口通过显式协议选项启用。
- 新 body 包含 `schema_version`、`candidate_kind`、`entry_url` 和 `requested_goal`。最小入口示例如下，实际入库还必须绑定下面规定的来源记录。

  ```json
  {
    "schema_version": "webcollect-data-candidate-2",
    "candidate_kind": "entry",
    "entry_url": "https://example.org/catalog#/search",
    "requested_goal": null
  }
  ```

| 项 | 协议要求 |
| --- | --- |
| `entry` 与 `target` | 默认 `entry` 的 `requested_goal` 为空。`target` 只接受可信调用参数显式给定的结构化目标和原参数，绑定其来源与摘要。模型不能自称调用方。旧候选的冻结目标继续按旧规则验证。 |
| 来源和建议 | 复用 `candidate_sources` 和现有 `path + sha256` 证据引用。搜索来源须能定位到原搜索请求、结果原件及原始命中序号。过滤后的 `source_index` 必须能映射回该序号。显式来源绑定调用输入及证据。模型参与时另绑原模型响应和行号。分类、业务方向、来源类型和 `suggested_goal` 均可空，留在来源上下文。生产者不写 `working_goal`。 |
| 身份 | 程序分配 `application_id`、`candidate_id` 和 `dedup_key`。`entry` 的键由协议、类型、整体应用和规范入口身份组成。`target` 的键由协议、类型、整体应用和冻结目标组成。同入口换建议只追加来源，同页不同的明确目标可以并存。 |
| URL | 分开保存可实际导航的原始 URL 和用于精确去重的身份。现有 `page_uri()` 会丢弃 fragment，因此新路径要从原始命中保存有意义的查询和 `#/search` 等路由。明确的跟踪参数或普通页内锚点不制造新库存。应用归属、别名和止损沿用现有规则。 |
| 领取 | 在池的 `rows/claim_next` 或对应接口中按支持的协议筛选。未声明新能力的旧调用方只读、只领旧协议，包括指定候选 ID 的领取。在原子事务内先筛选再建立租约，重放同一领取请求返回原结果。冻结候选 ID、版本、body 和当时的来源引用，后到的建议不改变在途快照。租约过期进入待核实，旧 token 不得提交。 |
| 状态与安装 | 新候选只写 `pending` 库存。重复来源不得把已领取或已结算的条目改回待消费。显式安装扩展，普通打开或只读查询不迁移。未安装时拒绝新协议写入，安装失败整笔回滚。优先复用原候选、版本、来源、领取、事件表及唯一约束。若未升级的 worker 仍会扫描所有 `pending`，启用前须验证其领取查询看不到新入口。 |

历史 body、编号、快照和收据不重写。两版候选按同一整体应用及原作业核对在途请求、生产占用和止损。生产者使用原发现池和 `BatchLedger`，正式尝试与样本编号仍由 `RuntimeStore` 管理。

交给消费者 Agent 的接口样例应含一条空目标入口、一条带可选建议的入口、一条有明确目标的候选，以及一个旧候选。提供临时池的读取与领取示例、预期快照和一个版本不匹配的结果。消费侧如何进入 ReAct 由对方实现。

## 2. 根据上一批结果调整搜索词

1. 以调用方的类目/业务范围、种子查询、已绑定的显式来源及原 session 预算为输入。保存策略版本、搜索词、词所属的业务方向、查询理由、结果引用和已用预算。已有显式来源可以独立处理。模型只从冻结命中中按索引选择、粗分类或提建议。程序从原始命中或显式来源确定 URL。
2. 从调用方种子开始。每个已完成查询分别统计原始命中、新入口、新应用、重复、归属错误和被 hold 的来源，并记录实际覆盖的类目。某方向有新增、覆盖还有缺口时，优先换具体业务或入口词。例如从“在线工具 推荐”转到“单位换算 在线换算器”。文章可作为其宿主的内容入口，工具类查询主要命中文章时调整下一词。多个类目都有缺口时，优先已搜索次数较少的类目，同分按种子顺序决定。
3. 给出可复现的换词规则。第一版可采用“同一方向连续两个已完成的不同查询均无新增入口，就转向仍有缺口的类目或已绑定来源”。例如两个换算词都只得到已有入口，仍缺阅读或检索类时，下一轮可选“公共图书馆 馆藏检索”。阈值可配置并随 run 冻结。对查询做规范化去重，对同义改写设置每方向上限。候选查询耗尽或达到停机条件时报告缺额。消费反馈只能异步参考，本轮决策只凭生产者已有证据就能完成。
4. 沿用原账、搜索缓存和请求身份。重启从已保存的选词决定继续，并发不得双发。搜索次数、模型请求、批次数、候选消耗和时窗分别受原预算约束。当前搜索每次请求 10 个结果，默认最多 20 次，仅靠这组搜索约有 200 个原始结果位置。目标 1000 不授予额外调用。原 `UNKNOWN`、在途、认证阻断、整站三次真实失败和适用 hold 按原作用域处理，换词、换批号或换账均不能绕开它们。

## 3. 按原响应逐条发布

1. 冻结本批输入、来源索引映射、规则和发布上限，保留原请求、原始响应、摘要与实际计费。新协议在模型网关只要求能解析约定的外层和候选数组，再对每行单独校验。给新请求单独传外层 schema，避免旧严格协议或其他网关调用失去原检查。
2. 批次允许返回零条或不足上限。按原始行序处理上限内的条目，超额行保留原件并标记 `OVER_LIMIT`。每行记录结果、原因和证据。有效新入口记 `NEW`，已有身份记 `DUPLICATE`，越界索引或明确归属冲突记 `REJECTED`。A 站推荐 B 工具的文章可作为 A 的内容入口，若声称该链接属于 B 工具则拒绝该行。仅建议有错时，记录建议问题，入口本身合规仍可接纳。被 hold 的来源在派发前排除并留证。写入前若新增 hold，则记 `HELD`。区分搜索阶段排除数和响应行结果。
3. 使用稳定逐行身份，如原 session＋批次＋请求 ID＋原响应行号，并绑定原响应摘要。显式来源使用原输入身份和行号。同一身份、同一原件重放时返回原结论。摘要冲突时停止并核对原件。在同一 SQLite 事务内完成候选、版本、来源及该行结论的可见写入。并发命中同一去重键只新增一个候选。若沿用单独提交的发现事件，要用同一稳定事件身份恢复。
4. 池与 `BatchLedger` 各用原账及幂等键。测试在记消耗后、写到一半、写完但未记批次完成时退出，恢复只核对原结算与已提交行，补剩余行或批次状态。重复、拒绝和超额不退还已发生的调用和费用。外层损坏、必需证据缺失/摘要不符、数据库或账本故障停止该批，保留此前提交事实。不能把基础设施错误记成普通坏候选或网站真实失败。
5. 去掉为了查重而逐批调用 `pool.rows()` 的路径。检查 `freeze_run()` 是否在每个新批次重复加载全库应用与别名。新协议按本批入口键、应用 ID 和索引定向查询，当批涉及的别名证据仍须核验。模型上下文只带有限的相关摘要。报告搜索/模型实际用量、缓存、原始返回、逐行结果、新入口、明确目标、缺额与停止原因。费用未知保持 `UNKNOWN`。候选消耗按原预算规则记账，目标缺额按本次实际新增的唯一库存计算。

| 场景 | 可以判定通过的结果 |
| --- | --- |
| 混合批次 | 预置一个重复入口。本批五行依次放入有效入口、仅建议无效的另一有效入口、既有入口的新来源、A 冒充 B、越界索引。预期 `NEW=2`、`DUPLICATE=1`、`REJECTED=2`，池净增 2。如本次目标是新增 5，缺额为 3。另测空批、超额和损坏外层，逐条结论与原件可追溯。 |
| 新旧协议与目标来源 | 旧候选、旧严格批次和在途 claim 可读可恢复。新入口允许未知类目及空目标，模型自报“用户要求”不能产生冻结目标。建议改写不增库存，同页不同明确目标可并存。原始 fragment 可导航，有业务含义的不同路由可区分。 |
