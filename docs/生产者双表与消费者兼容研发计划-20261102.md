## 二、两张业务表怎样分工

| 业务表 | 建议落地方式 | 责任 |
|---|---|---|
| Table1 站点 | 复用 `applications.id`、主机和已有别名。在同一 SQLite 库增设生产者专用的一对一扩展 `application_discovery`，按 `application_id` 主键关联。 | 保存经核实的中文首页、当前站点父类、枚举版本、判定及证据引用、挖掘状态、当前范围和进度引用。生产者查这一份记录决定跳过、续挖或增量扩展。 |
| Table2 可消费入口 | 复用 `data_candidates`、原 ID、原外键和原发布事务。功能名、页面类型、分类凭据和 GET 收据沿用来源记录。 | 每个候选指向可直达的原始 URI。消费者从自己的领取快照工作。逐候选的发现 token、消费结果由现有只读查询按 ID 关联。 |

这是两个业务实体。已核定父类只写一份，使用现有 `applications.category`。同一短事务在站点扩展中绑定这次分类的版本和证据。修订追加带出处的决定，既有任务的冻结判定仍能回读。现有 `pages` 继续留存来源页面，`candidate_sources`、`candidate_claims`、`candidate_results` 等表继续保存各自的收据。在站点侧使用一对一扩展，是因为现有写入有按位置传值的 `INSERT INTO applications VALUES(...)` 和 `INSERT INTO data_candidates VALUES(...)`。直接给原表加一列，即使有默认值，旧写入也可能失败。[候选库结构与写入](../projects/site-planner/site_planner/candidate_pool.py)

**站点状态。** 分类状态与挖掘状态分开。挖掘采用待挖、进行中、当前范围完成三个状态。进度引用应能找回冻结的目录或代表页清单、已处理入口和剩余工作。达到批次目标或中断只保存进度。全部选定项均有本轮处置收据才可标为完成，隔离项保留原始未决状态。重启先按站点身份查 Table1，再按原收据续做。在已完成站点发现有证据的新功能时，开启增量范围。Wiki 的范围是选定的浏览场景和入口，无须遍历全部文章。

## 三、Table2 的兼容合同

| 边界 | 必须保持的行为 |
|---|---|
| 表与正文 | 保留 `data_candidates(candidate_id, application_id, dedup_key, version, body, created, state)` 的原列顺序、约束和状态语义。V2 正文严格只有 `schema_version`、`candidate_kind`、`entry_url`、`requested_goal`。入口的目标为 `null`，显式目标保留调用方冻结的结构化值。沿用 `candidate-pool-2`、站点库版本及 V1/V2 协议筛选。 |
| 发布与领取 | 复用候选唯一键及 `publish_row` 的短事务，同一行的候选、版本、来源、批次结论一次可见。消费者继续按原顺序、批次、类目、固定名单或 ID 领取。原请求幂等、空池轮询、独占租约、心跳、过期对账和结果唯一约束均是兼容测试项。 |
| 分类传递 | 生产者把 Table1 判定转换成旧读取器已经认识的来源字段，包括 `category_hint`、`selection_version`、`application_classification` 及有效的 `references`。父类、枚举版本、站点身份和主营功能引文须可核验。发布前用现有 `confirmed_category` 回读，结果必须等于 Table1 的有效父类。消费者按原来源冻结和取值，无须查询新表或重新分类。 |
| 历史与结果 | `candidate_id`、`application_id`、旧 body 字节、版本、冻结名单摘要、既有 claim 的 snapshot/sources 和绑定、原结果及 QC 收据可逐项比对。新增信息进入生产者证据或只读报表。原命令、原参数、批次可见性及实际消费动作均列入回归。 |

例如，Muxtly 的中文首页 `/zh-CN/` 记入 Table1，科学计算器和分数计算器分别按各自 URL 发布。现有支持 V2 的消费者领到下面的候选后，第一跳就是科学计算器。若首页本身有可采集的导航任务，可以另外发布该首页为入口。普通入口仍按规范化 URI 去重，同页不同目标可用既有 `target` 表达，站点发现 Agent 只提供观察线索，消费者继续根据首帧规划。[候选与领取实现](../projects/site-planner/site_planner/candidate_pool.py) · [消费者入口](../projects/code/webcollect/candidate_consumer.py)

```json
{
  "schema_version": "webcollect-data-candidate-2",
  "candidate_kind": "entry",
  "entry_url": "https://www.muxtly.com/zh-CN/scientific-calculator/",
  "requested_goal": null
}
```

## 四、实施顺序

| 步骤 | 改动和产物 | 完成条件 |
|---|---|---|
| P0　冻结兼容基线 | 从实施当天的实际工作区固定原消费者及其依赖的源码摘要，包含未提交但实际在用的候选库代码。准备独立进程可运行的基线副本，以及 V1、V2 entry、V2 target、已领取和已保存的临时库夹具。 | 留下原命令、库结构、候选正文和领取／保存结果基线。对照进程实际加载冻结副本，避免测试双方误用同一份新代码。 |
| P1　站点登记与断点 | 做可重复安装的站点侧扩展。站点身份复用主机和已有证据别名，中文首页及落地语言用页面证据确认。冻结本次范围，用现有检查点和逐行结论记进度。 | 同工程跨批、重启仍解析到同一应用。已完成且无增量证据的已知输入，选源模型调用和入口 GET 均为 0。中途退出只处理剩余项。 |
| P2　发现 Agent | 搜索命中后先查 Table1。新站用第一方首页、目录或关于页判断**整个站点**的主营业务，工程核对引文、归属和现行父类枚举。已分类站点复用判定。返回有证据的直接 URI、页面功能或可观察的浏览方式。 | 搜索词、第三方介绍、某个工具或游戏名称都不能独自决定站点父类。证据不足或冲突留在生产者侧补证。所有新发布候选的父类有效、有据且一致，`UNKNOWN`、空值、枚举外及未解决冲突为 0。逐站抽核依据，另查混合站和冲突案例的正确性。 |
| P3　混合发现与发布 | 新站入口和已知站点的新入口共用原池。按证据选择 Muxtly 的独立功能页，按实际可执行场景选 Wiki 代表页。调整当前 mixed 中按路由／功能名过早排除内容页的分支。先查候选键和隔离记录，再执行轻量 GET。首次发布须同时具备有效分类和最终 HTTP 2xx 收据。新批的 Agent 选源与调用方显式目标共用这道生产者检查。 | 科学、分数两个计算器可分别入池。跟踪参数和普通锚点不产生重复入口，语义路由按原键处理。403、404、521 本次均不入池，失败行不阻断其他来源。两生产进程竞争同一候选仅一条 `NEW`。已冻结旧作业按原输入、原协议对账。 |
| P4　库存演练与兼容验收 | 在一致性副本盘点旧行并生成逐项处置清单。按下一节验证旧消费者，覆盖按批、固定名单、分类筛选、普通无筛选领取和结果回写。 | 对可消费范围逐项证明原读取器能取到正确分类。有效旧候选、新候选及在途 claim 都通过兼容矩阵。 |
| P5　质量、容量与成本 | 复用首帧反馈、角色账和显式有效交付集合，接入 Table1 分类、单应用计数和站点挖掘请求引用。 | 两个主指标及覆盖率均能回溯原收据。边界样本、每条分摊和项目总账通过下文对账。 |

P0 先行，P1、P2 确定数据来源后接 P3。P2 应交付原需求类别与现行 15 个工程父类的对应关系。每个新入口只引用本站本次有效决定和原证据，避免将同站全部历史判断反复复制到模型输入和每条来源。P3 在原发布事务内复核分类版本及唯一键，发现并发改判时留待复核。给重复候选追加来源前，须验证原消费者读取全部来源后仍能得到同一有效父类。P4 与 P5 都通过，才进入发布阶段。[站点发现与批次发布](../projects/site-planner/site_planner/candidate_discovery.py) · [入口 GET](../projects/site-planner/site_planner/entry_access.py) · [既有父类枚举](../projects/site-planner/site_planner/qualification.py)

**发现 Agent 的输入与输出。** 输入是本次冻结的来源索引、首页与目录摘录、已知站点决定、相关已有入口、可选父类和首帧反馈。输出引用来源索引，给出中文首页依据、整体类目及主营引文，再逐项指出入口的页面角色和可执行操作。工程从原来源绑定 URL、验证引文、执行去重和发布。Agent 工具和提示词可在新生产批次单独版本化，旧批次复用冻结版本。搜索方向优先补最终交付尚未覆盖或供给偏少的类别。

## 五、存量处置和切换

1. **先盘点。** 在同工程的一致性副本按实际候选 ID 区分未领取、在途、待对账、已失败、已保存或已审核。540 是上次封账的未知**应用数**，具体待处理候选数须从这次盘点得出。原模型请求、传输结果、费用和历史分类判断均保留。
2. **先处理未领取项。** 对只有缺证的旧入口，按站点补证后追加带出处的来源。分别经原版类目筛选和领取快照回读。同一候选补证不计 `NEW`。旧来源中只要有 `CONFLICT`，当前读取器即使收到有效新来源也仍会返回 `UNKNOWN`。这类候选单列为“旧协议仍不可放行”，禁止改写旧来源、伪造 claim 或另发一个候选绕过唯一键。
3. **把未知隔离放在生产者侧。** 对前一步仍不可放行的旧行，仅在短事务内确认“仍为 pending 且从未被领取”后，才可按原候选 ID 使用既有生产者拒收语义隔离，记录原状态、具体原因及证据。遇到并发领取则跳过，交还原 claim。隔离记为生产者分类处置，首帧和消费者失败计数均不增加。将来解除只针对有本次隔离收据、仍无领取且原读取器已能正确读回的原行，追加处置记录。已领取、已保存、待对账及原有失败走原账，不重派。
4. **逐批启用。** 先在已有批次范围验证新写端。全池切换前，用原消费者的无过滤领取条件在副本枚举所有可领旧行和新行，核对分类未知为 0、合格旧行仍可见。有未解释差异就保持在已验证的批次范围。已经持有租约的 worker 继续用原快照走完。扩展安装及切换只占短事务，取网页或调模型放在事务外。
5. **回退。** 关闭新批的发布，已投放的兼容 V2 候选继续由旧消费者处理。保留新表、原候选、进行中的领取和所有收据，从原进度恢复。回退演练须证明无重复派发及有效结果。全流程沿用当前工程，不用旧 R03 试点库替换。

原 GLM `UNKNOWN` 维持原请求对账。已在原工程明确隔离的只读入口 GET，只有连接已关闭且原收据满足隔离条件时才隔离原 URI。Muxtly 原 Roth IRA 请求保留一次访问，科学和分数计算器等独立 URI 可继续。模型未决、在途访问及正式执行未决仍受原隔离约束。[原 URI 隔离实证](../verify_results/producer-live-2000-20261101-r01/mixed-01/closed-get-uri-policy-and-original-guard.json)

生产者累计候选、GET 和模型用量按原工程计量，原 39 个剩余名额和 3 元预算已经解除。消费者沿用每次规划采集会话最多派发 25 次真实 GLM 调用的规则，单应用 500 条另按有效交付集合核算。[额度与计量口径](额度限制清单与取消说明-20261101.md)

## 七 本轮实现与证据

实现落在 `application_discovery.py`、原候选发布事务、原 `produce-entries`、逐候选角色账及累计有效集合检查中。站点决定与范围断点不要求消费者升级；旧批次以原冻结配置恢复。工程接口、有效集合容量投影和存量隔离见[工程说明](工程说明.md#生产者站点表与有效交付容量)。

原消费者源码在任何修改前从实际工作区冻结，包含未提交改动。独立进程的旧写端基线、新 entry/target、改造前在途租约、保存后恢复、双 worker 与分类读取证据，以及一致性副本库存和 R03 回算见[验收报告](../verify_results/producer-tables-20261102-114220/验收报告.md)。这些是离线工程证据；正式库补证、切换和真实改善仍须另有生产授权及原账收据。
