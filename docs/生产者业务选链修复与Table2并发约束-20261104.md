## Agent 的 goal、prompt、tool

- **Goal：**有据的主营业务入口及不同操作；网页数量与业务场景分账。后台仍需同一新应用的表格、表单、仪表盘等三种不同匿名业务；没有现场证据不计通过。
- **Prompt：**区分业务选择和用途；法律/隐私/登录帮助、营销与业务页面分别表达，知识站教程本身可属主营。混合页面按主要活动判断，不确定可 UNKNOWN 或不选。保留 Hi8、微信、京东与华为云反例。检索规划不再包含要求调用用途工具的矛盾指令。
- **Tool：模型可见 I/O：**一个有界用途工具显式返回两组结论：select/business/business_quotes 决定是否选入，type/quotes 支撑用途；允许零条。模型另见宿主冻结的应用 ID、主类与决定 ID；这些只约束主营范围，不代替页面证据。原件按语义块编号，补看只引用已保存材料，不提交任意 URL，不预填消费者目标或审核结果。
- **Tool：宿主实现：**保留第一方来源和目标 SHA/job/URI 绑定；业务与用途分别核验；新增材料才允许追加派发；按相同协议与原材料复用已付费回复，优先复用较完整回复；原未决请求仍由原账隔离，不换号重发。所有补证写生产者来源/派生记录，Table2 四字段正文不变。

## Table2 的 ID 与并发执行

**Table2 已有主键 `candidate_id`，本轮沿用这个统一任务 ID，没有另造或重编号 `id` 列。** 它位于数据库行和领取封装中，不塞入 `webcollect-data-candidate-2` 的四字段正文。

|职责|现有机制|
|---|---|
|唯一标识任务|`data_candidates.candidate_id TEXT PRIMARY KEY`|
|同任务不重复入池|`dedup_key UNIQUE`，仍允许同页不同目标按原任务身份处理|
|防止两个进程同时领取|同一 SQLite 内 `BEGIN IMMEDIATE` 短事务，读取 pending、创建 claim、更新 consuming 一起提交|
|数据库最后约束|`one_candidate_holder` 唯一部分索引：candidate_id 在 claim.state=consuming 时唯一|
|同一领取请求恢复|`request_id UNIQUE`，复用原 claim；真正执行仍走既有 stage/RuntimeStore 防重复链|
|进程失联或租约到期|转 reconcile，不自动改回 pending 给另一进程重跑；旧凭据失效，原账核对后再处理|

新增 `CandidatePool.concurrency_contract()` 只读描述及启动时约束核验；主键、独占索引或领取请求唯一约束缺失/被改坏时直接拒绝运行，不自行修库或重建历史 ID。原数据库本来就有上述主键和索引，本轮没有生产库迁移。

后续多个进程必须共享**原工程同一个 pool、生产者/消费者原账和 registry 绑定**，通过现有 `claim_next` 领取；不能各复制一份库，也不能先 SELECT 后在事务外自行标记执行。并发范围是候选任务，未增加“同页不同目标不能同时运行”的全页锁。
