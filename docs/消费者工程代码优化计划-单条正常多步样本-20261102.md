## 工程工作与验收方法

### 1．让交付标注写出结果

在 `describe_change`、`terminal_outcome` 和 `derive` 中优先提取可由原图和同步树核对的动作结果。分别填写本步发生的变化、末帧事实和完成依据。短流程的理由应说明为什么该次操作已经达成目标。[变化描述](../projects/code/webcollect/collect.py) · [整条加工](../projects/code/webcollect/postprocess.py)

**回归用例。** 车来了第一步的原标注只写了“「时刻表」已不在当前视口”。在独立目录用原件复验，新输出应能写出“运营时刻表已展开”，并把两个方向的运营时间对应到末帧表格。如果反例只有焦点或高亮变化，就只能记录该变化。具体站名和时间作为本例断言，生成逻辑复用于其他弹窗、列表和详情页。[原始标注](../results/candidate-project-20261101-r01/collections/consumer/focus-acceptance-20261102-a05/08fdbe04-5436-4b8d-b17a-b7fab48767c1/execution/candidate/samples/S000059_sample_000001/annotation.json) · [末帧原图](../results/candidate-project-20261101-r01/collections/consumer/focus-acceptance-20261102-a05/08fdbe04-5436-4b8d-b17a-b7fab48767c1/execution/candidate/samples/S000059_sample_000001/images/step_002.png)

### 2．分别核验单帧稳定和动作效果

保留完整视口 PNG 与同步树。采集一帧时核对目标、命中位置及结果区域是否可信。比较动作前后两帧时，再判断本次操作造成了什么变化。结果区域可以是弹窗、更新后的列表或落地页。[效果判定](../projects/code/webcollect/react_protocol.py#L112) · [浏览器取证](../projects/code/webcollect/browser.py)

| 离线场景 | 预期结果 |
|---|---|
| 只有无关侧栏刷新，操作对象和预期结果区均无变化 | 保留原图，有效步增量为 0。[已复现的侧栏反例](../verify_results/requirements-agent-progress-20261102-r01/contract-readback.json) |
| 旁侧视频持续播放，目标、点击位置和结果均清晰 | 可旁注媒体变化，取证和采集继续。 |
| 媒体遮挡目标或使其移位 | 派发前重新观察。已派发且后帧不可信时，仅补观察，效果未决则封存原动作。 |
| 点击链接使它获得焦点，随后打开详情页 | 点击最多计一次。只有见到实际落地页及正文后，才能记录“已打开详情”。 |

### 3．让每项 QC 结论可独立回读

复用正式保存收据及现有 QC 交接。用样本 ID、attempt、导出包路径和文件摘要串起采集、导出和审核。分别呈现样本级 AI、包级资料 AI、交付规模与分布检查的结论、分母和原因。先核对现有入口，只有报告丢失或混淆这些事实的地方才需要工程改动。[QC 交接](../projects/code/webcollect/qc_handoff.py)

**回归用例。** 用车来了封存的报告，验证系统能同时列出“样本 PASS、包级资料 FAIL、集合分布未达标”，并指出失败来自单条包的规模与占比。实际样本审核为 0 时显示未审。历史资料只读回归，写回须匹配当前工程真实存在且证据一致的结果。[逐项审核结果与归档边界](../verify_results/chelaile-s000059-independent-qc-20261102-r01/result.json)

从这三个问题的直接调用链做定向离线回归。用临时目录与本机夹具核对同页和同标签导航、合法返回后的新控件引用、工具被拒时零派发，以及派发后取证失败的记录。触及公共接口时再联测 ReAct、后加工、保存与 QC 交接。图书馆的新标签落地问题单独登记。所选任务若依赖该能力，须先证明点击与新页、实际主机和正文后帧的关系。[导航与派发后取证用例](../projects/code/tests/test_react_native.py) · [图书馆原始断点与改造范围](Agent优化与39条问题统一实施计划-20261101.md#操作引起的合法变化)

## 单条联合验收

1. **固定输入和版本。** 后续执行时核对当前 scope，在已发布、有来源证据和生产者 GET 2xx 收据、可独占领取的 Table2 行中固定一条。选本身支持自然多步操作的任务，记录 producer batch、候选 ID 与版本、原 URI、原目标及参数、源码和 prompt／工具版本。只有 URL 的入口在可信首帧上形成工作目标。生产者的 20 站点、200 入口是既有库存盘点，派发资格以执行当时的原账为准。[生产者库存记录](../verify_results/producer-live-20s200p-20261102-r01/完成报告.md)
2. **核对一条连续轨迹。** 保留同会话首帧、每次真实派发、动作前 PNG 与同步树、目标位置、动作后可见效果、实际页面主机和末帧。按唯一原子派发和对应的实际效果重算步数。`set_value` 按实际发生的原子动作核验，`wait`、`complete`、观察、查询和派发前拒绝计 0 步。同一会话最多 25 次真实 GLM 派发，达到上限后再次请求时，原账记录 attempt、次数及 `glm_session_call_limit`。合法短流程如实保存并单列，本里程碑仍要求一条正常多步样本。[轨迹需求](../request/web操作采集需求/需求书-Web浏览器自动化操作轨迹数据集.md#6-轨迹要求) · [动作与坐标](../request/web操作采集需求/附件B-动作空间与坐标系.md)
3. **核对保存。** 原 raw 封存后再做整条加工。回读正式保存收据、交付标注与 PNG／树摘要、候选池和运行库状态。将 claim、attempt 和样本 ID 对齐，确认保存时已达 `collected_pending_review`。失败或 `UNKNOWN` 绑定到原记录。若目标实际需要修复，另记原因、版本和后续处置，历史动作不重发或拼接。
4. **核对独立审核。** 将该样本纳入冻结名单并实际选中，沿原 QC 账对完整轨迹看图、与冻结历史做四路判重和差异审核。样本报告返回 PASS，且动作与画面对齐、终态语义、中文、隐私、实质差异五项均有实际审核证据，方可关闭第一里程碑。任何 FAIL、待补证或请求未决按原结论保留。包级资料独立列实际结论或未执行，正式质量批及累计集合分别统计短流程 ≤2%、单类目 ≤20%、近重复涉及唯一样本 ≤0.1%。人工、发布、客户验收各按自己的收据登记。[审核入口](../projects/quality-inspector/quality_inspector/ai_worker.py) · [正式集合口径](../request/需求澄清记录.md)

**交付记录。** 未来两条工作线共用一份实测报告，列出选入、访问、正式尝试、有效动作、正式保存、待审和实际样本级 AI QC 结果，附原件路径与摘要。把未执行、失败和替代输入分别登记。单条通过后，下一轮才冻结多站点小批名单，分别报告保存数／选入数、样本级 AI 通过数／实际终审数、已证实通过数／固定名单数。批内按固定版本执行，问题记回原候选，批末集中处理。
