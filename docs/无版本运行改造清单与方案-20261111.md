## 已确定的设计原则

1. 每项能力只维护当前实现。删除内部 VERSION、LEGACY_VERSION、Vn_VERSION、SUPPORTED_VERSIONS，以及按这些值选择实现的代码。
2. 新写入的工程内部对象不带 schema_version、protocol_version、rule_version、task_version 等版本字段。当前数据结构仍有字段、类型、必填关系和业务约束，继续做校验。
3. 每次启动直接导入当前源码。修改完成后再启动；运行中的所有相关进程退出前不修改源码，不做热更新。
4. 人工保证开发与运行不重叠。无需新增源码冻结服务、文件监视器、发布平台、兼容注册表或版本锁。
5. 后续缺陷在当前 goal、prompt、tool、解析、执行、完成判断、保存与 QC 中同步修复。不能通过增加协议号、代际 profile、旧版开关或另一套兼容层绕过问题。
6. 运行记录、业务身份和原始证据继续保留。取消实现版本不等于删除 attempt、request、sample、claim、费用、UNKNOWN、原始截图或审核记录。
7. 两种采集策略可以继续作为同时存在的业务选择。使用 react、screenshot_plan 等稳定名称，各自只有当前实现；不再携带 -1、-2 等实现代号。

该方向适合目前的单机、本地源码、多进程工程。主要收益是减少协议组合和交叉分支；明确的取舍是：当前程序不再保证执行任意历史结构的任务，也不再提供旧算法回放。历史结果仍可查看和对账；需要重新处理时使用当前代码和明确的输入，不改写原结果。

不建议仅把所有默认值改成最大的编号。那会继续保留多套实现、版本组合和旧数据触发的分支，后续修复仍然需要兼顾它们。

### 应移除和仍待收口的内容

1. closing_policy.completion_delivery_decision 的最新改动补回了 legacy_v5 和 5–10 步兼容分支，test_complete_goal_v6_20261110.py 也新增对应旧版断言。无版本改造应删除这条旧分支和仅服务旧版的断言，保留当前至少五步且无累计上限的业务检查；不能因为该分支刚修复就把它保留为新运行规则。
2. 当前 strategy_result 在会话结束时填入 eligibility=unresolved、save_status=not_saved，collect_runtime 在正式提交后仍原样透传。统一接口时，在 RuntimeStore 成功提交后根据实际保存收据构造最终结果；拒绝、未保存和提交失败分别写实。不能把会话阶段的暂态作为最终状态，也不能改写已封存的会话原件。
3. screenshot_session.plan_version 目前承担剩余计划修改的记录顺序，不是实现选择器。删除这个版本名称后，直接用当前计划及已有计划事件引用记录修改事实；保留已执行前缀和补证上下文，不建立新的“计划版本系统”。
4. 现有数据库的 candidate/claim.version、m4_tasks.task_version 有 NOT NULL 或唯一键约束，不能只停止传参。一次性处理这些影响当前读写的约束；纯历史元表/原 JSON 可以原样保留并退出活动代码，不为清除所有历史字符串而搬迁或改写原账。
5. 包装方式需要完整调整：如果采用直接源码启动，应同时处理 pyproject 中的 project/build/scripts/package-data 和文档命令，不能只删除必需的 version 留下一份无效的安装配置；外部依赖锁定仍保留。
6. 维护范围补充 projects/code/scripts 下的真实启动和验证脚本，以及三个包的根入口包装脚本。历史批次专用脚本退出当前执行说明，不做全历史回归或重写旧批次配置。

## 当前接口和实现如何收敛

### 生产者 消费者和 QC 的接口

三角色可以独立启动，均使用同一工作区当前代码和当前数据结构。生产者写 Candidate，消费者写 ExecutionResult 和 SavedSample，QC 写 ReviewResult；这些是领域对象名称，不是新的版本标识。

生产者建议以当前 entry-tools-14 分支的业务内容判定、共享观察、入口检查和发布行为作为合并基础，将这些逻辑提升到唯一当前入口，消除未传参数时退回 entry-tools-7 的路径。这是实施基底选择，不表示现有分支已经通过完整验收。消费者策略一以当前新候选构建链为基础，策略二保留本次实施时的当前实现；两者都继续在原文件直接修复。

Candidate 保留 candidate_id、application_id、candidate_kind、entry_url、requested_goal、来源引用和状态。entry 与 target 的差异仍是有无明确指定目标，不能因删除版本而混淆。消费者领取时仍冻结实际候选和来源，仍使用短事务、唯一约束和 claim 身份。

任务保留 task_id、candidate/claim 引用、目标、策略、真实运行参数；不再携带各模块协议清单。task_id 只标识一个任务，attempt_id 标识一次尝试。目标和策略在一次 attempt 内保持一致；修复程序后重新启动不改变历史 attempt 的含义。

执行结果继续分开记录目标状态、结束原因、保存资格和保存状态。QC 读取明确的已保存样本或有效集合；缺少输入就报告空输入，不生成审核通过状态。

仅在同一集合确实需要区分不同业务对象时使用稳定 kind/type；不要给每个旧 schema_version 机械换一个 kind，更不能加入 current_generation、compatibility_level 等替代版本字段。

### Agent 和宿主同步修复

每个当前接口只定义一份字段结构：工具 schema、回包整理、宿主校验和保存所用结构来自同一拥有者模块，避免再次复制出彼此不一致的定义。不新增通用协议框架。

Agent 侧保留当前目标、提示、工具和完成申请。宿主侧保留可确定的格式归一化、事实回算和实际效果判断。目标、来源、证据和实际动作存在歧义时仍如实报错；删除版本机制不意味着宽松猜测。

策略一与策略二各维护当前决策循环，共用当前动作执行、证据和保存入口。站点类型、阅读/计算业务、动作类型可以决定处理逻辑，历史协议号不能决定处理逻辑。

### 本地启动和开发方式

使用现有 projects/code/.venv/bin/python，并在统一入口明确设置三个源码目录的 PYTHONPATH，再运行对应 -m 模块。无需安装三份不同内部发行包；依赖安装只处理第三方库。启动入口可以是一个很短的本地脚本，不需要服务框架。

推荐完整退出三包内部发行流程，移除发布用途的 project/build/scripts 配置及包间发行依赖，保留仍有用途的工具配置和源码资源；同步调整安装与子进程启动说明。不能只删 project.version 后保留无效打包结构。不要维护假版本号或建立 CURRENT_VERSION。第三方依赖继续由现有依赖文件管理。

所有涉及同一源码树的生产者、消费者、QC 和测试进程停止后再修改。修改集中完成，做一次相关集成；随后按明确范围启动真实验证或工作。运行中只能观察、分析、记录问题。发现需要修复时先结束相关运行，再修复当前实现、重新启动。

进程启动后已经导入的代码不会自动变成磁盘上的新代码，因此“每次启动使用当前代码”必须配合上述人工约束。取消源码冻结比较后，不再添加替代的热更新或源码监视机制。

## 数据身份 历史原件与一次性切换

### 内容哈希和操作记录的边界

以下继续保留：原始文件 sha256、request_id、claim_id、attempt_id、sample_id、原请求体、模型用量、原收费数值、审核来源和时间。它们回答“哪份事实、哪次操作”，不回答“用哪代程序”。哈希不能替代被删除的版本号，参与实现选择或跨源码升级门禁。

当前校验依然检查必填字段、证据引用、原件内容、唯一领取和当前业务条件。删除 schema_version 以后，不应顺手删除这些真正保证数据正确性的检查。

### 既有数据库

改造应在停止相关进程后，使用 SQLite backup 等一致方式取得包含 WAL 内容的数据库副本，验证一次性结构调整，再作用到原工程；不能只复制主文件而遗漏未 checkpoint 的记录。禁止另起空账、重建 manifest 或新建候选池来绕过旧状态。一次性切换脚本不成为正常启动中的多版本迁移框架。

- 删除当前结构对候选版本号、task_version、taxonomy_version 和版本元表的依赖。必须处理阻碍当前写入的 NOT NULL、唯一键及位置 INSERT；纯历史表/列允许原样封存，不要求为清除名字物理删除。现有业务 ID、task_key、外键关系和状态原值保留。
- 原始 JSON、来源证据、历史事件和请求中已经存在的版本字符串作为历史字节保留；当前读取只取所需事实字段，不根据这些字符串分派实现。
- 当前形状的旧 pending 候选可继续从原池读取；无法确定映射的旧形状逐条列出，不自动猜目标或改状态。需要转换时生成明确的转换记录，原对象仍保留。
- candidate 的新去重键不再含协议号。一次性核对现有候选的业务身份及新键冲突，保留每个原 ID；不能使同一旧候选因为算法去掉版本盐而被当作新库存重新插入。
- m4_tasks 去掉 task_version 后，已有 task_key 和 attempt 外键不重算。先检查历史同 campaign_id/task_id 的多行，不能直接改为二元唯一键而丢失历史任务；保留各行原 task_key，当前新任务按明确任务/请求身份登记，后续始终引用已登记的 key。重跑同一任务必须有明确新请求并核对原状态，不能靠改版本号获得第二次派发。
- candidate_versions 等历史记录优先原地保留、停止活动读写；仅在结构调整确有需要时才在完整备份下转存。历史记录不再成为当前入口的格式协商条件。
- 原 consuming、interrupted、reconcile、UNKNOWN 逐项保持，不重置 pending，不回收编号，不重发未决请求。

一次性调整需要输出前后记录数、主外键关系、claim 状态、未决请求、样本引用和费用总额对照。这里核对的是本次结构调整影响，不要求重做历史生产审核。

### 重启和恢复

重启后的调度、对账和派生都运行当前代码，不要求恢复当时源码。去掉 bootstrap 中的源码一致门禁和“恢复原协议”的要求；保留原工程、输入、账本和输出归属核验。

恢复调度不等于接续中断的浏览器轨迹。已派发 attempt 的原始记录按原状态保留，未决效果先对账；需要重新执行的工作由明确新请求进入当前代码，不拼接新旧动作。业务输入本身不满足当前结构时给出具体缺项，不能自动启用旧解释器。

## QC 缓存和交付的简化方案

### QC 只维护当前规则

删除 RULE_VERSIONS、逐规则版本指纹、旧 prompt 兼容表和旧审核迁移评估。语义规则使用 visual_alignment、terminal_semantics 等稳定检查名称。规则修复直接更新当前检查实现。

建议本次先取消跨运行自动继承语义审核结论。历史审核仍作为原来的审核事实可查询；明确启动的新 QC 工作使用当前规则和本次实际结果。其取舍是主动重新审核时可能增加模型费用，但可直接删除最复杂的跨规则兼容机制。

删除版本或改路径本身不触发重审，也不自动创建模型请求。当前运行内请求仍按 request/job 身份幂等，旧 UNKNOWN 仍先对账，不得用不同缓存键自动重发。机械检查在当前代码下执行；加速缓存限定本次运行，不维护源码/规则版本兼容。

抽样事实、实际看图范围、人工记录、AI 记录、发布和客户验收仍分开。取消 pipeline_rules_version 不能让旧 AI PASS 自动变成人工 PASS 或当前发布许可。

### 交付只选择明确输入

移除 version_compare 的 version_id/supersedes 链、--version-policy 和按版本裁决“有效样本”的机制。保留一个当前交付集合，每个 sample_id 明确指向所选样本路径和原件摘要。

- 同 sample_id、相同内容出现在多个包中，只计一次。
- 同 sample_id、不同内容不能自动按目录日期、mtime 或最大序号挑选。调用方明确指定本次使用哪份内容，另一份仍留存。
- 文字订正和派生通过独立处理事件记录原输入与新结果，不覆盖原件、不重判历史目标完成。
- 明确选择一份内容只确定本次输入，不能自动授予 QC 或发布资格。

采样计划扩展、费用更正等仍可保留事件序号和事件 ID，因为它们是操作顺序。删除用于支持多套结构/规则的 revision 分支；不能只是将版本机制重命名为事件机制。
