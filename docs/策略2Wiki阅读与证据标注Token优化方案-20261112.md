日期：2026-11-12。状态：**已按后续授权集中实施，并完成受影响核心及离线集成；真实采集未运行。** 工程、prompt、tool、schema及首次标注一起更新；原交付包、生产账和审核状态保留。本文承接[试运行复审](策略2双站试运行交付与Agent设计复审-20261112.md)，设计依据与当前结果分开记录；本次实施明细见第12–13节及[证据报告](../verify_results/strategy2-wiki-plan-implementation-20261112-r01/report.md)。旧执行授权不因本文自动续跑。

## 1. 目标、依据与实施边界

本次优先目标是：**首次规划尽量覆盖完整必要路线，执行阶段沿用该路线；发生真实偏差时，二次规划一次补齐可预见的剩余动作，避免不断请求模型和反复取证。** 同时修复 Wiki 阅读证据接收、执行游标、首次标注生成及上下文重复问题。减少调用不能通过漏观察、漏动作、降低原目标或把未知结果记为成功实现。

依据：

- [交付独立审阅](../verify_results/delivery-agent-audit-20261112-r01/independent-agent-report.md)：5 份标注、47 张原图及对应树、执行事实。
- [Wiki 根因审阅](../verify_results/wiki-agent-audit-20261112-r01/report.md)与[原件索引](../verify_results/wiki-agent-audit-20261112-r01/evidence-summary.json)：10 条 Wiki 尝试。
- [计量汇总](../verify_results/strategy2-agent-design-audit-20261112-r01/metrics.json)与[195 笔请求明细](../verify_results/strategy2-agent-design-audit-20261112-r01/requests-metrics.json)：按精确 request ID 关联原账。
- [客户需求书](../request/web操作采集需求/需求书-Web浏览器自动化操作轨迹数据集.md)第 3、6 节及[需求澄清](../request/需求澄清记录.md)：原目标完成、必要有效动作至少五步、标注能解释相邻图、末步明确确认最终页面、禁止无效往返和完成后补动作。

本轮试运行已证明正常保存和导出链能走通：16 次尝试、5 条保存导出、114 个打包文件哈希一致。**这不等于 5 条内容均符合客户要求。** Wiki 唯一保存样本有明确内容缺陷，印花税样本有目标覆盖不足，五条 complete.user_goal 均过于笼统。原状态继续是 saved_pending_review；正式独立 AI QC／人工审核 NOT_RUN、发布 false、客户验收 UNKNOWN。本次独立 Agent 复审不冒充正式 QC 收据。

最小实现继续采用当前单 Agent、Python、SQLite 和文件链路：复用 `ScreenshotPlanSession`、`submit_plan`、`plan_decision`、既有观察和证据登记、正常 RuntimeStore 保存及导出。不新建页面 Agent、规划服务、协议代际、数据库迁移、通用 OCR 平台或额外逐步 AI 审核。

## 2. 已确认的反复请求，不能只归因于 prompt 长

本节为实施前的试运行事实与根因，保留作对照，不表示下列缺口在本次修复后仍全部存在。

### 2.1 请求、规划与动作分别统计

| 统计口径 | 本轮事实 | 含义 |
|---|---:|---|
| HTTP 模型请求 | 195 | 含失败回包及纠正；148 succeeded、47 invalid、0 UNKNOWN |
| 应用层模型 intent | 151 | 首轮 21、后续 130；另外 44 次 HTTP 请求带 correction |
| 已接受首轮计划 | 15 | 另有首轮被拒绝／未接受，不等于 21 个新任务 |
| 后续 decision 原件 | 127 | continue 39、revise 提议 61、complete 申请 27；不是 127 次都改了计划 |
| 实际接受的尾部修订 | 50 | 小于 revise 提议数；其中 Wiki 年号 9 次、Muxtly 加拿大 14 次 |
| 完成申请被拒绝 | 20 | 说明存在重复申请、缺项修复；不能把申请当成功 |
| 真实有效动作 | 86 | 与 284 次观察、157 次 business attempt 分开统计 |

上表事件数由 `metrics.json.workers[].event_counts` 和各 worker `raw/*screenshot-decision.json` 汇总；请求数由逐请求明细的 phase／correction 汇总。不能把检查点、HTTP 纠正和重规划相加作为动作数。

在不带 correction 的 130 次后续请求中，触发原因为：route_observation 70、body_evidence_visible 12、key_evidence_visible 13、result_reading_or_plan_end 17，其余 binding／预期不符／历史结果／无证效／计划耗尽合计 18。原因是调用入口标签，包含同一原因下的再次询问，**不能据此把每一笔都认定为无用**。

### 2.2 当前调用链为何容易反复

源码入口为 [screenshot_session.py](../projects/code/webcollect/screenshot_session.py) 的 `_execute_round`、`_checkpoint_needed`、`_progress_checkpoint_reason`、`_checkpoint`：

1. 路线观察点直接触发模型；只要尚有 content 缺项，新出现的正文 region 也会触发。连续阅读容易变成连续询问。
2. 尾部全是 wait／scroll 时，每次执行后都可能询问；它没有区分“仍按计划接近目标”和“路线已经失效”。
3. 页面变化、结果出现和路线观察可能同时发生；当前每轮选择一个原因进入调用，但后续缺项仍可再次沿相同原因请求。
4. complete 被拒绝、revise 绑定失败、inspect 失败等路径会再次进入 `_checkpoint`。已有停滞门禁限制循环，但在结束前仍可能付出多次请求成本。
5. Wiki 正文、表格和短链接无法正确引用，历史补图又被 max_images=1 丢弃；模型被诱导回到已经看过的页面，产生新的观察和尾部修订，却没有新的业务事实。
6. continue 携带非空 remaining_plan 造成 31 次 invalid；这是协议表达及纠正开销，不是实际执行了 31 次新增计划。

因此，用户担心的“反复”有事实依据。不能仅增加一句“尽量两次规划”，也不能只压缩 system prompt。必须同时改变触发调用的条件、证据复用、协议形状及重复请求的收口方式。

| 典型候选 | 首轮→实际有效动作 | HTTP 请求 | 已接受尾部修订 | 完成被拒绝 | 最终结果 |
|---|---:|---:|---:|---:|---|
| Muxtly 印花税 | 5→11 | 17 | 5 | 1 | 保存，但比较目标覆盖不足 |
| Wiki 中国年号列表 | 5→12 | 20 | 9 | 2 | 保存，但本次内容复审不合格 |
| Muxtly 加拿大 | 5→16 | 41 | 14 | 5 | 无进展失败，不能称16步后成功 |

## 3. 首轮优先、二次补齐的执行设计

### 3.1 完整计划与逐步观察分离

首轮继续提交完整原目标、原子完成事项、全部可预见动作、证据路线和结束页面。既有 `evidence_route.observation_steps` 表示**动作后捕获证据的位置**，不再无条件等同“此处必须调用模型”。宿主每个实际动作前后仍按原契约观察、留原图和树、验证效果、更新事实；连续执行的是已授权计划，不是无观察的盲执行。

未来目标使用已有 `target.text/role/href/region` 语义表达，当前帧才引用 control。接纳计划时仅为当前可执行段绑定当前控件；跨页／弹层之后的未来目标不得被提前固化为首帧 control。到该步时在新观察中唯一绑定。未观察到的文字、答案、编号和控件状态不得被写成事实。

跳转后必做新观察。**新页面出现不自动等于新任务或新规划。** 若已规划的语义目标在正确页面唯一成立、动作前提满足，继续首次路线；确有未知内容选择、目标歧义或页面形态变化，再调用一次局部规划。旧 control 的 document_identity 保护保留，禁止简单删除来源约束来跨文档复用编号。

首轮还应把必要输入焦点、选择／清空、结果阅读、展开说明和结束定位纳入自然路线。Muxtly 5→8 的三次漏聚焦，不应再靠执行中反复修订补 click；工程也不得暗中合成这些动作来缩短账面步数。

### 3.2 调用触发规则

| 执行现场 | 宿主先做什么 | 是否请求模型 |
|---|---|---|
| 当前步有效，下一步在当前观察中唯一可执行 | 归档证据、推进真实游标、执行原尾部 | 否；新正文、截图编号变化、尾部全是滚动本身均不构成调用理由 |
| 当前唯一目标缺一次可确定探针／同文档重新绑定 | 复用既有定向观察与严格绑定；不添加业务动作 | 处理成功不调用；仍有歧义才调用 |
| 进入新页／HTML 弹层，原语义路线成立 | 捕获新界面、核对当前可操作层和下一步 | 不因导航事件单独重规划 |
| 新页／弹层使下一步不可执行，或必须从新内容中作选择 | 把全部未完成事项、有效证据、当前形态及剩余路线一次提供 | 调用局部 revise，覆盖可预见的全部剩余动作及结束定位 |
| 到达需要语义判断的关键证据边界 | 先去重候选证据，合并同一观察上的所有待判事项 | 一次批量登记 answers；路线仍适用时 continue，不重写尾部 |
| 计划结束／目标可能已完成／继续动作可能多余 | 汇总当前与必要历史证据、全部缺项、末帧要求 | 一次完成判断；允许提前结束，不为了执行完计划继续操作 |
| complete 缺项只是引用错误，证据原件已存在 | 修正可确定的来源映射，或按需提供原历史图 | 不导航重取；确需模型重选引用时只走一次既有纠正通道 |
| 相同业务事实、证据和缺项再次出现 | 检查是否尚有有效原尾部，或已有可执行修订 | 可继续则执行；否则按既有无进展路径收口，不重复发相同问题 |

新正文不立即调用的前提是：下一动作仍有未完成目标用途，证据已捕获且之后能够合法核验。若新增内容可能已经回答全部问题，必须在继续多余动作之前作批量完成判断，不能为了减少调用而推迟到路线末尾。

### 3.3 二次规划不是每次只补一个动作

第二次真正改路线时，输入只包含冻结原目标、已完成／未完成事项、第一次偏差、当前可用控件、必要证据和原尾部；输出应一次安排“必要定位／展开 → 阅读 → 返回或关闭 → 剩余原目标 → 结束展示”。不得顺便加入额外定义、无关对比或重新取已核验事实。

区分 `continue`（不改路线）、`revise`（替换未执行尾部）、`complete`（请求核验结束）。证据登记可随这些决定一起提交，不另开一个模型回合。修订尾部不再要求五步；首轮的至少五步仍须自然成立，实际不足五步照实短流程，不追加动作补数。

结束定位也按一段必要路线处理。当前 `_presentation_step_pending` 只放行一次动作，随后 goal_ready 又会回到模型检查点，可能把已批准的两次必要上滚拆成反复请求。最小修改是逐步验证已批准的结束段：每步检查事实未被修改、下一步仍满足既有定位许可；末帧到位立即进入完成确认，未到位且下一步仍必要时连续执行，只有路线失效才再次修订。不能为了执行整段而越过已经满足的结束页面。

**“尽量首轮、其次二次”是优先级，不是把所有任务硬截成两次 HTTP 请求。** 末次语义确认仍可能需要一次调用；多个尚未提供的关键截图受图数限制，也可能需要证据批次。规划轮次、证据调用、完成调用及纠正调用必须同时报告，不能通过把重规划改名成“检查”隐藏成本。第三次及之后的修订须有新的实际偏差或新证据，不能仅因同一缺项换措辞。

确定性验收场景：无偏差且证据能在一次末次请求内提供的七动作路线，恰为首轮计划一次＋完成判断一次，零 revise；出现一次未知弹层形态时，首轮一次＋集中 revise 一次＋完成判断一次，后续新增动作连续完成。这里统计的是应用层 intent，另报 HTTP invalid／correction，不能把纠正请求藏起来。实施夹具使用两次“聚焦、全选、输入”及一次提交共七步，保持实际必要动作口径。

### 3.4 在模型调用前阻止相同问题反复出现

复用现有 session 状态、事件和 `_stall_check`，增加调用前的稳定判定：冻结目标、下一未执行动作的语义、相关输入／结果状态、已核验事项、缺项种类、待提供证据内容及纠正反馈是否实际变化。观察 ID、截图时间、无关动态文案、cursor 被错误推进和模型 reason 改写均不算新依据。

同一动作产生的多个检查原因合并为一次请求；返回 continue 后优先执行原尾部，不能再次停在同一观察发问。没有变化且无可执行路线时直接进入既有 no-progress 收口，不通过调大停滞阈值掩盖问题。未知派发效果仍走原 UNKNOWN／恢复合同，不能把去重机制变成自动重派或自动认定成功。

## 4. Wiki 阅读路线：条目、详情、必要滚动、返回

### 4.1 用户确认的阅读行为

“查看条目详情”是阅读、理解和取证阶段，**不是一个新的 GUI 动作类型**。可采用“点击条目 → 观察详情 → 必要时滚动 → 返回／关闭”；若确实执行 click、scroll、back/close，就是三个真实动作。详情首屏已经足够时，不再强制滚动；返回必须服务于剩余原目标或明确的最终页面要求。

不设目录点击比例，不固定四次章节点击。近处正文自然滚动；远处明确章节使用目录；正文链接只在原目标确实需要条目详情时进入。重复访问相同详情、只为消除引用报错而往返，不能算新的业务需要。只有阅读了原目标需要的新信息、且返回还承担任务用途的访问，才区别于客户禁止的无效往返。

| 详情形态 | 观察及执行方式 | 规划边界 |
|---|---|---|
| 同标签页新文档 | 检查标题／URL／文档身份，按当前正文读取，按需 back | 原语义路线可绑定则继续；未知内容选择一次局部 revise |
| 当前页面 HTML 弹窗／侧栏 | 识别实际可见的 dialog 或浮层及关闭控件，优先读取弹层内容 | 不按浏览器原生 dialog 处理；必要修订一次补齐弹层内操作与关闭后尾部 |
| 弹层内部可滚动 | scroll 的 target 绑定当前真实容器，记录容器位移和内容变化 | 不能只检查 window.scrollY，不能让底页滚动冒充弹层阅读 |
| 当前页面内联展开 | 点击真实展开控件，读取新增正文；只在任务确有用途时收起 | 不因展开必然增加收起步骤 |
| 新标签页或原生 JS dialog | 先核对现有执行能力与来源绑定 | 不假定原生 dialog 就是 HTML 弹窗；未接通的能力明确拒绝，不在本轮扩建标签页管理器 |

工程已有 scroll.target 可选 schema，但 `react_step → session_core → browser → 效果核验` 未完整传递／核验容器目标。必须一起接通，不能只改 prompt 宣称支持弹窗内滚动。无 target 继续表示页面滚动；有 target 时必须唯一绑定可见可滚动容器，失败不得静默退回页面滚动。

### 4.2 首轮目标资格与冻结约束

首屏自主选题同时检查：具体问题是否值得多步完成、是否有可用文本／表格证据、页面形态是否提供必要交互、预计结束页是否支持最终结论。明确一两次移动即可完成的题目，不用目录点击和滚动拼成五步；在冻结前选择更合适的问题，无法自然成立则 unsuitable。固定目标不得自行换题。

原目标中的明确字段拆成现有 requirements 的原子事项。例如年号的名称、起讫、使用者、指定例子及比较依据分别可核验；“点击某条目”属于路径，不能自动变成“必须额外回答这个词的百科定义”。准入同时检查目标→事项的无遗漏和事项→目标的有来源，复用当前目标覆盖检查；无法确定的语义覆盖不得仅因 schema 合法就记成 VERIFIED。

纯图片图表暂不新增 OCR／视觉验真工具。自主选题应避开只能从图内取数、当前宿主无法验证的目标；固定目标遇到这种情况返回明确能力缺项并留证，不反复滚动或伪造 DOM 引用。以后如增加视觉证据类型，需要独立的 PNG 来源、坐标、核验与交付设计，不能把本轮此项预防措施宣传为图表识别已修复。

## 5. 执行、证据与重复取证的最小修复

### 5.1 游标只依据真实派发和效果推进

修复 `_execute_round` 将“新增 business attempt”当作“已执行”的错误，统一传递真实 `actual_dispatches_delta` 与 `effective_steps_delta`：

- NOT_DISPATCHED：保留当前步骤；先修正当前观察／绑定，禁止 continue 越过未执行动作。
- 已派发且 VERIFIED：推进一次，归档该步后的证据。
- 已派发但无效果／效果未核验：保留真实状态，由既有策略判断修订、跳过或结束；不冒充有效步，也不默认重派。
- EFFECT_UNKNOWN：保留未知事实与原恢复约束，不能自动重复有副作用的动作。

修改在线执行、checkpoint 参数和恢复／封存核对的同一口径，不仅替换一个布尔表达式。保留原始失败与 UNKNOWN，不修写历史游标或旧账。

### 5.2 统一可见文本块，保留链接字和表格关系

复用 `snapshot.js` 的可见文本块采集，扩展到段落、列表项、表格行；`screenshot_observation.region_registry`、模型投影、完成核验和派生标注消费同一份规范文本及来源。最小方案沿用 `answers.evidence` 的 observation／region／quote／control 形状，不新造第二套引用接口。

| 内容 | 最小处理 | 必须保留的约束 |
|---|---|---|
| 段落中的内联链接 | 完整保留“夏景宗”“夏惠宗”等实际渲染文字 | 排除隐藏、遮挡和视口外部分，不从整页 innerText 拼答案 |
| 列表项及短名称链接 | 为完整可见 li／短词提供有来源的 region | 短词可依唯一 region 引用；不全局放宽无锚点引用的最低长度 |
| 表格行 | 按真实可见单元格及顺序形成行块，登记表头、行与成员节点关系 | 只允许同一真实行的规范空白组合；跨行拼接、缺表头而猜列义、不可见单元格均不通过 |
| 多字段目标 | 用原子 requirements 和多个 evidence 引用覆盖全部必需字段 | 一个真实短片段不代表整个清单／使用者／比较问题完成 |

宿主归档原字符、节点身份、bbox 和成员关系；模型只接收完成当前缺项所需的短块。规范化只统一确定的空白和阅读顺序，不补词、不改数值、不合成页面没有的句子。

逐字来源检查与语义覆盖检查分开：前者证明“引用来自哪里”，后者检查是否回答原问题中的全部对象、属性、范围和比较两端。复用现有目标覆盖／缺项反馈，将缺失的使用者、范围或比较一方具体指出；不新增每步第二个 LLM 裁判。通用自然语言语义不能靠字符串命中保证正确，未能验证的比较结论继续保留待审／缺项，不能自动合格。

### 5.3 历史证据复用先于回到旧页面

当前 195 笔请求都只有一张图；Wiki 45 次历史补图因 IMAGE_LIMIT 被丢弃。下一次实施明确接通策略2已存在的“当前图＋按需一张历史图”能力：配置构造／加载、chooser、prompt 中实际图片清单及 observation 白名单一致。现有正式配置本轮不改；未来明确配置仍只有一图时必须如实暴露限制，不能静默声称已提供历史图。

区分宿主已捕获、历史请求成功提供过、本次实际携带、已核验、已失效五种事实。已核验答案无需重新看图或重写；过去没提供给模型的正文不能仅因宿主有文件就被声称已看过。历史图与 inspect crop 竞争第二个图槽时，按本次缺项选择一个，不能把被挤掉的图加入已提供白名单。

相同缺项先检查原件、已有可信引用及相关失效事件。引用形状错误修引用，历史图缺失补原图，未登记事实批量登记；只有确实缺少原始观察、页面事实已变化或需要末帧定位，才新增网页动作。导航返回不应使同一条静态阅读事实自动失效；相关编辑／重新提交仍按原因果范围使计算证据失效。

图数上限意味着不能无条件承诺“一次最终请求读完任意多页”。尚未提供且必要的历史图超过单次容量时，在离开关键阅读段前批量登记可核验事项，并记为证据调用；不丢证据，也不把每个滚动帧自动都设为必须请求。请求批次按必要事实选择，所有原截图照常保留。

### 5.4 阅读进展与不能同时满足的目标

把“与未完成问题相关、首次覆盖的正文／表格范围”纳入进展，使用稳定内容及来源去重。已读区域重现、新 observation ID、无关公告和任意滚动次数均不重置停滞。解决 zh-04 正在接近金融章节却被当作无进展的问题，同时防止重复上下滚动无限续命。

Muxtly 加拿大的 ON→QC 比较超出当前同表单“最终单场景”证据合同：切换输入会使前场景证明失效。最小方案在自主目标冻结前拒绝同一控件同时要求互斥最终值，优先单场景任务；固定比较目标明确报告能力限制，不能反复切回重算。多场景快照与比较执行器另列后续需求，不在本轮为一条失败扩建新体系。

## 6. Prompt、tool、schema 必须同步修改

### 6.1 Prompt 分为稳定原则和当前阶段事实

稳定规则只保留：冻结目标、真实必要动作、当前控件身份、证据真实性、完整覆盖、原件留存、结束条件。首轮只给完整路线与资格规则；后续只给继续／修订／结束的字段及当前缺项。纯阅读请求不携带整段算术验算规则，计算任务需要时才带相应条款。

建议纳入的核心措辞：

> 首次提交覆盖原目标的完整必要动作和结束页面。已接受的路线由宿主逐步观察并执行，不因出现新截图就重规划。仅在当前路线确实不可执行、需要新内容选择或尚有未覆盖的原目标时修订。首次修订一次补齐当前可预见的全部尾部，不逐步试探追加。已核验事实直接复用；查看详情是观察，不单独计动作；不为步数补滚动、返回或取证。

该段替换旧的重复／冲突条款，不叠加成长提示。`reason/rationale/purpose` 分工保留；未来语义路线写前提，不冒充已观察结果。

### 6.2 保持两个既有工具，收紧条件字段

| 接口 | 最小修改 | 同步修改位置 |
|---|---|---|
| `submit_plan` | 保留 goal／requirements／steps／final_presentation_step；首轮自然至少五步，未来目标用语义，当前控件编号只绑定当前段 | 首轮 prompt、schema、normalize、准入、目标绑定及封存核对 |
| `plan_decision` | continue／complete 不携带 remaining_plan；revise 一次给完整未执行尾部；answers 为增量 | 分支 prompt、工具说明、同源 schema、归一化及 `_checkpoint` |
| 请求内的旧尾部 | 将模型输入字段命名为 `pending_steps`，避免复制进输出的 `remaining_plan` | `_branch_prompt`、规则、请求日志解析与相关夹具；不改历史日志 |
| 动作定义 | 共同字段只定义一次，按 action 条件要求 target／value／direction 等；使用当前已支持的 schema 构造 | wire schema 与宿主验证共享生成器，不另维护一套宽松校验 |
| `scroll.target` | 沿用已有可选字段；有目标时必须贯通容器执行和效果证明 | schema说明、normalizer、react_step、compile_step、session_core、browser、snapshot、效果核验与标注 |
| 当前能力清单 | choices、工具 schema 与实际配置一致；仅一图时不提供必需两图的 inspect，未接通的容器／对话框能力不宣传为可用 | 配置加载、工具构造、prompt 能力事实及执行许可 |
| `answers.evidence` | 沿用既有引用字段，region 可绑定完整 p/li/tr 文本块，按内容范围核验 | snapshot、region、提供白名单、verify_completion、封存派生 |
| 字段修复 | 一次处理全部独立可修复错误；只修当前 action／decision 生效的字段，禁止生成 null control | `model_gateway.field_repair_plan`、错误定位及策略2调用方 |

continue 的最小示例为 `{"decision":"continue","reason":"原尾部仍可执行"}`；complete 可以只给决定、理由和本次新增 answers，已核验答案由工程保留；revise 必须显式提交非空 remaining_plan。示例不复制旧尾部，不引导每次重写全部 requirements。

31 次 continue＋非空 remaining_plan 不能通过一律丢弃尾部“修好”：只有与当前尾部的动作、目标、参数及任务语义均确定相同，才允许可追溯的去重正规化；只改措辞但无法证明等价也不自动丢弃。含真实新增／修改时按具体字段反馈，要求 revise。正规化与条件 schema 的调用顺序必须一致，不能让无损处理永远排在 gateway 拒绝之后。

不新设多轮协议重试。必要的格式修复复用现有一次有界机制；修复仍失败，保留原请求与用量并有界结束。同一缺项不在 gateway、session、complete 三层各重新获得一轮无成本“机会”。

## 7. 标注首次生成和最终页面

修复 [postprocess.py](../projects/code/webcollect/postprocess.py) 的动作效果选择顺序：实际导航／文档变化先于通用输入值差异；输入效果叙述仅用于真实输入相关动作、同文档同输入身份的可核验变化。新页碰巧复用 e81、值从有到空，不能把链接点击写成“输入已清空”。点击导致的表单重置等特殊情况也须有真实作用关系，不能仅凭新旧 value 猜测。

首次生成链统一使用真实动作、对应前后观察、完整可见文本块和已核验原目标：

- `user_goal` 写本步业务用途；导航、展开、输入、滚动分别叙述实际效果，能够解释相邻 PNG。
- complete.user_goal 写明确认的实际页面和结果，例如“确认 WA 工资税计算结果页中的税额及计算说明”；不能固定为“确认结果并结束本次任务”。
- `final_result` 覆盖所有明确要求的字段、对象和比较结论；图上链接人名、使用者、单位、结果标签不得漏写或改义，不能出现“如 的……”残句。内部 r2／r3 等编号不泄漏到客户文本。
- `completion_judgement` 说明原目标满足的证据及末帧依据；完整性哈希、模型自称完成和已保存收据均不能替代内容判断。

**末帧约束按客户原文保留。** 当前“全部历史事实＋末帧任一相关正文”不能自动判为客户合格。原目标的最终结果和完成判断须能对末帧核验；历史图支持过程与来源，不能用来把停在无关定义页的完成画面解释成达标。首轮就选择能满足结束展示要求的题目和结束页，二次规划把必要回呈一起安排。

若跨页比较的最终结论无法由真实末帧支持，不伪造汇总页面、不拼贴截图、不用改写 final_result 隐藏缺项。当前客户口径下不计内容合格；以后只有明确的需求变更才可放宽为跨帧最终验收。这一限制不禁止有实际用途的详情访问，但详情访问本身不能豁免最终页面要求。

本轮仅修下一次生成链的设计。历史 annotation、PNG、收据和审核状态不自动订正；若另行授权历史修订，应另存修订产物与差异，原件保持不变。

## 8. token 与耗时：先减少无用调用，再减小每次请求

### 8.1 基线与可解释指标

本轮输入 5,466,889、输出 293,853 token；首轮及纠正 27 请求／507,728 输入，后续及纠正 168 请求／4,959,161 输入（90.7%）。失败候选消耗 70.2% 的输入。invalid 与 correction 并集 87 请求、2,348,525 输入（43.0%）；这些是相关开销，不是保证可全部节省。

批次墙钟 38分51秒，worker 均值 9分02秒、中位 5分25秒；5 条保存的 worker 均值 7分45秒，Wiki 保存一条为 19分07秒。模型累计 6,557.96 秒，占 worker 累计耗时 75.7%。图片 token 为 null，收费金额未提供；不编造图片精确占比或金额。缓存 token 已含在输入中，reasoning token 已含在输出中。

5→11 的印花税包含补找折叠说明和回呈；5→12 的 Wiki 包含反复取证；5→16 的加拿大最终失败。优化要减少漏规划与返工，不能把计划步数当实际步数上限，或把所有新增动作都判作多余。

### 8.2 模型上下文投影

用户 JSON 累计字符主要分布：controls 25.0%、historical_evidence 15.6%、page_directory 13.8%、action_facts 11.3%、visual_evidence 9.3%，合计 75.0%。这是字符归因，不是逐字段 token 计费。

| 输入部分 | 最小压缩方式 | 不能丢的内容 |
|---|---|---|
| page_directory | 仅投影本会话确实访问、当前返回／结束定位可用的页面；其余完整目录留宿主 | open_url 仅能引用已观察页面的约束，当前页面身份和来源 |
| controls／control_mapping | 当前可执行控件只描述一次；去掉无信息的重复状态，已有统一角标映射复用 | 控件身份、真实标签、当前值／焦点、必要 options、当前动作能力 |
| historical_evidence | 已核验事项给紧凑结论与来源引用；未完成事项只给相关候选片段及可补图入口 | 有效性、图是否真的提供过、引用来源、必要失效因果 |
| action_facts／last_effective／known_business_state | 当前输入状态、最近一次尝试、最近有效动作和相关因果各保留一个权威投影 | NOT_DISPATCHED 与有效动作区别，提交／编辑先后，未知状态 |
| completion／checkpoint feedback | 相同缺项合并一次；给具体缺字段及可用定位，不重复整段旧回包 | 全部独立缺项及一次修复所需信息 |
| system／rules／tools | 阶段化规则、阅读／计算按需规则；共同动作字段去重 | 业务语义、严格字段约束、原目标和完成条件 |

宿主事件、原图、树、费用和完整计划仍完整归档。压缩的是模型可见视图，不截断原证据，也不另调用模型压缩上下文。初期保持现有 high/high，避免同时换模型或降推理造成效果归因不清。

离线验收使用原 151 个应用层 intent 对应事实重建模型投影，至少报告首轮／分支分组的中位和 P95 字符量、schema 大小、图片数、关键事实保留检查。**设计目标：分支用户事实 JSON 中位与 P95 均下降至少 30%，常规工具 schema 序列化字符下降至少 25%。** 这是设计阶段设定的目标；本次离线结果见第13节，不以裁掉必要证据满足数字。字符量或可用 tokenizer 估计必须标注代理口径，不能写成真实 provider 节省。

调用触发修改会改变后续轨迹，不能对旧日志静态删掉一些请求就宣称真实成功率／耗时提升。确定性场景先验收调用次数；真实 token、耗时和成功率只能在另行授权的后续运行中比较。

## 11. 验收标准

下表是行为验收项，不等同新增测试条数。落入现有 `test_strategy2_visual_core.py`、`test_strategy2_completion_core.py`、`test_strategy2_save_core.py` 和相关核心契约用例；原件投影采用一次性只读核对，没有新增常驻核心用例。本次覆盖及限制见第13节，不把设计标准自动写成全部真实场景已通过。

| 编号 | 场景 | 必须满足 |
|---|---|---|
| A1 | 首次计划直达 | 七个必要动作的确定性路线，逐步留证但零中间无用模型询问；首轮一次＋完成一次，revise=0，HTTP 纠正=0 |
| A2 | 一次真实偏差 | 未知 HTML 弹层出现后一次 revise 覆盖必要滚动、关闭及剩余目标；必要结束定位段也不逐步请求补动作，到位即停；总计首轮＋修订＋完成三次 intent |
| A3 | 重复检查点／完成失败 | 相同业务事实、缺项和证据不重复发同一问题；同一动作多原因合并；新证据出现可继续；不同 request 的费用与 UNKNOWN 不丢失 |
| A4 | 零派发／不明效果 | NOT_DISPATCHED 不推进 cursor；真实有效动作只推进一次；未知效果不自动重派，不因 continue 跳过未执行步 |
| A5 | Wiki 详情路线 | 新页、HTML 弹层、内联展开分别按真实形态执行；阅读不计独立动作；无需求不强制滚动／返回；不把关闭弹窗换成 browser back |

| A7 | 正文／表格／短链接 | 保留夏景宗／夏惠宗／汉武帝刘彻；表格行与表头可核验；唯一短名称可引用；跨行拼接、隐藏字、未提供观察、错误列义仍拒绝 |
| A8 | 全目标与能力边界 | 缺使用者／范围／比较一端不得完成；辅助词条定义不增加冻结义务；自然短流程不补动作；仅图像证据和互斥最终输入不进入反复取证 |
| A9 | 历史复用与证据批次 | max_images=2 时确实发送当前＋需要的历史图；已核验事项不因移出视口重取；图未发送不能列为已提供；单图限制和 crop 竞争如实反馈 |
| A10 | 协议修复 | continue 不重写尾部；完全等价尾部可留痕去重，真实改动必须 revise；一次修复覆盖全部生效字段；不生成 null control 或进入第二层无限纠正 |
| A11 | 首次标注及末帧 | 链接导航不写成输入清空；final_result 字段完整、措辞与标签一致；complete.user_goal 明确最终页面；任意相关正文／定义页不能代替原目标最终结果 |
| A12 | 正常保存及导出 | 隔离环境走 `_react_collection → postprocess → RuntimeStore → verified_saved/candidate_results → delivery`；样本身份和哈希一致，PNG／树／路径说明齐全，报告图数正确；加工失败仍保留真实失败状态 |
| A13 | 开销与证据保留 | 分支 facts 中位／P95 字符目标均下降≥30%，常规 schema 字符下降≥25%；关键来源、未知、因果及控件约束不丢；原 raw／历史包／费用未改 |

调用验收的 A1/A2 使用预定真实形状观察与响应的隔离夹具，并约束可用图片槽和证据实际提供情况。不能通过 host 伪造语义答案、替模型声明看过图、删真实动作或把多次请求并记一笔达到次数指标。无偏差普通链及一次偏差链之外的复杂任务不套用固定两／三次上限，但每个额外调用必须可归因到新事实或必要证据。

离线集成保留成功计算、成功阅读和重要失败分支，所有输出写隔离目录，不污染正式候选／样本／审核账。离线通过只证明实现合同；没有真实模型结果时，Wiki 成功率改善、耗时下降及真实 token 节省均为 NOT_RUN。

若之后另行授权真实评估，应同时报告：候选准入／unsuitable、原目标成功、实际≥5、正式保存、内容复审、正式 QC 各自分母；首轮路线完成比例、至多一次有效尾部修订完成比例、第三次以上修订的新增依据；证据调用／完成调用／纠正调用；重复取证动作数；按尝试及合格样本的输入输出 token、用时中位与 P95。小样本不承诺跨页面稳定性，保存率不能替代内容合格率。

## 12. 本轮交付状态

上述联动改动已经按用户“集中实施、完成后验证、不启动真实采集”的授权完成。三个 `gpt-6.1-sol / low` 子Agent分别负责执行控制、协议、证据标注，主Agent完成跨模块接线与保存链集成。原客户包、生产候选、费用、UNKNOWN及审核记录不改写；未来Ark示例max_images改为2，既有冻结配置保持原值。数据库不迁移，历史失败不重新派发。

受影响19个不同核心用例最新全部通过；全工程维护总量仍50，没有全量重跑。含实际失败与局部复验，共35次执行（28通过、7失败），pytest累计5.549秒。一次离线集成工作集两条保存链最新32/32检查通过，期间5次失败场景及其后续局部修复如实保留；不称首次集成全过。真实本地HTML专项验证了当前snapshot和容器位移，未请求外网。

真实模型、真实网页采集和生产新增均为0；正式独立AI QC／人工NOT_RUN、发布false、客户验收UNKNOWN。历史客户包114文件SHA256只读核对全一致。完整明细见[实施报告](../verify_results/strategy2-wiki-plan-implementation-20261112-r01/report.md)与[计量](../verify_results/strategy2-wiki-plan-implementation-20261112-r01/accounting.json)。

集成查实并修复了三个额外接线缺口：输入历史帧误占语义图片批次、内部动作schema漏接scroll.control_id、容器目标误写入客户非控件标注。具体工具拒绝同步反馈给二次规划，避免模型在不知道失败原因时猜修订。

第9节的“PNG统计为0”查明在旧轮一次性 `verify_final.py` 按错误目录层级计数，不在 `client_reports` 产品导出实现；本次新集成按各sample的images目录计数并核对引用，没有为此改写旧报告、客户收据或产品模块。

“尽量首轮、其次二次”现已由执行与调用机制共同支持，仍不是所有任务最多两次HTTP请求的承诺。纯图像取数、同控件多场景互斥最终状态、无法由真实末帧支持的跨页结论，仍明确说明能力限制。后续真实评估须另有授权，不能沿用历史剩余额度。
