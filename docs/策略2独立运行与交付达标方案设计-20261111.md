## 1. 目标与范围

目标是让策略2从当前入口独立完成“观察 → 规划 → 动作执行 → 检查点 → 完成核验 → 留证 → 保存或拒绝收口”的完整功能，并使新产出的标注符合已确认的客户要求。是否达到目标，以相关测试覆盖的结果报告；没有真实运行证据，不宣称真实采集成功率、QC通过或客户验收通过。

正式保存条件保持：原目标完成、有对应可见证据、实际有效业务动作至少5步、无未决外部效果。首轮自然完整规划优先5–8步，必要时可以更长；剩余计划不补满五步，不新增累计8/10步上限，不为长度补动作。wait和complete不计有效业务动作。

范围内：

1. 解除策略2对策略1会话、观察、执行器和专属校验器的运行依赖。
2. 补齐策略2的可执行观察、目标绑定、动作执行及协议反馈。
3. 修正完成证据、进度保留、无进展判断与中断收尾。
4. 修复策略2新标注的源头生成及其保存、导出、QC交接必经断点。
5. 完成上述功能所需的当前源码、配置和依赖接线；本方案沿用现有数据库和字段，计划数据库结构变更为0，不新增实现版本或兼容分支。

范围外：策略1业务优化、生产者挖掘、历史交付订正、旧claim批量重置、UNKNOWN重发、历史费用改写、真实采集、独立AI审核、人工审核、发布及吞吐扩容。

## 3. 架构边界

### 3.1 责任划分

| 能力 | 归属 | 边界 |
|---|---|---|
| 观察 | 策略2专属 | 决定何时观察，组织截图、控件、焦点、选项、正文与模型上下文 |
| 动作执行 | 策略2专属 | 解析计划、绑定目标、编译参数、派发动作、验证效果、形成反馈 |
| 规划与完成 | 策略2专属 | 首轮规划、剩余计划修订、requirements、完成证据、无进展与结束原因 |
| 证据记录 | 公共层 | 记录原始截图、观察、请求、实际动作、失败、引用和哈希，不解释计划语义 |
| 收尾落账 | 公共层 | 按真实执行与存储结果封存、提交状态、生成保存或拒绝收据，不替策略判断业务成功 |
| 底层工具 | 可复用 | 浏览器API、文件与哈希、已有数据库事务等，不夹带策略1观察/执行规则 |

公共后加工可以组织客户文件和检查既定交付条件，但动作有效性、目标完成与封存回算使用策略2自己的验证逻辑。不能只相信一个success字段，也不能重新套用策略1的业务谓词。

- screenshot_session.py：独立会话，管理计划游标、检查点、进度、取消与结束申请；不再继承ReactSession。
- screenshot_plan.py：策略2的prompt、工具schema、等价整理、完成核验及对应证据回算。
- screenshot_observation.py：拟新增，承接策略2自己的观察与模型投影。
- screenshot_execution.py：拟新增，承接策略2自己的目标绑定、动作编译、派发与效果核验。
- 现有evidence/storage/runtime/collection_strategy及收尾接线：按最小范围复用记录与提交能力；需要抽出的方法只保留事实与持久化职责，不整体搬迁ReactSession。

上述两个新文件用于划清策略2内部职责，不新增策略版本或可选实现。已有同等职责的中立工具可复用，不重复建设浏览器驱动或数据库框架。

## 4. 集中实施内容

以下工作包共同组成第一阶段代码实施。工作包之间可以按依赖顺序实现，但不逐包交替更新或运行测试；全部实施变更完成后统一进入测试阶段。

### W1：策略2独立接线

1. 去掉ScreenshotPlanSession对ReactSession的继承，建立策略2所需的最小会话状态。
2. 策略2自己加载任务构造/校验适配、chooser、观察器、执行器、停止处理和封存验证；candidate_consumer与task_generation在现有策略分发点接入。
3. 封存回算使用与策略2采集一致的观察投影和验证逻辑；修postprocess.session_record不能继续无条件按策略1投影重建策略2观察。保持原始文件与引用完整，不把改变投影等同于可以重写旧raw。
4. 修公共入口及后加工中的间接依赖；策略1分支只允许必要的机械导入调整，行为不变。
5. 新路径直接使用当前实现，不保留新旧策略2双分支或回退到策略1的执行路径。
6. 保持候选、claim、attempt、样本及审核的既有交接契约。

完成条件：策略2从正常入口到保存/拒绝收口均有完整实现和接线，依赖链不要求加载策略1会话与规划器。

### W2：策略2观察与可绑定目标

1. 当前观察同时提供清晰截图、observation编号和紧凑控件清单。控件信息包含可见名称/标签、角色、当前值、焦点、可用状态及支持的动作；select补充真实观察到的选项及其值。
2. 控件筛选优先可交互业务区域和当前目标附近，避免简单截取前30项被导航占满；未下发的控件不冒充已向模型提供。
3. 正文和结果区域单独投影，优先正文、当前结果和相关标题；不再只取树中前8个文本节点充当所有可引用区域。
4. 控件编号绑定来源观察与页面身份。计划形成时的绑定信息由工程记录；执行前确认仍指向同一目标。
5. 导航、滚动、重渲染后由策略2刷新观察。编号过期时按原语义和身份重新唯一绑定；有歧义则反馈当前候选，不静默选择。
6. 未来页面允许语义目标，不能伪造未来控件编号。控件编号只解决身份，不能代替焦点、选项和可操作性检查。
7. 原始PNG与树保持真实；推理用投影或图片衍生物保留来源，不覆盖原件。

完成条件：模型拿到的信息足以表达当前可执行目标及可引用正文，执行器能够核对其来源和状态。

### W3：动作执行与协议反馈

1. 直接按策略2步骤编译执行，取消“先转成策略1原生step，再交给策略1_tool_act”的路径。
2. click、type、select、hotkey、scroll等分别使用实际前置事实。聚焦、选项选择、输入与结果读取要有对应的真实动作和效果记录。
3. type遇到焦点不符时明确反馈，并修订未执行尾部；不得隐式改错目标。需要新增辅助动作时必须真实执行并单独记录，不把一次fill事后拆成多步，不为长度制造动作。
4. select用真实选项文本/值唯一绑定。失败反馈区分目标不存在、目标歧义、焦点缺失、选项不可用、未派发、已派发无效果和结果未知。
5. 实际动作参数、dispatch结果、前后观察分别记录。业务尝试数、实际派发数、有效动作数各自统计。
6. submit_plan与plan_decision共用策略2的等价整理规则，覆盖已出现的wait冗余target、scroll参数及结构别名；无法确定方向、对象或业务含义时不猜。
7. schema错误回传动作位置、字段路径、预期类型及当前允许值，减少oneOf重复报错。已有correction中能看到字段路径，补充诊断应改善可读性与落账，不能描述成“模型完全看不到字段路径”。
8. 修复只针对出错字段或未执行尾部；保留已经执行的事实、冻结目标及有效证据。新增rationale时同步更新_KEEP_STEP_KEYS等整理白名单，避免新字段在schema前被现有整理器删除。
9. 保留去版本后的gateway当前调用签名，不重新引入plan_normalizer_version等已取消参数。

完成条件：可执行步骤能转为真实浏览器调用；不可执行步骤提供可操作的反馈，且不混淆未派发与失败效果。

### W4：完成证据、进度与无进展

1. 保留verify_completion现有逐项覆盖检查，以requirement_id关联答案与证据，不重新设计一套平行完成协议。
2. 保留已经核验的部分证据，在检查点反馈已证实事项和缺项；后续输入、页面变化使证据不再适用时说明失效原因。
3. complete可以在同一轮补齐新证据并结束。不得要求必须此前已全部VERIFIED，否则只能revise/give_up。
4. observation必须来自实际向模型提供过的观察；region必须由该观察注册，quote必须出现在该观察的可见内容中。
5. quote存在只证明引用位置真实，还要核对它是否支持observed_result及原requirement。修复当前quote命中即可放宽结果匹配的条件，以及因果缺失分支未定义quote的错误。
6. 计算任务绑定本次输入、实际提交和对应结果，排除输入回显与旧结果。阅读任务可由多次已提供的观察证明各事项，仍需一致的终态说明。
7. 完成补证先核验，再判断是否无进展，不能在有效补证被接受前提前关闭。
8. 无进展依据真实状态、失败类别、有效动作和新增有效证据判断；换reason、改措辞、重排计划不能算进展。新observation编号或一次无效果dispatch也不能单独清零。
9. 复用现有连续无进展阈值，不新增整会话调用数、时长或累计有效步配额；明确为何继续、为何停止，按现有结束类型如实留证。

完成条件：有效证据能完成闭环，无关引用不能过关；同事实反复修订能结束，实质补证不会被误杀。

### W5：取消、租约和最终状态

1. 核对模型作业租约与执行attempt租约的实际来源。保留独立心跳，不因600秒模型等待和300秒配置值直接修改租约。
2. 检查策略2观察、浏览器调用和派生中的阻塞点，使停止信号能传到执行链；停止后不继续派发新业务动作。
3. 公共收尾按已知事实封存并调用既有事务接口；中断请求的结果不确定时保留UNKNOWN/待对账，不强行改为失败或重发。
4. 正常失败、拒绝保存、派生失败、保存失败和成功保存均形成最终结果收据，使用现有finalize_strategy_result。
5. 目标状态、交付资格、保存状态分别赋值。目标完成且具备资格但落盘失败，应保留eligible/save_failed；不能因为没保存一律改成ineligible。
6. 真正无法确认的状态保留unresolved及原因，不把会话期占位冒充最终结论，也不改写已封存会话原件。
7. 旧卡死claim、旧reserved/UNKNOWN与历史费用不由本改造批量清理；新增执行沿用现有正式结算路径，未决项不得绕过原账。

完成条件：每条策略2退出路径都有一致的事实、状态与收据；不把停止成功等同于业务成功。

### 10.2 日志体系（本轮追加需求）

- 新增 `webcollect/runlog.py` `SessionLog`：stderr 每事件一行实时展示（`ts level sessionId strategy workerId siteId candidateId claimId attemptId sampleId event ...`），stdout 机器 JSON 不受影响；文件按 `<output>/logs/<workerId>/` 落盘：`runtime.jsonl`（运行事件）、`model-calls.jsonl`（每物理请求一条：request_started/request_finished/cache_hit/timeout_retry_scheduled 及 usage，usage 缺失记 null 不补零）、`model-debug.jsonl`（仅 DEBUG：模型输入输出，经 `sanitize_debug` 递归脱敏——authorization/cookie/api_key/token/password/credential/reasoning_content 置 `<omitted>`，`data:image*` 置 `<data-url-omitted:N>`，图片以 path/sha256/bytes/width/height 引用不内联 base64）。
- 统一 sessionId：claim 路径直接用 `claim_id`（`for_claim`），无 claim 直跑一次 `uuid4`（`for_direct_run`），仅展示关联，不进入业务身份哈希、模型 prompt，也不替换 GLM 凭据会话、claim/attempt/task_key/去重或 UNKNOWN 身份；每物理请求的 requestId 来自账本 `reserve_request`。
- 写日志失败按目标文件各警告一次（stderr），不重发请求、不改变业务结果；`success` 日志只在正式保存提交后。
- CLI：`python -m webcollect.candidate_consumer run` 与 `python -m webcollect collect` 均新增 `--log-level {INFO,DEBUG}`（默认 INFO）与 `--log-dir`（默认 `<output>/logs/<workerId>/`）。
