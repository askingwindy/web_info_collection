## 结论与消费影响

**页面用途 UNKNOWN 不会自动阻断当前消费者，但会影响供给筛选和诊断效率。** 本轮证明了机械入池和核类输入压缩，尚未证明业务场景选页质量或消费转化提高。 它表示生产者还没有足够证据判定页面角色，不表示网页不可用，也不是模型请求／访问账上的 UNKNOWN。

当前 `CandidatePool.claim_next()` 按状态、协议、候选与版本、来源绑定、类别和领取条件筛选，没有按 `page_type=UNKNOWN` 拒绝。`candidate_consumer.work_in()` 对 V2 候选先进入真实 `entry_session()`，取得首帧，检查公开状态，再构建能力记录并调用规划；`_entry_hints()` 读取的是应用主类，不把页面用途 UNKNOWN 当成主类 UNKNOWN。规划器仍须从实际观察形成工作目标。当前正式路径没有直接依赖该用途标签来制定目标，单纯补标签未必减少规划请求或 token；需要验证新证据摘要是否通过既有候选上下文实际传到规划器，并由首帧核验，不能直接改写 requested_goal。用途明确也不能绕过浏览器、账号、原请求、重复或可见终态门禁。

因此：

- 有用页面可能只是标签缺失，例如目录、文档或具体工具仍可消费。
- 同一个 UNKNOWN 桶也混有语言切换、公告、帮助、登录说明等页面，消费者要付出导航、首帧甄别、选目标和失败返回的成本。
- 用途分布、模板分布和同类型成功率难以精确统计，按“主机＋用途”的反馈会把不同业务混在一起；相同 UNKNOWN 标签也不能证明属于同一种模板或业务。
- 本批没有消费对照，不能给出 UNKNOWN 导致成功率下降多少或额外花多少 token 的因果结论。冻结消费快照中 21 份保存有 14 份原用途 UNKNOWN，只能证明 UNKNOWN 页面中存在可保存的实例；21 是按已保存筛出的分母，不能当作候选成功率，更不等于独立 QC 通过。

## 原因：站点挖掘 Agent 的 goal、prompt、tool

### Goal

原总体目标同时强调有据、可直达和公开业务，但真实批次以净增 URI 完成，规则扩页占绝大多数；后台查询规划的目标仍是“主营符合类目、能浏览多个公开栏目”，与“三种匿名后台业务”并不等价。

下一步将数量与场景成功分账：**先为指定场景寻找可证明的公开入口，再在已证场景内扩页。** 后台任务的成功输出是同一新应用三条不同业务入口及各自证据，不以三个 URL、三个产品介绍或三个不同记录 ID 代替。用途缺证允许 UNKNOWN，明确“入口库存达到目标”不能充当“场景验收通过”。

### Prompt

保留 Hi8 工具、微信登录／公告、京东同模板书摘及本批华为云页脚的对照，要求模型逐项回答：证据描述的是发布站还是被介绍产品？属于主内容还是导航／宣传？用户在目标入口可执行什么？与已选入口的操作有何不同？缺哪份证据？

输出允许“继续检查某个原件编号”“用途未知”“业务不同尚未证明”或零条；不能仅因目标类目是后台就推断存在公开后台。检索优先具体公开示例、实例画廊、匿名表格／表单／仪表盘，遇教程、产品介绍或登录墙时换检索方向。已有数字引用协议继续使用，不恢复重复发送首页正文和候选引文。

### Tool：模型可见协议

把“选链接”和“证明用途／场景”分开：

1. 给来源链接的编号、引用号和证据强度，明确这是来源线索，不是目标页观察。
2. 有界请求目标页原件编号；返回单份编号的主内容、区域、控件／访问证据，以及检查失败或缺失原因。模型不能任意提交 URL。
3. 提交用途、证据号、公开访问判断、操作描述、与已选页面的差异依据；不够就 UNKNOWN。模板相同与页面身份不同分别表达。

### Tool：宿主实现与接受条件

宿主继续解析第一方链接、限定来源应用、复核真实落地和 GET、从原账复用原请求；新增主内容区域定位和“证据—业务控件”归属核验。后台遇 JS 才渲染的界面，只有在另行授权的小规模复验中使用有界匿名只读浏览器观察，记录匿名上下文、落地、原图／树及控件位置；静态 HTML 缺证时保持 UNKNOWN，不为了通过而猜控件或安装插件。

主页只支持主类判断；目录只支持继续找入口；最终业务证明必须属于对应目标页。还须记录页面用途 UNKNOWN 与公开业务场景未决各自原因。共享工具的宿主验证不能以模型一句“可用”替代，模型也不替消费者预填工作目标或 QC 结论。

## 执行顺序与建议验收线

### 第一阶段：原件离线回放，先修真实性

不启动生产，先冻结 100 条本批候选：50 条规则 UNKNOWN、25 条规则非 UNKNOWN、25 条模型选页（其中模型唯一 UNKNOWN 必含），按应用和原用途分层，至少覆盖 10 个应用，名单先落盘不因结果差替换。另冻结至少 12 个关键对照：三条京东书摘、三个 Hi8 工具、三条微信入口、两条本批华为云页面及一条 `Shqip` 语言切换。对照与总体样本如有重叠，按候选 ID／版本去重并分别报告分母。

每条建立可回读的原件判定表，标注“证据足够／不足／冲突”，由独立复核者核对；记录复核方式，AI 复核不能称真人审核。没有可用目标页材料的样本只验证正确保留未知，不联网补齐来伪装离线覆盖。

建议通过条件：

- 候选、版本、文档及引用绑定 100% 正确；旧冻结协议可恢复，原 UNKNOWN 请求不得重新派发，离线外部请求为 0。
- 关键对照 100% 正确：营销／页脚不得证明匿名后台，工具不得算游戏，语言切换不当中文入口；三条京东页面保留三个 ID，同时识别为同模板、未证明不同操作。
- 对独立复核“证据足够”的子集，用途识别覆盖率至少 80%，非 UNKNOWN 结论精度至少 95%；“证据不足／冲突”集不得强填类型，严重场景误判为 0。全部给出整数分子分母与错例；低样本量不宣称统计显著。
- **不先规定全池 UNKNOWN 必须低于某个数。** 先量出可证比例；只有证据支持降低时才降低，不能以多填标签达标。抽样不足时扩大原件样本，而非宣称全池准确率。
- 对同一批原核类材料继续核对短编号还原、缺证和旧协议；不因补页面信息把首页重复材料重新发送。新的页面补证开销另记，不将原核类省下的 token 抵消后隐去。

### 第二阶段：待另行授权的后台小规模现场复验

先一站，再独立第二站；均须在各自启动站点基线之外。每站三条不同 URI、不同公开业务入口，例如数据表格交互、表单编辑、仪表盘筛选；若实际操作相同则不能靠换数据 ID 或菜单名称算不同业务。每页必须有第一方来源、最终 GET 2xx、匿名只读观察的实际控件证据及用途记录。三个都通过才算该站通过；登录墙、插件、宣传、文档、页脚、仅目录入口不充数。原运行只保存待审证据，不能预填消费者保存或 QC PASS。

第一站未过时记录缺额和原因，不扩大数量。第二站是独立泛化复验，不能换成第一站另一域名或同套页面三个参数。此阶段尚未获本次请求的启动授权。

### 第三阶段：由消费线验证 UNKNOWN 的真实影响

先在已有首帧／轨迹／失败原件上做相同观察、相同目标的离线对照，分别提供旧生产者信息与新补证信息，核对错误是否减少；不执行动作、不发真实模型请求作为本次复盘的一部分。需要模型重放时另计并先获得相应运行范围。

后续真实对照由消费线另行授权和冻结候选：建议 12 个固定候选，覆盖“有原件可补用途的 UNKNOWN”“仍缺证 UNKNOWN”“原用途明确”三组，各 4 个。遵循原领取／恢复及请求对账，不换作业重发 UNKNOWN；同目标复验产物不自动计成新增样本。名单、ID、版本、原 URL、目标及基线证据先固定，不按成败补位。

验收同时报告首帧公共可用率、规划 HTTP／token／耗时、正式尝试与保存、实际动作和可见终态、独立 QC 及全部失败归因。建议扩量目标是在保存与同目标独立 QC 不低于原基线的前提下，总规划 HTTP 或已知 token 降低至少 15%；未达或样本不足时只报告方向，不称消费效率已提高。所有均值包含失败开销，保存为零时不计算“每合格样本均值”。12 个样本不能替代全批质量或客户验收。
