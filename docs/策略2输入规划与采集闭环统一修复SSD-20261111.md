# 策略2输入规划与采集闭环统一修复 SSD

日期：2026-11-11。设计基线：`13a6ffb`。本方案针对 `screenshot_plan` 策略，统一修复输入规划、观察字段、步骤结果检查、重复提交及完成核验。用户已确认按本方案实施，实施子会话使用 `gpt-6.1-sol / low`。实施状态与实际检查结果见文末记录。

## 1 目标和业务口径

目标是让 Agent 根据原目标和真实页面状态，选择需要修改的字段与合法编辑路径，执行到目标完成，并让工程正确区分实际动作、步骤预期、目标证据和保存结果。

正式保存仍须原目标完成、对应证据可信、实际有效业务动作不少于五步且无未决外部效果。首轮优先规划五至八个必要动作，必要时可以更多；没有累计八步或十步上限。剩余计划无需凑满五步，达到资格且目标完成即可收尾。保存仅代表待审，独立 QC、人工审核、发布和客户验收各自保留证据边界。

### 1.1 按需修改输入框

Muxtly 混凝土页面默认长 10、宽 10、厚 4、数量 1。新浏览器会话可以带有网站默认值，不应预先清空全部输入框。

自主拟定目标时，可以选择计算 10×10×6，只修改厚度，保留已符合目标的长、宽和数量。已指定或已经冻结的 12×12×6 目标不能改写，仍须修改三个不匹配字段。

以下编辑路径均合法，选择由目标、当前焦点、选区和输入值决定：

| 编辑路径 | 适用条件 | 计步依据 |
| --- | --- | --- |
| 聚焦 → 全选 → 输入新值 | 替换已有内容 | 每个实际建立效果的原子动作分别记录 |
| 聚焦 → 全选 → 删除 → 输入新值 | 先清空再填写已有内容 | 删除造成非空到空的真实变化，独立计一步 |
| 聚焦 → 输入新值 | 输入框已空，或目标确实要求按光标位置插入 | 最终值符合该步明确预期 |

例如修改厚度时，聚焦、全选、删除、输入 6、点击计算五个动作各自产生真实效果且原目标完成，即可形成普通轨迹。不能因为全选后也可直接覆盖，就将显式删除一概视为无效或凑步。也不固定每次都执行四步编辑：已聚焦不重复聚焦，空框重复删除、没有选区变化的重复全选不补有效步数。

不同任务可以修改不同必要字段、选择不同合法编辑方式和操作顺序。轨迹差异必须来自真实执行，不修改轨迹标签制造差异，不为多样性反复改写已满足目标的字段，不改变现有业务身份和判重规则。

### 1.2 三个不同的执行判断

1. **实际效果**：动作是否真实派发并产生可验证变化。输入成 1012 仍可能是一个真实有效编辑，失败和费用均保留。
2. **步骤预期**：实际最终值是否等于本步期望值。目标是 12 而实际为 1012 时，该步骤不应被当作达成预期并正常推进后续提交。
3. **原目标完成**：输入条件、最新提交及结果证据是否共同满足被冻结的目标。动作数量不能替代完成核验，完成核验也不能替代正式保存收据。

## 4 Agent 协议与目标设计

### 4.1 动作契约

首轮和修订计划使用同一份动作说明与 schema。type 要求目标已聚焦；value 是本次实际插入的非空文字，expected_value 是该步执行后的最终值，清空使用 hotkey。select 的 value 是真实选项值，真实存在的空值选项也必须贯通两层执行校验。目标值为数值零或空字符串时不得用真假判断将其丢弃；空字符串表示真实清空，缺失字段不等于空。

全选使用已有逻辑按键映射，删除使用已有 hotkey。工程不暗中补点击、全选或删除，不把多个实际动作包装成一步。必要的只读定向观察继续复用现有机制。

prompt 说明输入值、焦点和选区都是当前观察事实；未来步骤可以规划其前提，但不能把尚未发生的聚焦或结果写成已观察事实。原目标包含多个结果时必须全部完成。

scroll 明确提供 direction；普通文档滚动无需捏造控件目标。plan_decision 顶层使用 reason，各步骤独立使用 rationale。仅有确切等价语义时才在当前 normalizer 整理字段，非等价或相互冲突的含义返回精确缺项，沿用现有有界纠正，不新增无限重试。

### 4.2 完成事项

直接修改当前 requirement 协议，采用稳定的 `kind=input/result/content`，不新增代际版本或通用断言语言。

| kind | 声明和证据 | 核验方式 |
| --- | --- | --- |
| input | 每项绑定一个 target；值使用 expected_value，布尔勾选使用明确的 expected_checked，不混用；证据引用 observation 和 control | 已提供且已校验观察中的对应可见控件状态；支持保留默认值；数值 6 不受八字符 quote 限制 |
| result | 原目标要求的业务输出；引用已有 region 或 quote | 真实结果文字及本轨迹输入/提交因果；输入回显不能充当结果 |
| content | 阅读正文、解释或摘录；引用已有 region 或 quote | 有来源的可见内容，不要求无关的输入或提交 |

schema、首轮提示、normalize、首轮接收、分支完成 evidence、verify_completion 和封存回放一并更新。`ScreenshotPlanSession` 接收 requirements 时必须保留 kind、target 和期望状态，不能仍只复制 id/description。requirements 接收后冻结，修订尾部不能改变原目标、事项类型和目标值。

输入条件应覆盖目标中明确要求的值，包括保留的默认值。模型声明本身不是证据。不得把所有含“计算”的任务事项都套用结果核验，也不得通过全局放开输入回显来解决输入事项无法完成的问题。

## 5 工程执行与事实读取

### 5.1 一个事实来源和不同判断用途

复用当前可信快照、控件绑定和轨迹，不新建数据库或状态服务。按 element_id 关联 values、elements 与 capture_controls，使用现有文档身份和目标来源。提供给模型的值遵循已有可见证据边界；未知值不能伪造为空。

观察应完整表达已知焦点 true/false、空值、选区以及数字输入框已有的 all_text_selected 证据。DOM 无法提供可靠选择信息时保留未知，不依据按下全选就预填成功。

同一读取方法供模型观察、步骤结果核对和业务事实比较使用，但用途不同：焦点/选区用于判断动作前提和全选效果；输入值/选择状态用于输入条件及提交依据；新结果与已核验证据用于完成进展。不能将整页哈希用于所有判断。

### 5.2 步骤执行和预期结果

每个实际动作按原入口派发、观察和留证。对 type/select 同步保存 expected_value 与实际最终值。原子效果和步骤预期分别记录；1012 与 10 不同可以建立真实编辑效果，却不能证明期望 12 已完成。

不符时进入现有 checkpoint，提供字段、预期、实际和原观察引用，由 Agent 修订未执行尾部，避免错误参数继续提交。不删除已经发生的编辑，不改写费用和历史动作，也不重发 UNKNOWN。全部目标已有有效证据时，仍保留现有完成核验优先于无进展停止的顺序。

删除后的空值依据实际前后观察验证，沿用现有 describe_change 的清空叙述。封存回放、动作审核与首次 annotation 生成必须能复核相同输入变化和计步事实，不能只修在线游标。

### 5.3 重复提交和无进展

提交身份沿用当前动作和控件来源；提交依据绑定相关输入及对应提交记录。相关输入发生已核验纠正时允许再次提交，工程可从事实形成依据，模型 new_basis 用于解释，不能以反复换措辞代替真实变化。

输入比较排除捕获时间、截图编号、焦点、几何和无关正文刷新。滚动导致控件离开视口不代表值被清空；通过同文档、同控件且未被后续事实推翻的已有观察/轨迹核验。文档切换或目标身份不确定时重新观察，不拿不明来源的旧值放行。

原生 form 不存在时，利用本任务已绑定的输入、提交对象及现有业务容器证据关联；不能把两个缺失 form_selector 简单视作同一表单。优先复用已有绑定，不引入通用表单发现框架。

无进展复用正确的业务事实、新有效动作及新增已核验证据。只改计划措辞、游标或重复被拒动作不能刷新进展；保留已有停止机制，不通过提高阈值掩盖错误提交判断。

### 5.4 旧结果失效

相关输入实际变化由前后状态和已派发动作建立，不能只枚举 type/select。全选与聚焦本身不改变输入值；删除、粘贴以及其他 hotkey 只有确实改变相关输入时才属于编辑。

核对并统一以下入口：verify_completion 的输入事实集合、_result_superseded、_post_submit_causality，以及直接结果路径 result_execution_binding。计算后删除输入使旧计算证据失效；重新填回原值也不能仅凭数值相同自动恢复旧提交资格。新完成结论要有对应的有效提交与结果证据。
