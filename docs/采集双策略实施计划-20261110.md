# 采集双策略实施计划

日期：2026-11-10。状态：待实施，本轮仅文档。设计依据见[采集双策略设计](采集双策略设计-20261110.md)。

实施目标是保留策略 1 的现有采集能力，新增策略 2，并让两个策略的原始事实经过统一完成回算、首次标注和正式保存。工作单元按完整调用链拆分，Agent 与工程配套一起交付。

## 1 实施顺序与完成条件

顺序为：确定策略 1 基线和接口 → 接通策略选择及共享结果 → 完成策略 2 的输入与剩余计划循环 → 接通完成和保存 → 一次相关集成 → 在新的明确范围内做真实 GLM 基线。

不在本次文档阶段写代码或启动上述验证。旧固定 40、20、4 条均保留其当时状态，不沿用其授权，不重派原候选。真实验证的候选清单、数量、并发与停止条件在实施阶段另行明确；不预设持续生产。

| 完成条件 | 所需证据 |
| --- | --- |
| 策略 1 保留 | 原版本能经适配输出统一结果；同一历史事实的原终态解释不改变 |
| 策略 2 可运行 | 首轮、当前截图、最新动作、剩余计划、完成申请走真实 gateway 和执行入口 |
| 协议工程同步 | 同一版本的 prompt、schema、整理、校验、完成核验与派生一起接线 |
| 防止重复派发 | 同一操作身份只派发一次；相同状态下无新依据的重复提交被阻止 |
| 完成收口 | 完整完成凭据优先于游标与单步预测，缺证可以局部补齐 |
| 保存统一 | 两种策略使用同一资格函数和保存接口；首次 annotation 与原证据一致 |
| 真实通过 | 选定生产目标完成、至少五个真实有效动作、原账与正式待审保存收据可核对 |

## 2 改动单元

### P0 确定基线与契约

目的：避免把当前漂移的工作树或历史策略标签当成固定基线。

- 查看当前 `git status --short`，保留已有用户改动；记录策略 1 的实际源码、任务协议和完成协议组合。
- 沿 `candidate_consumer → collect_runtime → ReactSession → postprocess → RuntimeStore` 确认现有对象与证据可复用边界。
- 定义最小 `CollectionStrategy.run(context) → StrategyResult`、版本化完成核验和 `save_strategy_result` 接口；不用新 HTTP 服务。
- 冻结两个策略 ID 及内部结果版本。新任务显式选择；缺省继续策略 1；旧任务读取已有版本，不自动升级。
- 明确模型字段与工程字段：模型不再填写内部身份、步数、band 或单步状态枚举；必要业务用途、预期和完成证据仍需存在。

产物：接口定义、字段所有权、旧结构映射表、策略 1 基线记录。基线记录是实施定位，不构成新的生产授权。

### P1 策略选择与策略 1 适配

目的：先建立真实策略边界，使截图、调用、执行及校验作为一套行为选择。

| 位置 | 计划改动 |
| --- | --- |
| `candidate_consumer.py`、任务生成入口 | 在新任务元数据冻结策略 ID/版本；保留原领取、身份、首帧和登录排除 |
| `collect_runtime.py` | 在创建采集执行器处选择策略；共用当前浏览器会话、原账、证据和保存上下文 |
| `react_session.py`、`banded_plan.py` | 用薄适配器承接现有策略 1；明确可复用原子执行/观察能力，避免策略 2 隐式继承全部 Controller 门禁 |
| 新的小型采集策略模块 | 两个实现与静态选择表即可；不用动态发现、插件加载或通用执行图 |

策略 1 原始事件继续保存。适配器只能映射实际存在的完成依据，不能用新字段掩盖旧 `no_path`，也不能把旧 `controlled_exception` 重新放入新交付集合。

完成条件：策略 1 仍可独立选择；任务结果明确记录实际使用的策略；策略 2 不触发策略 1 的计划 schema 校验。

### P2 策略 2 的模型协议与观察输入

目的：让 Agent 能看全局进展和当前页面，减少对工程内部字段的猜测。

- 编写同一版本的首轮 `submit_plan` 与 `continue/revise/complete/give_up` 分支协议。
- 首轮保留自然完整路径至少五个业务动作、优先五至八步、无硬上限；剩余计划不补五步，不预测未来答案字面。
- 首次接受后冻结目标及原事项。分支只输出未执行尾部或完成答案，不再重复提交完整目标。
- 输入默认当前截图、固定目标、原事项、确认进展、缺项、最新尝试、剩余计划、调用原因；必要时附少量当前可见控件标识及相关历史截图。
- 内部保留 DOM 绑定和确定性核验；不把屏外答案或全量 HTML 当作模型视觉输入。
- 一个策略定义同时供 provider schema、宿主解析和结构校验使用。等价整理先于严格检查，原回包与整理记录都保留。
- 必要缺项返回精确字段反馈；可选冗余字段不扩大为业务失败。不得丢失输入 value、焦点目标或滚动容器。

完成条件：方程初次计划无需猜 `x=1`；模型无需区分 `selected/text_selected`；原目标事项可完整继承，未来控件不需预编 ID；首次标注的用途与预期能追溯原模型输出。

### P3 执行事实与剩余计划循环

目的：消除旧成功轨迹覆盖最新失败的反馈，并阻止同状态重复提交。

- 统一生成最新动作尝试记录，包含未派发、已派发、无效果、失败和 UNKNOWN；与最后有效动作分开。
- 业务检查点包括提交、导航、显著变化、结果查看、偏离和完成申请；正常聚焦、全选、输入由工程顺序执行。
- 修订操作替换未执行尾部；保留已执行动作、原目标、用量、失败和旧计划版本。
- 下一动作执行前核对当前帧、目标唯一性和必要输入/焦点事实，实际变化后重新定位。
- 提交后先观察；结果未进视口允许滚动/等待，不要求它们已存在于旧剩余计划。
- 同一个动作身份不重复派发；同输入/同页面状态下重新提交须有可验证的新理由。
- 同一事实和反馈下反复返回相同无进展决策，由策略 2 结束本条并保留原因；不引入账户级或全局调用限额。
- 用户停止立即阻止新派发和新调用；迟到回包只结算原账，不恢复执行或重写取消事实。

完成条件：方程截图还未显示结果时，不连续点击求解；全选已成功时，不因旧枚举不同而重做输入；失败动作后的截图、文字和引用保持一致。

### P4 完成凭据与统一保存

目的：一次定义完成事实，贯通在线、封存回算、首次标注和提交。

- 复用 `result_completion.py`、`result_execution.py`、`plan_evidence.py` 现有来源和因果绑定；用策略 2 的原事项与实际可见结果生成完成凭据。
- 将完整原事项覆盖作为完成依据；语义预期和计划游标不再充当另一套终点。
- 同帧引用缺失可局部补齐；语义缺证才请求必要观察，不重放已完成输入或提交。
- 完成核验函数接受封存事实，在线和后加工使用同一实现。图像语义解释与工程来源核验的职责明确记录。
- `postprocess` 增加按策略版本的 raw 读取适配，输出共同的内部事实对象；随后复用标注、图像、收据和保存逻辑。
- 策略 2 不伪造 `HOST_PLAN_ENDPOINT` 或旧 plan-branch。`closing_policy` 中策略专属终点识别留在相应适配器，共享资格只消费统一完成事实。
- 正式文件生成前、RuntimeStore 提交及导出读取同一资格函数：原目标完成、有效步至少五步、证据可信、无相关未决外部效果。
- 目标完成但不足五步、未知、异常、放弃均保留 raw；不生成正式 annotation。保存异常单独记录，不改写目标事实。
- 保存收据绑定策略、版本和原始引用；按原身份去重，不因保存失败重做网页操作。

完成条件：`complete → 完成核验 → 正式派生 → 待审收据` 能走通；在线结论与封存回算一致；策略 1 和策略 2 使用同一保存入口。

## 3 一次相关集成的覆盖

集中改完 P0–P4 后运行一次相关集成，不按每个小修改反复启动测试。覆盖真实入口、gateway 整理、分支、执行收据、封存派生和保存边界；HTTP 边界的夹具需包含已观察到的真实输出形状，不能只用规范 scroll 回包证明完整适配。

历史原件只读，验证输出写新的隔离目录。以下案例是集成中的具体断言，不要求重复历史全量测试。

| 案例 | 必须观察到的结果 |
| --- | --- |
| 策略 1 的有效及失败原终态 | 适配前后语义一致；旧 no_path 不被重新标成功 |
| 首轮不足五个业务动作 | 明确区分 wait 与业务动作，不放行或补数；无正式文件 |
| 合法超过十步的路径 | 无旧 8/10 上限误拦截 |
| wait/scroll 冗余字段 | 无歧义时整理；容器等有业务含义的信息保留 |
| value 与标签分离、hotkey 目标 | 值和焦点语义正确；冲突明确反馈，不静默猜测 |
| 必要用途/预期缺失 | 同帧局部补齐；不靠后加工制造原模型语义 |
| 全选成功 | 工程按真实焦点和选择状态确认，不由模型谓词枚举否决 |
| 最新点击无效果，上一动作成功 | 反馈显示最新点击事实，不展示上一成功效果为本次结果 |
| 提交已派发，结果在屏外 | 观察/滚动后引用真实可见结果，无重复提交 |
| 同状态重复请求、UNKNOWN | 同一动作不重发；未知原请求不换编号重试 |
| 修订剩余路径 | 已执行步骤不重放，原义务不删改，剩余可少于五步 |
| 单步预期失败但原目标已证实 | 完成凭据通过，游标不造成 no_path |
| 输入标签或旧提交结果充当答案 | 完成申请不通过，保留具体来源/因果缺口 |
| Wiki 同名链接及标题命中 | 错页能修路；标题本身不替代原要求的正文结果 |
| 目标完成但只有四个有效动作 | 原目标完成、保存不合资格，二者同时如实记录 |
| 目标完成且至少五步 | 首次 annotation、保存资格和原收据一致，达到待审 |
| 缺来源或保存故障 | 无伪造样本；目标状态和保存失败分开 |
| 用户取消与迟到完整回包 | 原账正常结算，不发起新动作；字段错误与取消时序分开 |

本地输入/输出兼容与保存集成通过，只证明相关工程链路；不能证明策略 2 的真实视觉规划效果或独立 QC 通过。若失败，保留收据，修复实际断点，只复验受影响链。

## 4 有界真实 GLM 验收

实施授权明确包含真实基线后执行；本次文档不确定数量、不领取候选、不启动模型。只从当前工程生产 Table2 选择已发布的有效网页，不重新找站或绕过生产者。

基线至少覆盖需要输入并查看结果的 Muxtly 路径，以及含页面落地、阅读和剩余修订的 Wiki 路径。原方程与门户历史轨迹作为失败机制对照，不将旧 claim 重置重派。具体候选和目标在执行前冻结，保持模型、推理配置及交付资格一致。

如需真实比较两个策略，在符合原领取和去重规则的范围内，为两组选择业务条件可比的独立候选并冻结目标；无法获得完全同输入时如实报告差异，不宣称严格配对 A/B。相同已封存输入可做隔离契约比较，但不算新生产成功。

每组报告下列数据，避免只给一个成功率：

| 类别 | 记录内容 |
| --- | --- |
| 流程分母 | 固定候选、领取、本地生成任务、正式 attempt、有实际模型请求 |
| 规划 | 首次响应结构通过、纠正后接受、不适合、局部补齐次数 |
| 执行 | 实际派发、有效动作、同状态重复派发、错误落地恢复、无进展结束 |
| 完成 | 原目标完成、完成缺证、旧游标/预测与完成冲突 |
| 保存 | 完成但不合资格、正式待审保存、保存失败、导出 |
| 质量与成本 | 独立 QC、人审、发布各自状态；原账请求、tokens、耗时、UNKNOWN |

普通成功必须有原目标可见结果、至少五个实际有效动作和正式保存收据。不能把模型说完成、关键词 VERIFIED、集成 PASS 或内部异常片段替代该条件；采集验收也不替代客户验收。

固定范围结束即停止，不补位，不因失败自动切策略重试，不扩大到持续生产。出现真实失败时先归因到入口、协议、定位、执行、完成或保存，再决定相关修复，不再用全局放宽掩盖错误。

## 5 发布选择与回退

初次落地后策略 1 仍为缺省，策略 2 由显式配置启用。真实基线证明可用后，是否变更新任务默认策略另按发布决定执行。

回退只影响后续新 attempt 的策略选择。已开始任务继续按其冻结版本收口或停止，不能换策略接着执行未知尾部；旧结果、费用、失败和原始文件都保留。

涉及用户停止或 UNKNOWN，回退配置也不授予重派权限。生产者和 QC 的数据库契约若不改变，不要求它们同步升级；若结果交接字段语义改变，须显式更新契约版本并验证真实读取方。
