## 2. 解决了什么，为什么耗时这么长

已经解决的核心问题是：允许的动态内容可以穿过整条取证链；可用控件和真实正文能进入 Agent 观察；合法计划、引用及实际动作能进入执行与保存；403 的入口失效和中途导航失败有了不同处置；已经完成的真实目标不会再仅因终态说明混入无关代码而丢失保存结果。

反复卡住的主要原因在工程接入和验收设计，不能笼统归为“Wiki 太难”或“Agent 不会做”：

1. **多个层次各自添加格式拒绝。** 首轮、分支、引用、执行和保存分别解释同一输出，上一层接受后，下一层又因非业务差异拒绝。许多失败没有改变目标和动作事实，却重新消耗了完整模型会话。
2. **动态比较要求超出了用户实际要求。** 在明确允许公告和图片变化后，仍反复要求全页不变，再逐点加例外；本应统一的规则被拆成多次局部修补。
3. **集成样例没有包含真实断点的组合。** 静态页面保存通过，未覆盖真实页面里的控件展开、连续变化、模型原回复和末态派生。332 项通过不等于真实链路可用。
4. **工程派生数据与 Agent 业务判断混在一起。** 步数和短流程属于已执行事实，不需要模型申请；页面代码也不应直接被拼进工程生成的中文说明。
5. **历史验收条件被扩大成新研发的前置。** 旧 UNKNOWN 和严格六步双基线应按原账保留，但不应迫使每个新功能复验都等待旧作业，或为了达到长度延长已经完成的短任务。

Vue 阶段共 17 次领取、15 次正式尝试，消费请求 85 次，其中 28 次 invalid_response。消费 736,742 tokens，加同样本内容 QC 的 35,711 tokens，共 772,453 tokens。这个数量是失败成本的证据，不能用最终一条成功掩盖，也不能断言这些成本全部可由一个标签修复消除。完整长对话没有统一的研发用量账，本文件不把不同范围、可能重叠的历史统计强行合计。

## 4. 当前执行方式与优化依据

当前使用“首轮规划、工程逐步执行、遇到决策点再调用 Agent”的路线。首轮前先取得真实截图和 DOM；工程每次执行一个动作并保存前后证据。目标明确、效果符合预期时继续原计划；新正文需要理解、目标有歧义、结果偏离预期、路线失效或需要提交完成回答时，再调用 Agent。独立 QC 是保存之后的另一条流程。

| 当前事实 | 优化含义 |
| --- | --- |
| 原生和带计划路线已按轨迹长度计算短流程；旧 finish 仍要求 Agent 声明，派生还依赖摘要非空 | 复用现有能力，清除入口间的不一致，无需重建分类系统 |
| 已有计划和分支归一化，但 schema、引用回算和保存仍分别解释字段 | 在已有入口统一处理等价输出，避免前面接受、后面因格式再次拒绝 |
| 首轮与后续默认都使用 960×540、JPEG 质量 85 的推理图；原 PNG 保留 | 这次先优化上下文和调用次数，不继续降低图片清晰度 |
| 后续仍携带 system、受限 DOM、目标、分支 schema、正文及实际操作目录 | 后续输入没有自动变成很小；需要按实际决策选取必要材料 |
| Vue 出现同一页面连续“选择引用→决定剩余路线”的两次调用 | 可以把引用与下一步决定放在同一回复中，保留一次调用完成两项表达的能力 |

## 5. 目标、职责与短流程规则

本轮目标是让合法且有依据的 Agent 输出顺畅完成执行与保存，减少无业务价值的纠错和重复模型调用。优先复用已有 Python 模块、字段和账本，集中完成改动后做一次集成，再用稳定基线真实调用 GLM。

| 责任方 | 应负责的工作 |
| --- | --- |
| 规划采集 Agent | 理解网页，选择有意义的目标和路线；遇到实际分支时判断；阅读正文、回答原问题并引用依据；如实说明完成或未完成 |
| 工程宿主 | 绑定当前任务和观察；处理等价输出形式；执行真实动作、保存证据、核对实际来源；计算有效步数、短流程和正式保存状态 |
| 独立 QC／交付流程 | 按适用范围复核已经保存的材料，形成质量及批次接纳结论；人工、发布和客户验收分别记账 |

Agent 本身承担理解和完成任务的责任。工程保留可执行性、来源与实际动作核验，不用持续增加关键词、固定措辞和字段顺序规则来替代语义判断。

**短流程的最终依据是本次实际保存范围内的有效业务动作数 N。** 复用 `postprocess.effective_trajectory(record)` 和现有动作证据；计划长度、模型轮数、截图数及 Agent 自报步数不参与分类。

阈值沿用既有规则，本项工作清理残留的声明依赖并统一实现，不另创短流程标准。

| N | 工程结果 |
| --- | --- |
| 0 | 保持 `no_actions` 或原失败状态，不生成短流程样本 |
| 1–4 | 自动 `short_flow=true`，由工程生成原因 |
| ≥5 | 普通流程；内部为 false，交付沿既有格式省略或写 false，清除短流程原因 |

工程原因例如：“最终保存轨迹包含 2 个有效业务操作，少于 5 步，自动标记为短流程。”不拼入整页内容或 Agent 自由摘要。Agent 答案、停止原因和引用仍保存在各自字段。目标是否完成、是否可以保存、QC 是否通过，均不从这个标签推断。

`observe/inspect/wait/finish/complete`、未派发提案、无效操作与图片换帧不计入 N。可信前缀按其实际保存范围计数，原成立条件保持；UNKNOWN 按原账处理。短流程比例由后续交付集合检查，不让单条 Agent 为比例或步数补无关动作。

## 6. 工程优化：放宽形式，保留执行事实

### 6.1 输出校验的处理范围

| 输出情况 | 工程处理方式 | 保留的事实边界 |
| --- | --- | --- |
| 单一完整 JSON 的说明性包装、额外解释或草稿字段 | 沿现有解析入口提取唯一明确决定；说明原样留在原回包 | 不从多个冲突决定中猜一个执行 |
| 已知等价字段，如 label/text、单键字符串/数组；缺省可选字段 | 一次归一化；只补确定的默认值 | 显式冲突的执行参数反馈给 Agent，不静默选值 |
| check_answers 顺序不同，但 check_index 明确 | 按编号对应和整理 | 不丢失原检查项，不把重复或错编号映射成已完成 |
| 连续正文摘录，或缺少可由唯一已读来源确定的元数据 | 绑定原正文与实际阅读来源，不要求复制完整段落 | 错误来源、未读内容或未执行动作不能补造 |
| 重规划省略首次目标/checks，完成答复省略重复目标文本 | 工程绑定首次接受的原目标，不要求 Agent 反复逐字抄写 | 接口不接受将原目标替换为更容易的问题；实际答案仍需对应原事项 |
| 缺省或错误的 short_flow、原因、自报步数 | 字段保留在原回包作为历史输入，最终按 N 生成 | 不因补标签追加模型纠错 |
| 缺少动作必需参数、目标有歧义、引用暂时无法唯一对应 | 返回当前具体问题及相关候选，让同一有界会话修正当前决定 | 不重新采集已完成的前序动作，不重发 UNKNOWN |
| 截断/无法解析的决定、显式错任务或错观察、实际效果未知 | 保留原失败，沿现有反馈／停止路径处理 | 不用“宽松解析”猜动作、拼轨迹或改签原账 |

采集前只检查当前执行确实需要的条件；保存与导出可以独立核对原件及最终字段一致性，但共用归一化后的含义。删除的是重复的表达形式限制，不是独立证据核验。

### 6.2 Agent 输出和工程改动必须同时完成

**不能只改 prompt 或示例，再让旧 schema／保存器接收新输出。** 下面各层属于同一项改动：

| Agent 改动 | 必须同步的工程接入 |
| --- | --- |
| 不再填写短流程字段 | finish 的必填规则、会话收尾、派生原因、annotation 与输出一致性检查 |
| 核对项可不同顺序、引用采用连续摘录、重复目标文本可省 | 回复 schema、编号归一化、当前目标绑定、正文/动作引用回算及保存回读 |
| 同轮输出“引用＋继续／重规划” | choice schema、gateway 保留字段、Controller 的分支处理、引用事件保存及后继完成核验 |
| 分支输入和工具说明精简 | prompt 构造、实际发送的 schema、错误反馈、原生工具与普通 JSON 两条接入路径 |
| 完成答复或派生字段调整 | `direct_completion`、`postprocess`、客户导出和 QC 交接；只调整确实受影响的校验 |

继续复用当前 schema 构造和归一化函数，避免再复制一套“模型版规则”和“宿主版规则”。新输出在正常入口通过执行、保存和回读才算接入完成；原模型回包与工程归一化结果可分别追溯。

### 6.3 工程模块范围

- `react_session.py / closing_policy.py / postprocess.py`：统一最终计步、标签和原因；清除 Agent 声明及摘要耦合。
- `model_gateway.py / banded_plan.py / direct_completion.py`：统一等价输出接入、编号与引用绑定，贯通同轮引用和决策。
- `react_protocol.py` 及当前工具 schema／prompt：同步字段责任和明确的最小输出示例。
- `client_package.py / qc_handoff.py / quality_inspector/format_checks.py`：核对最终字段一致性；已有检查适用时直接复用，不要求一律修改。
- `inference_image.py`：本轮保持现有默认压缩与原图保留方式；原图或局部图只在实际看不清时使用。

终态叙述继续使用目标相关且已核实的正文，不把整屏代码拼入中文结果。短流程原因采用确定模板，无需新建泛化文本清洗器、黑名单、数据库或兼容框架。

## 7. Agent 优化：首轮规划，后续按需判断

### 7.1 goal、prompt 与上下文

**Goal 保持业务含义。** Agent 仍根据用户目标或真实首帧选择任务，首次接受后保持原问题；后续调整剩余路径。目标自然完成即可结束，不为五／六步填充动作。

**Prompt 删除工程性负担。** 不要求 Agent 申请 short_flow、自报有效步数、抄写可由当前会话绑定的元数据，也不要求每轮重述全部已做事项。保留当前页面限制、可用动作、真实证据来源以及“继续、重规划、完成、停止”的含义。

**后续输入按实际决策组织。** 当前调用是按请求构造上下文，不能假定模型会自动记住首轮；原目标和当前决定所需信息仍必须提供。

| 阶段 | 应提供的信息 | 要减少的重复 |
| --- | --- | --- |
| 首轮规划 | 目标、当前截图、任务相关 DOM、允许动作、最小计划结构及完成条件 | 重复的 schema 说明、示例和与该任务无关的规则 |
| 普通继续／目标选择 | 紧凑的原目标、当前步骤、最新截图、必要控件、最近实际结果和当前选项 | 全量历史、已经核实的重复证据、当前未提供的工具分支 |
| 重规划 | 原目标及尚未完成的 checks、当前状态、剩余路线与可用动作；足以同轮生成合法剩余计划的结构 | 重述已完成动作、重复抄写首次完整计划 |
| 阅读完成 | 原问题/checks、实际读到且回答需要的正文、引用对应的操作与末态 | 与回答无关的正文、全量动作详情和已重复表达的说明 |

先去掉 payload、schema、工具说明之间的重复，再做必要材料的选择；完成回答仍应保留覆盖全部原事项的证据。普通分支应更轻，重规划和完成回答可能较重，不规定每个后续请求必须比首轮更小或更快。

模型看到的输入与宿主可执行条件保持一致：能点击的目录或控件不能被裁剪到不可见；模型引用的正文必须来自实际观察。不新增网页正文自动摘要模型调用；原文件仍完整保存。

### 7.2 合并引用与下一步判断

复用现有 `choice` 和 `plan`／`reading_answer`，建议给继续、重规划回复增加可选 `citations`，条目结构复用现有 passages。它只记录来源，不改变执行选择或自动授予完成。

| 同轮回复 | 含义 |
| --- | --- |
| `continue_plan + citations（可选）` | 记下本次有关原文，继续原剩余步骤 |
| `replan + plan.steps + citations（可选）` | 记下本次有关原文，同时调整剩余路线；继承原目标/checks |
| `finish_reading + reading_answer` | 原问题已经有证据支持，直接提交含引用的完整回答 |
| `stop` | 如实结束；不把未完成改为成功 |

现有单独 cite 输出仍可解释，但新 prompt 不再把它设为完成或继续之前的必经调用。宿主收到带引用的 continue/replan 后，保存引用并按明确选择继续；不能因为引用入账，又立即用同一观察请求 Agent 重复选择下一步。

这项改动需要同步 `choice_schema`、直接阅读 schema、gateway 字段保留、Controller 选择逻辑和完成证据回算。避免新增 citations 在解析时被丢掉，或被后置 `additionalProperties` 拒绝。引用校验问题走现有同会话具体反馈，保留原回复。

Vue 的“引用→同帧重规划”是集成验证对象；真实模型是否自然合并及节省多少调用，需要后继实测。不强制所有样本固定为三次调用，也不跳过确实需要的新观察或业务判断。

### 7.3 性能指标与判断方法

沿用账本记录每次调用的阶段、输入/输出/cached tokens、请求耗时，结合实际保存收据报告每条目标的调用次数。图片字节、浏览器取证耗时和模型请求耗时分别列出；未记录的首 token 延迟不补造。

功能正确是前提。性能重点是普通分支的重复输入减少、同帧重复决策减少，以及同目标保存的总调用和用量。对照先使用同类阶段、相同目标及模型配置；单条结果作为个例，不声称统计平均提升。首轮与最终回答的输入大小可以不同，不用压缩必要正文来追求后续一律更短。

本轮不同时更换模型、推理档位或进一步压低图片质量，便于识别上下文与调用合并的效果；无须新建性能监控服务或大规模压测。

## 8. 集中实施与一次集成验收

实施顺序是：**工程责任和输出接入统一 → Agent 上下文与同轮决策同步 → 保存/导出一致性 → 一次集成 → 稳定 Table2 真实 GLM 试跑 → 汇总结果。** 前四项集中完成，不每改一个字段就重新单测、冻结或发模型请求。

| 集成覆盖 | 验收结果 |
| --- | --- |
| 0、1、2、4、5、8 个有效动作 | 0 不成样本，1–4 自动短流程，5／8 正常；等待和完成动作不计步 |
| 缺省／错误短流程声明、空原因；已证目标的摘要为空 | 最终分类相同，不因标签或摘要追加请求；目标证据问题单独判断 |
| 计划六步实际两步；计划短实际五步 | 按实际保存轨迹分类，不按计划或 Agent 声明 |
| 等价字段、额外说明、检查项不同顺序、连续正文摘录 | 在首轮与分支两条正常接入路径通过；原回包保留 |
| 引用和 continue/replan 同轮返回 | 一次模型决定完成记录引用与选择下一步；字段不丢失，后置校验不再次拒绝，同帧无被迫的第二次判断 |
| 完成答复直接带引用 | 覆盖原问题后正常保存，无强制前置 cite |
| 错来源、错任务/观察、必需参数缺失或业务歧义 | 原事实不被静默改签；能在当前会话修正的返回具体问题，UNKNOWN 不重发 |
| 页面代码、动态区域、无文字锚点 | 原图树保留，已有动态规则与控件执行能力保持；无关代码不混入派生中文说明 |
| 保存、导出、QC 交接 | 最终计数、标签、引用与保存收据一致；不在保存链中新增独立 AI QC 调用 |
| 上下文精简 | 当前可选动作和必需正文仍可见，原目标可追溯；普通分支去掉重复说明，重规划与完成拥有所需材料 |

使用新验证目录和现有正常入口，复用原失败回包及受控页面。失败时只修复并复验受影响链路，不重新执行旧 77／332 项套件；记录真实失败，不覆盖原件。

随后进行两个稳定场景的真实 GLM 验证：优先沿用已有 Vue 阅读目标验证自然短流程；常规流程使用当前 Table2 中已发布、可访问且原账允许执行的候选，固定实际目标后试跑。同候选重复研发沿已有入口，不改待审状态或另造账本绕过原记录。每会话沿用 25 次真实 GLM 上限；旧 Wiki 废弃、UNKNOWN 和其他历史缺口保持。

本项功能通过条件为：目标有实际结果、正式保存、短流程分类正确、合法新输出能贯通工程、必要上下文未丢失，以及没有因补标签或被迫先 cite 再决定而增加调用。常规场景需有自然成立的常规操作路径；已经完成的短目标不补空操作。原严格六步双基线缺口另列，不作为本项功能验证的前置。

报告分别列出首次规划、普通分支、重规划、完成的调用次数和用量，给出旧/新案例与失败原因。功能通过与性能收益分别报告，不因模型偶发排队而改签功能失败，也不把更快的失败调用计作优化成果。
