# 消费者 5–8 次动作尝试与异常收尾 V2

本轮按用户新口径追加工程实现，协议为 `webcollect-five-eight-attempt-ending-2`。原 459 文件 checkout、原账与所有 50 行名单不改写。工程会话只做离线模拟与源码冻结；真实接续、独立 QC 和两轮对比由主会话负责。

## 正常工程入口和历史边界

Table2 候选正常进入 `task_generation._generate_react_url` 时，把新 ending_policy 写入 task spec 与 fragment，再由原任务 ID 摘要冻结；`build_candidate_task` 也启用 V2。原 `candidate_consumer --cohort ... --protocol entry` 调用方式、工程、原 ledger、registry、claim 和请求绑定保持。已冻结的旧任务继续使用原 ending_policy；不能在原任务上补字段改变版本。直接构建任务可显式调用 `build_url_task(..., ending_policy=closing_policy.VERSION)`；未指定时保留 V1 构建语义。

V2 独立源码、全部文件指纹、原 50 行名单摘要和验收收据在 `verify_results/consumer-fifty-round2-implementation-v2-20261103-r01/`。主会话在当前候选自然收口后，再用新 checkout 接续同一 50 个原 ID 中尚未领取的成员；本会话没有暂停、领取、恢复或派发真实任务。

## Goal、prompt 和 tool

Goal 保留 requested_goal 和观察支持的 working_goal。目标可见结果已达到就正常 finish；自然短流程允许，不为凑次数继续操作。宿主不会用第五次或第八次自动证明目标完成。

Prompt 对新协议使用 5–8 次业务动作尝试的收尾区间。每个实际准备执行的原子业务动作记一次尝试；参数合法、引用当前观察且已有工作目标的具体 act 提案在编译或派发前拒绝时保留一次零派发尝试。无效参数、过期观察引用、observe/inspect、wait 和 finish/complete 不计业务尝试。复合 set_value 的 focus、全选、输入等实际原子操作分别计次；到第 8 次即截断其后尚未派发的原子操作，不能因同属一次语义工具调用而越过上限。语义调用数、实际派发数和有效步数不能互相替代。

宿主每次尝试冻结决策、模型意图、tool_call ID、请求观察引用、原子动作与证据引用、每个原子尝试的派发增量、有效步增量及原因。第 5–8 次尝试最后一操作明确失败或效果无法核定时，立即由宿主 finish，不再调用模型探索。第 8 次成功执行后仍无目标完成确认时也由宿主 finish，标为次数上限收尾，不派发第 9 次。原会话 25 次 GLM 上限若先耗尽且已有 5–8 次尝试的完整安全前缀，则标为模型预算收尾；没有有效前缀仍只封存原件。宿主 finish 与模型 finish 分开标明来源，均不计业务动作或有效步。

## 尾步原件、待审保存和待核封存

V2 原子原件存放在独立 `action-attempts/business-<次号>-primitive-<原子号>.json`，包括零派发、失败和未验证尾步。原始 journal 追加 `business-attempt`、`range-finish`，terminal 绑定 `collection_ending`；不会用末尾 complete 覆盖失败原件。

只有连续有效前缀、可信末态及原动作计量均能独立复核，且没有未证实外部效果时，才生成正式 `collected_pending_review`。当前安全异常尾步仅接受零派发，或已取得同步后帧、证明无视口/正文变化的本地 scroll；未核定的 click/type/select 等不能因页面看似没变就推断没有外部效果。后加工重新读取逐次尝试与原子原件，核对精确前缀集合、派发和有效计数、尾步与末态；不能只相信宿主布尔标记。

派生样本保留全部已验证的连续前缀，完整原始尾步保留在证据中并从样本末步引用，绝不删去中间动作后拼接。异常或上限收尾使用现有 `completion_status=controlled_exception`，末步 exception_evidence 和 final_result 明示目标未确认完成；可选 `tool_result.return_value.collection_ending` 冻结协议、尝试数、实际派发、有效步、未验证尾步、finish 来源、原请求/动作/证据、原因和末态。该扩展的程序支持不构成客户验收。

有效步不足 5 时仍标记 short_flow 并给出实际有效数和具体收尾原因。例如第 5 次本地滚动无效果时，尝试 5、实际派发 5、有效步 4、尾步 1、finish 1，派生样本是 4 个有效步骤与 1 个不计步的末态确认。原第五次失败记录另存并被引用；不能把它算作有效第五步。

派发后效果 UNKNOWN、无可信后图、末态不可绑定或原请求未知时，原始轨迹与 raw receipt 保留，终态明确为待核收口。正常采集入口另写 `raw-ending-pending.json`，表明原 attempt、原 raw、原因及需对账状态；不导出普通样本、不伪造待审保存、不启动 QC、不重发动作或模型请求。原账继续隔离未决，原编号不回收。

## 格式、导出和 QC 分层

正常保存、客户格式导出与 QC 交接沿用各自收据。新可选标记在本地 annotation schema、导出校验和 QC 格式检查中一致检查：计数必须与交付有效步骤一致，异常必须有 controlled_exception 和异常证据，外部效果未知不得作为安全样本导出。

独立 QC 材料显式提供 collection_ending，区别已达成、异常收尾和未确认完成；有效长度只数已验证步骤，不能把尾步、wait、finish 或 complete 凑入五步。必要原件缺失仍为 REVIEW_REQUIRED，不能预填 PASS。仅 terminal_semantics 升级为 `truthful-legal-fragment-and-flagged-five-eight-ending-3`，其他 AI 规则版本保持；旧审核原件不写回。程序格式、样本 AI、资料审核、人工审核、发布及客户验收各自保留状态。

## 离线验收

用临时库与模拟浏览器覆盖 5/8 边界、本地已知失败、编译/派发前零派发、派发后 UNKNOWN、后图缺失、自然成功与短流程、复合动作计数、原始尾步不覆盖、篡改计数拒收、正式保存/导出/交接及原始轨迹待核收据。旧协议超过八步仍按原义解释。没有真实网络、模型或 QC 请求，夹具收据不能作为真实采集产量或审核合格证据。
