# 消费者 A/B：单批生产、账本分组消费方案

日期：2026-11-09
状态：已获用户共识，实施中
上一运行：`verify_results/consumer-effort-ab100-20261108-r01`（completed_with_shortfall，A=0/100，B=0/100）

## 1. 背景与共识

r01 的两个失败根因：

1. A 组 613 条 NEW 候选在冻结前审核全拒（`GET_receipt_identity_or_status_mismatch`）。根因是 `candidate_cohort.verify_get` 仍要求旧凭据协议 `producer-entry-http-get-1`（`entry_access.POLICY`），而现行生产者写 `producer-entry-observed-get-2`（`producer_observation.py`，四个现行测试锁定）。真实消费者领取路径并不校验该 policy，613 条候选对真实消费全部合格——冻结路径是一套会漂移的平行校验。
2. B 组生产者 1.3 秒秒退（`BudgetStop: max_concurrent_jobs reached`）：A 组生产者被 SIGTERM 时在共享生产者账本遗留 running/queued 作业，阻塞 B 组。

2026-11-09 用户共识：**先单次生产建库存，再 A/B 分组消费**；取消冻结环节及其平行校验，分组分配记录写账本，消费走原领取事务与状态机。`candidate_cohort.py` 保留（正式 `run --cohort` 入口与基线校验仍用），本流程不再调用。

## 2. 流程

```text
生产者（一次，可选跳过） → 候选池 pending NEW
      ↓
分组分配（只读筛选 + 稳定交替 + 账本事件 + 运行目录名单）
      ↓
A 组 worker ×2 ──claim 原事务──┐
                              ├─→ consume → record_outcome → saves.jsonl
B 组 worker ×2 ──claim 原事务──┘
      ↓
按组汇总（分配名单 × claim 状态 × 有效保存）
```

## 3. 改动范围（只改战役层）

### 3.1 automation.py（驱动）

- 生产阶段：两组循环改为**单次** `produce-entries`，batch-key 统一，类目取两组 directions 并集；新增输入开关 `reuseInventoryBatch`：指定已有生产批次 run_id 时跳过生产，直接用该批次 pending NEW 库存（r02 复用 r01 的 613 条，验证不必先等 2 小时生产）。
- 删除 inspect_rows / freeze / cohort 段。改为：
  - 按 run_id 读 published NEW 且当前 pending、无 disposition、未领取的候选（纯 SQL 状态过滤，不做平行校验）；
  - 沿用 application 轮转排序后，**交替分配** A/B（order 从 1 起）；
  - 分配写入账本 `candidate_events`（`kind='ab_assignment'`，记录 campaign、group、order、producer_batch）并写运行目录 `group-{a,b}-assignment.json`。`disposition` 只查 `kind='disposition'`，分配事件不阻塞领取。
- 报告段：official `batch_report` 按共享批次出整批口径；每组口径按分配名单过滤（processed / saved / shortfall / claim 状态分布）。
- `EXPECTED_COMMIT` 钉子更新到当前 HEAD（先核对新增两个 QC 提交不碰生产/消费路径）。
- PROJECT_ID 升为 `consumer-effort-ab100-20261109-r02`，新运行目录，r01 证据不动。

### 3.2 ab_worker.py（worker）

- 输入从 `group-{x}-cohort/cohort.json` 改为 `group-{x}-assignment.json`（candidate_id、producer_batch、order、entry_url）。
- 领取改走原 claim 事务：`claim_next(worker, request_id, candidate_id=..., protocols=(VERSION2,), producer_batch=...)`，不带 frozen_row；版本、来源、状态由领取事务按原规则复核。
- 分片、目标计数、有效保存证明、事件/问题日志、completion 全部沿用。

### 3.3 不改

生产者 CLI、candidate_pool、账本、QC、`candidate_cohort.py`、`site_failure_stop.py`（旧 policy 引用随之成为死路径，不在本轮清理）。

## 4. 验收

1. **集成测试**：隔离工程、临时库、独立输出目录，小目标跑通「生产(夹具) → 分配 → 双组 worker → 汇总」全链，不污染正式账。
2. **真实基线试跑 r02**：复用 r01 库存，4 个 worker 真实 GLM 消费，目标每组 100 条有效保存。验收口径：各组 `verified_effective_saved`、claim 状态分布、消费者模型计量；缺额如实报告。
3. 本轮完成后同步 README / 工程说明 / 设计说明。

## 5. 边界

- 25 次 GLM 会话上限、站点失败计次、UNKNOWN 原账核对等原约束不变。
- 分配是批次内承诺，不改写候选正文与身份；失败不递补。
- 多机静态分片（`单机生产者多机消费者静态分片与结果汇总方案-20261108.md`）是另一未实施草案，本轮不合并。
