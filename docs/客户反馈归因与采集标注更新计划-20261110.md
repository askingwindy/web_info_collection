### 2.2 短流程包含两类问题

76 条中，61 条的**首份已保存计划**不足五步，15 条计划至少五步但最终保存不足五步。这反映首轮路径设计与执行中断两类问题；首份已保存计划不等同于真实第一次模型响应，不能据此计算首轮响应接受率。

从结束方式看，同一批 76 条中有 65 条来自停止或中断后的可信前缀，11 条由宿主判定到达正常终点。这是另一种分类，不能与 61/15 相加，也不能认定正常终点必然等于原目标完成。

规划侧应改善目标选择、完整路径与结果读取；宿主侧应修复实际绑定、重规划及停止断点。后加工可以修正计步说明和筛选交付资格，无法补足旧轨迹缺少的动作或截图。

## 4 工程代码更新

### 4.1 保留真实快捷键并随包提供执行依据

复用 `action_normalization.py`、`postprocess.py`、`client_package.py` 及 QC `format_checks.py` 的现有接入点，新增明确的实际按键输出规则，保留历史 Windows 映射的版本含义。

1. 新采集从真实派发记录取得键值。逻辑全选请求如何映射到宿主平台仍由执行器完成，交付记录使用实际执行键。
2. 历史 18 步从对应原轨迹、原派发和哈希恢复实际键，更新订正版中的 `tool_call.arguments`、`action.input_text` 和按键显示文字。没有唯一原记录时列待判，不根据 `os_name=macOS` 猜成 Command。
3. 在客户包根目录的独立执行记录附件中，随包提供必要的实际动作参数、平台、步骤对应关系、原派发引用及哈希。附件包含可读的实际键记录，不能只给客户无法访问的本机路径。最终路径和格式沿既有导出扩展点确定并版本化。
4. 同步校验器、包文件清单、SHA256SUMS、动作说明和合成说明。原始日志及模型请求仍在包外；附件不复制凭据、网络头或无关日志。
5. 订正版保持原 PNG、树、动作顺序、坐标和输入内容。快捷键改动是恢复真实派发的表达，不是改变实际执行。

验收：18 步均能逐步绑定原始实际键；新 macOS 与 Windows 样本分别保留真实平台键；缺原证据的映射不自动修复，旧原件及收据未覆盖。

### 4.2 将可用动作接入首轮规划

当前首轮 `STEP` 只含 click、type、hotkey、scroll、open_url、back、select，结束时再输出 complete。附件B允许的 Web 动作为 12 种，缺少 double_click、right_click、drag、wait 的首轮接入。

| 动作范围 | 宿主实现更新 | 模型看到的协议 |
| --- | --- | --- |
| 已有七类业务动作 | 保持当前观察绑定、真实参数和效果核验 | 首轮统一展示其用途及适用页面能力，避免示例只偏向点击输入或纯滚动 |
| double_click、right_click | 复用已有底层派发，贯通条件计划的目标绑定、执行和效果保存 | 可在真实页面存在相关用途时选择，不靠虚构菜单或双击效果制造多样性 |
| drag | 复用底层拖拽，补齐规划与编译的起终点绑定、动作效果和保存证据 | 描述有据的源与目标，由宿主计算坐标；没有可靠目标时不宣称可执行 |
| wait | 接入必要等待、观察与原始记录，独立于有效业务动作计数 | 为实际加载或变化安排等待，不用于凑五步 |
| complete | 继续由完成申请及宿主结果核验收尾 | 首轮包含明确的完成条件；结束确认不占有效动作步数 |

prompt、tool/schema、gateway、宿主校验、引用回算和保存作为同一项改动同步。沿已有协议扩展点明确新行为，旧任务仍按冻结版本解释。底层方法存在不代表整个规划采集链已支持该动作。

验收：可用动作能经真实生成入口进入首轮、执行、取证与保存；有据的混合动作可用，无相关控件时不强制混合。实际动作覆盖按计划和执行分别统计，wait/complete 始终计零有效步。

### 4.3 将采集完成判定绑定到实际结果

复用 `banded_plan.py`、`plan_evidence.py`、`numeric_result_evidence.py`、`react_session.py` 与现有收尾链。执行时明确“已完成事项、缺失结果、页面反馈”，由同一采集 Agent 修订剩余步骤，不增加每步审核模型。

- 结果型任务须证明指定输入及提交与实际结果有关。新进入视口的数值、静态示例表、输入回显、标题或结果标签，均不能单独授予完成。
- 不要求本次结果数值一定不同于默认值；同样的数值也可能是合法计算结果，但须有结果区域及本次执行的证据。避免把“值没变”一律判失败。
- 提交后页面校验拒绝时，区分已发生的点击与未完成的业务目标；把真实校验内容反馈到剩余规划。缺结果的结束只内部保留。
- 对关键控件中实际渲染的字面转义串作页面质量判断；正常技术文档展示代码不因出现 `\u` 被机械排除。无法继续的入口或任务记录具体原因，不扩大为整站禁用。
- 首份计划足够但实际不足五步的样本，按原断点分别定位，不能靠再加最小步数条件解决。UNKNOWN 保留原账，不因换 Key、作业或修订版重发。

验收：使用静态税率示例、校验失败、关键文字不可读等反例，以及真实结果可见的正例。已有结果能完成，未执行到结果不能导出 success，既定正常阅读与来源累计规则保持。

## 5 低成本标注订正

### 5.1 允许修改的判断标准

逐字段满足以下条件才自动订正：原件与来源可核验；依据唯一确定修改后的值；修改保持原目标和实际执行事实；新文字没有引入证据中不存在的结果或解释。不能确定时保留原值并列待判，不用空值或猜测代替。

| 字段 | 可自动订正的依据 | 保留待判的情况 |
| --- | --- | --- |
| hotkey | 原实际派发与对应步骤唯一绑定 | 只有操作系统信息、缺真实派发，或多个来源冲突 |
| expected_result | 原计划预期条件、当步动作、方向、输入值或目标明确 | 原计划未声明、前态也不支持，需要重新猜测业务结果；只有模糊控件名且不能确定预期效果 |
| next_step_rationale | 操作前状态与原计划用途共同支持理由 | 需从后续结果倒推当时意图、原计划无依据或有业务歧义 |
| final_result | 原目标所需结果已明确绑定最终观察中的具体内容 | 只能找到中间结果、输入回显、页眉、静态示例，或只剩旧 VERIFIED 标签 |
| completion_judgement | 已有独立完成依据能说明原目标各项如何被满足，并符合要求的终态证据 | 需要重新判定业务成功或把中间观察伪称末帧内容 |
| 叙述简体化 | 非引用叙述部分的确定性繁简转换 | 专名或原文边界不明，转换会改变目标或证据含义 |
| short_flow 与原因 | 实际有效步数、原停止事件和已证实的自然终点 | 有效步数口径冲突，或无法确定为何短于五步 |

理由修订是根据原证据形成的解释，不冒称恢复了模型未留存的原始思考。例如原前态确证输入框未聚焦、原计划要输入，才可写“当前输入框尚未获得焦点，先点击以便输入”。不得批量加“因为”来掩盖无依据的目标复述。

预期结果描述当时计划的变化，不把执行后的数值倒填成执行前预知的答案；实际发生的变化仍由 `step_result` 和终态字段表达。

`task_instruction` 如需简体化，只作不改变含义的表达订正；不得缩小、扩大、替换原目标来适配已有轨迹。控件真值、引用内容、输入值和原始计划文本不随叙述转换。

### 5.2 完成状态单独处理

本轮低成本订正不自动修改 `completion_status`。客户反馈中的“96 条状态不符”“78 条实际完成”作为待核对清单，不能直接作为改标指令。旧 VERIFIED 也不能替代业务完成判断。

需要改变完成状态时，另依据原目标、动作和结果证据作语义判定；证据不足继续待判或保留失败事实。若后续要调用模型核对，只针对明确未决样本单独确定范围、计费与规则版本，不默认给全部 193 条增加图片审核。语义重判的结论仍与独立 QC、人工和客户验收分开。

阅读的累计正文证据可以支持原问题，但不能被写成“全部答案同时出现在末帧”。最终状态描述与累计完成依据分别引用其真实观察，是否满足适用交付要求继续按原规则判断。

### 5.3 复用入口与输出边界

- `narrative_revisions.py` 现有能力适合带图片/树哈希依据的文字订正，当前不支持快捷键或完成状态修改。保留其动作不可变约束，快捷键恢复使用第 4.1 节的独立规则。
- `postprocess.revise` 能从封存原件在新目录重新派生，但会执行现有终态判定和派生逻辑。实施时不能直接批量调用并接受全部结果；需限制允许变化的字段并比较差异，避免顺带重判状态或改变其他输出。
- 原包、原轨迹、PNG、树、审核收据、费用和编号保持原样。先在独立修订目录形成候选版本，不自动替换客户包、激活新有效集合或发布。
- 每项修改保留样本/步骤/字段、旧值、新值、修改规则版本、原文件哈希、依据文件/观察以及处理结论。处理结论区分已订正、无需修改、证据不足待判、采集缺陷无法订正；不得用这些标签替代 QC PASS。
- 汇总分别报告样本数和字段数，包括已修项目、未决项目、仍需重采或排除的记录。某个字段修好不代表该样本全部合格。

### 5.4 成本约束

历史确定性订正的默认成本是本地读取原动作、状态、界面树、计划和证据摘要，以及生成修订记录；**新增模型请求数为 0，新增浏览器动作数为 0**。需要看图或语义判断却不能由已有证据唯一确定的字段进入待判清单，不自动触发调用。

不新增每步审核、独立事后补采 Agent 或失败自动重试系统。新采集使用现有规划调用保留用途与预期；未来代码改造的固定真实 GLM 验证单独计费，不混入“零新增模型的历史标注订正”。

## 7 实施顺序与验收

以下是后续实施的建议顺序，本次仅形成计划。83 条逐条重采、193 条重新做图片语义审核、持续批量生产均不在本次文档任务中启动。

1. **接续当前代码与协议交接。** 保留已有工作区改动；读取并行任务的实际结果，确定剩余改动。把快捷键、动作空间、结果证据、标注规则及版本边界集中设计完成。
2. **集中实现。** 按本次优先次序处理真实快捷键、五类采集缺陷、首轮动作空间，最后接通确定性标注生成与历史修订。先完成相关链的全部改动，再统一验证。
3. **一次相关集成。** 从真实任务生成入口覆盖计划、解析、执行、封存、后加工、导出及 QC 交接；历史订正另走无模型、无浏览器路径。失败只修实际断点并复验受影响链，不跑历史全量回归。具体执行以当次明确指令为准。
4. **固定真实基线。** Agent 或执行链改动使用当前生产者 Table2 中的有效网页，固定候选与原目标，沿正常入口验证。优先覆盖真实按键、自然多步、结果读取和页面校验反馈；动作必须有真实用途。名单、数量和结束条件在实施范围中明确，不沿用旧十条授权或借本计划重发 UNKNOWN。
5. **独立标注订正。** 对 0331 包逐字段判断可改性；有唯一依据才生成新版本，其余保留原值和待判原因。新增模型、浏览器计数为零。无法由标注修复的缺陷列重采/排除清单，实际重采另按确定范围执行。

必要验收用例：

| 范围 | 正例 | 反例及保留边界 |
| --- | --- | --- |
| 快捷键 | 原派发 meta+a 在订正版与附件一致，Windows 实际 Ctrl 保持 Ctrl | 仅凭平台猜键拒绝；原包与截图哈希不变 |
| 动作空间 | 有据的双击、右键、拖拽、必要等待走通对应链 | 无相关控件不硬造动作；wait/complete 不计有效步 |

| 页面质量 | 合法中文技术页面保留代码原文 | 关键控件字面转义串不能靠标注翻译修好 |
| 文字订正 | 前态支持理由、条件支持预期、真实终态支持摘要 | 不引入未见结果，不改目标含义，不自动重判完成状态 |

最终分别报告：正式尝试、业务动作、内部保存、普通完成待审候选、标注修订、独立 QC、人工、发布和缺额。实际修订多少条、多少字段以结果为准，不预承诺 110 或 193 条全部修复合格。
