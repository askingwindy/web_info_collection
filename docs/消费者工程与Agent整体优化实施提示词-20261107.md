BF1 / P0：修复 visit UNKNOWN 与迟到 failed 的投影竞态

涉及 batch_core.py 的 recover、finish_visit、sync_visit_failures，site_failure_stop.py 的 record 及 candidate/probe 调用点。

- 已确认根因不是“每应用第二候选非法”，而是同一 visit 先写 unknown / Unresolved visit dispatch，原 worker 随后以同一 execution id 结算 failed / Error，触发不可变身份守卫，后续候选同步时快失败。
- 原 visit 封存 UNKNOWN 后，迟到 definite failure 不得改写 visit、execution identity、应用或站点原 UNKNOWN。
- 在 BatchLedger 原事务中保留迟到结算事件、原错误和 usage/evidence；finish_visit 对已经证明的同 visit 迟到结果返回明确 late_outcome_recorded。

- 确定性重放 UNKNOWN→迟到 failed 至少两轮：站点账只有原 execution id 和 UNKNOWN，迟到错误有独立事件，后续同应用候选不再因该投影冲突快失败。反向顺序、不同 visit、不同应用和真正身份改判仍拒绝。

四、规划采集 Agent 的 goal/prompt/tools 同步改造

goal：
- 配对两臂使用完全相同的显式 session_objective，冻结 candidate id/version、entry URL、requested goal、目标描述、参数、checks、preferred band 和 minimum effective steps。
- 目标描述自然必要业务结果，例如进入工具、输入指定参数、触发计算、读取新结果，而不是“执行五步”。
- 生产候选原无显式目标时，Agent 可提 working goal，但必须标 model-proposed，不伪称用户目标，不回写生产者原目标。
- minimum_effective_steps 只是规划提示，不是成功充分条件或保存硬门禁；short ≤2% 是集合交付门禁，不能用无关动作解决。

首轮 prompt 落实同一语义：
“终点必须证明 requested_goal/session_objective 所要求的结果，而不是页面任意位置已有关键词。若终点在首帧已经成立，检查它是否只是说明、导航、标签、默认参数或示例；需要动作产生的结果必须绑定动作后的新证据。计划长度是路线估计，不是完成依据；不得为达到档位添加无关动作，也不得删去原目标必要步骤。”

后续 prompt 落实同一语义：
“先核对原目标/checks、已执行动作的真实效果和剩余计划。finish_when 命中只说明该条件可见；剩余计划未走时，确认它确属冗余才能申请提前完成。聚焦不是输入，输入不是计算，计算说明/示例不是本次计算结果；列表标题不是已读正文。自然完成可少于五步并如实标短；无法证明完成时继续有据路线或停止，片段保存由宿主另行判断。”

tools：
- click/type/select/scroll/hotkey/open_url/back 保持一计划步一原子动作。
- request_original_image 只补图证，不执行动作、不推进计划；同 observation＋branch context 仍只提供一次。
- replan 只替换未执行步骤，保留原 goal/checks、已执行证据、总额度和 25 次 GLM 上限。
- 正常收尾收据区分：原计划总步数、已执行有效步数、未执行剩余步数；finish_when 是否首帧已成立/动作后新产生；显式 checks 进度；正常完成、Agent 提前完成、可信前缀、预算/阻断/UNKNOWN；工程 short/normal。
- 无显式契约的目标状态为 UNCONFIGURED/待独立 QC，不伪造 VERIFIED。实验可报告 ≥5 占比诊断路线，但不设“≥5 占比 50% 即通过”。

七、固定真实 GLM 配对基线（本轮授权范围内直接执行）

规模与变量：
- 12 个分层候选，每候选 high/high 与 high/low 各一次，最多 24 个研发会话。
- 两臂 candidate/version、显式 session_objective、代码、模型、图像协议、输出上限、预算和页面能力完全相同；唯一变量是后续分支 effort。
