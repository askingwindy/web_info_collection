## 3. S1：共享 SQLite 与事务范围

### 3.1 配置与准备入口

复用现有小型连接助手，统一默认 `busy_timeout=90000ms`；实际等待必须受会话剩余时间、停止信号和当前租约约束。禁止把“90秒×多层3次重试”叠成不可中断等待。

| 层 | 修改职责 |
|---|---|
| `site_pool.py` / `candidate_pool.py` | 保留已完成WAL/90秒；补连接设置和短事务的安全重试；固定候选用SQL精确筛选 |
| `batch_core.py` | 两个 BatchLedger 的新建、连接、heartbeat统一；外部请求reservation的持久化顺序保持 |
| `current_chain.py` / `registry_db.py` | 注册库初始化与现有读写入口一致；只读快照不执行DDL或恢复 |
| `runtime.py` / `storage.py` | 同一物理注册库的所有连接一致；资源盘点移出写锁；编号/attempt提交不重放 |
| `site_failure_stop.py` | 站点事实库初始化与连接一致，不把页面拒绝写为程序级整站停机 |
| `candidate_project.py` | 准备阶段真正初始化本轮所需五库、表和配置；目前该入口只给两本jobs写配置/路径，不能等自检时临时建库 |

WAL 在新库准备时设置，已有库仅在批准的切换步骤设置；worker连接不反复执行 `PRAGMA journal_mode=WAL`。`synchronous` 和 `busy_timeout` 则在实际写连接建立时配置，不能只在初始化连接设置一次。

原案统一 `synchronous=NORMAL` 可作为候选池/站点事实的吞吐选项，但要显式记录耐久性取舍：WAL+NORMAL 在系统崩溃/断电后可能丢失已提交事务。**评审建议：模型请求预留账及编号/attempt注册库保持 FULL，其余按NORMAL；这是对原案的建议调整，尚未决定或执行。** 若仍选择全NORMAL，本次验收只能证明正常运行与应用进程中断，不得声称断电后仍绝不丢预留、绝不重发。[SQLite synchronous说明](https://sqlite.org/pragma.html#pragma_synchronous)

WAL仍只有一个同时写者，不能保证不会发生BUSY；“零锁错误”是本轮验收要求而非架构承诺。只读WAL通常要求已有可访问的 `-wal/-shm` 或可创建它们的目录；实际验收使用普通 `mode=ro`，不在活动库使用 `immutable=1` 绕过检查。[SQLite WAL说明](https://sqlite.org/wal.html)

### 3.2 必改的热路径

- `runtime.resource_checkpoint():1494–1510`：当前写事务内递归扫描资源目录、stat、disk_usage。改为锁外获取资源事实，锁内只更新本条账/核对必要状态；不要让20进程同时全盘扫描后又长持写锁。
- `CandidatePool.claim_next():671–725`：把固定 candidate_id 条件放进SQL；GET原件读取/哈希等放锁外。进入锁后复核原候选版本、状态、唯一持有者及准备事实所对应引用；变化则退回重读，不绕开来源验证。
- `CandidatePool.publish():351–419`：锁外校验不可变GET证据，锁内复核本条发布条件、去重与原证据引用；网络/模型调用不得进入事务。
- 首次同步heartbeat与后台renew统一处理BUSY/LOCKED。只有确认当前claim token/owner仍有效才续租；不能先把租约误判失效，也不能将确已失效的租约复活。锁后计算实际时间。
- `RuntimeStore.close_failed_scope():1296–1437` 仍有锁内文件遍历/写入。S2接线后核实该路径是否被本轮停止流程触达；若触达一并移出，若不触达则列为未覆盖边界，不宣称“全库无长事务”。

备份统一使用 SQLite backup API；若用checkpoint后复制，须已停止所有写者，核对checkpoint完成并保证复制窗口无新写入。多库备份不是跨库原子事务，正式迁移先排空使用者，再逐库备份并保留对应同一停机截面的范围记录。相对路径改造不提供备份或删除恢复能力。[SQLite Backup API](https://sqlite.org/backup.html)

## 4. S2：失败分类、有限重试与轮内停派

### 4.1 保留原失败事实，单列处理类别

旧 `failure_class` 含 model/collector/network/program/interrupted/duplicate 等，消费者与保存逻辑已在使用。保留历史值与原错误，不将它们批量重命名；新结果增加明确的处理类别及原因，供各层消费。模型输出schema不合规与宿主自身schema配置损坏必须区分。

| 新处理类别 | 例子 | 本条与本轮动作 |
|---|---|---|
| `business` 业务/页面拒绝 | 页面登录/不可用/不合适目标、规划拒绝、导航许可拒绝 | 有反馈路径则交回规划器；否则本条失败，继续本轮 |
| `global` 确定性全局错误 | 配置/绑定/schema缺失、启动自检失败、策略1入口、证据盘不可写/空间不足 | 首次停止新派发，在途有界收尾 |
| `page_program` 单页程序错误 | 已排除全局配置问题后，某页触发的宿主异常 | 本条失败；本轮同特征达到3个独立失败事件才停派 |
| `transient` 暂时错误 | 数据库忙、确定未派发前的DNS失败、可确认安全重试的运输失败 | 同一安全操作最多重试3次，超限按下述规则结算 |

`interrupted/unknown/duplicate` 同时作为独立终态/原因保留，不为凑四类把用户取消或未知请求硬归程序错误；报表四类之外列出取消、未决与无法分类数量。

### 4.2 共同处理位置

在 `collection_strategy.py` 或现有相邻模块保留一份分类/处置函数；三模板独立session各自调用共同函数，不共享模板业务实现。导航模块抛出专门的业务拒绝类型，携带已有code、source/destination和phase；不要靠广泛字符串匹配把任意 ValueError 降为业务错误。

operation 已有局部 `NAVIGATION_SOURCE_UNPROVEN` 映射，须覆盖 long_reading/generic 与入口导航。已存在的 `NAVIGATION_DESTINATION_NOT_PERMITTED` 反馈继续由规划器处理，不新增放行分支。配置绑定真的丢失仍为global，不能因为错误文字含navigation就降级。

处置需要同步贯通：session终态 → `collect_runtime` → `RuntimeStore.finish_attempt`/scope暂停 → `candidate_consumer` → 协调器 → `site_failure_stop`。不能只改最外层协调器，而内层仍首次program暂停scope或退出worker。业务失败、首两次单页程序错误结束当前claim后，worker继续自己的剩余固定页。

计数由本轮唯一协调器维护，按 **原始异常类型 + 抛出模块/函数/源码位置** 聚合；使用稳定文本，不新造业务SHA。固定源码下记录行号可辅助定位，不使用包含URL、UUID、临时路径的错误全文作为聚合键。同一claim的同一原始故障跨session/runtime/worker只计一次，阈值按出现该特征的不同claim数计算；重复日志、包装异常、清理次级异常和同一操作的3次重试不各算一笔。将特征、序号、关联claim与触发停派写入现有轮次事件记录，协调器恢复只读重建计数；不另建服务。

### 4.3 重试边界与超限语义

- 本方案将“最多3次重试”明确为初次操作之外最多3次，建议等待1、2、4秒；等待可被用户停止打断，共同服从原deadline。只允许一层拥有重试预算，底层busy等待计入该预算。
- 数据库锁：仅重试已回滚/未提交、无外部副作用的本地事务；提交结果不确定先查原唯一记录。租约不足时缩短等待或结束当前操作，不越过租约/1920秒硬截止。
- 本条安全锁操作预算耗尽时，保留transient原原因，以page_program处置参与本轮同特征计数；派发前共享库持续不可用则按共享依赖超限停止，不制造claim。提交/派发结果不确定保持未决隔离，不改判为可重试。
- DNS预检：在reservation和HTTP之前重试同一预检，不能重启worker换job重复调用。共享provider预检连续超限则停止派发，记录 `transient + shared_dependency_exhausted`；不消耗100页去逐页重试已知全局断网。这与单页运输失败超限进入page_program计数分开。
- 已派发模型超时/未知回包、网页取页unknown、工具unknown：**不重试**。保留原请求及费用未知状态，不把本条未决改成可重新领取。已知invalid_response的原有有界纠正继续按原合同执行，计入40次HTTP，不由S2再套一次3重试。
- 浏览器操作只在能够确定未派发且不会重复提交时允许局部恢复；不因“网络抖动”自动重启整条轨迹、重放POST或输入。

## 5. S3：收紧结构匹配，保留当前站点规则

当前路由顺序包含显式站点规则、站点确认关系和结构判断。保留用户已有 Muxtly 全站 operation 规则，记录 `source=site_rule`；本轮不顺带取消它。因此Muxtly实采路由正确只证明站点规则生效，结构匹配能力须另用去站点规则的离线计算器首帧验证。

## 6. S4：准备、自检、启动、停止分开

准备步骤负责创建本轮合法工程/批次、初始化schema、准备固定输入；自检本身只读。现有 `candidate_consumer.startup_check`、`consumer_campaign.main` 或 BatchLedger/RuntimeStore 构造器可能写库/恢复，不能直接包装成“只读自检”。

统一自检在启动worker、浏览器、账号探针、claim、模型reservation前执行：

- 所属五库存在且能只读连接，模式为WAL；用 `sqlite_master`/`PRAGMA table_info` 核对实际查询依赖的表列，不硬猜字段。本次核查确认 Table2 为 `state`，没有 `status`。
- scope/config/manifest/结果根/来源证据路径可解析且绑定一致；根选择与历史未决保护明确。检查磁盘空间及证据输出可写条件，但不在账本上做写探针。
- 消费者cohort可读、站点和数量为50+50、candidate_id唯一、无旧claim/未决阻断、策略为 `screenshot_plan`；所有有效任务的策略字段一致。
- 从最终冻结配置读取并确认实际生效的40次HTTP、1800秒软时限和120秒宽限，不能只引用代码默认值。
- 原生产者与既有接续协调器已退出或按明确安排不再派发；20worker分片无重叠、每片5页；禁止automatic export/保存数早停。
- 实际启动解释器依赖可用。当前venv为 Python3.14.4 / SQLite3.53.0，仅记录已核实环境；不在本次文档任务升级依赖。

自检失败输出结构化code和具体字段，派发数0、浏览器0、账号探针0。DNS连通预检另列在只读自检之后，按S2处理；它不是纯离线检查。

`key_health.probe_accounts` 发出真实“Reply OK.” HTTP，独立记录在 `consumer_key_probes`，不属于“无请求自检”。如沿用现有必要探针，只执行原有启动流程所需次数，纳入总请求/用量报告，不由20worker各自额外反复发探针。

协调器异常也须在finally中停止自己拥有的worker、等待并保存真实退出码；诊断/写报告失败不能跳过收尾。不得取消其它工作线的子任务。停止后不重启失败worker来补跑原5页；停派造成的未领取明确计入缺额。

### 8.1 分母与八层事实

固定consumer cohort=100是总分母，站点各50。单候选以 candidate_id+冻结version关联claim→attempt→模型job→runlog；原生缺失关联列为缺失，不按相近时间或文件名猜归属。

补齐目前缺少的阶段接线：正常 `entry_session` 成功取得首帧anchor后追加 `first_frame_completed`，带claim和anchor引用；现有 `observation_complete` 只覆盖observation-only release，不能当作正常消费首帧事件。会话started/finished与单调耗时覆盖成功、失败、取消全部出口。历史无事件只依据已有原件/时间事实标明来源或unknown，不追写旧runlog。

| 层 | 权威事实/判定 | 不可以替代它的内容 |
|---|---|---|
| F1 领取 | candidate_claims 中属于固定候选的真实claim | 进程启动、cohort行数 |
| F2 首帧完成 | 首次观察原件/回执与对应runlog完成事件 | 有浏览器PID或仅入口已派发 |
| F3 模板选择 | template_selected及冻结模板 | 默认模板名、worker配置推测 |
| F4 模型首请求 | 关联到本会话的真实HTTP dispatch；保留unknown | reservation、缓存命中、账号探针 |
| F5 首轮规划接受 | 首个被宿主接受的初始submit_plan事件/原件；首请求即接受另列 | 模型HTTP成功、模型声称有计划 |

| F7 原目标核验通过 | 当前正常完成验证收据/封存结果，目标身份匹配 | ≥5步、模型声称complete |
| F8 正式保存 | 正常RuntimeStore正式结果+候选回写+证据可读一致 | marker存在、只读重放PASS、仅旧saved状态 |

同时输出每层的独立事实数和严格前缀漏斗数（F1∩…∩Fn）；原目标可在不足5步时通过，不能为让漏斗单调而抹掉这一事实。每层输出 reached/failed/not_reached/unknown；缺日志/原件为unknown，真实未请求为0，未评估不可填失败0。

### 8.2 故障、请求、token与时间

- 四类处置计数、原failure_class、最终reason、错误特征、出现序号、重试次数及是否触发停派逐条输出；取消、UNKNOWN、重复、无法分类独列。旧数据无法确定新类时标 `unclassified`，不改原账。
- 另按程序、业务、模型、站点/外部环境报告原因归属，与上述business/global/page_program/transient调度处置分开。根据原failure_class、拒绝码、异常及原件给出归因依据；没有证据时保持unknown，不把模型输出不合规或站点不可用误写为宿主程序故障。采用现有记录派生报告，不因此引入第二套业务状态机。
- 模型账按实际请求ID去重，列 succeeded/invalid_response/unknown/reserved，以及已派发/未派发/无法证明；不把reserved全部当HTTP，也不把同一请求在日志和库中算两次。输出缓存命中但不算真实HTTP。
- 生产者模型、消费者会话模型、启动账号探针分别统计并给总计；网页GET和工具请求另列，不混作模型调用。usage缺失为null，并报告已知token合计与未知请求数，费用没有收据保持UNKNOWN。
- 自然耗时分别记录claim至终态、entry_session至关闭，含等待/重试；补足明确的会话开始/结束事件与单调时钟耗时，attempt时间不能替代首帧/生成阶段时间。历史缺边界则标null及可用范围，不凭mtime推测。另列整轮开始至全部退出。每条正式保存样本报告自己的请求/token/耗时；再报告整轮全部消耗÷正式保存数的摊销成本。正式保存0时，两种均值均为null/未定义，不能除以0或写0成本。
- 报表先检查100候选的归属/终态/保存一致性；缺原件或未决按真实缺项标记。报表生成成功不代表完整性PASS。
