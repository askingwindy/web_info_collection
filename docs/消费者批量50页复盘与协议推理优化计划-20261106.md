### 1.2 已证实的根因与仍未证实的判断

| 发现 | 证据与含义 | 本轮处理 |
| --- | --- | --- |
| 普通分支的模型协议与宿主校验不一致 | `ModelGateway.call_message` 仅在 `grounded_choice` 下注入实际分支 schema；普通分支删掉 `response_shape`，prompt 允许省略 ID，校验仍要求 ID。10 次无效分支中：7 次完整计划被 choice schema 拒绝、1 次缺 ID、2 次 JSON 外附说明被拒 | 统一普通分支的出站协议、归一化、校验及 Controller；不只修直接阅读基线 |
| reasoning 占用大部分输出 | 有 usage 的 42 次输入 436,582、输出 478,613，其中 reasoning 452,076，占输出 94.46%；18 次无效响应扣除 reasoning 后平均约 424 token | 优先降低实际派发的 effort；保留最终答案空间，暂不缩小总输出上限 |
| 首轮存在明确输出截断 | 8 次首轮 `finish_reason=length`，均触及 16,384 输出上限，其中 7 次 content 为空 | 将低 effort 纳入固定基线验证，不接受截断回包、不从 reasoning 提取可执行指令 |
| 超时与调用阶段高度相关 | 74 次全部使用 `max`；首轮等待 600 秒、无 UNKNOWN，分支等待 180 秒、32 次约在该边界超时 | 先验证协议统一与降档后的耗时；不能直接断言供应商整夜故障 |
| “纠正重试同样冗长”不成立 | 普通路径 `attempts=1`，本批格式纠正请求为 0；32 笔超时包含 12 笔首次超时和 20 笔后续重试 | 区分格式反馈与传输重试；复用已有机制，不叠加重试层 |
| 分阶段 effort 字段不是任务配置入口 | `first_plan_reasoning_effort`、`branch_reasoning_effort` 是 chooser 选档后写出的运行记录；普通分支实际写死 `max` | 修改真实调用参数及记录来源，不能仅向任务或 boundary 文件补字段 |
| `KeyError: 'text'` 是实际工程缺陷 | cohort order 19 的首轮计划允许 `focused` 缺 text，后续宿主仍按必填读取；原终态记录 `host_failure=true` | 让 schema、唯一目标补全、焦点判定与补图逻辑一致 |
| 待对账原因并不相同 | 10 个 claim 对应的 attempt 已记 `rejected/interrupted`：6 个因模型未决，4 个因浏览器效果未确认 | 分项核证，有证据才结算；不承诺一次清空 |

智谱[模型文档](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash)明确 GLM-5.3-Flash 不支持关闭 thinking；降低 effort 与隐藏显示是不同事情，隐藏 `reasoning_content` 不等于消除已生成 token。既有低档 Muxtly 试跑输出为 998、438 token，但不是与批量同样输入的对照，不能宣称普遍降低 20 倍或推算可救回多少页。

## 2. 实施范围与最小方案

采用现有 Python 模块、两个原账职责和候选池，集中完成一轮修改。计划为新任务增加显式 `webcollect-banded-conditional-plan-9`，冻结本次分支协议与推理策略；旧 V1–V8 原任务、旧请求和原收据保留原义，不原位迁移。

本轮必做：普通分支接入统一、后续轮必要状态补齐、实际 effort 降档、`focused.text` 缺省接入修复、原账分类核查、一次集成、固定生产表候选的真实验证。第 8 节给出查找能力和浏览器未决处理的追加设计，区分已有能力复用、明确断点与仍需验证的能力。目标完成、连续片段保存和 QC 仍各按既有契约判断。

结合第 10 节新诊断，建议将 **E5：可信历史区间派生待审短流程** 提升为 P0，与 E1/E2 同轮集中实现。该项是对既有异常前缀六步资格的显式调整建议，不是把短流程分类自动等同于保存资格；实施与正式派生尚未执行。

本轮不以修改浏览器全局阈值、增加平台框架或更换模型解决问题。16 页入口失败、非轴对齐几何及其他问题保留具体证据；对已由原件定位的收尾、导航身份、资源就绪及固定基线断点定向修复。R03 已恢复的结果只核对复用，不再重复恢复。此计划不启动新 50 页批次、生产者扩量、独立 AI QC、人工审核、发布或定时任务。

### 方案取舍

| 方案 | 本轮决定与原因 |
| --- | --- |
| 只改全局 `reasoning_effort` 或给任务补两个字段 | 不足。普通分支仍写死 `max`，而且原 BatchLedger 配置有冻结校验 |
| 直接提高 16,384 上限或延长所有超时 | 暂不采用。可能缓解截断，但不能修复结构错误；是否增加耗时和成本由实际生成决定 |
| 给普通候选补特殊 `evidence_contract`，借用基线通道 | 不采用。会改变任务语义、校验与重试行为，不能证明普通入口被修复 |
| 在原 chooser/gateway/controller 内复用现有协议与归一化，新调用显式传 low | 采用。直接覆盖已出现的断点，保留原账、旧协议及已有能力 |

## 3. 工程代码优化

### E1. 统一普通分支的请求、解析与执行

主要位置：`projects/code/webcollect/{banded_plan,model_gateway,react_session,task_generation,direct_article,direct_completion}.py`，只修改其中实际参与新协议的路径。

1. 用同一份 choice/remaining-plan schema 派生模型可见协议与宿主校验。每次出站包含当前可选 choice、必要参数、当前观察和剩余约束；首轮继续使用现有 `submit_plan`，分支使用现有普通 JSON 消息。
2. 新普通分支明确推荐 `choice` 结构，`replan` 只交剩余 `steps`。去掉仍要求整份首轮计划的相冲突说明；直接阅读的 `citations/reading_answer` 仅在对应任务契约支持时出现，不向普通任务承诺这些能力。
3. 工程从当前请求补全唯一的 attempt/observation ID，然后校验；显式错误 ID 拒绝。复用 `bind_reply_scope` 等函数，使 gateway 与 Controller 的处理顺序一致，不发生前端允许省略、网关提前拒绝的分歧。
4. 对已观察到的输出做确定性归一化：单个完整 JSON 围栏、明确封装、同义字段、可唯一继承的剩余计划。只有当前 options 允许 replan 且语义无冲突，才将裸剩余计划包装成 replan；不得静默改 goal/checks、混入已执行步骤或猜测新目标。
5. 原始 content、tool arguments 和解析结果分开保存。围栏后的说明可在确认只有一个完整结构、无第二个结构化指令时单独保留；截断 JSON、多份相互冲突的动作或不确定业务含义仍返回明确问题，不手工补造答案。
6. 原响应有有效 usage、错误可确定且尚未派发动作时，复用现有同决策纠正机制，最多追加一次格式反馈；使用同一观察与原目标，全部请求计入原 attempt。不能以换任务或新作业重试格式失败，更不能把 UNKNOWN 当成已结算格式错误。
7. 将新协议标识贯通任务生成、prompt/tool/schema、网关、Controller、执行记录及保存解释。旧冻结数据仍可读取，不改签历史失败；导出与 QC 的外部字段及规则不因本次协议改动自动升级。
8. 将第 8.1 节的必要状态加入普通分支出站内容，实际检查覆盖情况；不依赖服务端记住首轮计划，也不把 schema 长度当成上下文充分。

验收：实际发送的普通分支消息与其校验 schema 一致；已知确定等价的回包能进入正确分支；错目标、错观察、无证动作仍被明确拒绝；同一归一化结果能继续到正常执行、派生和保存回读。

### E2. 在真实派发点降低推理消耗

主要位置：`react_session._native_chooser`、`ModelGateway.call_tool/call_message/_call`、boundary/request 记录。

- 新 V9 初始策略为 **首轮 low、分支 low**，通过现有单次调用的 `reasoning_effort` 参数传入；选档不再依赖是否带特殊目标证据契约。复用现有 chooser 参数传递，不新建通用路由器或自适应升档框架。
- **保持原模型账本及冻结配置文件不变。** 原配置可保留历史 `max`，新调用的明确覆盖值记录在请求身份和边界中，方式与已有契约基线传 low 相同；不能改库中的 frozen config，也不能另开账绕过未决请求。
- boundary 的总体/分阶段记录从实际选用值生成，消除“总体记录 max、实际 low”的歧义；API 出站参数、原 request 记录和运行报告须一致。
- 本轮保留模型 `glm-5.3-flash`、thinking 开启、图像配置和 16,384 输出上限；先不缩上限、不提上限。首轮 600 秒、分支 180 秒作为首个新基线的等待设置，统计实际耗时后再决定是否需要定向调整。
- 保留原有传输超时的有限重试、退避、账号绑定及每会话 25 次真实 GLM 上限；协议统一不得意外新增或取消既有重试授权。UNKNOWN 的原请求和预留不因后继回答成功而改写。
- 对格式错误给具体字段反馈，不把整份 schema 报错或 reasoning 长文再次塞回模型。原请求和原始响应完整留存。

验收：抓取的实际 API payload 中首轮和分支均为 low；boundary/request/报告相符；原账配置摘要不变；原超时与请求计数规则保持。真实基线另报 reasoning、正文/工具输出及等待耗时，不能仅凭参数写入认定性能改善。

### E3. 修复 `focused.text` 的 schema 与宿主分歧

主要位置：`banded_plan.plan_schema/bind_reply_scope/Controller.prompt/proved` 及其动作调用点。

当前 schema 允许点击的 `expected={kind:focused}`，宿主补图仍使用 `expected['text']`。复用当前观察中已唯一绑定的 target/node/可见标签回填该事实，或直接以同一已绑定控件验证焦点；无唯一目标时返回具体缺证与合法分支，不抛 KeyError，也不把空字符串当有效焦点证据。

验收使用 order 19 原计划及观察的只读投影：允许缺省的 focused 能走到正确宿主分支；目标冲突或错观察仍拒绝；不得凭缺省字段虚构点击成功。该波兰语游戏页仅作本次工程原件回放，不新增为中文真实基线。

### E4. 按原账处理已知未决状态

主要位置：`candidate_consumer.finish_or_reconcile`、RuntimeStore 现有恢复/结算入口、BatchLedger 请求/访问记录。

1. 在本轮新验证目录写只读核对清单，列出每个 claim 对应的 attempt、模型请求、访问和动作边界、终态、原件收据及未决原因。不能把 10 个 claim 与 32 笔请求当作一一对应。
2. 模型 UNKNOWN：只有原请求的提供方结果/用量或现有合法核对证据才能支持结算；无证据继续 UNKNOWN，不记零成本、不凭超时推断未执行，也不重发历史请求。
3. 浏览器效果未确认：从原派发记录、同步前后帧、原始边界及已有收尾证据判断。可证明的失败沿既有入口追加处置；效果仍未知则保持隔离，不因程序退出而改成普通失败。
4. `finish_or_reconcile` 当前主要补投影已提交的保存，并非“清空所有失败”的命令。只补已证实的收尾能力缺口，不直接 SQL 改成功或批量解除 interrupted；不将有实际 attempt 的任务送入零执行结算函数。
5. 原 claim/attempt/编号/失败/费用/UNKNOWN 不覆盖、不回收。成功保存最多到待审，恢复与新采集分别计数。

验收按“已证实并结算、仍缺证据、发现记录冲突”分别列出数量和收据。**清空所有 UNKNOWN 不作为其他独立、已结算候选研发验证的全局前置条件**，仍由当前原账按候选/任务隔离。

上述是历史原账处置；第 8.3 节另列新执行在封存前如何确认结果、减少可避免的挂起，不能用新会话页面替旧会话补证。

### E5. 可信历史区间派生为待审短流程（新增优先建议）

主要位置：`trusted_prefix.py`、`postprocess.py`、`collect_runtime.py`、RuntimeStore 的离线派生恢复与候选结果投影入口。证据、完整设计与验收见第 10 节。

- 对新的明确派生规则允许有证据的非空连续前缀；最终有效动作 1–4 步标记 short_flow、≥5 步普通流程，0 步不成样本。原 V1 六步规则保留历史解释，新派生规则明确版本，不全局改常量后重解释旧收据。
- 区间终点使用最后纳入动作的原可信动作后帧；后续未知/失败动作全部留在原件中，不能纳入样本，也不能跨越它拼接后面的动作。
- 模型请求结果/费用未决、浏览器效果未决、样本区间可核验性分别判断。符合区间证据条件的派生不要求先清除模型 UNKNOWN；派生本身不能结算或重发请求。
- 原 requested_goal、working_goal、失败、编号及账本绑定保留；派生描述仅陈述真实区间，明确 `original_goal_completed=false`。正式保存及待审登记沿既有加工、去重、身份与收据校验入口完成，不把诊断 PASS 当保存。
- 补齐“原执行未完成，但历史区间完整”的正式登记路径。现有 `_derived_recovery` 仅覆盖 ready、program/加工失败、请求已结算且已有失败派生的恢复，不能直接套用，也不能伪造原失败类型来进入。

原目标真实完成与可信短前缀保存分开验收；后者不能替代普通分支固定目标的真实 GLM 基线。新建议不构成本次直接加工旧 8 条原件或修改原账的执行。

## 4. 消费者 Agent 的 goal、prompt 与 tools 优化

| 项目 | 本轮调整 | 验收口径 |
| --- | --- | --- |
| Goal | 保留原 `requested_goal`；有调用方固定目标时遵守 session_objective。一般候选仍从真实首帧形成工作目标，不为长度或保存率另选更简单目标 | 原问题、参数及需要看的内容不变；以真实可见结果和保存收据核对 |
| 首轮 prompt | 给自然必要路径、少量关键 checks、实际动作及结果条件；工程已知 ID、长度和短流程原因由工程生成 | 正确可执行的计划，不要求重复工程事实或输出长解释 |

### 8.2 让规划按需使用查找，而非固定添加快捷键

**2026-11-06 用户决定：删除“直接阅读协议禁止浏览器原生查找”的约定。** 查找是按任务需要选择的能力；工程尚未接通的部分按能力缺口实现和报告，不再作为业务禁令。源码中的旧禁用尚未在本次文档任务中移除，具体位置与其他限制评估见第 9 节。

已保存的 `S000097_sample_000001` 实际是 click → scroll → scroll → back，没有查找动作。原目标包含通读第一篇正文并打开第二篇；当前保存的四步不能单独证明全部目标完成。这条轨迹没有使用查找，本身不能证明规划错误。后续应让 Agent 根据阅读目的和当前内容选择目录、链接、滚动、页内查找或站内检索。

| 情况 | 规划建议 |
| --- | --- |
| 已打开目标文章，需要定位人名、日期或具体术语，正文较长 | 有经过验证的页内查找能力时，按需查找并阅读命中位置的上下文 |
| 页面有清楚可见的目标标题或目录锚点 | 直接点击或继续阅读即可，不强加查找 |
| 目标是通读连续内容 | 保留必要阅读与滚动；一次关键词命中不能证明全文已读 |
| 需要寻找另一篇文档或站内条目 | 使用网站搜索框或有页面证据的网站快捷键；浏览器页内查找只定位当前页 |

“打开查找 → 输入关键词 → 关闭查找或定位下一匹配”可以形成三个真实原子动作，但有效数由各步效果证明：查找框出现/聚焦、输入状态改变、关闭或匹配位置改变。输入时已经定位成功时，不要求再按 Enter；Enter 没有产生新效果就不多算一步。查找关键词应服务原目标，不预填未知答案。对用户交付仍用 `ctrl+f` 等 Windows 标记，真实平台映射另留原执行证据。

**需要随集中实现移除的旧限制：** [banded_plan.py](../projects/code/webcollect/banded_plan.py) 的直接阅读 prompt、`native_browser_find=False` 常量以及 [direct_article.py](../projects/code/webcollect/direct_article.py) 的宿主拒绝仍体现旧约定。**需要补齐的工具能力：** [browser.py](../projects/code/webcollect/browser.py) 的 type 目前需要网页内已聚焦输入控件，截图/树以网页视口为主；[react_protocol.py](../projects/code/webcollect/react_protocol.py) 尚无原生查找框与匹配状态的效果判定。实施时一起贯通，避免只删文字而宿主继续拒绝，或只放开按键却不能完成输入、取证与保存。

最小实施顺序：先复用已支持的网站搜索/快捷键和目录，把实际能力告诉模型；原生浏览器查找单独验证打开、输入、匹配、关闭能否在当前运行模式下真实操作和取证。能成立时，将 capability、prompt/schema、输入目标、平台按键映射、效果计步及保存回算一起接入新协议；不能成立就清楚报告该能力未实现，保留其他路线。不得用 DOM 检索或程序滚动伪装成用户按了 ctrl+f；内部只读检索也不计业务动作。

智谱公开的[查询异步结果接口](https://docs.bigmodel.cn/api-reference/模型-api/查询异步结果)要求任务 ID；这不能证明现有同步超时请求可凭本地账本 ID 直接取回。其[对话补全接口](https://docs.bigmodel.cn/api-reference/模型-api/对话补全)提供 request_id 用于请求标识，但不能据此推断幂等重发保证。未查到原响应/用量时继续保留 UNKNOWN；本方案不预设切换异步或新增供应商查询能力。

原 10 条未决轨迹的已验证有效动作均为 0–4 步；当前 [trusted_prefix.py](../projects/code/webcollect/trusted_prefix.py) 的历史可信前缀规则要求至少 6 步。不能直接套现成入口保存，也不应将这个旧阈值当作不可调整的要求。新增诊断表明其中 8 条存在有据区间；第 10 节据此明确提出短前缀派生的资格、收据、状态和业务描述方案。该方案尚未实施，不能记为 8 条保存成功。

### 8.4 追加方案的验证口径

- 工程集成复用上述 4 个浏览器失败原件：明确区分稳定零效果、实际导航后等待超时、落地绑定冲突、资源未就绪和真正无法取证；不要求所有原件转为成功。
- 对新执行补取证，核查业务动作派发次数没有增加、原始失败与全部中间观察保留；模型查询/对账也不得隐含重新生成。
- 查找能力验收分别覆盖“适合使用”“无需使用”“无匹配/无效果”；每步有真实效果才计步。生产表固定目标本身不需要查找时，不强插查找来完成测试。
- 新协议若允许确定零效果后续行，必须验证原动作尝试留账、有效步数不增加、后续证据连续、保存不冒称目标完成。做不到这些时，先明确失败收尾，不能改成虚假成功。
- 仍沿用集中修改后一次集成、固定生产表真实 GLM 基线的研发顺序；原件回放只能证明工程分支，不能代替真实 Agent 验证。

这些是显式 direct-article 契约的专用限制，不是所有普通生产者候选的统一规则。普通分支 schema、effort 和上下文问题仍按 E1/E2 修复，不能归因于下表全部限制。

### 9.3 建议保留的事实边界与更简单的替代方案

保留原目标及参数、真实页面和引用来源、操作是否实际发生、每步效果、原始图树与轨迹、原请求及费用。原文确实存在只能证明来源，仍需判断它能否回答原问题；采集完成与独立 QC 分开。模型不能为了通过而删减未完成的 checks；工程也不能只凭目录里出现标题就认定已打开正文或完成阅读。

建议让直接阅读只负责原目标、阅读来源与完成回答的绑定，路线由 Agent 在当前工具能力和显式任务约束内选择。优先复用现有工具、观察和导航，减少 direct 专用动作白名单与重复拒绝，不新建一套浏览器执行框架。原任务明确的“只读该页”“离开后立即返回”继续作为任务约束，而不是所有阅读任务共享的默认限制。

直接阅读子项须落实本次明确撤销的查找禁令及其所需能力；其他建议按最终确定范围处理，整体实施优先级另见第 10 节。同步更新 prompt/tool schema、派发与动作后校验、引用/有效步数回算、保存和原有测试断言。旧 `test_direct_article.py` 目前仍断言“不提供浏览器原生 Ctrl/Cmd+F”，不能让它成为恢复已撤销约定的理由，也不能只删测试而遗漏宿主限制。最后按本计划进行一次集成与固定生产表真实 GLM 验证；本次文档修订未执行这些调用。

## 10. 综合原 10 条未决诊断：优先保存可信短前缀

### 10.1 可采信的结论与状态口径

新增依据：[逐条诊断](../verify_results/pending10-save-diagnosis-20261106-r01/diagnosis.json)、[诊断汇总](../verify_results/pending10-save-diagnosis-20261106-r01/findings.json)、[核查脚本](../verify_results/pending10-save-diagnosis-20261106-r01/read_only_audit.py)。本轮另行只读核对 10 条原收据所列 645 份封存文件，摘要全部一致；按请求 ID 与原 attempt 核对，10 次首轮请求 succeeded、24 次后续请求 UNKNOWN，后者耗时 180.02–180.12 秒，未发现这些记录的正式 saved_sample 收据。

可采信“8 条有可核验的非空动作区间，2 条没有已验证有效动作”。诊断脚本在内存中将终点限定为已确认区间，暂不套用原异常收尾资格，调用现有原子效果、连续性和导航回算；它没有执行正式 prefix 派生、格式/去重、保存、独立 QC 或人工审核。这个 PASS 正确证明区间事实基础，不能扩大为正式样本通过。

当前统计应写为：**原批已有 1 条保存待审；另有 10 条封存待对账，其中 8 条是短前缀派生候选、2 条暂无样本基础；本次新增正式保存/独立 QC/人工审核均为 0。** 这 10 条不是已有 10 条正式待审样本。

6 条最终停于模型超时，共留下 24 笔 UNKNOWN，其中 5 条有有效动作且浏览器未知尾动作数为 0。全批 32 笔 UNKNOWN 的其余 8 笔位于其他最终失败记录，整体对账不能缩成只核这 10 条。原响应/费用无法确认，不等于之前取得的真实网页动作证据失效。

### 10.3 派生与原任务、原账如何共存

1. **确定区间。** 只取同一原 attempt 中从开头连续、动作效果和边界完整的区间。最后纳入动作的原 after 帧就是样本终点；可选择有明确业务意义的更短连续前缀，但不能跳过中间失败、拼接其他尝试或用新截图补旧动作。
2. **分别陈述目标与结果。** 保留原 requested_goal、session_objective、working_goal 和失败；派生说明描述区间内实际完成的活动及可见结束状态。明确 `original_goal_completed=false`，不把“点击河北省”改写成“进入办理页”、附件链接改写成“读完清单”、聚焦改写成“计算完成”。
3. **明确新派生规则。** 新的区间规则允许 ≥1 个有效动作，1–4 标 short_flow、≥5 普通；0 步拒绝。源任务仍保持其原版本，派生收据记录新规则、原收据、动作区间、边界帧及排除尾部；旧 V1 六步派生收据照原规则核验。
4. **走正式加工。** 使用现有 postprocess 和审计/去重/身份校验生成标注、步骤、终态、文件摘要及保存收据。新描述必须与交付截图一致；同图焦点动作、混合语言、登录限制等仍按现有质量要求检查，不为增加条数豁免。
5. **正式登记且可回读。** 复用 RuntimeStore 与候选结果的正式提交入口，给历史区间追加派生记录。仍使用原 source attempt/编号绑定，不新增浏览器执行或回收编号；一个原始执行最多一个当前有效交付版本，重复运行复用相同区间结果。若推进当前状态投影，原失败终结事件与原请求引用必须保留，报告明确为历史派生恢复，不计生产新增执行。
6. **原请求继续对账。** 模型 UNKNOWN、用量/费用预留及原有隔离范围保持。派生保存只表明选定区间已生成待审样本，不清账、不解锁重发原请求，也不解除未决执行限制。此前 32 笔请求仍逐笔核对。
7. **分别验收。** 成功结果最多 `collected_pending_review`。原目标未完成、区间已保存、独立 QC、人工终审、发布分别报告；历史短前缀成功不能抵扣固定原目标的真实 GLM 验证。

以上为待实施建议。它不要求现在重发模型请求、重新访问旧网页或提前清空 UNKNOWN；也不授权本次文档分析直接修改原账。

8 条是有据区间候选数量，不是预计交付数量；优先 4 条也不是承诺新增 4 条。技术可派生性、正式保存和业务质量分别验证。

### 10.5 工程与 Agent 的共同优化

**工程侧：** 优先 E5 及零效果/未知分类；同轮完成普通分支 schema、后续状态和真实 low 派发。4399 的加载判定、财经的导航身份与动态区域各按已有证据定向修复，不把扩大同步阈值作为短前缀保存的前置。原生查找按第 9 节已撤销禁令接入，但不阻塞无需新动作的历史区间派生。

**Agent 的 goal/prompt/tools：** 后续输入给出实际页面类型线索、正文/附件链接、登录提示、焦点与数值变化、已完成和未完成事项。Agent 根据可见证据调整路径：附件页不能继续当正文读，登录限制不能当正文加载完成，聚焦不能当输入或结果。原目标保留；确实不可完成时诚实停止，工程只对有据区间派生。可用查找能力按需参与自然路径，不为让短前缀变长而添加动作。

**同一轮验收：** 集中改完后做一次集成，覆盖非空短前缀、5 步普通片段、0 步、未知尾动作、确定零效果、只有模型未决、错误边界、重复登记及正式回读。随后按明确实施范围用原 8 条封存材料进行离线派生，逐条报告保存或实际拒绝原因，原模型/浏览器新增调用均应为 0；同时核对原 raw、失败、UNKNOWN、费用与编号未被覆盖。Agent 协议修改仍通过固定生产表候选的真实 GLM 基线验收，不能用原件离线成功代替。当前只完成分析与计划更新，未执行本段流程。
