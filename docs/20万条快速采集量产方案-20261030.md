# 20万条快速采集量产方案

2026-10-30，方案 v1.4。今日目标为新增1000条有效片段，最终交付20万条；按[今日程序规划](今日1000条与20万条量产程序规划-20261030.md)组织流水线，数据口径以[片段补充](../request/轨迹采集口径补充-20261030.md)为准，QC按[全量程序检查＋AI抽检方案](QC抽检与批次合格计数方案-20261030.md)执行：基础随机10%、首批/新组/风险必审、问题扩检，按实际批次接纳计合格。允许导航/浏览、多轮操作、同页多个5–8步片段，不强制完整业务完成；切段共享边界单独统计。旧P0离线验证不能证明新规则通过。本次仅更新方案，不改代码、配置或启动生产；后续实施见[P0计划](P0快速闭环实施计划-20261030.md)。

规划判据直接收敛为：按[附件B](../request/web操作采集需求/附件B-动作空间与坐标系.md)动作合法、满足5步要求、实际重复度达标。页面或业务未完整结束不是拒绝片段的理由；不增加“每一步必须对某个独立业务目标不可替代”的条件。阿里云阅读/点击/配置/购买等站内组合是候选供给方向，当前未访问或实测该站。

## 1. 本版对上一轮方案的调整

逻辑主线为“站点发现 → 按站点滚动规划与采集 → 独立批次QC”，三个Python包与原持久账继续复用。今日以1000条有效片段为目标；首条、10/50/100条是同一目标中的检查点，不能把停在首条视为今日完成。后续用同一流水线组织1万条交付包并滚动完成20包，不为1000条另建一次性手工流程。

| 保留的核心要求 | 直接减少的工程开销 | 首条闭环后再做 |
| --- | --- | --- |
| 真实动作前PNG、同步树、实际片段末状态；以5–8个实际操作为单位，10操作可切2段 | 已成功且绑定有效的来源、模型和审核结果复用；来源screen与资格沿用已合并入口 | 通用多页状态框架、长期运行服务、集群及数据库迁移 |
| 总体重复度指标、切段边界单列、当前链隔离 | 按任务/片段或小批冻结，已准备好的先采；减少“等所有站点都准备好” | 全量功能地图、复杂跨站语义检索平台、专门运营界面 |
| 编号、失败、费用和UNKNOWN原账；真实三次失败整站停止 | 一次本地检查返回完整诊断；先离线修接口再请求GLM | 更大的批量和并发、复杂流程支持 |
| 全量程序检查与累计指标、AI抽检/扩检及批次接纳；发布和客户验收另列 | 稳定组随机10%，首批/新组/风险必审，实际审核有效复用 | 内部不新增固定真人比例，客户2%人工抽检保留 |

不增加每条任务完整演练、独立准入、重复视觉审核或必须人工先看图的步骤。速度收益首先来自减少返工和重复工作。来源资格与审核缓存仍按原证据、规则和范围判断有效性，不修改旧收据来获得复用。

## 2. 目标与实际起点

交付为200000条最终有效轨迹/片段，20个ZIP，每包10000条；网站数与每站数量按实际可生成、可切段且重复度达标的容量分配。同一页面可以多条，参数变化或相同动作骨架不再作为一律拒绝理由；单一类目不超过20%。见[最新口径补充](../request/轨迹采集口径补充-20261030.md)、[当前需求澄清](../request/需求澄清记录.md)与[原需求书](../request/web操作采集需求/需求书-Web浏览器自动化操作轨迹数据集.md)。

撤回“20万条需要至少20万个任务页”的推算。同页多轮输入、清空再输入、货币对切换、购物滚动浏览、百科目录导航等都可提供实际操作序列；主要限制转为可执行操作、有效切段、实际质量与总体重复度。在线工具最多4万条的类目上限未改变，其他类目仍需逐步覆盖。

三站真实结果见[网站规划修复记录](网站规划与GLM交互修复-20261030.md#三站真实验证结论)：ntxen为导航UNKNOWN，108ai来源合格但规划未产出可冻结任务，esk365为同步取证拒绝。三站并不是同一种“GLM规划失败”，也不能据此统称三个网站无任务容量。当前P0先解释并修复库存、编译及诊断的断点，不承诺修完后这三站必定全部通过。

用户已明确更新“每页最多一条”和切段共享边界的解释：同页可有多个片段，同次连续执行的共享边界单独统计；静态阅读不额外计步。当前执行器、Schema和QC权威还需后继版本对齐，不能因本次文档校正就宣称代码已支持或改签历史结论。

## 3. 桌面Codex、工程程序和GLM的分工

“一次交互”指用户下达一次有边界的批次指令，工程侧可以进行多次有记录的工具和模型请求；严格只有一次模型请求时，输出只能是提案，不能证明实时网站可用。

| 阶段 | 桌面Codex或交互式GLM | 工程程序 | 工程调用的GLM |
| --- | --- | --- | --- |
| 批次发起 | 给出本轮目标、类目、范围与停止条件；解释报告 | 保存指令、原链绑定和队列；检查既有额度与hold | 根据实际统计建议下一轮方向 |
| 网站规划 | 开拓来源、研究陌生功能、给出带证据的路径组合；分析困难案例 | 搜索、访问、提取控件；动作合同/能力检查；检索已有任务；编译和冻结 | 批量判断类目、合法动作组合、片段范围与实际末状态；解释空候选 |
| 数据采集 | 处理确需判断的异常，产出可复用修复；不成为每条任务手工编写的必经步骤 | 单次真实执行，动作前取证、目标重验、保存、编号与恢复 | 默认不逐步调用；计划外状态返回规划阶段处理 |
| 独立质检 | 可作为另一AI复核渠道分析问题，不算真人 | 全量程序检查、累计判重、分组抽样/扩检、批次接纳、回写和封包 | 对选中轨迹全原图审动作/片段末状态，裁决必要重复候选；按批审资料 |

桌面App可以直接启动已有程序、读取报告、提交结构化决定，无需先接入新SDK或长期服务。进度留在原任务库和账本；聊天退出后不丢状态。无论Codex还是GLM提出的规格，都经过同一编译和真实QC路径，不直接成为生产数据或PASS。

## 4. 最短采集路径

~~~mermaid
flowchart LR
    A[已有来源或多渠道候选] --> B[工程核对初值和可用动作]
    B --> C[AI提出合法动作路径组合]
    C --> D[程序归一化和完整诊断]
    D --> E[冻结单任务或小批]
    E --> F[单次真实采集]
    F --> G[独立QC并回写]
    G --> H[当前有效集合]
    G -->|失败或重复反馈| C
~~~

1. 先用现有共享池及仍有效的来源证据，选择原hold允许、目标清晰、当前执行器能覆盖的功能。新站发现补充后续库存，不阻塞已经准备好的任务。
2. 调用模型前，程序核对控件允许动作、能力库存和执行器是否一致；确定性缺项先一次报全，不让GLM反复为工程不支持的动作写提案。
3. AI声明连续操作顺序、阶段条件和片段边界。程序按各阶段真实状态生成动作并计步；无须重复执行的已满足条件可保留为断言，但不能把合法的多轮输入/清空/点击压缩成一次初值到终值，也不能因复用同一控件就删除操作。所有计划归一化在冻结前完成。
4. 主要生成5–8有效操作的片段；10有效操作可拆成2段各5操作，原规划更长不直接判为无任务。点击、输入、清空按键、选择、滚动按实际执行计数，静态阅读不另计。第一轮结果出现后可以继续真实操作，不要求整段业务完成才结束。
5. 编译完成就冻结该任务，复用现有执行和独立QC入口。一个站点未准备好时挂起该站，其他合法任务可以继续；旧批次的冻结成员及原协议不原地改变。
6. 一次模型提案若发生已知编译失败，沿用既有一次反馈修订边界。原UNKNOWN先核账；旧模型响应和失败规格仅作原证据，后继计划重新绑定实际实现和有效来源。

初期以标准DOM工具、检索/筛选等执行器已能覆盖的有限任务族进入生产；每次扩展一个能带来实际任务供给的通用能力。跨页面动态控件必须有实际观察，首条闭环不等待建立任意网站通用规划器。

## 5. 小批量运行与质检

首条先选择能记录5–8实际操作及真实末状态的连续片段，复用现有取证/QC模块并先对齐片段合同；不要求先实现全自动长轨迹切割。首个小批建议5–10条保存候选，后续再验10动作切2段。采集尝试数按原执行计，交付片段数分别计，避免一次切段虚增尝试；达到小批数量、队列结束、原额度耗尽或停止条件时交接实际已有候选。

程序检查与累计判重覆盖100%候选；片段结束、同页数量和边界共享按最新规则执行。AI按[新策略](QC抽检与批次合格计数方案-20261030.md)基础随机10%，启动前10条、新组累计前5条与风险样本必审；抽中一条覆盖其全部原图和动作。相似路径按总体重复指标裁决，不把所有命中直接淘汰，也不只对重复候选抽10%。

稳定组发现1个普通FAIL扩至累计30%；再发现FAIL或共性/范围不明升100%，新组首批失败及严重问题直接全检相关范围。扩检绑定原总体、原随机顺序及原分母，未决不能放行；跨批次共性问题追溯并撤回相关计数，无关联组继续。

内部固定2%真人审核不是首条和小批的新增门禁。合同中的客户2%人工抽检保留；适用政策确需真人或AI有未决时，进入实际待审队列，不预填结论。按原因抽查被拒样本可以用于纠正误拒，其结果及成本如实记录。

采集仍只保存collected_pending_review。后续将实际AI结果与批次接纳分开：程序/全局指标通过且所属质量单元有效接纳后，实际AI PASS和NOT_SELECTED但按批次接纳的片段都可计合格；两项分列，不伪造逐条reviewed_pass或真人收据。尚待审核、扩检或裁决的单元不补数。QC输出在候选包外，历史结果不改签，原有效审核只在绑定仍适用时复用。

## 6. 供给与20万条扩量

网站规划分别提供“发现新应用”和“扩展已知应用的功能/操作序列”两条入口，统一写共享池。同一应用不因增加功能页或片段变成新站；同页多个业务参数、操作窗口和分段允许进入候选。同一原任务/片段重复派发仍需幂等拦截，页面占用不能继续代表该页永远只能一条。实际容量由规划、执行、切段和QC逐步证实。

给规划AI的上下文逐步增加：当前类目/任务类型缺额、已规划和已采集片段的相关摘要、历史失败与近期页面状态。利用现有索引检索相关路径，识别实际状态和重复候选并按总体指标核算，不因同类业务或相似操作骨架直接否决。阿里云这类站点可按产品/介绍或文档/配置/购买入口等维度组织已观察路径组合，再执行和分段；组合数量以实测重复达标的产物计，不提前宣称容量。

不提前冻结20万条计划。先保持下一到两个小批的有效待采库存，待采不足再发现/规划，待审积压则减速采集。20万条级别再完善持久增量判重、跨包索引、存储和跨机分片，不将这些列为首条开发前置。

| 里程碑 | 目的 | 最小证据 |
| --- | --- | --- |
| 首条真实闭环 | 证明当前短路径可用 | 真实正式尝试、原PNG/树/动作、独立QC和回写；发布另计 |
| 10条小批 | 验证连续产出与合批收益 | 真实有效片段、原执行到片段映射、边界共享/普通重复分列、完整分母及耗时/费用 |
| 100条检查点 | 看供给和返工是否改善 | 报告类目、任务族、尝试/保存/待审、实际AI审核/批次合格、发布/缺额 |
| 1000条 | 决定是否增加并发与资源 | 多批连续运行，测得日有效产量、每有效条成本和人工介入 |
| 1万条及后续20包 | 正式交付组织 | 全局有效集合、跨包报告、实际审核、资料、校验和及封包复验 |

这些数量只是后续目标。当前文档任务没有恢复采集、增加正式尝试、搜索、模型额度或发布的授权。

## 7. 速度、成本和工程止损

优先看五项：每小时新增批次合格数、正式尝试到合格的转化率、每合格条模型请求与已知费用、每10条人工/Codex介入时间、待采/待审停留时间。AI实际审核数、抽检/扩检比例和未抽中批次接纳数分别计量，不再把全部合格量称为逐条AI终审。沿用现有计量和JSON报告，不先开发仪表盘。零合格时单位成本未定义；实际扣款、平台和搜索费缺证据时保持UNKNOWN，不阻塞不依赖该信息的离线修复。

同一候选的确定性协议错误先离线修，不让真实模型作为逐项报错工具。模型输出成功、编译有效、正式保存和QC通过分别计数。工程修复只跑受影响模块及直接调用链的选定夹具测试；真实质量要靠随后有范围的实际运行验证。

若一个小范围实施轮加一次针对性补修后，仍没有可冻结且满足5步要求的真实任务提案，先给出完整阻断和最小选择，停止扩大开发；不继续把新框架列成前置。同样，不要求把三个旧问题站全部救活才尝试其他合法来源。真正的UNKNOWN和整站hold仍按原范围保留。

仅按每片段5–8个实际动作加末状态，20万条约涉及120万–180万个帧/树引用；切段共享原件的物理数量另计，另有取证、失败和版本。用真实小批测量字节、存储增长和压缩率，再决定备份、批量和机器数；不沿用旧磁盘快照承诺容量。

## 8. 本轮文档与后续实施边界

当前工程基线为54cb56a。已有语义工作流、一次编译反馈、来源审核合并/复用、阶段计量、队列和独立QC；这些能力的存在未使原三站闭环通过。P0先修能力登记、条件归一化和完整诊断，再验证最短真实闭环；原多页框架、长期编排和规模平台改造后移。

后续文档与实施记录应分别写已实现、离线已验、真实已验及UNKNOWN。此前P0-1至P0-3的离线记录保留；新定义中的多轮操作、片段结束、同页多条、切段与边界统计需按[P0口径对齐](P0快速闭环实施计划-20261030.md#11-最新轨迹口径对齐2026-10-30未实施)验收。本次只改文档。原[统一优化方案](WebCollect统一优化方案-20261029.md)和[三站记录](网站规划与GLM交互修复-20261030.md)保留作历史与证据导航。
