# 共享站点池与自主发现

2026-10-31 下一版库存与消费边界按[生产者消费者职责拆分与轻量化计划](生产者消费者职责拆分与轻量化改造计划-20261031.md)实施：新入口候选不强制摘要阶段生成具体目标，文章类型转提示，可独立校验条目分别入库；来源归属矛盾仍拒绝，UNKNOWN 与整站止损不放松。复用当前 SQLite 领取与原账，通过显式版本/扩展接入同会话消费者；旧严格五条、具体目标和冻结指令校验保留原规则。当前仅规划，下文 V1/V2 协议及命令不是已实现的新入口协议。

2026-10-29新增的发现支路只搜索与读取页面，不生成任务、不分配生产编号、不执行轨迹采集。实际运行事实以本地独立报告和原账为准，离线夹具不折算产量。

`site_planner.site_pool.SitePool.record()` 是 GLM、Codex 会话及基线导入的共同入口。每个事件提供 `schema_version=webcollect-site-discovery-1`、origin（`glm_agent` / `codex_session` / `baseline_import`）、run_id、event_id、uri、name、固定父类 category_hint 和 source_refs（绝对路径及 SHA256）。相同事件重放无副作用，事件身份相同而内容变化则拒绝。多个来源和多个页面保留各自记录，不重复增加同一应用的候选行；搜索消耗永不因重复而删除。

SQLite 分开保存 applications、aliases、pages、discoveries、assessments、capabilities、runs、tool_requests、checkpoints、merges。当前 schema 为 `webcollect-site-pool-2`，不隐式迁移。`www` 可规范化，其他别名必须提供证据；已入池应用合并使用显式 merge，保留源应用、原始事件及合并证据。类目提示不等于实际分类；判断类目不一致时统计为 UNKNOWN，并保留所有判断。来源基线分类保持提示，不伪装成 GLM 判断。

## 命令与程序2接口

以下命令在仓库根目录运行；若未editable安装三个包，先设置 `export PYTHONPATH=projects/code:projects/site-planner:projects/quality-inspector`。`POOL`、`RUN`、`LEDGER` 由操作者选择绝对路径。运行前先初始化池并导入明确范围的元数据。真实配置须复制模板、设置唯一 run_id，并绑定当前既有 `site_failure_guard`；模板不包含凭据，不自动建立或清零整站失败账。

```sh
projects/code/.venv/bin/python -m site_planner pool --pool "$POOL" init
projects/code/.venv/bin/python -m site_planner pool --pool "$POOL" import-events --input "$EVENTS"
projects/code/.venv/bin/python -m site_planner pool --pool "$POOL" stats
projects/code/.venv/bin/python -m webcollect site-pool --pool "$POOL" --purpose candidates
projects/code/.venv/bin/python -m webcollect site-pool --pool "$POOL" --purpose capabilities
projects/code/.venv/bin/python -m site_planner discover-ai \
  --config "$CONFIG" --pool "$POOL" --ledger "$LEDGER" --output "$RUN" \
  --category 图书文化 --category 学习教育 --category 政务与公共服务查询 \
  --category 健康科普 --category 电商浏览 --target 10 --per-category 2 \
  --max-rounds 3 --max-searches 20
```

`read_site_pool(path, purpose='candidates', categories=None)` 是程序2只读 Python 接口；CLI 接入 `webcollect site-pool`。候选只含发现与待审判断，始终声明 `collection_dispatched=false`。`purpose=capabilities` 只返回事先绑定的真实能力目录，并重新校验原目录字节、资格/复核来源、契约、证据及有效期。空能力池返回空数组；发现线索不能创建 ready。`bind-capability` 只接受已有有效证据，不产生能力判断。

`pool export` 输出兼容的 `webcollect-site-candidates-1` 与来源清单；状态为 review_required。`pool alias` / `pool merge` 需要显式 ID 与证据列表文件；不能依域名相似推断所有权。

## 发现、恢复与计数

按轮次轮转全部类目，避免前几类耗尽总搜索预算；失败判断和实际类别反馈进入下一轮查询。模型主导每类1–2个搜索词、真实结果选择、原始截图判断及至多一次真实同 host 链接导航。初始语义输入只含类目、数量和通用规则，不提供站点名称/种子；排除基线由程序执行。搜索独立调用智谱网络搜索 API，和模型 token 分账；`--search-engine search_std` 为默认基础搜索，`search_pro` 可用于显式质量比较并写入冻结运行配置。程序不替模型挑选新站。

首次运行冻结池内应用和别名基线、模型配置及输出/账本路径。重复搜索、重复站点、无效链接、未读、失败、跨域落地与未决全部保留。任务线索率同时报告“全部新增候选”为分母及“本轮确认站点”为分母，不能只展示成功项。

新增候选行、可访问应用、本轮有身份与公开中文页面证据的应用分别统计。TARGET_REACHED 要求五个指定实际类目各2个；页面不可读、跨 host 身份未证实、模型输入截断、分类冲突均不能填目标。模型必须显式给出 page_kind=TARGET_APPLICATION；目录介绍、下载/报道、仅提及别的应用以及缺少该字段的旧判断，均不证明目标站身份。模型名称与冻结基线应用名匹配也排除新增。多页只计一次应用。相同品牌名和相关域名保守排除重复；域族规则覆盖常见中文及部分国际后缀，并非完整公共后缀/所有权认证，未知身份仍需复核。发现的“确认”仅限模型对保存的实时证据判断，不是正式资格 ready 或任务可执行性证明。

搜索、浏览先预留再请求；成功结果按原请求缓存。搜索缓存命中先于预算检查。UNKNOWN/失败不自动重发；应核对原请求账。模型使用 BatchLedger 与 ModelGateway，失败作业不自动换身份重试。阶段输入、搜索选择列表、完成判断与失败进入不可覆盖检查点；恢复复用原列表和成功模型结果，不因入池后变成“已存在”而丢掉未完成观察。池/批次账依各自事务持久化，跨库中断保守保留未决，禁止按无消耗重跑。

浏览器使用隔离 Chrome 上下文、禁止下载与非 GET/HEAD 请求，只导航、截图与读文本/链接，不输入或点击业务按钮。整页读取（包括JS执行）总限时60秒，清理单独限时；空白/浏览器错误页也保留原图、原文与安全归一化的网络错误码，不能误报可访问。拦截、超时和同页恢复记录在证据中；拦截写请求可能使页面数据不全，应据实保留未知。沿用原整站失败guard和访问账；新发现账不重置历史hold。

本地输出保留完整搜索响应、PNG、页面文本/控件/链接、初始输入、冻结基线、配置、模型原响应与用量、阶段检查点和报告。模型仅接收有上限的输入；任何截断都转待审。中断/预算/UNKNOWN输出不可覆盖的 `report-partial-*`；正常结束输出 `report.json`，未达数量仍为 PARTIAL。轨迹成功率、实际厂商扣费、搜索未返回用量、基础设施费用缺证据时标 UNKNOWN。定价估算不能冒充账户扣费。

## 状态回写与防重

发现入池不代表采集完成。共享池增加按页面/任务的生产投影，记录 `queued`、`reserved`、`running`、`collected_pending_review`、`reviewed_pass`、`failed`、`qc_failed` 和 `published`；每次尝试、失败原因与QC引用均保留。采集成功自动到待审；独立QC报告及包检查实际通过后登记审核通过，失败保持失败，必要审核未完成保持待审。原采集attempt不改写为QC通过，真人审核与客户验收不自动生成。

`single_record.source` 在资格目录写入绑定原池及能力目录摘要的 `site-pool-binding.json`，后续execute自动消费；使用已有能力目录时可显式传 `webcollect.task_generation execute --site-pool /absolute/shared.sqlite3`。必须使用原池与原registry，不允许通过换池绕过已绑定scope。原有未绑定任务不静默回填，需明确核对后绑定并同步，运行本轮代码测试不会改动真实池。

QC自动回写使用原 `webcollect-qc-handoff-1` 收据。`single_record.qc` 自动传入；直接调用delivery pipeline时，prepare显式传 `--production-handoff /absolute/qc-inputs/receipt.json`。run/status核验收据摘要、原生产保存记录、候选字节及报告集合后回写；审核复用不触发额外模型请求。任意PASS文件或缺失原件不能授予成功。

`webcollect site-pool` 默认排除在途、待审、通过/发布以及同步未完成的页面；用 `--include-unavailable` 只读查看全部记录及 `collection` 状态。同站其他功能页不因一条任务完成被排除；相同页面换参数、任务ID或scope不能再派发已保存任务。失败仍显示，不清零止损或自动重试。

原生产事务先提交，同步失败在原scope留下pending；claim/start在编号派发/执行前强制补写，跨库并发通过池事务确认页面/任务占用。恢复只同步状态，不执行采集或模型请求：

```sh
projects/code/.venv/bin/python -m webcollect.site_pool_sync \
  --registry /absolute/original-registry.sqlite3 --scope ORIGINAL_SCOPE
```

该命令只使用原scope已冻结的池路径，不能创建替代池。未核实的UNKNOWN、整站hold、编号和当前链manifest保持原有门禁；投影回写不等于累计有效集合登记或正式发布。

候选任务的业务目标和参数保持原领取快照；`candidate-fragment-ending-1` 仅冻结本段实际结束口径，允许5–8个连续真实动作后在业务中间结束。不能因为完整业务有9–12步而直接拒绝可采片段，也不能写成未执行参数已满足。采集成功依然只到待审。

### 对象与唯一性

- 整体应用负责归属、访问限制和整站止损；业务种类是阅读、电影等分区，不是固定数据父类。
- 数据候选是一个具体交付目标；一次领取是消费尝试；正式执行的 attempt / sample_id 仍由 RuntimeStore 管理。
- 候选总数、待消费库存、消费成功、QC接纳、发布分别计数。1000条指去重候选，不指1000个站点或1000条合格数据。
- `candidate_id` 是程序分配的 UUID 主键。确定性 `dedup_key` 为协议版本、共享池 application_id、结构化 `target={kind,entity,parameters}` 的规范化摘要，数据库 `UNIQUE` 保证。字符串 NFKC、合并空白；保留大小写、数字类型、数组次序及参数差异。分类、业务种类、描述和入口URL不参与身份；相同目标换描述、纠正类别、重复发现返回原 ID，追加来源，不重置状态。
- kind/entity 应使用稳定的目标类型和对象身份；不能只把自由句子或URL当目标。该键不解决全部语义近重复，不增加强制AI复核；搜索/模型估计不计为产能。目标参数有意义地改变可以产生不同候选，同URL、多业务、多父类可以共存。

### 显式附加表

`CandidatePool(path, install=True)` 为旧 `webcollect-site-pool-2` 增加 `candidate-pool-1` 元数据、候选、版本、来源、领取、空领取请求、事件、结果附加表及唯一索引；在一个 SQLite 事务内安装、校验版本/表和外键。未安装则新接口拒绝读取，普通旧接口不自动升级。候选表不替代生产账，没有样本编号分配器。本轮未迁移真实池。

每次元数据变化保存新版本；领取把当时版本和目标快照冻结。后续分类/描述纠正不改变该次消费目标。生产者完整清单保留已消费项；`webcollect site-pool --purpose data-candidates` 和消费者 `list` 提供候选粒度视图；旧 `--purpose candidates` 保留页面粒度含义。

### 轻量生产者

严格原始输出入口为 `produce --strict --batch-key ROUND_ID`（Python同名参数）。同一config/run/ledger下多个独立batch共享模型、搜索和候选预算，各批冻结输入、来源索引和已有目标；旧v1及显式原回答复核保持原解释。严格模式按本批剩余目标收紧原始回答数量、来源索引范围和非空文字，禁止flat flags归位，所有结构/身份检查完成后才发布本批候选；JSON/来源/重复拒绝保留原回答和费用，不自动补一条或换作业重发。

搜索结果进入模型前核对原整体应用止损；还可通过 `excluded_applications` 加入原模型账明确绑定的未决应用，投影滞后时也不能放行。工具类查询保守避开明确的教程、推荐、作者文章，阅读查询仍可使用文章本身。该筛选只是搜索资料分流，不宣称页面资格；目标显式应用域名与来源域名不符时拒绝，不能用介绍文章承接其引用的外站工具，也不把正文URL悄悄替换为入口。

`TARGET_REACHED` 只表示结构与入库数量达到本批目标。生产者语义验收另核对原搜索标题/摘要中的来源归属、分类/业务一致性、具体目标与参数及语义重复；审核是AI来源核对，不是人工审核或轨迹QC。成功请求/已提交批次可从原缓存读取；同一生产者账出现UNKNOWN时阻断新批次，保留已完成批次的缓存读取，不新建身份重发原未决请求。

流程为真实搜索/已有来源 → 同轮结构化AI分类与候选清单 → 程序校验/候选去重 → 分批落库。此路径不启动 DiscoveryBrowser、不截图、不提DOM、资格审核或站内探索，不先证明5步，不编具体动作。入口URL只能选当前来源的 source_index，不能由模型编造深层URL。没有详情URL时，保留来源入口与具体目标。

搜索沿用 `glm_search` 原请求缓存/费用UNKNOWN；模型沿用 BatchLedger / ModelGateway，保存原始回答、输入身份、usage和原账。每批输入、已落库ID与拒绝原因均有不可变checkpoint；中断后使用原run/config/ledger/output恢复。原UNKNOWN/未决作业不会重发。重复批次不重复请求；没有“站点已存在”过滤。

`--target` 默认1000，`--batch-size` 默认50（最多100），`--max-batches` 默认20，`--max-searches` 默认20。输入是有限的重复 `--query` 或 `--sources` 文件；已有来源也按批切分。达到去重清单目标、输入耗尽或预算停止即结束，不无限补库。BatchLedger 的模型次数/token/费用/运行时长及 `max_discovery_candidates` 继续约束本轮，1000目标需显式匹配候选预算。每轮报告列出实际去重清单数、缺额和池库存；合格目标从消费者原 campaign 的 target_total 单列，不用模型估算替代。

以下为未来另获真实运行授权后的调用格式，本轮未执行：

```sh

  --pool /absolute/path/candidate-pool.sqlite3 --create-pool
projects/code/.venv/bin/python -m site_planner.candidate_discovery produce \

```

### 规划前领取与消费

### 状态、恢复与QC

消费状态为 pending（待消费）→ consuming（消费中）→ succeeded（消费成功、已保存待审）；失败 failed，不确定 reconcile。租约过期进入 reconcile，不自动重领。过期token不能续租、写阶段或提交成功。心跳维持当前凭证；controller派发、生成和发布也校验原领取。

只有原 RuntimeStore 中匹配 candidate_id/claim_id/version 的 `collected_pending_review` attempt，及校验全部样本/原始采集文件的 `saved_sample.json`，才能支持 succeeded。规划done、文件夹存在或模型完成均不足。规划失败可以在正式编号为0时记录消费失败，不伪造生产attempt。

`finish_or_reconcile` / CLI `reconcile --claim-id ...` 只核对原账和完整收据后补写，保存后断线/回写失败不会再次采集、调用模型或分配编号；已退役旧claim不能覆盖新尝试。没有完整保存时明确返回当前状态和核实原因，不能自行宣布成功。远端UNKNOWN或无法证明未发送的请求维持原账；本地预检零发送、明确失败与远端UNKNOWN仍按controller v2分级。新run/目录不能让同候选重新消费。

QC由现有独立报告及RuntimeStore验证后回写：结果的 pending_review / failed / accepted / published 与消费成功分开；不能传字符串PASS直接改状态。QC失败不自动入队。显式 `retry --candidate-id ... --reason ...` 先核对原请求/访问/正式尝试无未决，再允许失败目标或QC拒绝结果新建领取；保留旧claim、结果、费用、样本编号和事件。待审/接纳结果不可重领。三次真实失败、原UNKNOWN和应用hold不清零。候选只投影结果与QC引用，不重建当前链、不改QC策略、不重审历史。

`list` 分别报告候选总数、pending、consuming、failed/reconcile、消费尝试数、正式尝试、采集成功、待审、QC接纳、发布及原campaign合格目标。历史替换结果保留，当前有效结果最多一份，QC合格/发布不重复计数。原始证据不覆盖；QC输出仍在客户数据包之外。
