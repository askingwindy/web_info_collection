## 二、站点挖掘 Agent 优化

| 对象 | 下一步改动 | 如何验收 |
|---|---|---|
| P0　Goal | 将发现目标定为“选择有第一方证据、可直达、面向中文用户并有可观察操作的入口”。站点级决定回答主营业务，页面级决定回答用户可在该入口做什么。Muxtly 可以选择多个独立计算器，Wiki 可以选择目录定位、引用跳转等有依据的浏览路径。 | 对同站的不同页面只复用一个核定父类，同时能提出不同的页面角色和操作线索。导航与浏览可正常入选。工作目标由原消费者结合首帧形成。 |
| P0　Prompt | 把站点判类与链接选择分两步。第一步只看本站首页、关于或目录的主营证据，复用已有有效决定。第二步只看候选链接的锚文本和上下文，区分功能页、检索或列表、内容详情、第三方介绍。语言切换、登录提示及证据不足分别说明。 | 按原批次回放 14 条缺分类拒收，区分索引错配、首页不可用及主营依据不足等能被原件证实的原因。模型错配不能发布新候选。对 `English` 切换链接能说明不适合作为中文入口。只有通用链接文案时允许页面类型待补证。 |
| P0　Tool | 站点阶段沿用 `submit_site_classification` 与原文编号。为入口阶段向模型提供有界的第一方链接清单，每项含 `link_id`、锚文本、相邻标题和证据 ID。入口提交工具只接收本次清单的链接 ID、角色、依据和操作线索，URL 由宿主绑定。规则可可靠判断的入口可批量处理并注明归属。 | 首页证据 ID、入口链接 ID 与其他站点 ID 相互错用的反例全部拒收。每个已判定页面类型都可定位原证据。批量提交或复用已有站点决定时，逐候选分摊合计能与原请求对账。 |
| P1　选源排序 | 同等可用时优先补供给较少的站点类别和交互方式，并使用已有可判定首帧反馈。对于已占 72 条的开发者文档，优先寻找其他有证据的来源和不同操作，记录选择依据。 | 给定同一组有替代来源的冻结输入，比较前后实际选中哪些入口。候选分布作诊断。每 5,000 条及累计有效轨迹的类目 ≤20%、单应用累计最多 500 条，仍按有效交付集合核算。 |

## 实施次序与停止条件

站点主类仍是入池条件，可消费候选中必须 100% 有据，`UNKNOWN` 为 0。页面类型是另一个字段，证据不足时单列。新版本的 goal、prompt 和 tool 随发现批次冻结，新增页面信息使用来源记录，原 entry 正文的 `requested_goal` 仍为 `null`。

1. **先做离线工程回归。** 用本轮冻结证据和临时库跑正常生产入口，核对原行结论、编码反例、落地去重、分类未知隔离和原消费者兼容性。单独对照 20 个公开检索入口与 180 个第一方链接的来源。旧行若因新语言或选源策略改判，记录差异和证据，保留原账。
2. **再验证 Agent 的选择。** 在相同的宿主实现上冻结同一组来源、模型版本和输入范围。比较旧、新策略的有效索引、站点分类、页面类型、误收／漏收及每个净新增的生产者 token。回放旧收据验证工具协议。实际新 prompt 的决策质量需要后续有界模型对照。建议下一组 200 页将有据页面类型覆盖率 **≥80%** 作为内部试验目标，同时用预先选定的对照页逐项核验正确性并报告分母。缺证单列，不能靠填标签达标。
3. **最后验证实际能否消费。** 下一次取得实跑授权后，按相同的 20 站／200 页规模检验正式生产路径。明确区分仅给方向的找站测试和给定种子的扩页测试。建议从冻结的 Table2 清单按站点固定最多 2 页，20 站最多 40 页，兼顾功能、内容及不确定入口，用原消费者取得首次观察。报告净新增候选数、可信及可用首帧数／可判定首访数、可判定首访数／净新增数，并按主机和页面类型分组。抽样分组结果单列，分母为零时报未评估。已结算 token 分生产者与消费者，零新增和未结算单列。

这三个阶段分别交付可重放的工程收据、带原文引用的 Agent 对照清单和实际首帧结果。真实执行以另行明确的范围为准。[既有首帧口径](../projects/code/webcollect/candidate_feedback.py) · [交付计数口径](../request/站点分类与轨迹采集口径-20261102.md)
