## 一、先让一个候选进入 ReAct

R03 的 20 条新增候选均由同一消费者各领一次。15 条已生成正式任务，运行时在编号前因 `campaign_worker_time_limit` 暂停，任务仍为 `queued`，候选池却写为 `failed`。另外 2 条浏览器访问返回 521，2 条首帧截图和界面树不同步，1 条类目为 UNKNOWN。消费者模型请求为 0，本轮没有可用于分析提示词表现的真实回合。[R03 逐条结果](../verify_results/producer-consumer-live-20261101-r03/accounting/candidate-outcomes.jsonl) · [运行时任务](../verify_results/producer-consumer-live-20261101-r03/accounting/runtime-tasks.jsonl)

**原账恢复规则。** 先只读试算。有可信结束证据时，按原事件在 SQLite 中追加一次带依据摘要的核对记录。只有上界时要标为上界，保留“准确结束时间未知”。相同依据重放应返回原结果。证据不足或复核后仍超限，则继续报告阻断，实际运行须等证据补齐或活动预算另行明确调整。当前的 `runtime-resume` 只切换 scope 状态。R03 那 15 条先按 claim 与 task key 列为历史待对账，本次单站实测另选一个新业务目标。

工程改动集中于[工时核算](../projects/code/webcollect/runtime.py)、[worker 生命周期](../projects/code/webcollect/telemetry.py)、[正式编号前检查](../projects/code/webcollect/collect_runtime.py)、[执行结果返回](../projects/code/webcollect/task_generation.py)和[消费者领取与回写](../projects/code/webcollect/candidate_consumer.py)。普通退出复用现有 `finally`。补测 worker 已登记但阶段日志初始化失败的路径，让同进程可处理的异常也能正常结账。硬中断走原账对账。

工程提交分两步。先提交工时计算与只读诊断，让工程人员能按 worker 查看上下界。需要追加对账时，在现有 runtime CLI 旁提供窄入口，输入原 scope、worker ID 和证据引用，默认试算，显式应用时在原 SQLite 短事务内再次核对。再提交消费者的领取前判断和暂停回写。已封存样本的零派发对账仍可在全局暂停时运行。

## 三、工程验收及一次真实测量

**先跑离线回归。** 在临时库中覆盖四种情况。① 跨 scope 累计超限时零领取。② 领取后、正式编号前出现暂停，当前 claim 可对账，下一条仍待领。③ 工时充足时走正常 V2 入口，独占领取、同页观察、原生工具回包、动作和保存可通过同一 attempt 串联。④ 旧 UNKNOWN 不重发、已有完整保存只回写、重复工时对账不双计。复用[资源门禁测试](../projects/code/tests/test_launch_production_gates.py)、[候选消费测试](../projects/code/tests/test_candidate_entry_engineering.py)和[联合夹具](../projects/code/tests/test_pipeline_offline_e2e.py)。领取与编号之间的竞态需用可控时钟复现。

**再跑一条真实消费者基线 A。** 用一个消费者、一个专属批次、`--limit 1`，观察器独立写日志。冻结当前提示词和工具定义的摘要。沿用 GLM-5.3-Flash、thinking、`reasoning_effort=max` 和原生工具参数 schema。当前新原生任务默认上限为 12 次决策、24 次实际模型请求、900 秒，实际采用任务与原作业账更紧的限制。现场按三个里程碑分别报告。[ReAct 配置](../projects/code/webcollect/react_session.py) · [原生工具与效果判断](../projects/code/webcollect/react_protocol.py)

| 里程碑 | 必须看到的证据 |
| --- | --- |
| A1　进入真实 ReAct | 一个绑定到候选和 claim 的正式 attempt。消费者模型账至少 1 条 `http_dispatch=true` 且成功的请求，模型返回合法原生工具名、schema 合法参数、原 `tool_call_id`，宿主结果能与该 ID 对上。记录从领取到首个成功回包的耗时。 |
| A2　获得可诊断轨迹 | 至少 1 次真正下发的 `act`，有同会话动作前后的截图、同步树和可核验效果。分别统计有效动作、无效果动作、模型决策、实际请求、协议错误、耗时和已知费用。只有观察或模型建议时，单列 A1。 |
| A3　保存并验收样本 | 两处业务事实有当轮证据，原始终态与保存收据绑定，候选最多 1 个有效结果。目标是正常轨迹 ≥5 个有效动作，`complete` 和静态观察不计步。1–4 步按实际动作派生 `short_flow` 并核验理由，保留其真实结果。采集保存计待审，最终功能验收另需该条实际通过独立 QC，人工、发布和客户验收分别计数。[原验收口径](../request/需求澄清记录.md) |

运行记录用一行关联 `candidate_id → claim_id → attempt_id → request_id/tool_call_id → action/帧 → sample_id`。模型调用记录取原账，动作取宿主执行和原始收据。访问失败、521、快照不同步、资源暂停、无效回包和未知请求均保留发生阶段。首个里程碑失败时先归因，避免把同一问题扩到一批候选。

## 四、用真实回合决定改哪句提示词

取得 A2 后，按轮并排看“模型看到了什么、选了什么工具、宿主执行了什么、页面发生了什么变化”。若错误集中于已有信息被重复探查，优先压缩历史并保留已证实的页面事实。若集中于无效果滚动或提前结束，先调整动作反馈与结束依据。工具参数或调用 ID 错误先修协议，页面访问或预算暂停继续归到执行链。

一次 B 版只改一个可描述的因素。先用 A 的冻结观察检查上下文及工具格式，再对获准的同站、同类、未使用题做真实对照。对比任务事实是否完成、有效动作占比、无效回合、每条已保存样本的请求数和费用。单条结果用于定位问题，跨题复现后再确定通用提示词。首轮验收只看上表 A1–A3，不据此估算正式批次成功率。
