## 修改顺序与验收

### 1. 接通批次目标和候选处置

沿用 scope、SQLite、短事务和当前运行入口。在原候选事件上记录处置、原因、触发阶段、证据引用及适用的策略或修复版本，能回到原 candidate、claim 和已有 attempt。只读报告按批次展示首轮库存、已尝试、保存待审、实际审核或批次接纳、放弃、待优化、待对账和目标缺额。重复读同一收据、恢复同一 claim 均只计一次。复用现有用量报告，保留生产者、正式消费和诊断调用的分账。

保留 `--limit` 作为候选处理上限，另行表达目标的数量和计数口径。保存目标从完整有效保存收据计数，合格目标从独立 QC 或已生效的质量批次接纳收据计数。所需审核未到时明确报告待审及缺额；批次结束原因可区分达标、候选耗尽、处理上限和资源暂停。生产者仍开放时沿用已有轮询语义。多消费者同时运行时，沿用已有独占和配额，不把同一样本重复计入目标。[批次启动](../projects/code/scripts/start_candidates.py) · [独立接纳口径](../projects/quality-inspector/quality_inspector/delivery_sampling.py)

### 2. 首轮分流，批末定向回收

| 从现有证据能确定的情况 | 当轮处置 | 批末处理 |
| --- | --- | --- |
| 首帧或动作回执证明必要工具缺失，或工作目标过宽 | 标记待优化，保留第一个断点，继续下一个候选 | 按原因汇总涉及的候选、请求和费用，修复后仅选择这组 |
| 原动作、同步图树和末帧齐全，仅交付描述错误 | 标记重加工 | 用原 raw 派生修订件，核对零浏览器、零模型调用。未封存的沿用原加工机制；已封存的先写隔离修订件并绑定原收据，保持唯一有效结果。生产原件和已有审核结论按原版本留存 |
| 真实页面已明确不存在、必须登录且无公开路径，或已取证的专用交互缺乏复用价值且有可替代入口 | 放弃该候选和目标，记录证据与理由 | 普通首轮和修复回收均跳过它，同站其他目标仍可领取 |
| 模型或访问请求未决、派发后效果不明、活动预算或授权暂停 | 保持原账待对账或活动暂停 | 按原作用域处理，不计作站点低价值，也不因换批重发 |

沿用显式 retry 的原请求、尝试、保存和 QC 校验。回收绑定原因、修复版本和原候选集合。只有修复命中的项目进入下一轮，同一版本重复启动不会新增重试；普通 worker 不能先从公共 pending 池抢到待修复项。需要重采时新建 attempt、保留原分母，绝不拼接两轮动作。已判定的站点暂时出错、单轮工具选错、页面元素多都不足以作永久放弃依据。优先使用已有首帧或一次有针对性的原工具观察取证。

### 3. 逐项改规划 Agent

先把已做过单轮对照的工具反馈接入正式 ReAct。仅当当前已知控件缺少目标探针时，回传 `observe(focus_control_id=实际控件ID)`。保留原始拒绝与观察 ID，提示本身计零动作。Muxtly 原第 2 轮选 `inspect`，同图同历史只换这一条回执后真实 GLM 选了 `observe(e_12)`。该实验只验证下一工具的选择。[对照收据](../verify_results/consumer-muxtly-live-20261101-r01/decision-comparison.json)

下一项单独调整 goal 和终态。显式 `requested_goal` 保持冻结，URL 入口从当前可见状态建立一个可完成、可核对的 `working_goal`。把实际完成的阶段、可见结果与宿主停止原因分开传给后加工。Muxtly 首轮拟做两组，末帧只支持第一组的判别式 1、两个根 3 和 2。离线回放要能把实际结果写入修订件，并保留原意图。输入、点击、定向观察已有可用工具；优先改善反馈和目标表达，确有多个候选复现无法表达的必要动作时再改工具集。有效步数、short_flow 与样本去重继续按原规则核算。[逐轮动作、截图与终态](../verify_results/consumer-muxtly-live-20261101-r01/trace.json)

### 4. 用两轮临时批次验收，再划定实测范围

通过正常 Python 入口运行一次可重复的离线两轮批次。夹具至少覆盖正常保存、可修复阻塞、只需重加工、明确放弃、同站另一个可用目标。另测原请求 UNKNOWN 和全局预算暂停。检查首轮处理数与保存数可以不同，待审不会增加合格数；修复轮只取命中的候选；第二次执行同一回收命令零重复派发；重加工零重采；重复 worker 只产生一个有效结果。模拟审核与真实质量证据分列。

使用仓库的 `verify_current_offline.py`，在新目录运行修改模块及直接调用链，保留日志、源码摘要与失败。重点复用候选、ReAct、整条加工和 QC 交接夹具，并只读回放 Muxtly。工程实施只用临时库与模拟外部传输。现有后台生产者由其原会话管理，本次不变更其进程、预算或运行范围。离线通过后，给出下一次有界真实消费者试跑所需的批次、目标口径、数量、请求与工时上限、停止条件和比较指标，待明确实跑范围后执行。[离线验证入口](../README.md#离线验证) · [现有联合夹具](../projects/code/tests/test_pipeline_offline_e2e.py)

## 本轮离线实施记录（2026-11-01）

消费者 `run` 保留候选处理上限 `--limit`，增加 `--target` 和 `--target-basis saved|qualified`。指定目标必须绑定生产者批次；返回处理数、逐候选结果、收据计数与停止原因。保存数来自原 RuntimeStore 已提交尝试及完整原件哈希；合格数另核验原运行库的独立质量报告或重算批次接纳，不使用候选池的 PASS 投影作证明。批次接纳和逐条审核分列。目标是批次当前总结果数，恢复时沿用同一分母，不是每次启动新增数量。并发任务仍受原独占与工程配额约束；目标检查发生在领取前，在途工作可能使最终数量超过目标。

候选处置写入现有 `candidate_events`，保留 candidate、claim、binding、原因、阶段、证据与策略版本。状态包括 `optimize`、`reprocess`、`abandon`、`reconcile`、`paused`；修复轮使用 `recovery_ready` 与显式版本。普通领取不消费这些项目。首帧只对直接不存在或无公开路径的登录证据作候选级放弃，暂时访问受阻进入待优化；页面复杂、缺探针、单次失败不构成永久放弃。失败默认待优化，未决请求与资源暂停分别保留原账。

`webcollect.candidate_batch` 提供只读 `report`、显式 `disposition`、`recover` 和 `reprocess`。回收必须同时给生产者批次、原候选集合、原因和修复版本，并复用原 `retry` 的请求、访问、尝试和保存校验。新 attempt 独立取证；同版本重复准备不新增重试。原件文字重加工写到数据集外的新目录，记录 `revision_pending_review` 和原保存收据；原有效结果和审核结论不变，本轮没有自动替换有效结果或发布的入口。

缺 `MISSING_TARGET_PROBE` 且实际控件已知时，正式 ReAct 回执增加具体 `observe(focus_control_id=...)` 建议、原拒绝和零动作增量。未知控件或已有探针但缺可读标签时不发该建议。目标提示单独限定当前可见、可核对的一阶段。后加工以实际动作描述交付指令，将原目标、工作目标、执行阶段、末帧证据、Agent 摘要和宿主停止原因分别保存在 `completion-evidence.json`。

两轮临时验收的首轮处理 5 个候选、正式尝试 4 次、保存待审 3 条、待优化 1 条、放弃 1 条；其中一个已保存项另分流重加工。修复轮只重采命中的 1 个候选，新建 1 次正式尝试，累计保存 4 条。重复回收与修复轮重启均零新增派发；另一个单条目标夹具验证达标后重启处理 0。原生质量检查加人工编写的 AI 审核夹具使其中 1 条计入**模拟独立审核**，其余 3 条待审；真实独立 QC、批次接纳、发布均未运行。保存目标 5 条仍缺 1 条；模拟合格目标 5 条仍缺 4 条，不能换算生产进度。
