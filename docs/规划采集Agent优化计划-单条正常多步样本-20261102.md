# 规划采集 Agent 优化计划（单条正常多步样本）

2026-11-02。范围已确认，本次交付为计划。Agent 侧负责 `goal`、`prompt` 以及模型看到的 `tool` 说明与反馈。浏览器是否命中目标、如何证明结果、正式保存和 QC 交接由[工程代码计划](消费者工程代码优化计划-单条正常多步样本-20261102.md)负责。两条工作线使用同一候选、同一运行和同一份样本级 AI QC 收据。

## 本轮要验证的能力

从当前工程 Table2 的一个新合法入口，依据真实页面建立可判定的目标，自主完成自然需要 **至少 5 个有效操作** 的一条连续轨迹。Agent 自选下一步，在终态可核验时结束。正式保存的同一样本须通过真实独立的样本级 AI QC。下轮才扩大到多站点小批。

车来了提供了一组可对照的真实决策。原会话依次用了 `inspect`、`act`、定向 `observe`、`act`、`finish`。第一条 `act` 因缺目标探针在派发前被拒，补观察后实际点击一次，末帧能核对时刻表。样本 QC 五项通过。因此，本轮优先评估 Agent 能否更早辨认所缺证据，同时保留它在简单目标完成后及时结束的行为。[原拒绝及成功点击](../verify_results/chelaile-s000059-independent-qc-20261102-r01/独立AI质检结果.md#问题归类) · [既有实施方案](消费者Agent整体研发与单条真实验收实施方案-20261101.md#后续优化的生产表基准)

## Goal、prompt 与 tool 的具体设计

| 工作项 | 拟采用的约定 | 判断是否奏效 |
|---|---|---|
| Goal | 有 `requested_goal` 时保留对象、参数和目标约束。只有 URL 时，根据可信首帧写出一个工作目标，明确“要查或改什么、用哪些已知条件、做到时应看到什么”。有新的可见事实才更新 `working_goal`，保存依据的观察 ID 和理由。网站分类沿用生产者元数据。 | 离线对照一个带参数的任务和一个仅含 URL 的入口。前者全程保持原对象和参数，后者能指出可在末帧核对的事实。例如可验证“按指定条件找到一条结果，并在详情中读到指定字段”。条件、字段和取值来自原目标或页面观察。 |
| Prompt | 决策前让 Agent 判断证据是否足以派发。工具返回后，让它说明哪些效果已得到证实。明确区分“链接获得焦点”和“详情正文可见”。按目标决定继续或结束，步数由宿主从真实动作重算。 | 用缺探针、证据齐备、只有焦点变化、结果已出现四种观察检查下一工具及结束说明。到第 5 步时目标尚未完成，应继续按观察操作。若提前自然完成，则如实结束并保留短流程。 |
| Tool | 沿用 `observe / inspect / act / finish` 四工具，每轮一次调用。复用已有的动作可用性、原因、当前观察 ID 和下一工具提示，优先调整模型当下能看到的说明与反馈呈现。宿主仍负责最终校验与实际派发。 | 在真实请求投影的离线复验中可找到当前目标、当前控件的可用性、工具反馈及当前观察引用。旧观察、缺失标签、派发后的未决各能导向不同处置。协议或字段含义确需变化时，单列版本与旧任务兼容检查。 |

现有系统提示已包含缺证用观察、证据齐备用动作、达到目标可结束等原则。先用下表核对提示是否出现在模型当前能读到的位置，以及选项是否明确，再决定有必要改哪一处。[系统提示与工具定义](../projects/code/webcollect/react_protocol.py) · [请求上下文投影](../projects/code/webcollect/react_context.py) · [控件可用性](../projects/code/webcollect/agent_observation.py)

## 工具决策回归

| 当前观察或反馈 | 预期决策与证据 |
|---|---|
| 目标可见，状态为 `INSUFFICIENT / MISSING_TARGET_PROBE` | 对当前控件定向 `observe`，取得新观察再判断。以车来了原断点为正例，离线决策用例的预期是缺证时直接补观察，省去那一次被拒的 `act`。 |
| 控件和所需证据已 `PROVEN`，目标、参数和范围均匹配 | 可以直接 `act`。材料不足以选目标时用 `inspect` 查询当前观察。读过控件说明并不自动证明点击位置。对于有证据的链接、目录返回和另一分支，根据实际观察决定是否进入，返回后使用新的控件引用。 |
| 目标被遮挡、缺少可读标签，或已派发但效果未决 | 区分派发前与派发后。派发前可补观察或使用同一目标允许的、有证据的路径。已派发后只核对后帧，保留未决动作及其原因。旁侧媒体变化可旁注，目标与结果仍清晰时继续。 |
| 工作目标的结果已经出现在当前页面 | 用 `finish` 引用当前有效的原始观察 ID，区分实际操作、末帧事实和未完成部分。在 OSGeo 的回归材料中，能看到计算值并正确引用该观察。旧 attempt 的超时仍按原请求待对账。[OSGeo 与车来了的实测对照](../verify_results/consumer-focus-real-20261102-r01/单条真实采集验收.md#本轮实际运行) |

## 验证顺序与交接

1. **先离线。** 在同一组冻结观察上，对照当前与拟优化的提示、工具说明和投影，记录预期工具、可见依据以及宿主会接受或拒绝的原因。用缺探针与已具备探针的成对用例检查提示方向，用错误 `finish` 引用验证可纠正反馈。此处的模拟选择仅作协议回归，真实 Agent 的决策能力留给下一阶段实测。[目标与上下文用例](../projects/code/tests/test_agent39_contract.py) · [原生工具用例](../projects/code/tests/test_react_native.py)
2. **与工程侧联合实测一次。** 实施阶段从 Table2 固定一个自然多步的新候选，优先有公开查询、筛选或详情查看能力的入口，保留原发布行、来源和 GET 收据。只约定业务目标及可见完成条件，具体操作和顺序由 Agent 逐轮决定。冻结候选、目标依据、代码、提示和工具版本。每个正式 attempt 最多 25 次真实 GLM 派发，第 25 次合法返回可正常处理，第 26 次在发送前停止并记录 `glm_session_call_limit`。已发出的 GLM 请求即使选错工具也计一次。本地工具拒绝和缓存命中本身增加 0 次真实派发。请求未决时按原账核对。[原账计数规则](额度限制清单与取消说明-20261101.md)
3. **用结果复盘。** 在同一份报告列出原目标与工作目标更新、各工具的选择依据、派发前拒绝原因、真实模型调用及已知 token、有效动作和最终观察。`wait` 与 `complete` 均不计有效步。以 [单条联合验收](消费者工程代码优化计划-单条正常多步样本-20261102.md#单条联合验收) 的正式保存和独立样本级 QC 为关闭条件。把工具选择或目标表述问题归到 Agent，把控件实际不可取证、后加工描述缺失或保存问题归到工程。对缺少可行路径的候选记录理由，分类缺失本身不作丢弃依据。

## 实施与真实证据

本计划已进入实施。工程、Agent、原件只读回归及多次实际尝试分别记录于[联合实施与真实验收报告](../verify_results/consumer-multistep-20261102-r01/联合实施与真实验收报告.md)。关闭条件仍按本计划的正式保存和同一样本实际独立 AI QC 收据核验；离线结果及失败轨迹不替代该条件。
