# 单机生产者、多机消费者：静态分片与结果汇总方案

日期：2026-11-08  
状态：**讨论共识草案，尚未实施，未进行多机真实采集验证**

## 1. 目标与选型

目标是在保留现有单机 SQLite 主链的前提下，让一台生产者发现的站点和候选能够由多台消费者并行处理。

本轮选择**按整体站点静态分片、按轮导出任务包**的最简单方案：

- 暂不引入 MySQL、共享队列或动态扩缩容。
- 不让多台机器共同打开或修改同一个 SQLite 文件。
- 每台消费者使用自己的 SQLite 工作副本、浏览器、临时目录和生产账本。
- OSS 只作为文件中转站；固定机器之间也可用 `scp/rsync` 代替。
- 现有静态多 worker 协议作为全局站点编号、固定 shard、结果冻结与合并的复用基础，但该协议当前不等于已经部署好多机生产。

后续只有在固定分片造成的负载不均、动态加入退出或共享领取成为实际问题时，才重新讨论 MySQL 共享队列。阿里云 RDS 免费试用不作为本方案前提。

## 2. 核心分片规则

分片单位是**整体站点 application**，不是单个页面或单条候选。

- 一个消费者可以负责多个站点。
- 同一个站点在同一批次 `run_id` 内只能属于一个 shard。
- 同站点的不同页面、不同目标和后续新增候选，在该批次内都继承原 shard。
- 消费者之间不能使用重叠 shard；同一 shard 不能同时有两个活跃执行者。
- `c1/c2/c3` 是本轮的分片标识。首版可让一个 shard 对应一台消费者。
- 分片在同一批次内保持固定，不能因某台消费者空闲而把另一台的站点直接改派过去。

示例：

| 消费者启动标识 | 负责站点 | 处理范围 |
| --- | --- | --- |
| `c1` | `S000001`、`S000002` | 两个站点下的全部本轮候选 |
| `c2` | `S000003`、`S000004` | 两个站点下的全部本轮候选 |
| `c3` | `S000005` | 该站点下的全部本轮候选 |

## 3. 分派清单不是站点永久属性

`c1/c2/c3` 表示“某一轮中站点交给谁”，不是站点天然、永久的分类。

分派身份至少由以下三元组确定：

```text
run_id + shard_id + site_id
```

分派关系写入本轮 `manifest.json`，不改写 Table1 的站点业务事实、Table2 的候选正文或历史候选身份。清单还应绑定候选快照和来源证据的 SHA256，保证消费者执行的是同一份冻结输入。

示例：

```json
{
  "run_id": "round-001",
  "assignments": [
    {"site_id": "S000001", "shard_id": "c1"},
    {"site_id": "S000002", "shard_id": "c1"},
    {"site_id": "S000003", "shard_id": "c2"}
  ]
}
```

同一站点后续需要改派时，应发生在明确的新批次或显式恢复流程中，不能覆盖历史分派记录。

## 4. 生产者如何派发和共享数据

这里的“共享”是**按轮复制冻结快照**，不是消费者在线连接生产者数据库。

### 4.1 导出

生产者在每轮分派前：

1. 选定本轮可分派候选，按整体站点分组。
2. 为每组站点分配 `shard_id` 和全局站点编号。
3. 冻结 `manifest.json`，记录 `run_id`、分派关系、候选版本和文件摘要。
4. 对当前候选 SQLite 做一致性快照。
5. 打包候选引用的来源证据，不能遗漏候选 body 之外的原始引用。
6. 在本机登记本轮已经分派的候选，防止下一轮重复分派。

任务包首版可采用：

```text
round-001-input.zip
├── manifest.json
├── pool-snapshot.sqlite3
└── source-evidence/
```

如按消费者分别打包，则每个目录仍包含独立 SQLite 副本和该消费者的分派清单。具体采用“全量快照加领取过滤”还是“按 shard 导出子集”，在实现时以代码改动最小且能保留原 candidate ID/version 为准，不在草案阶段新增另一套候选格式。

### 4.2 传输

使用 OSS 时：

```text
生产者上传任务包
    → OSS 保存 round-001-input
    → 各消费者下载并解压到各自独立目录
```

OSS 不承担数据库、锁或实时状态同步职责。固定机器之间也可直接复制文件。

### 4.3 消费者启动

消费者启动时显式指定本轮和分片，例如逻辑参数：

```text
--run-id round-001 --shard-id c1
```

消费者读取任务包后：

- 将快照恢复为自己的本地工作副本。
- 将包内来源证据映射为本机路径，并核对原 SHA256。
- 只领取 `run_id + shard_id` 覆盖的站点候选。
- 对不属于本 shard 的候选，禁止创建 claim 和正式 attempt，不能仅靠界面或提示过滤。
- 使用本地浏览器和本地 SQLite 执行，不访问生产者的在线数据库。

本轮运行期间生产者新发现的候选留到下一轮，不自动进入已冻结任务包。

## 5. 消费者输出的两个部分

消费者输出明确分为客户交付数据和生产者汇总数据。

### 5.1 客户交付数据

包括但不限于：

- 标注文件；
- 原始 PNG；
- 同步 DOM 树；
- 动作轨迹和终态证据；
- 完成证据；
- 原始采集文件、保存收据及后续 QC 所需 lineage。

完整交付数据上传到约定的交付目录，由汇总/QC 链读取、检查、合并和封包。原始 PNG、树、动作、失败和编号仍按现有边界保留，不覆盖、不拼接中断轨迹。

### 5.2 生产者汇总数据

生产者只需要理解小型、结构化的结果清单，不需要打开 PNG、DOM 或完整客户包。

每条结果至少关联：

- `run_id`、`shard_id`；
- 原 `candidate_id` 和 `candidate_version`；
- 原 `claim_id`、`attempt_id`；
- `site_id`，以及真实分配时的 `sample_id`；
- 实际状态，如 `collected_pending_review`、失败或 UNKNOWN；
- 失败类别、原因及必要的用量信息；
- 原始保存/失败回执引用及 SHA256；
- 客户交付数据或证据清单的位置及 SHA256；
- 相关协议和结果 schema 版本。

示例仅表达字段关系，不是已经实现的 schema：

```json
{
  "run_id": "round-001",
  "shard_id": "c1",
  "candidate_id": "candidate-xxx",
  "candidate_version": 1,
  "claim_id": "claim-xxx",
  "attempt_id": "attempt-xxx",
  "status": "collected_pending_review",
  "sample_id": "S000001_sample_000001",
  "delivery_ref": {"path": "...", "sha256": "..."},
  "saved_receipt_ref": {"path": "...", "sha256": "..."}
}
```

失败和 UNKNOWN 同样返回控制结果，但不伪造正常样本或交付引用。

## 6. 为什么需要结果回传

“回传”不一定指回传给生产者进程，而是回到统一的结果交换位置，供生产者和汇总/QC 链分别消费。

没有结果回传时，生产者无法可靠知道：

- 哪些候选已真实保存、失败或仍未决；
- 下一轮能否继续分派；
- 原 UNKNOWN 是否需要继续隔离；
- 样本与证据位于何处；
- 各站点实际产出和用量。

生产者只读取汇总数据，用于候选状态、库存、失败事实、后续分派和计量。汇总/QC 链另行读取完整交付数据和原账，执行独立检查、跨片去重与最终封包。

汇总清单不能只是消费者自报的“成功”字符串。状态必须绑定原 claim/attempt、机器可读原始回执和交付字节摘要。生产者读取 `collected_pending_review` 也只能记为待审，不能据此写成审核合格、发布或客户验收通过。

## 7. 恢复和一致性边界

- 同一 shard 故障时，先保留原任务包、原账和已产生结果；确认原执行者停止后才能显式恢复或改派。
- 不能把同一 shard 同时复制给两台活跃机器当作故障转移。
- 消费者本地已成功上传的同一结果应支持幂等重传；同一身份但内容不同的结果必须拒绝，不能覆盖。
- 文件上传与生产者汇总更新不是一个事务。恢复时按原回执和 SHA256 对账，不能通过重采或重发 UNKNOWN 消除不一致。
- 结果合并后仍需执行跨消费者机械去重和适用的全局实质差异审核；局部 QC PASS 不自动等于全局合格。
- 缺片、全局未决或证据哈希不符时，不进入后续补采和正式发布。

## 8. 后续最小实施范围

后续整体重建时，优先复用现有候选池、消费者和 `batch_protocol`，只补以下薄适配：

1. **任务包导出**：冻结 run、站点分片、候选快照、来源证据和摘要。
2. **消费者 shard 过滤**：在真实 claim/attempt 入口强制校验，不只过滤展示列表。
3. **文件传输**：首版可选 OSS 或受控目录复制，不引入在线数据库。
4. **结果清单生成**：从原生产账和保存/失败回执生成生产者汇总数据。
5. **生产者汇总读取**：按原 candidate/claim/attempt 对账，更新投影，不改写历史原件。
6. **结果合并**：复用现有冻结、搬运、机械去重和全局 QC 边界。

本方案不改造浏览器动作、Agent 协议、截图规则或 QC 语义规则，不因分片而放宽原保存和审核门禁。

## 9. 首轮验证建议

先在本机用两个完全隔离的目录模拟 `c1/c2`，不默认启动真实网站或模型调用：

1. 构造三个站点及各自候选，分给两个 shard。
2. 导出同一轮两个任务包，核对 candidate ID/version、全局 site ID 和证据摘要保持一致。
3. 启动两个隔离消费者，验证各自只能领取本 shard，交叉领取被拒绝。
4. 用受控夹具产生保存、失败和 UNKNOWN 三类结果。
5. 验证客户交付数据与生产者汇总数据分离，生产者无需读取完整客户包即可对账。
6. 验证重复回传幂等、冲突回执拒绝、缺片不合并、UNKNOWN 不重发。
7. 离线集成通过后，再按单独授权进行两台真实消费者的小样本基线验证。

## 11. 最终改造前的优先级与专用能力取舍

本节记录 2026-11-08 后续讨论结论。**等待 zcode 最终结果后，再确定并实施最终改造；当前只写文档，不修改代码，不启动 A/B 或真实采集。**

### 11.1 实施优先级

1. **消费者优化优先级最高**：结合 zcode 最终结果确定消费者工程与 Agent 的最终改造内容，并在执行 A/B 分组前完成。
2. **UTF-8 是必须完成的跨平台改造**：跨机器交换和程序读写的 JSON、CSV、Markdown、清单、日志等文本显式使用 UTF-8，不依赖 Windows、Linux 或 macOS 的默认编码。
3. 消费者改造完成后，按既有研发约定进行一次集成测试和稳定基线试跑，再冻结 A/B 所需的代码、Agent 配置、候选和运行参数，避免实验期间混入无关功能变化。
4. 多机静态分片、结果回传和跨平台适配仍复用本文前述最简方案，不因消费者优化另外引入 MySQL 或动态共享队列。

### 11.2 三项 Apple Vision 专用能力退出新链

| 能力 | 新链决定 | 保留边界 |
| --- | --- | --- |
| QR 原始 PNG 像素解码与位置核验 | 取消；不再生成 QR 专用任务，不调用对应 macOS 校验器 | 历史代码、样本和收据保留；若以后重新保留 QR 任务，必须另行定义可核验终态，不能默认成功 |
| 固定 `400×200`“预览图”中文 OCR | 取消；退役该专用任务策略及其新链校验调用 | 不把删除专用 OCR 解释为取消所有动作证据和通用 QC |
| 固定网址、固定日期的相差天数 Apple Vision QC | 不作为通用必需能力，新链不再使用 | 旧审核证据保留；除非后续客户明确要求该固定样本的专用 OCR，否则走通用终态与常规 QC |

以上决定只针对新任务链，不回写、删除或改签历史结果。

### 11.3 超大图片规则保持现状

为控制 A/B 前的改动面，本轮最终改造仍保留生产者和消费者现有的**首帧图片覆盖率 `≥95%` 即排除该页面**规则，不执行此前讨论过的“优先采集可关闭超大图片页”反转方案。

同步暂缓以下能力：

- 不识别或绑定“关闭”“×”等关闭控件；
- 不新增点击关闭后的浮层消失、底层内容显露等效果证明；
- 不新增 `unclosable_large_image` 排除原因；
- 不调整现有候选 `abandon`、页面路由或短流程策略。

因此，本阶段仍不采集首帧超大图片页面。这样可以只退役“预览图”专用 OCR，而不同时改变生产者和消费者已经一致的页面筛选契约，是当前改动最小的选择。以后若重新启用可关闭超大图片页，必须作为独立需求同步修改生产者筛选、消费者动作协议、效果验证和候选状态，不能只改 Agent 提示词。

### 11.4 跨平台改造的既定边界

UTF-8 之外，最终实施时仍需按实际代码核对并处理 Windows/Linux 运行所需的文件锁、证据绝对路径重定位、Chrome 安装与启动、启动脚本和依赖锁定。macOS 的可选 `launchd` 后台启动分支不作为普通前台采集的必需能力。

这些事项只记录为后续最小适配清单，不在 zcode 最终结果出来前提前扩张实现范围。
