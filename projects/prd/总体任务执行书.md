# WebCollect 总体任务执行书

版本：v1.3

更新日期：2026-10-25

当前阶段：2026-10-25已完成10站点、200条正式包，本轮执行类目占比检查；实际交付目录独立QC、200条/1297帧AI复核、资料审核及隔离重建通过。新增人工审核0条，客户验收UNKNOWN。已达到M3的200条数量节点，但持续站点/任务供给及M4约1000条的质量、恢复、吞吐与成本验证尚未完成，不据此宣称规模生产就绪。当前产物以[正式入口](../../results/delivery/LATEST.md)为准；问题和后续建议见[200条生产复盘](200条生产复盘与20万条规模化改进计划.md)。旧18条类目占比豁免只适用于其原批。

本项目通过浏览器自动化采集中文网页操作，交付 20 万条完整、真实、可核验的操作轨迹。工程按六个阶段推进：先固化规则并产出约 20 条真实样本，再扩展至约 200 条和 1000 条，最后规模化生产和交付。每阶段以样本、检查结果和完成标准作为进入下一阶段的依据。

本执行书用于安排开发、采集、质检、交付和进度记录。20、200、1000 条是实施阶段的累计目标，可依据试验结果调整；最终交付数量与质量要求按需求文件执行。

## 1 需求依据与执行口径

执行时优先采用已确认的[需求澄清记录](../../request/需求澄清记录.md)，再遵循[需求书](../../request/web操作采集需求/需求书-Web浏览器自动化操作轨迹数据集.md)、[附件A 字段说明](../../request/web操作采集需求/附件A-字段说明.md)和[附件B 动作空间与坐标系](../../request/web操作采集需求/附件B-动作空间与坐标系.md)。[原始样例](../../request/web操作采集需求/samples/样例说明.md)用于理解交付形态，其中与需求冲突的错误不作为实现依据。

| 项目 | 已确认口径 |
|---|---|
| 交付规模 | 20 万条完整轨迹，约 1 万个中文站点，每站约 20 条；站点数和每站条数可以灵活分配 |
| 站点来源 | 自行寻找，无预设审核清单；交付站点清单及类目 |
| 站点计数 | 同域名下不同 URI 可以作为独立站点，按登记的 site_uri 分配 site_id，不按域名合并；initial_url 仅表示任务起始页；轨迹仍须具有实质差异并通过去重 |
| 有效步数 | 每条至少 5 个显式页面操作；`wait` 和 `complete` 不计入；短流程须标记并说明原因，占比不超过 2% |
| 完成判定 | 按任务规划及实际结果判断，轨迹连续、不跳步骤，最终页面符合任务描述 |
| 中文与覆盖 | 可见文本中文占比至少 70%，导航及控件名为中文，单一类目不超过 20% |
| 图像与界面树 | 每步保留操作前的真实视口截图和同步界面树，统一使用截图像素坐标；同一轨迹分辨率一致，全集视口规格不超过 3 种 |
| 重复控制 | 交付前剔除已检出的重复和近重复轨迹，内部目标为 0；甲方算法检测结果须低于 0.1% |
| 账号与信息 | 使用测试账号或对相关情况作出声明，无需额外特殊脱敏处理；账号来源写入交付说明 |
| 真实业务操作 | 不执行真实支付、转账、下单和交易；相关流程使用演示环境 |
| 验收范围 | 核对已采集轨迹、截图、动作和终态的逻辑一致性，不要求后续重跑网站复现 |

## 2 项目目录与工作产物

沿用现有目录组织，以下为用途约定，阶段产物随实施逐步建立。

```text
WebCollect/
  request/                    需求、澄清记录、原始附件与样例
  projects/
    prd/                      总体执行书、规则说明、阶段报告与技术决策
    code/                     采集、标注、校验、去重、调度及打包程序
    sample/                   少量精选示例及回归检查所需样本
  results/
    _work/                    采集中间状态与内部运行数据
    <批次号>/                 合格样本及正式批次交付物
  verify_results/             检查明细、人工抽检记录及淘汰证据
```

`sample_id` 在全集内唯一，批次和站点映射保持可追踪。正式批次内的 `samples/` 严格遵循交付目录约定；运行日志、失败记录、浏览器状态和调试文件存放在交付样本目录之外。

每批记录所用程序版本、规则版本和非敏感配置，便于定位质量问题。采集程序维护原始动作证据及目标控件真值，标注和质检据此核对。

## 3 六阶段执行计划

| 阶段 | 核心目标 | 主要产物 | 依赖 |
|---|---|---|---|
| M1 固化规则 | 将需求转成工程能够执行的规则 | 数据结构、检查清单、工程骨架 | 已确认需求 |
| M2 打通采集 | 在 3–5 个站点产出约 20 条真实样本 | 最小采集流程、样本、自检和人工核对记录 | M1 |
| M3 扩展任务 | 累计约 200 条，验证不同站点与任务 | 站点池、任务规划、自动标注流程、分布报告 | M2 |
| M4 试生产 | 累计约 1000 条，完成质量与成本验证 | 完整质检与去重程序、试生产报告、资源估算 | M3 |
| M5 批量生产 | 持续产出并补足 20 万条合格轨迹 | 调度程序、批次数据、运行及质量统计 | M4 |
| M6 全量交付 | 完成全集检查及交付材料 | 正式交付包、总报告、说明与校验文件 | M5 |

### M1 固化规则与工程骨架

工作内容：

1. 整理 `annotation.json`、界面树和 `metadata.csv` 的字段、枚举、类型及引用关系，将可空字段和不同动作的适用条件编码为规则。
2. 分别定义轨迹总步骤数和有效操作步数的统计方法，落实短流程标记及原因记录。
3. 固定站点编号、样本编号、批次编号和目录生成规则，记录同域名不同 URI 的站点映射。
4. 将需求书检查项分成可确定执行的程序检查、需要图文语义判断的检查和人工抽检；为每项规定证据与输出结果。
5. 建立工程入口、配置样例、依赖管理和必要的校验用例。动作默认行为、数据类型编号等实现约定写入规则说明。

完成标准：能够生成结构完整的样本骨架；检查程序能识别缺字段、错误枚举、断号、文件缺失、坐标错误和有效步数不足等问题。接口联调样本与真实采集样本明确区分。

### M2 打通真实采集流程

工作内容：

1. 自行选择 3–5 个中文站点，设计目标具体、可核验的任务，覆盖点击、输入、滚动、筛选或页面跳转等基础操作。
2. 建立逐步执行流程：观察页面、同步保存操作前截图与界面树、确定动作、执行动作、记录结果、继续下一步。
3. 从浏览器页面结构或无障碍信息取得元素文字、边界和状态，验证视口裁剪、像素比例和目标控件引用；不使用视觉模型编造界面树真值。
4. 将实际操作映射到统一动作空间，显式记录影响轨迹的聚焦、导航、弹窗等操作，确保动作记录解释相邻截图的变化。
5. 根据采集证据生成中文标注，以最终页面为依据添加 `complete` 和完成判定，产出约 20 条样本。

完成标准：首批样本逐条人工看图核对，结构与文件检查通过；操作无跳步，控件引用和坐标对应正确，终态符合任务描述。出现问题时保留问题记录并修正采集流程。

### M3 建立站点发现与任务生成流程

工作内容：

1. 建立候选站点池，记录 URI、站点编号、类目、中文情况、可访问性、登录方式及可执行任务。同域不同 URI 可分别登记，保持站点映射可追踪。
2. 使用独立只读预检入口记录动态广告／视频等媒体线索、广告依据和对正文／任务的影响，优先安排稳定或经正常准备可采的 URI；持续动态、未知或阻断候选保留证据和原因。当前已实现预检、全任务排序及采集前SHA交接校验，现有原生动画等待和正文准备继续使用，具体见[页面预检与URI站点策略](M1-页面预检与URI站点策略-20261023.md)。形成站点筛选和淘汰规则，筛除无法产生完整轨迹、无法取得必要证据或不满足中文要求的候选页面；已冻结实验的困难页面仍保留在原分母。
3. 为每个任务提前写明目标、初始条件和完成证据，结合实际页面规划操作路径；执行过程中依据当前状态调整。
4. 建立中文标注生成流程，分别处理动作前状态、动作决策和动作后观察，保证叙述有截图、动作或界面树证据。
5. 扩展至累计约 200 条样本，检查不同站点和任务类型的适配情况，及早进行重复筛查。

完成标准：可持续从站点候选生成可执行任务；多类页面能够沿用通用流程，站点特殊处理有记录；任务目标、路径或结果存在实质差异，不依靠更换关键词或无关操作扩充数量。

### M4 完成质检并试生产

工作内容：

1. 完成结构、动作、元素引用、坐标、截图、中文标注和终态检查，将不合格原因落实到样本及步骤。
2. 实现四路重复筛查和跨批索引，保留候选对及处理结果；对检出的重复轨迹执行淘汰。
3. 试生产至累计约 1000 条，按类目和操作类型分析采集失败、标注错误、重复淘汰及最终合格情况。
4. 对语义检查保留判定证据，开展人工抽检并抽查淘汰样本，发现误判后调整规则并检查受影响数据。
5. 测量实际耗时、并发吞吐、模型调用消耗、存储和人工检查投入，形成 20 万条生产所需的资源估算。

完成标准：机器可验证的必检项通过，语义检查和人工抽检有记录，未处理的重复候选为 0；已发现的不合格样本已剔除或重新采集；能够给出有实测依据的批次规模、运行配置和资源计划。

### M5 分批规模化采集

工作内容：

1. 实现任务调度、站点访问频率控制、并发执行、超时处理、有限重试和断点续采。
2. 跟踪任务从待执行、执行中、已采集、已标注到合格或淘汰的状态，避免重复提交和重复计数。
3. 每批完成采集、标注、质检和跨批去重后，才将样本计入累计交付量。
4. 持续监测站点、类目、任务类型、有效步数、短流程和视口规格分布，针对不足部分补充站点与任务。
5. 保留失败及淘汰证据，遇到系统性错误时暂停受影响的采集流程，修正后重采或复查相关样本。

完成标准：累计合格且去重后的轨迹达到 20 万条，分布满足需求要求。失败尝试、待检查数据和重复样本不计入交付量。

### M6 全量检查与交付

工作内容：

1. 对全部正式批次执行最终检查，核对文件引用、样本唯一性、总量、类目占比、短流程占比和视口规格。
2. 对全集再做重复检查，核对跨批候选处理结果及最终保留清单。
3. 完成人工抽检和淘汰样本抽查，修正已发现的问题并更新相关批次结果。
4. 生成各批 `metadata.csv`、`qc_report.md` 和 `SHA256SUMS`，核对清单与实际文件一致。
5. 编写总 README、字段说明、合成方式说明、来源与合规说明，并将目标控件真值留档随批次交付。

完成标准：交付包完整，统计可对账，质量报告及校验值与交付内容一致；最终样本均可依据已采集的截图、动作和界面树核验。甲方重复率检查须达到低于 0.1% 的要求，内部自检结论与甲方实际验收结果分别记录。

## 4 质量检查与去重

所有阶段沿用同一套检查规则，规则变更记录版本、原因和影响范围。影响已有合格数据的变更需要重新检查相关数据。

| 检查层次 | 检查重点 | 处理方式 |
|---|---|---|
| 文件和结构 | 字段、枚举、连续编号、文件数量、路径、分辨率 | 全量程序检查，按动作区分合法空值 |
| 操作与真值 | 目标元素、文字、边界、触点、工具名与参数、真实执行结果 | 与同步界面树及原始动作记录核对 |
| 轨迹与终态 | 动作和相邻截图对应、不跳步、没有凑步，最终页面符合任务 | 逐条语义检查，并保留证据供人工抽检 |
| 标注 | 简体中文、原文控件名、没有无依据描述或采集过程用语 | 规则检查与图文核对 |
| 分布 | 数量、站点、类目、任务类型、短流程、视口规格 | 批次及全集统计 |
| 重复 | 四路筛查、跨批检查、候选处理 | 已知重复剔除，未裁决候选数为 0 |

四路重复判定按原需求书执行：

| 判定路线 | 条件 |
|---|---|
| 相同截图 | 不同轨迹中存在 SHA-256 相同的截图 |
| 相同动作序列 | 完整的“动作类型、控件文字、页面名”序列哈希相同 |
| 相近首末帧 | 首帧与末帧的 dHash 距离同时不超过 4 |
| 相近任务文本 | 任务指令的 SimHash 汉明距离不超过 3 |

同域名不同 URI 的独立站点计数不豁免上述检查。相同起始页、同类任务模板等对有效产出率的影响，应在试生产阶段实测。

正式批次沿用需求书的人工验收口径：随机抽检 2%，不合格率超过 5% 时整批退回处理。前期约 20 条样本逐条检查。对已经发现的不合格样本及时处理，不以抽检比例替代已知问题的修正。

## 5 试生产指标与资源估算

每批记录候选任务数、实际执行数、采集完成数、质检合格数、重复淘汰数和最终保留数。另记录任务耗时、模型调用费用或用量、输出字节数、人工检查时间及主要失败原因。

试生产报告按以下口径估算后续投入：

- 有效产出率 = 最终保留样本数 ÷ 实际执行任务数。
- 预计剩余尝试数 = 剩余合格样本目标 ÷ 有效产出率。
- 单条合格样本成本 = 同批全部尝试产生的成本 ÷ 最终保留样本数，包含失败和淘汰带来的消耗。
- 剩余生产时间依据相同并发配置下的实际合格样本吞吐估算，另列站点访问限制和人工检查所需时间。
- 交付存储依据平均合格样本体积估算，中间状态、失败证据及备份空间单列。

第 M4 阶段后补充工期和资源计划。若产出率或成本不适合规模化，先调整任务来源、规划方式或采集流程，再继续扩大批量。

## 6 Git 与数据存储安排

工程仓库只管理核心代码、运行依赖与配置、需求规范和可复用审核说明。测试、运行过程和结果保留在本地独立目录，不纳入 Git；排除只改变版本管理范围，不删除本地材料。

| 内容 | 管理方式 |
|---|---|
| `projects/code/webcollect/`、通用 `scripts/`、依赖锁与配置模板 | 纳入 Git |
| `projects/quality-inspector/` 的源码、运行配置与依赖 | 纳入 Git，排除 `tests/` |
| 本执行书、`M1-规则说明.md`、`M1-检查清单.md`、`M2-人工核验SOP.md` | 纳入 Git |
| `request/` 的需求、字段与动作约定、客户原始样例 | 作为需求附件纳入 Git；原始样例是质检基准的必要输入 |
| 本地测试、测试夹具、联调样本、具体批次采集计划 | 不纳入 Git |
| 阶段报告、进度记录、根因分析、对照实验与验收记录 | 本地过程资料，不纳入 Git |
| `results/`、`verify_results/` 的截图、界面树、标注、审核记录与批次包 | 独立数据存储，按批次管理并保存校验清单 |
| 账号密码、密钥、Cookie、登录状态、虚拟环境与缓存 | 不纳入 Git |

运行数据、失败和淘汰证据、共享编号注册表应随数据独立备份。批次记录引用实际程序提交号和规则版本，审核记录绑定实际文件校验值。忽略文件仍需保存和审核，不能因为不入 Git 就省略证据。

后续按可检查的功能提交。涉及需求变化时，先更新需求澄清记录，再同步本执行书和规则；阶段进度与验证结果在本地过程报告中记录。
